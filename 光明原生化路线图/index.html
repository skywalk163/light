    光明原生化路线图（排期）¶

    目标：让依赖光明标准能力的项目（以 lightharness 的 src/总入口.light 为标尺） 能用 --backend native 编译出可执行档，而不是只能走解释后端。

    本文件基于实测而非估算：依赖闭包、每个依赖的引用点、原生运行时的能力边界， 均已逐项验证（见 §1、§2）。

    0. 结论先行¶

    「原生化」的真实工作量是 4 个 Python 生态依赖，不是想象中「要自建一个异步运行时」：

    # 依赖 引入方 引用点 性质 状态
    1 asyncio 客户端.light:17 0 处使用 残留导入 已解决（删掉即可）
    2 builtins.ord / .hex 持久化.light:24,37 2 处 缺码点内置 排期 P0
    3 codecs 增量 UTF-8 解码 SSE.light:29,36,48 3 处 缺字节级解码 排期 P0
    4 re.search 工具.light:219 1 处 正则引擎 排期 P1（可协商降级）

    1. 实测方法与数据¶

    用 C:/temp/scope_scan.py（从入口出发正则提取导入 → 走 ModuleResolver → 解析不到 .light 且 importlib.util.find_spec 命中者记为 Python 生态依赖）扫描 lightharness/src/总入口.light：

    依赖闭包内 .light 模块数 : 16
需 Python 生态的导入     : 4 个模块
    asyncio                      ← 1 处: 客户端
    builtins (同名 .py 影子)      ← 1 处: 持久化
    codecs                       ← 1 处: SSE
    re                           ← 1 处: 工具

    这个数字本身就是最重要的结论：原生化不是一个开放式的巨大工程， 而是 4 个边界清晰的小项。

    2. 纠正一个关键误判：异步原语光明已经有了¶

    原以为要「实现异步原语」——不需要。

    • 异步睡眠 / 并发等待 / 限时 / 创建任务 / 首个完成 是光明一等内置 （src/lexer.py:268 内置名表）。
    • src/code_generator.py:291 把 异步睡眠 映射成 asyncio.sleep —— 这只是 src （Python 产出）后端的行为。
    • 原生腿有自己的异步/事件循环实现：src/llvm/runtime_typed.c + src/llvm/codegen_typed.py；tests/test_llvm_async.py 11 个异步用例在原生腿全绿。
    • lightharness 实际用的就是光明原语： 客户端.light:265 异步 段落 真实对话协程 + 等待 异步睡眠(0.02)； 重试.light:48 异步 段落 带重试 + 等待 目标()。

    所以 客户端.light:17 的 导入 asyncio 是零使用的残留，删掉即消灭该依赖 （已删，并留注释防止加回；相关 6 个用例 test_客户端*/test_*代理* 均 rc=0）。

    3. 硬约束（决定了每一项怎么做）¶

    1. 原生运行时是纯 C：src/llvm/runtime_typed.c（5778 行）零 Py_* 引用， 链接为 clang ir.o runtime.o -o exe，不链 libpython → 没有任何 Python 互操作。 因此「识别 Python 模块后跳过」是错的：只会把错误从编译期推到链接期（未定义符号）。
    2. 原生侧没有一等的 bytes 类型：dv_socket_recv（runtime_typed.c:4467）把 socket 数据按 char* 读入并转成 LightValue。所以「纯 .light 实现字节级增量解码」无从下手—— 必须由编译器/运行时提供原语。
    3. 码位（ord）与「UTF-8 解码」是同一个核心问题：都需要在 C 侧把 UTF-8 字节序列 解成码点。做一次 UTF-8 解码内核，两个依赖一起解决。

    4. 排期¶

    P0 — 让 总入口 能原生编译（核心，2 项）¶

    P0-1：UTF-8 解码内核 + 码位 / 字符自码位 内置

    • 在 src/llvm/runtime_typed.c 加 UTF-8 解码内核：
    • dv_utf8_decode(buf, len, &consumed) → 码点；非法序列按 U+FFFD 惯例处理； 返回 consumed 以支持「尾部不完整序列留在缓冲」。
    • 内置 码位(字符)（字符→码点，等价 ord）、字符自码位(n)（码点→字符，等价 chr）。
    • 在 src/code_generator.py 加映射（src 后端 → Python ord/chr）。
    • 验收：新增原生腿用例——ASCII / 中文 / emoji（4 字节）/ 跨 chunk 切断 / 非法序列， 覆盖 编码段("会话") == "~4F1A~8BDD"（lightharness 现测点）。
    • 风险：中。C 侧需处理 1–4 字节、代理对、非法序列；做错会静默产生乱码， 因此必须有跨 chunk 与非法序列的对照用例。

    P0-2：增量 UTF-8 解码器（消灭 codecs）

    • 复用 P0-1 的内核，提供有状态解码器： UTF8增量解码器 类，解码(块, 是否最终) → 增量产出字符串，不完整尾部留在内部缓冲； 解码(b"", 真) 刷新。
    • src 后端映射到 codecs.getincrementaldecoder("utf-8")，两后端语义必须一致 （含非法序列与刷新行为）。
    • 改 SSE.light：去掉 导入 codecs，改用新解码器（3 处）。
    • 验收：test_SSE*、test_流式*、test_客户端*、test_进程树* 原生与 src 双后端结果一致； 专门加「多字节字符被 chunk 边界切断」用例。
    • 风险：中高。SSE 的「不能炸」正是靠它，属于正确性与鲁棒性关键路径。

    P1 — re.search 子集（消灭 re）¶

    • 工具.light:219 唯一一处 re.search(模式["pattern"], 值) == 空， 用于 JSON Schema 的 pattern 校验，pattern 由工具调用方提供（开放输入）。
    • 先测出仓库/示例里实际出现的 pattern 集合，据以实现够用的子集 （预计：字面量、^ $、字符类、量词 * + ?、|、分组）。
    • 若确认无法在纯光明内覆盖开放正则 → 按「原生腿能力边界」显式登记， 绝不静默降级（静默降级会让原生档行为与解释后端不一致，是最坏的失败模式）。
    • 验收：实际 pattern 集合全部通过；未支持的 pattern 响亮报错而非返回错结果。
    • 风险：中（工作量取决于 pattern 复杂度，需先测后定）。

    P2 — 收口¶

    • 总入口.light 原生编译出可执行档并运行，与 src 后端输出一致。
    • 把「原生腿能力边界」文档与 CI 对齐：新增一个原生腿可用性门禁， 防后续再引入 Python 生态依赖而不自知。

    5. 纪律¶

    • 先量后做：本路线图的每一项都源自实测，不靠估算。后续新增项同样先量。
    • 同环境三步对照：基线 → 补丁 → 复测，通过/失败数逐项一致才落地。
    • 双后端一致：任何涉及语义的新增内置，必须同时给出 src 与 native 的对照用例。
    • 不静默降级：能力不支持就响亮报错（这也是上一轮把「找不到 .light 源文件」 改成点名 Python 生态模块诊断的原因）。
