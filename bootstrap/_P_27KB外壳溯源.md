## 1. 实测方法（含一处必须说明的偏差）

任务书要求 `python -m cli.light compile` 编 `bootstrap_level6.light`。实测该路线**被方言不匹配阻塞**：

| 输入 | 命令 | 退出码 | 结果 |
|---|---|---|---|
| `bootstrap_level6.light`（65927B，E.7 后版本） | `cli.light compile … -o <tmp>`（默认 `--backend src`） | rc=1 | **1237 个语法错误**，首错「行 9，期望冒号『:』但得到换行」 |
| `.scratch/bootstrap_level6.orig.light`（61961B） | 同上 | rc=1 | **1175 个语法错误**，同一起头错误 |

根因：`cli.light` 的 `src` 后端实现的是**新冒号方言**，`bootstrap_level6.light` 是**旧无冒号纯缩进方言**（头注 `# 无空格分词 + 纯缩进语法`），根本不兼容。`src` 后端不可能编它——这本身就证明 `cli.light compile` 不是 `level7_generated.py` 的生成来源。

**忠实实现"编它"的替代路线（在允许边界内）**：`level7_generated.py` 自身就是一个 Light→Python 编译器，其 `编译(src)` 直接接受 `.light` 源码（`bootstrap/_E6_词界修复判决.md` §1 已实证）。用仓库既有 harness 模式（`bootstrap/test_bootstrap_level6.py`：造一个注入 `假/真/打印/列表*/字符串*/截取/建` 等 Light 内建的名字空间 `ns`，`exec(compiler_code, ns)` 后取 `ns['编译']`）来运行它：

| 编译器（输入） | 对 `bootstrap_level6.light` 编出的产物 | 合法性 |
|---|---|---|
| 现状 `level7_generated.py`（89852B） | **P_cur = 55001B / 1454 行** | `ast.parse` 通过 ✅（COMPILE_OK=True） |
| 备份 `level7_generated.orig.py`（88256B） | P_ori（能跑通、但前期报告已钉 `COMPILE_OK=False`，`:42 def ():`，与 E.5 一致） | 非法产物 |

以下对拍以 **P_cur（55001B，合法）** 为"真源干净编译产物"代表。

## 3. 逐段归类：现状产物 89852B 的三层构成

### 3.1 已并入 E.6/E.7 的词法缩进修复（~1.6KB，已收口，无需进 .light）

- **E.6 词界修复**：现状 vs 备份 diff 恰好 **+17 行 / +1596B、−0 行**（见 `p1b_trace/diff_current_vs_backup.txt`）。内容位于 `level7_generated.py` 的 `扫()` 机制1（行 451–469）：用 `行首`/`前一字符`/`后一字符` 判据做关键字词界保护（`段主函数`→KW段+ID主函数、`设 返回类型`→KW设、`列表获取(类型结果,0)`→不误切）。
- **E.7 块边界闭环**：已落入真源 `bootstrap_level6.light`（本次 65927B = E.7 最终版），属源侧修复，不在产物 diff 内。
- **结论**：这 1.6KB 修的是 **level7 的 Python 分词器**（机制1）；level6.light 自己的分词器走整词 `词()` 路线、本就正确（E.6 实证 `KW结束=0`、无贪心切词问题）。**已随 89852B 收口，不要回填进 `.light`。**

### 3.2 调试打印（真·外壳，~2.6KB，不该并入）

宿主侧调试设施，与其编译语义无关。实测 footprint（含调用点）：

| 构成 | 行数 | 字节 |
|---|---|---|
| `调试模式 = 假` / `调试日志文件 = None` | 2 | 66 |
| `def 日志(msg)`（含 `打印("[DEBUG]",…)`、`调试日志文件.write` 分支） | 10 | ~430 |
| `def 调试模式设为文件(路径)` | 8 | ~360 |
| 散布的 `日志(...)` 调用 + `[DEBUG]` 字样 | 12 | ~1764 |
| **合计** | **32 行** | **2620B ≈ 2.6KB** |

它是纯 Python 宿主调试脚手架（stdout/文件日志开关），真源自举语义完全不需要——`P_cur` 证明不依赖它也能编出合法产物。**写回 `.light` 会让最小自举源背上只服务 Python 宿主的死重，违背自举链最小性。→ 不并入。**

### 3.3 未合入的升级特性（~25KB，能力代差，该并入但须按 level6 方言重写）

这批是 level7 编译器相对 level6 源**多出来的编译器能力**。实证：现状产物的 **56 个顶层签名中，有 13 个在 P_cur（真源编出的产物）里完全没有对应**——即它们服务于 level7 编译器自身、且 level6 源尚未具备。按功能归类：

| # | 类别 | 产物中标志 | 行命中/字节（keyword 命中，近似） | 性质 |
|---|---|---|---|---|
| ② | 缩进 / DEDENT 机制 | `INDENT`/`DEDENT`/`加缩进行`/`续接缩进行` | 46 行 / ~2748B | 升级特性（块边界对接，正是 E.7 同域） |
| ③ | 类型检查发射 | `生成类型检查代码`/`开启类型检查`/`关闭类型检查` | 8 行 / ~1055B | 升级特性 |
| ④ | 转字符串 | `转字符串` | 19 行 / ~2028B | 升级特性（拼接前类型转换） |
| ⑤ | 编译错误异常 | `class 编译错误(Exception)` | 27 行类体（keyword 仅 1 行） / ~646B | 升级特性 |
| ⑥ | 反引号转义 | `反引号` | 2 行 / ~177B | 升级特性 |
| ⑦ | 最长匹配（贪心字符位分词机制1） | `最长匹配` | 3 行 / ~158B | 升级特性 |
| ⑧ | 编译单行块 | `编译单行块` | 5 行 / ~321B | 升级特性 |
| ⑨ | 列表弹栈 helper | `列表弹栈` | 3 行 / ~92B | 升级特性 |

**签名层证据**（13 个产物独有、P_cur 无的顶层 def）：
`def 且表达式` / `def 或表达式` / `def 加减表达式` / `def 乘除表达式`（逻辑/算术表达式，对应 level6 的异名 `且/或表达式`、`算术和差/积商表达式`——**异名扩写**，证明不是同源多出来的壳，而是特性代差）、`def 列表弹栈`、`def 加缩进行`、`def 异常类型映射`、`def 最长匹配`、`def 生成类型检查代码`、`def 编译单行块`、`def 转字符串`、`def 日志`、`def 调试模式设为文件`。

含义：差距**不是"同源多出来的调试壳"，而是 level7 比 level6 多的一整批编译器能力**。其中 ② DEDENT/缩进对接 + ⑤ 编译错误异常 正是 E.7/E.8 要补的"块边界定位"同域问题——level6 源缺它们，STAGE2（out1 再编 level6.light）才会挂在 `find_matching_end` 期望 `结束` 块关闭符、而 level6 是纯缩进方言（E.6 报告 §4 已 pin）。

## 5. 建议：**部分并入**

| 部分 | 处置 | 理由 |
|---|---|---|
| **① 调试外壳（~2.6KB）** | **不并入** | 宿主侧 Python 调试脚手架，与编译语义无关；P_cur 证明真源自举不需要它；回填只会污染最小自举源。 |
| **② 缩进/DEDENT + ⑤ 编译错误异常（最急）** | **并入，按 level6 方言重写** | 这正是 E.7/E.8 块边界闭环的同域能力——level6 源缺它们，STAGE2 才会无限递归（E.6 §4）。应并入 E.7/E.8 修复方向一起做。 |
| **③④⑥⑦⑧⑨ 其余升级特性（~22KB）** | **并入（分批，按 level6 方言重写）** | 是编译器能力代差：③ 类型检查发射、④ 转字符串（拼接缺转字符串会静默出错）、⑥ 反引号转义、⑦ 最长匹配、⑧ 编译单行块、⑨ 列表弹栈。优先级次于 ②⑤。 |
| **E.6 词界修复（+17 行 / 1.6KB）** | **不并入 `.light`** | 修的是 level7 的 Python 分词器；level6 自身 `词()` 整词路线本就正确，已随 89852B 收口。 |

**关键约束（硬）**：
1. **不能字节回填**：level7 是生成的 Python，level6 是无冒号纯缩进方言，必须**按 level6 语法重写**这些能力，不能用 Python 文本直接贴回。
2. **执行前提**：`bootstrap_level6.light` 的 E.7 修改须已收口（本次 65927B 即 E.7 最终版，旁证 `bootstrap/_E7_块边界闭环判决.md`）；并入后须复跑三阶段阶梯（out2 ≡ out3 逐字节一致才算绿），否则会重演 E.6 §4 的 STAGE2 挂起。
3. 本溯源**只调查、只出报告**；实际回移植（~25KB 升级特性）应作为 **E.8 候选**单独排期，与 E.7 块边界修复合并规划。
