# MiniBridge 规格（B1 进程编排 / B2 C FFI）

**版本**：1.0 · **适用**：Track B · **被测实现**：Light（光明）v0.4.2
**本文件自包含**：只读这一份即可实现，不需要外链、不需要先看别的文档。

---

## 0. 一句话定位

MiniBridge 测的是「**光明作为中文编排层**，把一行数据路由给外部生态处理」的能力：
路由决策在光明侧，实际计算在 Python / Go / C 里。

对应修订版 `06-design/评测方案修订版.md` §3：Track B 是**能力展示 / 可行性验证**，
不与对标语言横向排名，只回答三个是非题（L4 首试成功率、跨语言边界错误分桶、
路由与外部调用是否结构分离）。

## 1. 数据模型

### 1.1 输入：NDJSON

- 编码 UTF-8，无 BOM；行分隔 `\n`。若行尾带 `\r`（CRLF 输入），**先去掉 `\r`** 再处理。
- 每条记录是一个 JSON 对象，**必须**含字段 `service`（JSON 字符串）。
- 额外字段（如 `message`）允许存在，实现不得因额外字段判错。
- **空行忽略**：整行去掉首尾空白后长度为 0 即为空行，不参与编号、不产生输出。
- **序号**：忽略空行后按出现顺序从 **1** 开始编号（1-based）。序号只用于 stderr 告警。

### 1.2 输出

- 每条**被接受**的记录在 stdout 产生**一行**：`service<TAB>结果`，行尾 `\n`。
- `TAB` 是单个 0x09；`结果` 是 handler 返回的单行文本（已 strip），或字面量 `ERR`。
- 输出编码 UTF-8；**最后一行之后必须有 `\n`**；若无输出则 stdout 为 0 字节。
- 输出顺序 **严格等于**输入顺序。

## 2. 路由（光明侧的职责）

### 2.1 `route.conf` 格式

```
service<TAB>handler
```

- 每行一条映射，列间是**单个 TAB**（0x09）；两列各自去掉首尾空白后不可为空。
- `#` 开头的行是注释；空行（含只有空格/TAB 的行）忽略。
- **必须且只能有一行通配**：service 列恰好是单个 `*`，作为默认分支。
- 同名 service 出现两次 → **后一条覆盖前一条**（便于本地调试，不是错误）。
- 缺 TAB 的行、列空的行、缺通配行 → 视为**配置错误**，实现必须报错退出（退出码非 0）。

### 2.2 决策规则

对每条记录：

1. 取记录的 `service` 字段（必为 JSON 字符串；缺失或非字符串 → 视为空串 `""`）；
2. 用 service 在映射里查 handler 名；
3. **查不到就走 `*` 那一行的 handler**；
4. 把整行**原始文本**交给该 handler。

> **硬性要求**：上述「读配置、查表、默认分支」三步**必须发生在光明侧**，
> 且**不得出现在任何 `引 ...:` 块内部**。块内只允许 handler 调用或纯计算。
> 理由：这一条就是 Track B 要度量的「编排能力」本体；若把路由写进 C/Go/Python 块，
> 测的就不是光明了。

### 2.3 句柄名 → handler 的解析

`route.conf` 里写的是**句柄名**（逻辑名），不是路径。句柄名到可执行文件的登记
属于编排配置，由光明侧维护（本实现放在 `mb_进程.light` 的登记表里）：

| 句柄名 | handler | 语言 |
|--------|---------|------|
| `h_py_append` | `handlers/h_py_append.py` | Python |
| `h_go_len` | `handlers/h_go_len/h_go_len` | Go |
| `h_c_hash` | `handlers/h_c_hash`（B1）/ C FFI（B2） | C |

**未注册的句柄名**（例如 `h_does_not_exist`）不是配置错误，而是**运行期失败**：
该行输出 `ERR`，其余行照常，退出码 0（见 §3.3）。

## 3. B1：进程编排

### 3.1 handler 调用约定

光明侧以**外部进程**方式启动 handler：

- 把该记录的**整行 JSON 文本 + `\n`** 写入子进程 stdin；
- handler 的 **stdout 第一行**作为该记录的结果（光明侧必须 strip 前导/尾随空白）；
- 子进程 stderr 不参与结果，可忽略（但不得污染光明侧 stdout）。

### 3.2 三个 handler 的语义（必须极简且确定）

| handler | 语言 | 输入 | 输出（stdout 单行） | 度量点 |
|---------|------|------|---------------------|--------|
| `h_py_append` | Python | 一行 JSON | `OK <累计行数>`，并把该行**追加**到 `out.log` | 有状态、落盘 |
| `h_go_len` | Go | 一行 JSON | `LEN <字节数>`（剥离行尾 `\r\n` 后的 UTF-8 字节数） | 纯计算、无状态 |
| `h_c_hash` | C | 一行 JSON | `HASH <FNV-1a 64 位结果的低 32 位，十进制无符号>` | FFI 直接调用 |

**`h_py_append` 的累计行数**：`out.log` 中当前的行数（**落盘计数**，不是内存计数器）。
这样每次处理都起一个新进程也能拿到正确的累计值——这正是「有状态」的考点。

**`h_c_hash` 的哈希**：对**整行原始文本的 UTF-8 字节**（不含行尾 `\n`/`\r`）算
FNV-1a 64 位（offset basis `14695981039346656037`，prime `1099511628211`，
每字节先 XOR 再乘、模 2⁶⁴），取**低 32 位**，按十进制**无符号**打印。
按字节而不是按码点：中文一字占 3 字节，与各语言默认行为一致。

### 3.3 错误处理（三条，都必须实现）

1. **handler 退出码非 0**（或可执行文件不存在/不可执行）→ 该行输出 `service<TAB>ERR`，
   **继续处理后续记录**，最终退出码 **0**。
2. **非法 JSON 行**（解析失败，或解析结果是数组/标量而非对象）→ 跳过该行，
   向 **stderr** 写 `WARN invalid_json index=<序号>`（行尾 `\n`），
   **不改变退出码**。与 `01-spec/MiniLog规格.md` §0.3 口径一致。
3. **配置错误**（`route.conf` 缺 TAB / 列空 / 缺通配行）→ 报错并非 0 退出。
   这类错误是「部署错了」，不是「某条数据坏了」，所以不能降级成 `ERR`。

### 3.4 handler 实现约束

- 三个 handler **不得解析 JSON**：它们只做 §3.2 那点事。把 JSON 解析放进 handler
  会把「解析器工程能力」混进「进程编排能力」的度量里。
- handler 只依赖各自语言的标准库，**不允许联网安装依赖**。

## 4. B2：C FFI

### 4.1 与 B1 的唯一差异

- `h_c_hash` 从「启动外部进程」改为 **直接 C FFI 调用**（同进程内，不经子进程）；
- `h_py_append` / `h_go_len` **仍然走进程**（它们本来就不是 C）；
- 路由决策（§2）与错误处理（§3.3）**完全不变**；
- **输出必须与 B1 逐字节相同**：同一输入，`run_b1.sh` 与 `run_b2.sh` 的 stdout
  逐字节相等。这条是本卡最容易被糊弄过去的判据，也是唯一能证明「FFI 真的等价」的判据。

### 4.2 语言与降级（**任务包必须指定一套语法**）

本实现**指定**用 **`引 C:` 块**这一套语法：

```
引 C:
    long long mb_fnv1a32(const char* s) { ... }
```

即「C 源码内联在光明程序里 → cc/gcc/clang 编译成 .so → ctypes 绑定并直调」。

**不采用**另一套 `加载库 "x.so" 为 别名。外部 段落 名 接收 ... 返回 ... 在 别名。`
显式声明语法（两套在 v0.4.2 都可用，本地均已实测）。理由：两款语法并存时，
Agent 会在其间反复试错，把「语法选择成本」混进 L4 引用成功率（修订版 §3 明确要求
任务包指定一套）。

**降级形态（允许，但有硬约束）**：若本机确实没有 C 编译器，
B2 标记 `B2_status=blocked_no_c_compiler`，`run_b2.sh` 打印 `SKIP: no C compiler`
并 **退出码 0**（不算失败），并在报告里记为 `environment_blocked`，
不计入 L4 引用成功率。

**禁止**（这两条一旦违反，本卡按不合格处理）：

- 为了「让 B2 通过」而把 `h_c_hash` 改成用 Python / Go 顶替，假装是 C；
- 在没有编译器时伪造 `.so`。

> 本机实测：`cc` 与 `clang` 均存在，`引 C:` 路径可用，因此 B2 走 **(a) 真实 FFI**，
> `B2_status=ok`，未使用降级路径。

### 4.3 一致性防线

`引 C:` 块里的 C 文本与 `handlers/h_c_hash.c` 是**两个物理副本**，天然会漂移。
`tests/selfcheck_handlers.sh` 做**四向交叉对拍**（由 `build.sh` 自动调用，失败即红）：

1. `handlers/h_c_hash`（C 可执行文件，B1 用）；
2. `handlers/libh_c_hash.so`（C 共享库）；
3. 从 `mb_cffi.light` 里**抽出来现场编译**的 `引 C:` 块（B2 用）；
4. 一份**独立重写**的 Python 参照实现（防「三份错得一样」）。

## 5. 交付物与判据

```
07-track-b/
├── 规格.md                     本文件
├── route.conf                  service → handler（TAB 分隔）
├── handlers/
│   ├── h_py_append.py          Python handler
│   ├── h_go_len/{go.mod,main.go}  Go handler
│   └── h_c_hash.c              C handler（同一份源码编 CLI 与 .so）
├── minibridge.light            光明侧主程序
├── mb_路由.light               路由表读取与查表（决策在这里）
├── mb_进程.light               B1 handler 调用（外部进程）
├── mb_cffi.light               B2 C FFI 绑定（`引 C:` 只在这里）
├── mb_调度.light               B1/B2 的唯一分叉点
├── build.sh                    一键构建（幂等）
├── run_b1.sh / run_b2.sh       端到端入口
└── tests/
    ├── case_basic.ndjson       3 条记录、3 个 service
    ├── expected_b1.txt         B1 期望 stdout（B2 必须与之逐字节相同）
    ├── case_edge.ndjson        边界用例：坏句柄名 / 非法 JSON / 通配
    └── selfcheck_handlers.sh   handler 四向交叉对拍
```

### 5.1 判据

```sh
cd benchmarks/light-lang-bench/07-track-b

sh build.sh
sh run_b1.sh tests/case_basic.ndjson | diff - tests/expected_b1.txt   # 必须无差异
sh run_b2.sh tests/case_basic.ndjson | diff - tests/expected_b1.txt   # 必须与 B1 相同
```

### 5.2 边界用例

`route.conf` 中某 service 映射到不存在的 handler（如 `h_does_not_exist`）→
该行输出 `ERR`，其余行仍正常，**退出码 0**。
（`route.conf` 里预置了该句柄名的说明；`tests/case_edge.ndjson` 覆盖此路径，
需要临时改 `route.conf` 的 `hash` 行复现。）

### 5.3 结构判据（`引 ...:` 块隔离）

`git grep` 可验证：**路由决策（读配置、查表、默认分支）不得出现在 `引 ...:` 块内部**。
本实现的 `引 C:` 块只出现在 `mb_cffi.light`，块内只有 `mb_fnv1a32` 的纯 C 计算。

## 6. 环境事实与结论边界

| 项 | 实测值（本机 FreeBSD 15.1） |
|----|------------------------------|
| Python | 3.12.13 ✅ |
| Go | go1.25.14 freebsd/amd64 ✅ |
| cc / clang | `/usr/bin/cc`、`/usr/bin/clang` ✅（**gcc 缺失**，但 `引 C:` 探测 `gcc→cc→clang` 命中 `cc`） |
| 光明后端 | `--backend src`（转译腿） |
| B2 形态 | **(a) 真实 FFI**，`B2_status=ok` |

**结论边界**：Track B 的结论**只对被测的这一个光明版本 + commit 成立**
（`light_version=0.4.2`）。B2 走的是 `引 C:` → ctypes 路线，因此
「跨语言边界错误」里若出现 ctypes 类型错误，属于 **Python 运行时**而非光明语言本身，
报告时必须单独分桶（修订版 §1.4 强制要求）。
