# 光明语言「地道度」评分标准（LLM-as-Judge Rubric v1.0）

> 适用对象：**仅 Light 语言的 Track A / Track B 最终 `.light` 源文件**。
> 评测的是「中文语义基元的使用方式」，**不是**代码正确性、性能或可读性。
> 正确性由黑盒测试独立判定；本评分**不得**参与 Pass@1 计算，只作为附加观测指标。

---

## 0. 为什么需要这份 rubric

原方案提出用 LLM-as-Judge 判断「中文思维 vs. 英文逻辑逐字翻译」。直接这么问会有三个问题：

1. 评判模型对「地道光明代码」没有稳定内部表征，同一份代码换一次采样分数可能跳动很大；
2. 没有 ground truth，"地道"容易退化成"看起来中文很多"；
3. 可能奖励堆砌中文标识符，反而惩罚了清晰简洁的正确实现。

本 rubric 的对策：

- **把主观判断拆成 5 个可观测、可计数的二元/三级指标**（§2），不设整体印象分；
- 提供 **6 份人工标注的校准样例**（§3，`examples/` 目录），作为 few-shot，含正例、反例、边界例；
- **要求输出逐条证据（引用源码行）**，无证据的打分视为无效；
- **报告评分者间一致性**（§5），并给出「低置信度时转人工」的兜底；
- **与正确性解耦**（§6），并明确防作弊条款。

---

## 1. 评判输入与前置条件

### 1.1 提供给 Judge 的材料（固定顺序）

1. 本 rubric 全文；
2. 6 份校准样例（`examples/*.md`，含标注与理由）；
3. **光明 L0 核心字表**（见 §1.2，必须作为权威定义注入，不得让 Judge 自行想象）；
4. 待评 `.light` 源文件全文（带行号）；
5. 该文件的黑盒测试结果摘要（仅 `passed/total`，**不提供**具体失败用例）。

> **严禁**向 Judge 提供：实现者身份、语言对比结论、token 成本、其他语言的实现。
> **严禁**让 Judge 判断代码是否正确——它只评「写法」。

### 1.2 权威 L0 核心字表（30 字，永久冻结）

摘自光明语言仓库 `README.md` §L0 核心字表（v0.4.2）：

| 分组 | 字 |
|------|----|
| 控制流（7） | 若 否 当 遍 跳 过 返 |
| 定义类型（6） | 设 段 类 承 接 配 |
| 异常（4） | 试 捕 抛 终 |
| 自指连接（5） | 自 之 并 从 是 |
| 逻辑值（6） | 且 或 非 真 假 空 |
| 组织（2） | 导 出 |

判定要点（**必须**写入 Judge prompt）：

- `若` = 条件分支；`当` = while 条件循环；`遍` = for-each 遍历。**三者不可互换**。
- `设` = 变量绑定；`段` = 函数/过程定义（组合与抽象）。把本可用 `段` 抽取的重复逻辑摊平成一长串 `设` 中间变量，是典型的「翻译腔」。
- L0 是**单字**；`如果`、`遍历`、`否则`、`返回` 等**双字形式属 L1/L2 别名**，不是 L0。评的是「是否恰当地用 L0 表达」，不是「中文字符占比」。
- 代码中出现的**中文标识符**（变量名如 `记录`、`总数`）不计入 L0 密度，只计入「命名」指标的观察。

### 1.3 分层口径

光明 v0.4.2 明确 **L3–L7 属实验态**（`STATUS.md`）。因此：

- 若实现使用了 L4 `引 Python:` / C FFI，评的是**声明与调用是否结构清晰**（指标 D5），**不**因「用了实验特性」扣分；
- 若实现退化为「整个程序就是一段 `引 Python:` 里的 Python 代码」，则判为 **D1 = 0（编排层空心化）**，见 §3 反例 E-05。

## 2. 评分指标（5 项，总分 10 分）

每项 0–2 分，均为整数。**必须逐项给出源码行号作为证据**；无证据则该项记 0 并标注 `no_evidence`。

### D1 · 语义基元选择正确性（0 / 1 / 2）

考察控制流与抽象是否用了**对的**那个 L0 字。

| 分 | 判据 |
|----|------|
| 2 | 分支一律 `若`、条件循环 `当`、集合遍历 `遍`；重复逻辑用 `段` 抽取；无关键字误用 |
| 1 | 有 1–2 处可争议用法（如用 `当` + 手工索引模拟遍历），但主体正确 |
| 0 | 出现「用 `若` 表达循环条件」「`遍` 与 `当` 系统性混用」等语义错位；或整个程序几乎不用 L0（如全塞进 `引 Python:` … `结束引`） |

**反模式（命中即 ≤1）**：`当 索引 < 长度` 手工递增去遍历一个已知集合（本应 `遍 ... 于 ...`）；用 `若` + 递归/跳转模拟 while。

### D2 · 单字基元的组合密度（0 / 1 / 2）

先看静态分析给出的客观量 `l0_density`（定义见 §4），再按区间给分：

| 分 | 判据 |
|----|------|
阈值由 `05-analysis/l0_density.py` 在 6 份校准样例上**实测标定**（见 §3 表格）；
更换词法口径或新增样例时必须重跑标定，不得凭直觉改数。

| 分 | 判据 |
|----|------|
| 2 | `0.30 <= l0_density <= 0.38`，且无明显为凑数而插入的空洞语句 |
| 1 | `0.20 <= l0_density < 0.30` 或 `0.38 < l0_density <= 0.50` |
| 0 | `l0_density < 0.20`（几乎没用光明语法）或 `> 0.50`（疑似堆砌）或 `flags` 含 `no_light_code` |

> 实测分布：E-01 正例 0.3171、E-02 正例 0.3333、E-03 翻译腔 0.2405、
> E-04 误用 0.3000、E-05 空心 0.0000、E-06 堆砌 0.4400。
> 注意 E-04（语义误用）密度 0.3000 会落进 2 分区间——这正是 D1/D2 必须独立评分的原因：
> **密度只测「用了多少」，不测「用得对不对」**。

> **独立性硬规则（必须写入 Judge prompt）**：D2 **只**依据 `l0_density` 数值、
> `flags` 与「是否存在冗余空洞语句」判分。**不得**参考 D1 的结论、不得因「语义误用」
> 而压低 D2（见 E-04），也不得因「写得漂亮」而抬高 D2。同理 D1 不得参考 D2。
> 两项由 Judge 分两遍独立给出，再合并（见 §5）。
>
> 注：密度过高不等于地道。Judge 有权在「明显堆砌」时把 D2 降为 1，但必须在证据里
> 指出具体冗余行；除「明显堆砌」外的任何降分都属无效输出。

### D3 · 命名与语义贴合度（0 / 1 / 2）

考察标识符是「中文业务语义命名」还是「英文标识符音译/直译」。

| 分 | 判据 |
|----|------|
| 2 | 领域概念用中文自洽命名（记录、级别、服务、组、最新时戳…），且与 L0 字不冲突、不造生硬缩写 |
| 1 | 中英混用但一致（如 `json_line`、`记录`） |
| 0 | 全盘照搬英文命名（`records`、`group_by_service`、`tmp_i`），或把中文词硬缩成单字造成歧义（如把「记录数」写成 `数`） |

> 本项**不鼓励**把 JSON 字段名 `timestamp/level/service/message` 改成中文——它们是外部协议字段，必须原样。把协议字段改名反而应扣 1 分。

### D4 · 结构地道性（0 / 1 / 2）

考察是否利用光明的组合能力组织代码，而非把英文三段式逐句对译。

| 分 | 判据 |
|----|------|
| 2 | 有清晰的「读取 → 解析 → 判定 → 汇总 → 输出」`段` 分层；每个 `段` 职责单一；`若`/`遍` 嵌套层次合理（≤3） |
| 1 | 有一定分层，但存在一处「大函数」承担 3 个以上职责，或嵌套 >3 层 |
| 0 | 单一超长线性块；或逐句镜像某英文实现（连临时变量名、语句切分都一一对应） |

### D5 · 编排边界清晰度（0 / 1 / 2）— **仅 Track B 计分**

考察 L4 外语调用与光明原生路由逻辑是否结构分离。

| 分 | 判据 |
|----|------|
| 2 | 路由决策（映射表、条件分派）全部在光明侧完成；外部调用被收拢到独立的 `段` 或 `引 ...:` / `结束引` 块；边界处数据格式（JSON 行 → 参数）有明确转换点 |
| 1 | 分离存在但不彻底（如路由与外部调用在同一个 `遍` 体内交错） |
| 0 | 混杂不可分；或光明侧只剩单个 `引 Python:` 块包办全部逻辑 |

**Track A 的 D5 一律记 `N/A`**，总分按 D1–D4 满分 8 分折算为 10 分制：`score = (D1+D2+D3+D4) * 10 / 8`。
**Track B** 用 5 项满分 10 分直接计分。

## 3. 校准样例（few-shot）

`examples/` 目录含 6 份，每份是「代码 + 标注分数 + 逐项理由」。判卷前必须全部注入。

| 文件 | 类型 | D1 | D2 | D3 | D4 | D5 |  teaching point |
|------|------|----|----|----|----|----|-----------------|
| `E-01_地道正例.md` | 正例 | 2 | 2 | 2 | 2 | N/A | `遍` 遍历、`段` 分层、中文命名 |
| `E-02_地道正例_编排.md` | 正例 | 2 | 2 | 2 | 2 | 2 | Track B 路由与调用分离 |
| `E-03_翻译腔反例.md` | 反例 | 1 | 1 | 0 | 0 | N/A | 英文变量名直译、手工索引遍历 |
| `E-04_L0误用反例.md` | 反例 | 0 | 2 | 1 | 1 | N/A | 用 `若`+跳转模拟循环、`当` 做遍历 |
| `E-05_空心编排反例.md` | 反例 | 0 | 0 | 1 | 0 | 0 | 全部逻辑塞进 `引 Python:` |
| `E-06_边界例_堆砌.md` | 边界 | 2 | 1 | 2 | 1 | N/A | 关键字正确但为凑密度插入冗余 `设` |

> 这些样例**写在评测组织者侧**，不下发给参赛 Agent，避免 Agent 针对 rubric 做风格投机。

## 4. 静态分析：L0 密度与辅助量

由 `05-analysis/l0_density.py` **客观计算**，Judge 不自行估算。

```
l0_density = L0核心字出现次数 / 标识符出现次数
```

- **L0 核心字出现次数**：源码经词法切分后，token 恰好等于 §1.2 表中 30 字之一的次数。双字别名（`如果`、`遍历`）**不计入分子**，另记为 `alias_count` 单列报告。
- **标识符出现次数**：所有标识符 token（含变量名、函数名、模块名、字符串字面量以外的中英文名字）的总出现次数。
- 注释、字符串字面量、以及 `引 Python:` / `引 C:` 块**内部的外语代码**全部排除在分子分母之外（但块本身计入 D5 观察）。
- 同时输出：`l0_token_count`、`identifier_count`、`alias_count`、`loc`（非空非注释行数）、`max_nesting`。

> 密度是**观测指标**，不是优化目标。任何 Agent 若在代码注释里明写「为提高 L0 密度」，Judge 应把 D2 直接记为 0 并标记 `gaming`。

## 5. 评分流程与一致性

1. **两遍独立评分**：每份代码由 **2 个独立 Judge 会话**评分，参数 `temperature=0`，模型可不同（建议 1 个强模型 + 1 个异构模型）。每个会话内先只看源码给出 D1/D3/D4/D5，**再**单独注入静态分析数值给出 D2，避免互相污染（§2 独立性硬规则）。
2. **一致性**：计算 5 项指标的 **Cohen's kappa（线性加权）** 与总分 ICC。
   - `kappa >= 0.6`：取两者均值；
   - `0.4 <= kappa < 0.6`：标记 `low_agreement`，报告两者分数区间，不取均值；
   - `kappa < 0.4` 或任一项分差 ≥ 2：**转人工复核**，由 1 名熟悉光明 L0 的评审定分。
3. **校准漂移检测**：每次批量评分前，先让 Judge 重评 6 份校准样例；若与标注分差总和 > 3，本批次结果作废，重做 prompt 校准。
4. **无效输出**：缺少行号证据、输出非整数分、或 Attempt 评价代码正确性 → 该次评分作废重跑。

### Judge 输出格式（强制 JSON）

```json
{
  "file": "minilog.light",
  "track": "A",
  "scores": {
    "D1": {"score": 2, "evidence": ["L12 遍 行 于 行表：", "L31 段 汇总(...)："]},
    "D2": {"score": 2, "evidence": ["l0_density=0.3171，见静态分析"], "flags": []},
    "D3": {"score": 2, "evidence": ["L8 设 记录表 为 []"]},
    "D4": {"score": 2, "evidence": ["L5/19/31/44 四个 段 各司一职"]},
    "D5": {"score": null, "evidence": ["Track A 不计分"], "na": true}
  },
  "total_10": 10.0,
  "flags": [],
  "confidence": "high"
}
```

## 6. 结果使用约束（重要）

1. **不得**把地道度并入 Pass@1、隐藏测试通过率或任何「完成度」指标。
2. **不得**用它给六种语言排名——其他五种语言没有 L0 概念，跨语言比较无意义。**只对 Light 的多次 trial 做纵向比较**。
3. 报告中必须同时给出 `l0_density` 原始值与 kappa，让读者能自行判断该分数是否可信。
4. 若某 trial 的 `l0_density < 0.20` 但黑盒全绿，应单独标注为「**Python-in-Light 疑似绕过**」并人工检查是否滥用 `引 Python:` … `结束引`，而不是直接给低地道分了事。
5. 本 rubric 测的是「AI 是否习得了 L0 语义基元」，**不是**「光明语言是否优秀」。结论表述必须限于前者。

## 7. 与「语义习得成本」指标的关系

`语义习得成本`（DSH 轨迹分析，见 `05-analysis/`）与本地道度互为印证：

| 轨迹表现 | 地道度预期 | 解释 |
|----------|-----------|------|
| 前 N 轮大量关键字猜测、最终 D1 高 | 高习得成本、成功习得 | 语义重构确实发生了，且被克服 |
| 前 N 轮大量猜测、最终 D1 低 | 高习得成本、习得失败 | 最值得关注的失败模式 |
| 无猜测、D1 低、`l0_density` 低 | 疑似绕过 | 很可能整段 `引 Python:` 块，需人工核查 |
| 无猜测、D1 高 | 低习得成本 | 模型已内化 L0，或任务过简 |

两组数据应在最终报告中**交叉列表**，不做单一归因。
