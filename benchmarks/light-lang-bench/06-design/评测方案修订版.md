## 1. 【阻断级】原方案中的事实错误——必须先修，否则评测无效

在 `/home/skywalk/dswork/light`（v0.4.2，2026-11-15）核实到以下事实，与原方案描述冲突。
这些不是措辞问题：**Minimal 模式 Agent 只有 Bash 和文件编辑工具，写错一条命令就会
把整个 trial 耗在环境调试上，且失败会被错误归因成「语言能力差」**。

### 1.1 CLI 入口写错了

| 原方案 | 仓库实际（`docs/user_guide.md` §3.1 / `STATUS.md`） |
|--------|---------------------------------------------------|
| `light compile minilog.light -o minilog` | **不存在** `compile` 子命令 |
| `light run minilog.light`（解释执行） | 实际为 `light 程序.light`、`light 程序.light --emit-python`、`light 程序.light --native` |
| — | CLI 入口是 `light` / `lightc`；后端为**转译腿（Python）**与**原生腿（C runtime）**双后端 |

**修正**：Track A 的 Light 构建入口统一为

```bash
light minilog.light --native -o minilog     # 原生腿（若该轮稳定）
# 或
light minilog.light --emit-python > minilog.py && 生成 ./minilog 包装脚本
```

> **必须做基线校准**：原方案第一步「hello, NDJSON」只验证「能跑」，不够。
> 应额外把「`light --native` 产出的可执行文件能独立运行且不依赖 Python 运行时」
> 列为环境就绪门槛。若某轮原生腿不可用，**该轮 Light 结果应标记 `backend=transpile`
> 并单独分组报告**，不得与原生腿混算。

### 1.2 「L4」术语与仓库文档冲突

原方案的「L4 = 外语引用」符合 `README.md` 的 L0–L7 分层叙事，但：

- 仓库 **`docs/level4_spec.md` 实际是旧版「Level 4 面向对象」规范**（类、属性、继承、
  `己`/`父`），与外语引用无关；
- `STATUS.md` 明确 **L3–L7 属「实验性」：「不保证 API 稳定，接口、内置名与行为可能随轮次调整」**；
- `docs/分层语法设计_v4.0.md` 才是外语引用的当前设计文档。

**风险**：Agent 在 Minimal 模式下 `grep` 到 `level4_spec.md` 会学到一套完全错误的 L4 语义。

**修正（三选一，推荐 A）**：

- **A（推荐）**：在给 Agent 的任务包里**附一份冻结的、自包含的《L4 外语引用速查》**，
  明确禁止引用 `docs/level4_spec.md`，并把 L4 判为固定版本能力；
- B：把 Track B 降级为「能力展示」，不进正式计分（见 §3）；
- C：允许 Agent 自行查仓库，但把「是否被 level4_spec 误导」单列为观测项，
  并在报告中注明这是**文档缺陷**而非语言能力问题。

### 1.3 L4 外语块定界符：`结束引`，不是 `出`

核实 `examples/E阶段_L3L4原生语法/E4_L4_沙箱隔离验证.light` 与
`examples/J阶段_L4_C_Go_MoonBit/README.md`：

```光明
引 C:
    double 快速求和(...) { ... }
结束引          ← 块结束标记
```

`出 result`（见 `examples/L0_core/10_导_模块导入.light`）是**导出单个变量**的语句，
不是块尾。此外 `引` 后可带名称：`引 Python 工具库:`、`引 Python 敏感数据:`。

**影响**：`05-analysis/l0_density.py` 最初按 `出` 判块尾，导致整份 `.light` 被误判为
「无光明代码」。已修正为 `结束引`，并保留顶格 L0 关键字开头的兜底判定。
**这是本次实测抓到的真实 bug**，说明静态分析口径必须在校准样例上验证过才能用。

### 1.4 「Python 运行时依赖」风险比原方案估计的更严重

原方案已经指出「Light 默认后端依赖 Python 运行时，而 Python 也在对标列表」。
核实后需补充两条：

1. **转译腿本身就是生成 Python 代码**（`--emit-python`），不是「依赖」而是「同构」；
   若 Light 用转译腿、Python 用 `python3 minilog.py`，两者测的几乎是同一套执行语义，
   Light 的额外成本**全部来自编译器/语法层**，这恰恰是要测的东西，但必须显式声明，
   否则会被误读为「Light 比 Python 慢」。
2. **C FFI 也基于 Python ctypes**（`docs/ffi.md`：「光明 C FFI 基于 Python ctypes 实现」）。
   因此 Track B 的「B2：C FFI 直接调用」并没有脱离 Python 运行时，
   「跨语言边界错误」里会有相当比例是 ctypes 类型错误，不是光明语言的问题。

**修正**：所有 Light trial 必须记录 `backend`、`python_runtime_version`、
`uses_ctypes` 三个字段；报告中列出**「环境/运行时相关失败」**并从语言能力指标中剥离
（原方案已有此建议，本修订版把它变成强制字段）。

## 2. 规格层面的公平性修正（对应原方案 §对标语言配置）

### 2.1 Rust 的矛盾与 C++ 的不对称 —— 统一为「JSON 能力对等」原则

原方案表格里 Rust 同时写了「可以使用 serde_json」和「限定 stdlib-only」，自相矛盾；
C++ 允许 nlohmann/json 单头文件，Python 用标准库 `json`，Go 用 `encoding/json`，
MoonBit 用其标准库 JSON —— 六者 JSON 能力完全不对等。

手写 JSON 解析器在 Rust stdlib 下的工作量远大于 Python `json`，**这一项会淹没所有
其他变量**，是比「L0 语义重构」大得多的干扰。

**修正**：不采用「一律 stdlib-only」，而采用**能力对等 + 显式分层**：

| 档位 | 规则 | 适用 |
|------|------|------|
| **主榜（默认）** | 每语言允许使用**该语言生态中最常用、无需联网安装**的 JSON 库，且必须在任务包中**预先放置** | Python `json`、Go `encoding/json`、C++ 预置单头 `json.hpp`、Rust `serde_json`（预置 vendor 或离线 crate）、MoonBit 标准库 JSON、Light `导 解析 自 JSON`（`stdlib/json`） |
| **副榜（可选）** | 一律 stdlib-only，且各语言**都**手写极简解析器 | 仅作稳健性对照，不与主榜合并排名 |

无论哪一档，都必须在规格里写明「JSON 库随任务包提供，Agent 不需要、也不允许联网安装依赖」
（与 ai-coding-lang-bench 的 "No external libraries allowed" 用法保持一致：**禁止的是
临时拉取依赖，不是禁止使用任务包内已提供的库**）。

同时 `01-spec/MiniLog规格.md` 已做三处**降低解析器差异敏感度**的设计：

- 输出要求「原样输出原始行文本」，禁止重新序列化 → 消除键序/空格/Unicode 转义分歧；
- 时间比较退化为 **20 字符串典序**、分组排序固定为 **UTF-8 字节序** → 消除日期库与
  哈希表遍历顺序分歧；
- **非法 JSON 降级为 stderr 警告、跳过、不改退出码**（§0.3）→ 避免手写解析器因
  容错能力差被过度惩罚。

> 注：副榜若要做，`--output`/`stats` 之外的语义仍按同一规格，只是解析实现受限。

### 2.2 构建入口统一约定（修订版）

| 语言 | 入口（统一为由 runner 调用 `./minilog`） | 备注 |
|------|------------------------------------------|------|
| Light | `light minilog.light --native -o minilog`；不可用时转译腿 + 包装脚本，标 `backend=transpile` | 见 §1.1 / §1.4 |
| Python | 生成 `./minilog` 包装脚本调用 `python3 minilog.py` | 标准库 `json` |
| Go | `go build -o minilog minilog.go` | `encoding/json` |
| Rust | `cargo build --release` 后复制 `target/release/minilog` | 任务包预置 `serde_json`，离线 |
| C++ | `g++ -std=c++17 -O2 minilog.cpp -o minilog` | 任务包预置单头文件 |
| MoonBit | `moon build --release` 后取产物 | 标准库 JSON |

**二进制污染防护**（原方案已提，这里给可执行规则）：每个 trial 从干净目录开始，
runner 在**每次调用前**校验 `./minilog` 的 mtime/hash 是否属于本 trial；
不同语言 trial 之间**不共享**工作目录，且 Go/Rust/MoonBit 的 `target/` 在 trial 结束时
随目录一起删除。

## 3. Track B 的定位修正：不与对标语言横向排名

原方案说「对标语言中，只有 Python 具有类似的胶水能力（ctypes/cffi）」，并打算把
Track B 纳入六种语言对比。这个比较在方法上不成立：

- Python 的路由逻辑是英文语法，不存在「语义基元重构」；
- C++/Go/Rust/MoonBit 的语言定位根本不是「中文意图层编排其他语言」；
- 让它们做 MiniBridge 等于让它们做一个**为另一种语言量身定制的任务**，
  分数差异只反映任务错配，不反映能力。

**修正**：

| Track | 参与语言 | 输出性质 |
|-------|----------|----------|
| **A（MiniLog v1/v2）** | 六语言全参与 | **对比式基准**，可横向排名 |
| **B（MiniBridge B1/B2）** | **仅 Light**；可选加 1 个 Python 作为「无 L0 重构成本」的**参照基线**（不排名、不计算优劣） | **能力展示 / 可行性验证**，单独报告 |

Track B 的报告口径改为回答三个是非题，而非打分排名：

1. 在 Minimal 模式（仅 Bash + 文件编辑）下，Agent 能否**在没有 IDE/LSP 的情况下**
   完成一次 L4/FFI 调用？（`l4_first_try_success`）
2. 跨语言边界的错误主要来自哪里？（`boundary_error_rate` 按错误类型分桶：
   编码 / ctypes 类型 / 生命周期 / 动态库加载）——**必须把 ctypes 类单独列出**，
   因为它属于 Python 运行时而非光明语言（§1.4）。
3. 光明侧的路由逻辑与外部调用是否结构分离？（rubric D5 + 人工复核）

另外，B2 的「C FFI 直接调用」与仓库真实能力对应关系：
`引 C:` 走的是 **gcc → .so → ctypes 加载**（`examples/J阶段_L4_C_Go_MoonBit/README.md`），
`docs/ffi.md` 的 `加载库 "..." 为 ...` + `外部 段落 ... 在 ...` 是另一套显式 FFI 声明语法。
**任务包必须明确指定用哪一套**，否则 Agent 会在两种语法间反复试错，
把「语法选择成本」混进「L4 引用成功率」。

## 4. 「地道度」评分：从印象分改为可校准的 5 指标

原方案提出「LLM-as-Judge 判断中文思维 vs 英文逐字翻译」，但未给 ground truth、
未给校准集、未处理一致性。修订版见 `03-judge/rubric.md`，要点：

- **拆成 D1–D5 五个可观测指标**（语义基元正确性 / 单字密度 / 命名贴合 / 结构地道 /
  编排边界清晰度），每项 0–2 分，强制引用源码行号作证据；
- **6 份人工标注校准样例**（`03-judge/examples/`）作 few-shot，含 2 正例、3 反例、
  1 边界例（密度堆砌）；
- **阈值实测标定**，不是拍脑袋：用 `l0_density.py` 在 6 份样例上跑出
  0.0000 / 0.2405 / 0.3000 / 0.3171 / 0.3333 / 0.4400，据此把 D2 的 2 分区间定为
  `0.30–0.38`（原稿凭直觉写的 0.35–0.75 与实测完全不符，已纠正）；
- **D1/D2 独立性硬规则**：语义误用只由 D1 扣分，密度分不得连带压低（E-04 案例）；
- **双 Judge + Cohen's kappa**，低一致性转人工；批量前重评校准样例做漂移检测；
- **结果使用约束**：地道度**不并入 Pass@1**、**不参与六语言排名**，只对 Light 的
  多次 trial 做纵向比较；报告必须同时给出 `l0_density` 原始值与 kappa。

### 4.1 防作弊：Python-in-Light 绕过

校准样例 E-05 展示了最危险形态：整个 `.light` 文件只有一个 `引 Python: … 结束引` 块，
路由逻辑全在 Python 里。它**可能黑盒全绿、token 极低、迭代极少**，只看完成度会给
Light 一个虚假高分。

**强制规则**：`l0_density < 0.20` 且黑盒全绿 → 标记 `Python-in-Light 疑似绕过`，
人工复核；复核成立则该 trial 的完成度加注限定、**不进入主排名**。
`l0_density.py` 已输出 `no_light_code` / `python_in_light_suspect` / `gaming_marker` 三个 flag。

## 5. 「语义习得成本」的可操作化

原方案说「前 N 轮有多少轮在搜索/猜测关键字」，但没给检测规则。
`05-analysis/dsh_analyze.py` 把它定义为**可审计的正则命中轮数**（同一轮多次命中只计 1）：

| 信号类 | 具体模式 |
|--------|----------|
| 检索行为 | `grep/rg/cat/find ... L0/核心字/关键字/语法`，或对具体 L0 字的检索 |
| 编译器报错 | `未定义/未识别/undefined/unexpected/SyntaxError/NameError ... 关键字/标识符`，或 `Lxxxx` 语法/词法诊断 |
| Agent 显式猜测 | 文本含「试一下/猜测/不确定/查一下/应该是」+ L0 字或「关键字/L0/写法」 |

同时给出第二观测量 `first_l0_usage_seq`（首次在编辑内容里出现正确 `若/遍/当/设/段/导`
用法的轮次）。两者与 rubric 的 D1 交叉列表（见 `rubric.md` §7），区分：

- 高习得成本 + 最终 D1 高 → **语义重构确实发生且被克服**（这正是要测的核心现象）；
- 高习得成本 + D1 低 → 习得失败，最值得关注；
- 无猜测 + D1 低 + 密度低 → 疑似 `引 Python:` 绕过。

> **重要限制**：本机未发现可直接对接的 DSH Minimal 会话日志 schema 样本
> （`lightharness/docs/编辑日志格式.md` 是「编辑 + check」格式，不是 Agent 会话轨迹）。
> 因此脚本**不假设私有格式**，而是定义公开的规范化中间格式 + 3 个 adapter
> （normalized / openai / editlog），对未知格式明确报 `unparsed_lines` 而**不猜测、不静默丢行**。
> 正式跑之前必须先用 1 个真实 trial 日志确认 adapter 选择正确，并把 `adapter` 字段写进报告。
> `token_coverage=none`（如 editlog 格式无 token 字段）时，成本指标必须记为**不可得**，
> 不得填 0 当作「零消耗」——这是脚本已实现的保护。

## 6. 统计设计

| 项 | 原方案 | 修订 |
|----|--------|------|
| trials | 6 语言 × 2 Track × 3 = 36 | **Track A：6 语言 × 5 trials = 30**（v1→v2 顺序执行，v2 含 v1 回归）；**Track B：仅 Light × 5 trials**（+可选 Python 参照 5 次，不排名） |
| 报告 | Pass@1、均值 | 均值 **+ bootstrap 95% CI**（对 pass_rate / total_tokens / cycles 分别做 10000 次重采样），并报告标准差 |
| 显著性 | 无 | 语言两两比较用 **Mann–Whitney U**（不假定正态），多重比较做 Holm 校正 |
| 上下文隔离 | 新 DSH 会话 | 保留；额外要求**固定模型版本 + temperature + 相同的任务包字节**（用 sha256 记录），避免跨 trial 的包内容漂移 |

理由：AI Agent 行为方差很大，3 trials 的均值极不稳定；5 是最低可接受数，
若预算允许建议 8–10。

## 7. 测试隔离与防过拟合（落地约定）

原方案已有「可见测试用于迭代、隐藏测试最终评分、独立验证」。补充可执行细节：

- `02-tests/cases/visible.json` 与 `fixtures/` 中**可见用例用到的文件**随任务包下发；
- **`hidden.json` 及仅隐藏用例用到的 fixture（`long_line*`、`bulk_5000*`、`stats_utf8*`
  等）不随任务包下发**，由 runner 在 Agent 会话结束后从独立只读目录加载；
- 隐藏用例**只在规格已声明的语义空间内取值**（`01-spec/MiniLog规格.md` §4 的 15 条自查表
  已覆盖全部隐藏点），不引入规格未定义行为 —— 这点很重要，否则「隐藏测试」会变成
  测「猜中出题人意图」而非测语言能力；
- runner 每个用例在**独立临时目录**执行，比对为**逐字节 bytes**（不做 strip/normalize），
  采集逐用例耗时与退出码，输出 JSON 供 `dsh_analyze.py` 合并；
- 测试脚本在 Agent 会话之外独立运行；Agent 环境里**不放** runner 源码
  （只放可见用例与规格），避免针对性硬编码。

### 7.1 规格/用例自身的可信度

本次用 `04-reference/python/minilog.py` 作 oracle 跑 `--suite all --stage v2`，
**53/53 全绿**。过程中确实抓到并修正了 1 个用例期望值错误（H-02：
3 条记录 `tail --n=2` 应输出 2 条，原稿误写成 1 条）。

**建议固化为流程**：任何规格或 fixture 改动，都必须先让 oracle 全绿再下发任务包；
并且至少用**第二种语言的参考实现**（建议 Go，与 Python 差异最大）再对拍一次，
以排除「oracle 与用例共享同一个 Python 心智模型」导致的同源错误。

## 8. 修订后的执行流程

```
阶段 0  环境就绪门槛（不计分，每语言 1 次）
        hello-NDJSON 跑通 + 构建入口实测 + 记录 backend/runtime/ctypes 字段
```

## 9. 仍然存在的开放风险（诚实登记，不粉饰）

1. **L3–L7 实验态**：`STATUS.md` 明示「不保证 API 稳定，接口、内置名与行为可能随轮次调整」。
   Track B 的结论**只对被测的那个光明版本成立**，报告必须带 `light_version=0.4.2` 与 commit。
2. **原生腿语义分歧**：`STATUS.md` 登记「原生腿经模块限定名调用 .py 侧函数返回空」
   仍是语言级限制。若 Track A 用 `--native`，需先确认 `stdlib/json` 在该腿上可用；
   不可用则该轮必须回退转译腿并标记，否则测的是后端缺口而非语言能力。
3. **MoonBit 编译失败率**：原方案引用「约为 Rust 的 2.25 倍」。该数值应在本次评测中
   **重新实测并给 CI**，不直接沿用外部结论；且要区分「编译失败」是工具链问题还是
   语法反馈质量问题。
4. **LLM-as-Judge 的构念效度**：即便有校准集与 kappa，「地道度」仍是构念而非客观量。
   本修订版已把它限制为「Light 纵向观测指标、不参与排名」，但读者仍应把它当作
   **探索性结果**。
5. **JSON 库对等是近似对等**：不同库在 1 MiB 单行、非法 JSON 容错上的行为仍有差异。
   规格已尽量降低敏感度，但无法完全消除；建议把 `H-01/H-12` 两例的失败单独归类为
   「解析器差异」而非「能力差异」。
6. **单一任务的外推限制**：MiniLog 只覆盖 JSON/字符串/文件/聚合。原方案选择它而非
   MiniGit 的理由成立，但不能据此断言「光明语言的整体 AI 友好度」——
   结论表述应限于本任务族。

## 10. 一句话总结修订重点

原方案的**双 Track 结构与核心判断是对的**，但要让结果有决策价值，必须先修三类问题：

1. **事实层**：CLI 入口、L4 术语冲突、`结束引` 定界符、Python/ctypes 运行时耦合 ——
   不修会把环境失败错记成语言能力失败；
2. **公平层**：JSON 能力不对等会淹没所有其他变量，必须「能力对等 + 预置依赖」，
   并在规格里把日期/哈希/序列化差异压掉；
3. **度量层**：地道度与语义习得成本都必须可校准、可复算、与正确性解耦，
   并明确**不进入六语言排名**；Track B 只做 Light 的能力展示，不做横向比较。
