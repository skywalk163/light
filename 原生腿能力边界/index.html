    原生腿能力边界表（C3-3 + B7 网络层补登）¶

    这张表是给 A3/B3 与后来者的地图。 第二轮的能力边界靠读源码猜；这轮把它 变成源码级守单点：tests/unit/test_native_leg_capability.py 会读 src/llvm/codegen_typed.py 的分派链，与下文「已支持」清单比对——加了新节点 忘了更这张表，测试就打红。

    证据行号指向 src/llvm/codegen_typed.py（2026-08-22 快照，改后会漂移； 权威判据是 grep isinstance(.*ast\.) 所在的两条链）。

    B7 纠正（2026-08-24）： 此前文档和报告中的「原生 runtime 一行网络代码都没有」 是过期结论。runtime_typed.c 5779 行中已有完整的 socket / poller / 事件循环 / Windows Schannel TLS 实现。本文档 §5-§8 补登这四块能力面。 机读数据见 docs/原生腿能力清单.json（四张表，每条带 文件:行号）。

    0. 一句话¶

    原生腿（LLVM）只认它分派链里列出的节点。链尾一律 NotImplementedError 带源码行号 + 转译后端指路；拼错名字的段落调用会列出本模块已定义候选。 没有任何「编译成功、产物行为错误」的静默降级留在表达式层。

    网络层（B1-B4）同样遵循此原则：POSIX TLS 不支持时返回明确错误码，不静默失败。

    4. 适配层伪装揭穿¶

    AstAdapter（src/compiler.py）对它不认识的 v3 节点包成 Identifier("<unknown:XXX>")。原生腿在语句位（_gen_statement ExpressionStatement 分支）与表达式位（_gen_expression Identifier 分支） 都用 _ADAPTER_UNKNOWN_PREFIX（:2680）拆开，报出原 v3 类型名——<unknown:DictLiteral> 不会报成「未定义变量」。

    5. B1 Socket（runtime_typed.c:4368-4525）¶

    5.1 能力面¶

    原生腿在 runtime 层实现了完整的 BSD/Winsock socket 双后端，覆盖 TCP 服务端与客户端。

    运行时符号 定义行 功能

    dv_socket_connect :4409 客户端连接
    dv_socket_bind :4442 绑定地址
    dv_socket_listen :4447 监听
    dv_socket_accept :4455 接受连接
    dv_socket_send :4468 发送数据
    dv_socket_recv :4475 接收数据

    5.2 平台差异¶

    • Windows: Winsock2，启动时 WSAStartup（:4372-4389），退出时 WSACleanup。
    • POSIX: BSD socket，同一段代码 #ifdef _WIN32 分支。

    5.3 内置函数入口¶

    codegen 侧注册的中文名别名（_gen_typed_builtin，:1695 起）： 创建socket/socket_create、连接socket/socket_connect、发送socket/socket_send、 接收socket/socket_recv、关闭socket/socket_close、socket错误/socket_last_error、 socket错误码/socket_last_error_code。

    5.4 真跑判据¶

    tests/test_llvm_net.py 以「真编译 + 真运行 + 断 stdout」范式验证 socket 回环通信， 端口段 19500-19599。

    7. B3 事件循环（runtime_typed.c:4858-5074）¶

    7.1 能力面¶

    dv_scheduler_run_event_loop（:5004）是原生腿的真事件循环，实现：

    1. IO 等待队列（:4858-4920）：协程挂起等待 fd 读写时入队，poller 返回就绪后唤醒。
    2. 定时器最小堆（:4922-4970）：dv_coro_sleep 注册的定时器按到期时间排序。
    3. 事件循环主体（:4975-5074）：循环 dv_poller_wait → 检查定时器 → 唤醒就绪协程 → 检查退出条件。

    7.2 协程模型¶

    • 最大协程数: 4096（DV_MAX_COROUTINES，:4047），不是 256。
    • 实现方式: 单线程 Duff's device，codegen 发 IR。
    • 入口 switch：codegen_typed.py:3459-3475
    • 挂起点：codegen_typed.py:3634-3651
    • 注意: Duff's device 在 codegen 层，不在 runtime 层。
    • 线程模型: 单线程，无 pthread。
    • await_io: 协程挂起等待 IO 就绪（dv_coro_await_io）。
    • sleep: 协程挂起指定毫秒后恢复（dv_coro_sleep）。

    7.3 内置函数入口¶

    运行事件循环/run_event_loop（:1844）、睡眠/sleep（:1848）、await_io（:1852）。

    7.4 真跑判据¶

    tests/test_llvm_async.py 以真编译 + 真运行验证协程调度与事件循环。 tests/test_llvm_net.py 验证 socket + 事件循环联合工作。

    8. B2-4 TLS（runtime_typed.c:5076-5779）¶

    8.1 平台裁决（B7 首日裁决，2026-08-24）¶

    取「显式降级」方案：

    • Windows: Schannel 后端，真实现（:5111-5745）。
    • POSIX: 不支持 TLS。dv_tls_* 返回 DV_TLS_ERROR (-1) 并设置 g_tls_error 错误文本为「本平台未实现原生 TLS：当前只有 Windows Schannel 后端（POSIX 待补 mbedTLS）」。 dv_tls_backend() 返回 "none"。

    不静默失败——调用方会拿到明确的错误码和可读错误文本。

    2026-08-24 Linux 实机复核（docs/POSIX验证报告_Linux.md §C.2、§4 #L2）：此前这一节只有 读码结论，现已在 Ubuntu 22.04.5 + clang-18 上实测——dv_tls_backend() 真返回 none、 dv_tls_wrap 真返回 NULL，且 dv_tls_last_error() 在 POSIX 上确实可用 （定义在 runtime_typed.c:5107，位于 #ifdef _WIN32 之前，无条件存在）， 返回上面那句错误文本。所以「TLS 可用」这句话在任何文档/清单里都只对 Windows 成立。

    改选引 OpenSSL/mbedTLS 必须先拿用户裁决（依赖红线）。

    8.2 运行时符号¶

    符号 声明行 (codegen) 定义行 (runtime) Windows POSIX

    dv_tls_handshake :456 :5111 Schannel 握手 返回 DV_TLS_ERROR

    8.3 POSIX 降级桩（:5747-5778）¶

    dv_tls_unsupported()（:5747）写入 g_tls_error 错误文本，所有 POSIX TLS 函数桩 调用它后返回错误码。这保证 POSIX 上的 TLS 调用方拿到可读错误而非段错误。

    8.4 内置函数入口¶

    包装tls/tls_wrap（:1902）、握手tls/tls_handshake（:1923）、 发送tls/tls_send（:1940）、接收tls/tls_recv（:1955）、 释放tls/tls_free（:1989）、错误tls/tls_last_error（:2000）等，共 26 个别名。

    8.5 真跑判据¶

    tests/test_llvm_tls.py 已有 仅Windows/仅POSIX mark： - Windows 用例：真编译 + 真运行验证 Schannel TLS 回环。 - POSIX 用例：验证降级桩返回正确错误码（:286-310）。

    9. B9 多模块导入与名字修饰（2026-08-24）¶

    9.1 入口与分派¶

    compile_light_typed 检测到模块级导入（_module_has_imports，compiler.py:459） 时，不再走单文件快路径，而是委托 compile_light_project（compiler.py:987）： ModuleResolver 递归收集依赖 → compile_modules_typed（compiler.py:835）用一个 TypedLLVMCodeGen 实例编译所有模块、合并成单份 IR → clang 编译链接。判据见 tests/test_native_import.py（单层 / 两层传递 / 从 X 导入 Y 别名，均真编译真跑）。

    run/compile --backend native 走同一条生产路径（compile_light_typed）， 故命令行触发的多模块编译与库调用等价。native 是 llvm-typed 的一等别名（B9 S1 2.2）。

    9.2 掩码拒绝：同名 .py 影子不许静默降级¶

    原生腿不加载 Python。compile_light_project 收集依赖时（compiler.py:1028的 collect_modules）遇下列情形抛 NativeImportError（compiler.py:42），给出可读 错误（点出模块名 + 缺什么），绝不留一个「跑起来就崩」的产物：

    • 依赖解析到 .py（无 .light 实现）→「原生腿不加载 .py」。
    • .light 与同名 .py 都在，但 .light 是 decl 0 空壳（_is_decl0_shell， compiler.py:48，无段落无类的纯导出清单）→「decl 0 空壳，实现在同名 .py」。

    9.3 名字修饰规则（跨模块段落符号）¶

    符号 原生 LLVM 名 出处
    寄存器 / 局部变量 中文名 → ASCII v{counter} _safe_var_name（llvm/core.py:103，:110 是调用点）
    本模块段函数 裸名收集，函数 @_seg_f{N}（f{N} 按收集顺序） _collect_segment（codegen_typed.py:2484）、_safe_func_name（core.py:116）
    跨模块可见别名 {模块名}_{段落名} → @_seg_f{M} _gen_exported_aliases（codegen_typed.py:787）
    导入侧调用目标 {模块名}_{Y}（从 模块 导入 Y 取 Y 所在模块名） _process_imports（:767）、_gen_imported_segment_call（:1170）

    要点： 1. 源头商责：每个模块为导出的段（无显式导出则全部）注册 {模块名}_{段落名} 前缀别名（_gen_exported_aliases:808），跨模块撞车身由前缀消解。 2. 调用侧做同名前缀解析：从 模块 导入 Y 记入 _imports[Y]=(模块名,Y)，调用时 按 {模块名}_{Y} 取目标（_gen_imported_segment_call:1173）。 3. 单 codegen 全局收集的已知限制：self._segments 以裸段落名为键 （_collect_segment:2488），两个模块若定义同名段落，后收集的模块覆盖先者 （后写胜）。{模块名}_{段落名} 前缀能区分「去重后仍需被 import 的名字」，但 同名裸段的覆盖是 M23 级已知限制，导入方不应依赖「同一裸名在不同源实现不同」。 4. 中文模块名/段落名经 _safe_func_name 统一映射为 ASCII f{counter}，保证 LLVM 标识符合法；同源非 ASCII 名不会撞 LLVM 保留字。

    10. 模块解析边界（2026-08-29 补登，v7.0.0 实测）¶

    本节补登两条实测发现的边界。§9.2 的 NativeImportError 只覆盖了 「依赖解析到 .py」这一种情形；下面两条会走到 ModuleResolver 的通用 ModuleNotFoundError，报错信息与真实原因不符，排查时容易误判。

    10.1 不区分「外部 Python 生态模块」与「light 模块」¶

    导入 asyncio / 导入 codecs 这类引用 Python 标准库或第三方包的语句， 原生腿一律当作 light 模块去找文件，找不到就抛 模块未找到，并逐级向上搜索到盘符根目录。

    最小复现（_speedcheck/nativetest/t_asyncio.light）：

    导入 asyncio

段落 主:

    10.2 项目 stdlib/ 默认不在搜索路径内¶

    src/module_resolver.py:263 find_module 的搜索顺序是 from_dir → self.search_paths → 环境变量 LIGHT_PATH。 项目自身的 stdlib/ 不在默认的 search_paths 里。

    实测（lightharness）：

    $ light compile src/总入口.light -o 总入口.exe --backend native
原生（native）编译错误: 模块未找到: 'SSE'
搜索路径:
  - lightharness\src\SSE.light
  - lightharness\src\SSE.py

    而 SSE.light 实际位于 lightharness/stdlib/。

    绕过方式：显式设置 LIGHT_PATH（os.pathsep 分隔多路径）：

    LIGHT_PATH="lightharness/stdlib;light-merge/stdlib" \
  light compile src/总入口.light -o 总入口.exe --backend native

    注意：这只是绕过 10.2，随后仍会撞上 10.1（下一关报 模块未找到: 'codecs'）。
