    0.88（FreeBSD 15.1）全量预验证 145 failed — 根因分解与并行任务¶

    数据来源：0.88 上 pytest tests/ -n 8 全量（145 failed / 18 errors）+ 13 个失败文件 --tb=short 隔离重跑回溯（2026-09-09）。 结论：145 个失败按根因聚成 9 个可并行任务。其中 vscode(18)+native_leg(8) 共 26 个最初以为是"上传缺目录"，实测是测试顺序污染全局状态（见 Task A）；其余 119 个是真实代码/测试问题。

    一、重要前提：0.88 上传 tar 必须包含 docs/ 与 vscode-extension/（已补，但仍不够）¶

    0.88 验证机用 tar czf 上传时曾排除 docs/ 与 vscode-extension/，导致这两类测试缺文件。已重打包补回并重传（单独跑这两文件 29 passed，文件确实存在）。 但这只是必要前提，不是修复：全量里这 26 个仍失败——见 Task A（污染问题）。 固化项：本地 tar czf 打包命令不要再排除 docs/ 与 vscode-extension/，否则快机验证持续假红。

    二、待分发：9 个并行任务（共 145 个失败）¶

    通用验证命令（本地）： cd light-merge && python -m pytest <文件> -p no:cacheprovider -q 0.88 快机验证（代码已上传后）： cd /home/workbuddy/light_verify && python3 -m pytest <文件> -p no:cacheprovider -q

    通用决策规则（命名/API 类任务适用）：先查 docs/功能对标/对标清单.json 与 lightharness 复刻规范，确认目标 API；优先最小改动——若 stdlib 现有名是约定实现，改测试的 import/调用；若特性本应存在而缺失，补实现并在 stdlib 导出。每改一处都要让对应测试在 0.88 转绿。

    Task 0 — vscode_extension_completions + native_leg_capability 测试隔离（26 个 ERROR/fail，全量专属）¶

    文件：tests/test_vscode_extension_completions.py（18）、tests/unit/test_native_leg_capability.py（8） 现象：这两文件单独跑（含 -n 8）都 29 passed，但在全量里仍失败： - vscode：AssertionError: 扩展文件不存在: /home/workbuddy/light_verify/vscode-extension/extension.js（路径是绝对路径、文件确实存在、事后 os.path.exists 也返回 True） - native_leg：能力清单 JSON 不见了: tests/unit/../../docs/原生腿能力清单.json（相对路径，依赖 cwd） 根因：测试顺序污染全局状态——全量里排在它们之前的某个测试改了 cwd 或泄漏了 monkeypatch，使后续用例的（相对）路径解析失败 / os.path 行为异常。原生腿用相对路径所以对 cwd 敏感；vscode 用绝对路径仍挂，说明还有更全局的泄漏（cwd 或 os.path 被 mock）。 修复指引： 1. tests/unit/test_native_leg_capability.py 的 _加载清单：把 tests/unit/../../docs/原生腿能力清单.json 改成基于 __file__ 的绝对路径（os.path.join(os.path.dirname(__file__), '..', '..', 'docs', '原生腿能力清单.json')），消除 cwd 依赖。 2. 定位污染源：在 0.88 上跑 python3 -m pytest tests/ -n 0 -p no:cacheprovider -q（单进程、确定性），然后二分/逐个目录加入 vscode+native_leg 重跑，找出哪个测试让 cwd 变脏或未还原 monkeypatch（重点嫌疑：tests/ 下多个文件在 import 时 os.chdir(..) 到仓库根，以及 test_v4_1_integration.py/test_module_system*.py/test_missing_stdlib.py 里 os.chdir 到临时目录的用例——确认其 restore 在所有异常路径上都执行）。修法：用 monkeypatch.chdir 或 fixture 的 yield+finally 严格还原，不要依赖模块级 os.chdir。 3. 验收：0.88 全量里这两文件不再出现（从 FAIL/ERROR 变为 pass）。 注意：这是"全量才暴露"的隔离 bug，不要当代码逻辑 bug 硬改业务逻辑；核心是让测试不依赖全局 cwd 且不泄漏状态。

    Task 1 — 数学.light 命名/特性对齐（5 个 ImportError）¶

    文件：tests/test_stdlib_complete.py 失败：from 数学 import 排列, 复数实部, 黄金比例, 双曲正弦, 反正弦 → cannot import name 现实：stdlib/数学.light 当前导出 绝对值/最大值/最小值/幂/平方根/立方根/正弦/余弦/正切/对数/自然对数/.../pi/pow/sqrt/sin/cos/tan/floor/ceil/round/random，无上述 5 个。 修复指引： - 双曲正弦→ 应实现为 sinh(x)（或别名）；反正弦→ arcsin(x)；黄金比例→ 常量 φ；复数实部→ 复数类型的实部取值；排列→ 排列组合函数。 - 若复刻规范里这 5 个本不属于数学模块范畴，则改测试 import 到正确模块。 验收：tests/test_stdlib_complete.py 在该类 import 处全绿。

    Task 2 — 数据结构.light 命名对齐（6 个 ImportError）¶

    文件：tests/test_stdlib_phase2.py 失败：from 数据结构 import 栈, 队列, 双端队列, 二叉搜索树, 单链表, 优先队列 → cannot import name 现实：stdlib/数据结构.light 导出的是动词形 创建栈/创建队列/创建双端队列/...，且 二叉搜索树/单链表/优先队列 可能根本未实现（"Did you mean" 提示 创建二叉搜索树/双端队列空/优先队首）。 修复指引： - 短名 栈/队列/双端队列：在 数据结构.light 补导出别名（或在测试里改用 创建栈/创建队列/创建双端队列）。 - 二叉搜索树/单链表/优先队列：若属应实现的数据结构，按模块既有 创建X 风格实现并导出；否则改测试。 验收：tests/test_stdlib_phase2.py 全绿。

    Task 3 — 小模块命名对齐（网络请求/进度条/数据验证/编码解码/断言工具，~12 个 ImportError）¶

    文件：tests/test_stdlib_phase3.py、tests/test_stdlib_phase4.py、tests/test_stdlib_phase9.py 失败与对应现实导出： - 网络请求：响应(缺失；现有 响应文本/响应成功/响应状态码/获取响应头，可能需补 响应 对象)、拼接URL(→ 已有 合并URL)、解析查询串(缺失)、请求错误(→ 已有 错误响应) - 进度条：进度条(→ 创建进度条)、多阶段进度条(→ 创建多阶段进度条) - 数据验证：验证结果(→ 创建验证结果)、数据模式(→ 创建数据模式) - 编码解码：字符集转换为字符串(→ 字符集转字符串) - 断言工具：断言失败异常(→ 现有 断言失败 是函数/段落，测试可能想要异常类；若 stdlib 用 断言失败() 抛错，测试应 try/except 断言失败) 修复指引：逐条对齐——能加别名导出的在 stdlib 补导出；命名不同的一目了然直接改测试 import；缺失特性（响应/解析查询串/请求错误）按规范补实现。 验收：上述三文件的 ImportError 全消除。

    Task 4 — 日期 模块 LunarDate snake/camel 命名（8 个 AttributeError）¶

    文件：tests/test_datetime.py 失败：LunarDate.to_solar_date → 'LunarDate' object has no attribute 'to_solar_date'. Did you mean: 'toSolarDate'；LunarDate.from_solar_date → 提示 fromSolarDate。 根因：底层 lunardate（0.88 装的是 py312-lunardate）API 是 camelCase toSolarDate/fromSolarDate，而测试/某层 wrapper 调 snake_case。 修复指引：定位调用点在 日期 stdlib wrapper 还是测试自身——统一为 camelCase（或 wrapper 暴露 snake_case 别名）。注意这是 0.88 装的 lunardate 版本决定的 API 形态，gitea(1.5) 上同包也可能一致，需确认两机 lunardate 版本。 验收：tests/test_datetime.py 全绿。

    Task 5 — phase4 对象式 API 契约（~17 个 AttributeError）¶

    文件：tests/test_stdlib_phase4.py 失败示例：'dict' object has no attribute '是否有效'、'bool' object has no attribute '是否有效'、'dict' object has no attribute '设置'/'获取'/'验证'/'_总数'、'bool' object has no attribute 'get'。 根因：测试把 stdlib 返回的对象当成带方法的对象（如 结果.是否有效()、状态.设置(...)），但 stdlib 实际返回普通 dict / bool，方法以函数式提供（如 是否有效(结果)、设置当前(状态, 值)）。 修复指引：二选一，按复刻规范统一—— - (A) 改测试：把 X.方法(...) 改成函数式 方法(X, ...)（风险低，推荐先试）； - (B) 改 stdlib：让这些构造返回带方法的类（改动大，需确认是否目标设计）。 - 涉及模块：数据验证(验证结果)、进度条(状态)、缓存管理器(见下) 等。 验收：tests/test_stdlib_phase4.py 的 AttributeError 全消除（该文件还剩 bytes/str、ord、kwarg 等见 Task 8）。

    Task 6 — phase13/comprehensive/pure_light_hook 的 NameError（~17 个）¶

    文件：tests/test_stdlib_phase13.py、tests/test_stdlib_comprehensive.py、tests/test_pure_light_hook.py 失败示例：name '列表' is not defined(×7)、name '无' is not defined(×3)、name 'split'/'去除空格'/'replace'/'find' is not defined。 根因：测试用了一批解释器未定义的标识符——列表(应用 新建列表 或 [])、无(None，light 里可能是 空)、split/replace/find/去除空格(字符串方法，误当作裸全局名，应为 文本.分割() 等方法式或对应 builtin)。属于测试方言/写法与 light 解释器不符。 修复指引：按 light 实际 builtin/方法替换这些名字；split/replace/find 改为 文本.分割(分隔符) 等（查 src/keywords.py 注册表确认正确写法）；列表→新建列表()；无→空。逐文件修完让 NameError 消失。 验收：上述三文件 NameError 全消除。

    Task 7 — 原生腿能力边界：函数值传递（~13 个 RuntimeError/Exception）¶

    文件：tests/test_stdlib_phase3.py（时间管理：倒计时/定时器/多次计时/计时函数 报 原生腿不可用：回调需函数值动态调用）、tests/test_stdlib_phase9.py（断言失败/断言可调用/断言满足条件/链式断言器 报 能力边界：原生腿函数值不可调用…降级 stub） 根因：这些是已知语言限制——原生腿（native backend）暂不支持把函数作为值传递/动态调用。测试在验证解释器这一能力，当前必败。 修复指引：不要当 bug 硬修代码，改为在测试上标注预期失败，让 CI 不红但保留追踪： 

    @pytest.mark.xfail(strict=False, reason="原生腿暂不支持函数值作为值传递（见原生腿能力边界.md）")
    或整文件/整类加 pytest.mark.xfail。待原生腿支持函数值后再摘掉标记。 验收：这些用例从 FAILED 变为 XFAIL（不计失败），全量 summary 不再出现它们。

    Task 8 — 具体真 bug（bytes/str/ord/kwarg + R13C + llvm_c3_expr，~12 个）¶

    文件：tests/test_stdlib_phase4.py、tests/unit/test_原生腿_R13C_对拍扩展.py、tests/test_llvm_c3_expr.py 失败与定位： - bytes/str：AssertionError: 'hello' != b'hello'、'68656c6c6f' is not an instance of <class 'bytes'>、IndexError: string index out of range、TypeError: ord() expected string of length 1, but int found → 编码/字节处理（编码解码/字节转字符串/字符串转字节）返回 str 而测试期望 bytes；某处把字符当 int 传 ord()。 - 缓存管理器 kwarg：TypeError: 缓存管理器() got an unexpected keyword argument '最大容量' → 调用用了 最大容量= 但定义形参是 最大（查 stdlib 缓存模块）。 - R13C URL 编码：实际=['a%20b%26c%3D1',...,'path/to?q=光明'] 期望=[...,'path/to?q=奥楥'] → URL 编码对 光明 两字结果不一致（编码实现差异，疑似字符集/引号 bug）；另 实际=['1','0.571429','1','0'] 期望=[1.0,1.0,1.0,0.0] → 数值被转成 str。 - llvm_c3_expr：Failed: DID NOT RAISE <class 'NotImplementedError'>、数值差（+ 1.33333）、Use -v to get more diff → 原生腿表达式求值（异常传播 / 除法精度）错误。 修复指引：逐条定位 stdlib/编译器代码修： - 字节函数明确返回 bytes；ord() 调用前确认传入是长度为 1 的 str。 - 缓存管理器 形参对齐（最大容量 或调用方改 最大）。 - R13C 的 URL 编码对非 ASCII 字符（光明）需要按规范（UTF-8 percent-encoding）实现；数值型断言确认类型。 - llvm_c3_expr 的 NotImplementedError 应在对应未实现分支抛出；除法精度对齐 Python 语义。 验收：对应用例在 0.88 转绿。

    三、收敛后预期¶

    • Task 0（vscode + native_leg 隔离）做完后，这 26 个在全量里转绿（需先满足"前提"：上传包含 docs/+vscode-extension/）。
    • Task 1–8 全做完后，0.88 全量应接近 0 红（仅剩 Task 7 标 xfail 的已知限制 + 可能的网络/真实环境差异）。
    • 每完成一个 Task，建议在 0.88 上单独重跑对应文件确认（命令见通用验证），再合入 main；合入前仍走 check_regression.py 基线闸门（只拦基线外新增失败，安全）。
    • Task 0 的污染源定位建议在 0.88 用 pytest tests/ -n 0 单进程确定性复现后二分，避免本地 Windows 的 421 噪声干扰判断。
