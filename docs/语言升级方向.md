### 🥇 E-2 · 分布式模块「每轮分配路径」内存画像（L-194 残余）

| 要素 | 内容 |
|---|---|
| **现状** | **L-194 主体已修（R144）**：`收全部` socket 无限拼接 OOM（~120 MB/s）已止血（0.82 实测孤立 `客户端.请求` 干净错误返回 rc=0、`节点网络.light --sample` rc=0/SMOKE_OK）。<br>**残余未定位**：完整 `节点 --sample`（真实链 `节点` → `节点核心.主` → `工人.运转` → `客户端.请求`）在 `ulimit -v 6000000` 下 208 s 涨至 5.99 GB → `rc=-11`（SIGSEGV），斜率 **~29 MB/s**。<br>**R119-B（协程回收）已修（R156）**：`LightFuture` 加 `refcount`/`owner` + `dv_future_ref/unref/dv_coro_free`。<br>⚠️ **关键**：memory 明确记载「~29 MB/s 无界增长 **≠** 协程泄漏，`DV_MAX_COROUTINES=4096` 封顶使协程泄漏有界；主导根因在分布式模块**另一条每轮分配路径**（socket 收包/请求对象）」——**根因未定位到行**。<br>⚠️ **R156 之后无人复测**：残余曲线是 R144 时点测的，R156 的协程回收修复**可能已改变该曲线，也可能没有**，当前 HEAD 状态未知。 |
| **阻塞什么** | **是（唯一真阻塞项）**。① `native_run_readiness` 可跑率卡在 67/68，无法升到 68/68；② **任何把 `节点` 当库导入的原生腿程序都会挂死并吃满内存** —— 缺陷账原文定性为「本轮唯一有『打爆机器』风险的现象」。带这种风险的项进正式版不可接受。 |
| **预估代价** | **1~2 人日**（内存画像 + 定位 + 修复 + 0.82 复验）。若根因落在 runtime 值所有权（R11C-2 长期缺口），则 **3+ 人日**，需独立立项。 |
| **建议窗口** | **R158 独立轮**（深水区，不给普通轮；须远端 0.82 跑，本机禁实跑） |
| **验证判据** | 完整 `节点 --sample` 在 `ulimit -v 6000000` 下 **RC=0 + 内存有界（无线性增长）** + 0.82 权威门 new_reds=0。**必须先做「post-R156 复测」这一步**，再决定是本轮修还是销账。 |

> **为什么必须先复测**：本轮 E 线的价值就在于指出——R156 修的是协程回收，
> 而残余增长的**主导根因被判定在另一条分配路径上**。那么在 R156 之后重新测一次，
> 是分辨「残余已随 R156 消失 → 可销账」与「残余仍在 → P0 必修」的**唯一判据**，
> 且成本极低（一次 `native_run_readiness.py --sample 节点`）。不测就排期等于猜。

### 新发现 2 · 「高精度」是假高精度，风险形态比「没有」更危险

`dv_decimal_*_str` 内部是 `atof` → double → `%.10f` 固定 10 位小数，源码注释自认非生产级。
调用方看到 `高精加法("0.1","0.2")` 返回值会**误以为拿到了 Decimal 精度**，实际误差与 double 无异。
这是典型的「缺失 ≠ 空值」同族问题（见 `docs/编程注意事项.md` 坑 04）——**用降级实现冒充完整特性**。
建议（二选一，需业主裁定）：① 补纯字符串算术（~2 人日，只改内部，接口不变）；
② 在 `docs/api/builtins.md` 显式标注精度上限，避免误用。

### 新发现 3 · 缺陷账 §十状态未随落地更新（F 族文档漂移）

三项落地分别发生在 R149 / R151，但缺陷账 §十表格至今仍是「方案待审」。
根因与 R153 登记的 L-201「账实不符九轮」同源：**账本条目与代码落地之间没有闭环检查**。
建议：① 本轮订正 §十；② 把「账本条目 → 代码落地」的一致性检查挂进现有门禁（可与 E-4 的全套扫描合并）。
