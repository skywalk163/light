# 历史开发轮次问题总账（开发前必读）

> **这份账的目的：让同一个坑不要踩第三次。**
>
> 背景：截至 R153，项目跑了 **150+ 个轮次**，问题记录散落在**七个互不相通的地方**
> （缺陷账、known_issues、各轮 `_Rxxx_报告`、编程注意事项、`.workbuddy/memory` 日志、
> 能力清单、API 文档）。结果是：**R152/R153 连续两轮在同一个 `是空` 上炸红**，
> 而它的完整答案早在 R55（L-059）就出现过一次，只是没人知道。
>
> 本文是**索引，不是第三份拷贝**。每条只给「一句话根因 + 去哪看」，
> 权威细节仍在原载体——那样才不会再制造新的漂移。

## 5. 维护规则（这份账要不变成第四份漂移，必须守）

1. **本文只做索引**。发现新问题 → 先决定它的权威载体（空值族→空值规范；编译器族→缺陷账；
   坑点→编程注意事项），把细节写那里，**本文只加一行索引**。
2. **每个新问题必须给一个编号**（L-2xx 顺延），并在对应载体留「轮次 / 症状 / 根因 / 修法 / 防再发锚点」。
3. **修完一个问题，必须留一个会红的测试锚点**——没有锚点的「已修」等于没修
   （R152-E1 的静默 ImportError 就是这样活下来的）。
4. **改口径类语义（判型/内置/异常名）前，先跑空值规范 §6 的十条检查清单**，
   再全仓 grep 同步所有文档。
5. 每轮收口时，把本轮新问题补进本文 §2 对应族；若开出新族，在 §0 用法表加一行。
6. **删载体必须同步销账**（L-201 教训）：删除文件/模块/影子时，先查缺陷账有无挂在它名下的条目——
   有则同轮显式裁定（「修后删」还是「删了就算消解」）并更新状态，**禁止「文件没了、账还挂着」**。
   已关闭的条目保留原文 + 追加实际处置记录，不删条目（编号是不可再生资源）。
