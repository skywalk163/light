## A 章 · M1 stdlib 别名层

### A-1 `导出` 语句是否已支持别名形态？—— **不支持（确定）**

证据 1：全仓 531 行 `导出` 语句中，无一条别名形态。

```bash
cd /g/dswork/duan-light-merge/light-merge/stdlib
grep -rn "导出 .* 为 " *.light      # 输出：（空）
grep -rn "别名" *.light             # 输出：全部是注释，无语法使用
grep -rn "^导出\|^ *导出 " *.light | wc -l   # 输出：531
```

证据 2：`src/` 里没有「导出别名」的任何语法实现。

```bash
grep -rn "别名" src/ --include=*.py | head -40
```

命中全部是三类无关内容：`ast_nodes.py` 的**类型别名**定义节点、`chinese_units.py` 的**单位别名**、`code_generator.py` 注释里的**转发表别名**。没有任何 `ExportAlias` / `导出 … 为 …` 的解析分支。

证据 3：`导出` 语句的完整实现只收「符号列表」，见 `src/parser_stmt.py:2616-2675` `_parse_export_stmt()`：

```
formats: 导出 符号一 符号二。 / 导出《符号一》，《符号二》。 / 导出 全部。
分派点:  src/parser_stmt.py:309-310
AST:     ExportStmt(symbols: List[str])   —— 只有 symbols 一个字段，无处放别名
```

**结论：`导出 X 为 Y` / `导出 X 作为 Y` / `别名` 关键字 / `从 X 导入 Y 为 Z` 全部不支持。**
（注：`导入 … 出 符号 为 别名` 形式的 **import** 别名是支持的，见 `tests/test_context_manager.py:1572-1575`
`导 学生模块 出 人 为 P` → `from 学生模块 import 人 as P`。**导入侧有别名，导出侧没有**。）

### A-4 命名空间冲突检查（**这是 M1 的关键结论**）

真正的「AI 免 import 就能写」注册中心是 **`src/code_generator.py:317` 的 `self.builtin_map`**（实测 289 条），
不是 `src/keywords.py`。逐个核对：

```bash
.venv/Scripts/python.exe -c "
import sys; sys.path.insert(0,'src')
from code_generator import PythonCodeGenerator as G
m = G().builtin_map
print('builtin_map 条目数 =', len(m))
for k in ['读取','写入','存在','获取','解析','序列化','反序列化','去空白','去除空白','去除首尾空白']:
    print('  %-8s in-map=%-5s -> %s' % (k, k in m, m.get(k,'-')))
"
```


**冲突清单（逐个实跑确认）**

| 候选别名 | 冲突对象 | 位置 | 证据 | 判定 |

> **注意一个陷阱**：本地定义会**遮蔽** builtin_map。实测探针
> `段落 读取(路径): 返回 "本地别名被调到:" + 路径` + `打印(读取("x.txt"))` → `[OK] '本地别名被调到:x.txt'`，
> 产物里发出的是 `def 读取(路径):`（没有被改写成 `input`）。
> 这意味着：即使在 `文件系统.light` 里加了 `段落 读取(...)` 别名，用户若**不 import**，`读取(...)` 仍走 builtin_map → 仍是 input。
> 换句话说：**「在 stdlib .light 里加别名段落」这条路对 AI 零收益**（AI 不会记得 import）。必须落到 builtin_map。

### A-5 M1 的最终方案建议（改方案）
