## 单 02 · 紧凑写法（无空格）分词族（15 例）

**受影响**：`tests/test_level6_indent.py` 4 + `tests/test_level6_lexer.py` 3 + `tests/test_lexer.py` 1 + `tests/unit/test_lexer.py` 1 + `tests/unit/test_parser.py` 1 + `tests/_test_null_safety.py` 1 + `tests/e2e/test_e2e_chain.py` 4

实测 实际 vs 期望：

- `设x为10` → `IDENTIFIER '设x'` + `为` + `10`；应为 `设`(KW) `x`(ID) `为`(KW) `10`(NUM)
- `如果x大于0` → `IDENTIFIER '如果x'` + …；应切开
- `遍历i从1到10` → `IDENTIFIER '遍历i'` + …
- `打印x` → `IDENTIFIER '打印x'`
- `left自right` → `IDENTIFIER 'left'` + `IDENTIFIER '自right'`
- `甲加1。` → `IDENTIFIER '甲加1'` + `PERIOD`（期望 4 个 token，实得 2）
- `n乘阶乘(n-1)` → `n` + `IDENTIFIER '乘阶'` + `KEYWORD 乘` + …（`tests/unit/test_parser.py:65`：`'n乘阶' != 'n'`）

第二个缺口：纯汉字序列不在内部运算符动词处切分（`甲加`、`乘阶乘`，`加`/`乘` 在 `src/keywords.py` 的 `VERB_ARITY` 里）。

## 单 20 · L4 引 C/Go 导出函数名被拆分/顶替（4 例）—— 已落地

**受影响**：`test_duan_run[J阶段_L4_C_Go_MoonBit/J1_C_快速求和.light]` + product、`[J2_Go_斐波那契.light]` + product

**症状**：J1 报 `NameError: name '快速' is not defined`，J2 报 `NameError: name '斐波那契' is not defined`。工单原先把这四例归给单 19（`串` 缺失），实测证明 `串` 只是**先炸的那一个**，补完 `串` 之后立刻露出下面两条真根因。

**根因一（词法 + 生成两层）：L4 块导出的函数名，在光明侧不被当作用户标识符。**

`引 C:` / `引 Go:` 块里定义的函数会在产物运行期被绑进模块 `globals()`，所以在光明侧就是「用户显式声明的名字」。但：

- 词法层：`Lexer._scan_user_definitions` 只认 `《》` 段落/类/方法、`导出/导入` 列表、`函数/段落`、`段 名(...)`、`定义/设` —— **完全不认 L4 块**。实测 `_scan_user_definitions(J1源码)` 只返回 `['运行']`。于是最长前缀匹配把 `快速求和` 切成 `IDENTIFIER 快速` + `KEYWORD 求和`（`求和` 在 `VERB_ARITY`），J1:18 的产物变成 `串(快速, sum(1))` —— **一个实参变成了两个**，比「名字被顶替」更糟。
- 生成层：`builtin_map` 无条件顶替 —— `阶乘` → `math.factorial`（`src/code_generator.py:244`）、`求和` → `sum`（`:213`），产物根本没调到外语函数。`_user_defined_functions` 护栏思路是对的，但只登记 import 符号与段落名，不认 L4 块。

注意：**「撞表」不是受害的必要条件**。`快速求和` 本身不在任何关键字/动词表里，但因为**尾部含 `求和`** 仍被切碎。所以白名单必须登记**全部**导出名，不能只登记撞表的那些。

**根因二：Go 路径只在编译成功分支绑定导出名。**

`src/code_generator.py` 的 Go 分支里，`globals()` 写入只有两处，且都在 `if _LIGHT_GO_OK:` → `try:` 成功分支内。`except`（编译失败）只 print 不绑定，`else`（无 go）只 print 不绑定；更糟的是**导出名提取本身也在 try 里面**，无 go 时连「要绑哪些名字」都不知道。对照 C 路径：提取无条件执行，绑定覆盖三分支（真实函数对象 / `[C:x 未加载]` / `[C:x 编译器未找到]`），所以 C 侧无 gcc 时也能跑通。

反证：把 C 函数名换成不撞内置的 `myfunc`、无 gcc，产物输出 `结果=[C:myfunc 编译器未找到]` 且 EXEC OK —— 证明只要名字不撞内置动词，无工具链也能跑通。

**判定**：编译器缺陷。用户按规范写 L4 引 C/Go，只要导出名撞了（或含）内置动词，程序就静默走错分支。**已否决「改 examples 改名」的方案**（属改被测输入），采用方案 B：解析期注册 + Go 占位绑定。

**落地（三处）**：

1. `src/lexer.py` 新增模块级 `extract_embed_export_names(language, code)`，C 用 `(?:int|float|double|void|long|char\s*\*)\s+(\w+)\s*\(`、Go 用 `//export\s+(\w+)`，与 code_generator 运行期绑定用的正则**逐字同源**。MoonBit 与 Python 返回空集 —— 它们运行期不往 `globals()` 写名字，登记了反而制造「白名单有名、运行期无绑定」的新 NameError（J3 靠这条保持现状）。
2. `Lexer._scan_user_definitions` 开头加**一遍独立扫描**（不改主循环一个字节）：`str.find` 找 `引`/`嵌入`，套用与真实分词器相同的前缀门槛（`嵌入` 两字；`引` 必须紧跟空格/制表/冒号/换行），再加**行首门槛**（前缀之前只能是空白），然后调用 `_tokenize_embed_block` 定界。
   - 行首门槛是必需的：预扫描是裸文本、不认字符串字面量，而 `examples/L4_python/all_in_one_demo.light:90` 与 `demo4_requests_http.light:30` 的字符串里就写着 `引 Python:`。真实分词器不会踩，因为字符串在更早的分支就被整体吞掉了。
   - 复用 `_tokenize_embed_block` 而不另写一套定界，是为了让单 15 刚加的缩进回归闭合、EOF 闭合、显式 `结束引/结束嵌入` 三条判据**同源**，不出现「预扫描认为块到这、分词认为块到那」的错位。
   - 只前进一个字符、**不跳过块体**：今天的主循环本来就会扫进块体并从中登记名字，跳过会减少既有白名单、可能打红既有绿。
3. `src/code_generator.py`：`_register_imported_names` 把 L4 导出名与 import 符号同级登记进 `_user_defined_functions`（必须在这个预扫描里，不能在 `_generate_embed_block` 里懒登记 —— 生成器是单遍，块写在调用点之后时懒登记来不及，实测「块在后」时懒登记失效、预扫描顺序无关）；Go 路径把导出名提取上移到 `if _LIGHT_GO_OK:` 之外，并在 `else` 之后补全量占位绑定（`if _LIGHT_GO_FN not in globals()` 保证不覆盖 build 成功时绑好的真实对象）。

**顺带修掉的一个真实崩溃**：C 路径原先 `del _LIGHT_C_CODE, _LIGHT_C_FN, _LIGHT_C_FUNCS` 会 del 循环变量 `_LIGHT_C_FN`；块内提不出任何函数声明时（如只有 `#define` 的 C 块）它从未被绑定，`del` 直接 `NameError` 打断整个产物。J1 有两个函数所以没触发。已改为不 del 循环变量，Go 侧新写的 `del` 同样避开这个形态。

**语义取舍（必须记住的代价）**：白名单是**模块级**，不是块级。词法层 `user_definitions` 对整份源码算一次；生成层 `_user_defined_functions` 每次 `generate()` 重置后只增不减。所以一旦某个 L4 导出名撞了内置名，**该内置名在整份文件内不可达，且静默** —— 合成用例实测：同文件内 `引 C:` 导出 `求和` 后，另一个段落里真心想调内置 `sum` 的 `求和(表)` 也会拿到 C 占位串，打印 `[C:求和 编译器未找到]` 而不是 `6`。

这个取舍与仓内既有口径一致，不是新发明：`src/code_generator.py:452` 的注释就写着「显式导入是用户最强的意图表达，必须压过内置映射」，`引 C:` 里写 `double 求和(...)` 与 `从《X》导入《求和》` 是同一类声明，遮蔽范围理应一致。要做到块级/调用点级需要真正的作用域符号表（parser + 类型系统改造），远超本单。**中间态建议**：导出名撞 `ALL_VERB_ARITY`/`builtin_map` 时发一条编译期 W 级告警，把「静默」变成「响一声」，成本几乎为零 —— 未做，待裁决。

## 单 25 · 引 C 绑定缺 argtypes 导致 FreeBSD 上 SIGSEGV + lexer_perf 门禁抖动 · 已完工（v7 收尾第 18 轮）

**裁决（用户拍板）**：(1) J1 走**方案 D**——修编译器安全性 **并** 把 J1 加进 `E2E_EXCLUDED`；
(2) lexer_perf 走**两手**——本轮按抖动不阻塞结论，同时把 CI 阈值提到 20.0 防未来周期性误伤。

### 25-A · 引 C 的 ctypes 绑定缺陷（真缺陷，必修）

**现象**：J1 两条腿在 FreeBSD 上 `assert -11 == 0`（SIGSEGV），stdout/stderr 全空；Windows 本机全绿。

**根因**（`src/code_generator.py:3814` 起，`_generate_embed_block` 的 `lang_main == 'c'` 分支）：
- 旧实现的正则只抓**函数名**（`(?:int|float|double|void|long|char\s*\*)\s+(\w+)\s*\(`），
  然后把每个函数的 `restype` **硬编码成 `c_double`**，且**从不设 `argtypes`**。
- 缺 `argtypes` 时 ctypes 按默认 `c_int` 传参：J1 的 `快速求和(1,2,3,4,5)` 把整数 `1` 传给
  `double* arr` 形参 → C 侧 `arr[i]` 解引用地址 `0x1` → SIGSEGV。
- 附带静默错误：`int 阶乘(int n)` 被按 `double` 读返回值（x86-64 SysV 下整数在 `eax`，
  ctypes 却读 `xmm0`），结果全错但不崩。这条影响**所有** `引 C` 代码，不只 J1。

**为什么 Windows 看不见**：产物先探测 `gcc → cc → clang`（`:3798`）。本机三个都没有 →
`_LIGHT_C_DLL = None` → 走 `:3826` 占位 lambda，`快速求和(...)` 只返回字符串
`[C:快速求和 编译器未找到]`，**跨语言调用从未发生**。FreeBSD base 自带 `/usr/bin/cc`（clang），
所以只有它真编译、真 dlopen、真调进去——平台差异出在「有没有编译器」，不在 flag。

**改点**：改为在**编译期**解析完整签名并据此绑定——
- 新正则 `([A-Za-z_][\w ]*?[\w*])\s+(\w+)\s*\(([^)]*)\)\s*\{` 取 (返回类型, 函数名, 形参串) 三元组，
  中文函数名可命中（Python `\w` 匹配 CJK）。实测 J1 得
  `[('double','快速求和','double* arr, int n'), ('int','阶乘','int n')]`。
- 产物内新增 `_LIGHT_C_CTYPE` 表 + `_light_c_type()`：标量按 C 语义映射，指针转
  `POINTER(...)`／`char*` 转 `c_char_p`，`void` 转 `None`，未知退化 `c_int`/`c_void_p`。
- 绑定循环改为 `restype = _light_c_type(返回类型)`、`argtypes = [各形参类型]`。
  此后参数不匹配的调用抛 `ctypes.ArgumentError`（可诊断、有 stderr），**不再崩进程**。
- `del _LIGHT_C_CODE, _LIGHT_C_FUNCS` 随变量改名同步为 `_LIGHT_C_SIGS`。
- 未动显式 FFI 声明通路（`:3197-3223` 的 `_ffi_type_map`），控范围。

**回归用例**（新增 `tests/unit/test_c_embed_ffi_binding.py`，5 例）：同样**不跑产物**——
`引 C` 只在有 C 工具链的机器上才真绑定，本机那把尺子是瞎的（这正是缺陷漏到 runner 的原因）。
改为从产物 AST 里单独取出 `_LIGHT_C_CTYPE` + `_light_c_type` 求值，直接断言
「C 声明 → ctypes 类型」的对应（含 `double* arr` / `double *arr` / `char* s` 两种星号位置），
断言签名正则抓到三元组，断言绑定循环设了 restype/argtypes 且**不得**再出现
`.restype = _light_ctypes.c_double`，并附产物 AST 合法性断言防止判据在坏产物上仍通过。

**判据有效性自证**：`git stash push -- src/code_generator.py` 抽掉修复后重跑该文件 **5 errors**
（「产物里找不到 `_LIGHT_C_CTYPE` / `_light_c_type`」）；`stash pop` 恢复后 **5 passed**。

## 单 29 · 族 4：编译产物不自洽——L3 运行时模块不在 sys.path（2 例）· 兑现单 17

**打红清单**（**只有 `test_duan_compile_and_run_product` 这条腿**，`test_duan_run` 一直是绿的）：

### 29-A · 根因：产物引导段只铺 stdlib/，从来没有 src/ 那一档
- `l3_echarts` / `l3_markdown` 是**编译器官方注册的 L3 领域模块**（`src/compiler.py:46-59`
  的 `L3_MODULES`，注释明写「通过 `引 Python:` 语法在 .light 文件中导入使用」），
  实体是 `src/l3_echarts.py`、`src/l3_markdown.py`。示例里那句
  `from l3_echarts import L3ECharts` 是**顶层名**形式。
- `引 Python:` 块的代码被**原样**塞进产物的 `_LIGHT_L4_SRC` 字符串里 exec
  （`src/code_generator.py:3626-3632`），所以这句 import 在产物里照样要解析。
- 产物引导段（`src/code_generator.py:611-639`）只把 `stdlib/` 与**项目根**
  insert 进 sys.path。项目根让 `import src.l3_echarts` 成立，但 `src/` 有
  `__init__.py`、是包，包内模块**不会**作为顶层名暴露 → `import l3_echarts` 必炸。
- `stdlib/_light_import_hook.py:131-150` 的导入钩子也救不了：它只找
  `<名>.light`/`<名>.duan`，仓库里没有 `l3_echarts.light`。

### 29-B · 为什么 run 绿而 product 红（差异只在 sys.path）
- **run 腿并不是解释执行**：`cli/light_unified.py:355-357` 生成同一份 Python
  代码后在 CLI 自己的进程里 `exec`（`:379-386`）。两腿产物字节完全相同。
- 两腿 **cwd 也相同**（都是 `REPO_ROOT`，`test_e2e_chain.py:116`、`:151`），
  两腿都**没设** `PYTHONPATH`（`:28-32` 只加 UTF-8 两项）——「cwd 差异」这个
  常见嫌疑可以排除。
- 唯一差别：run 腿的进程里 `cli/light_unified.py:36-42` 为**编译器自己**
  `sys.path.insert(0, <repo>/src)`（为了找 lexer/parser/codegen），`l3_*` 搭了便车；
  product 腿换进程裸跑，没人铺这一档。
- 其它 L3 示例是绿的，因为它们引块里只 import Python 标准库（`sqlite3`/`re`/`os`）；
  全 `examples/` 只有 demo4/demo5 引块 import 了**仓库自带、放在 src/ 里**的模块。

### 29-C · 修法：随产物落盘依赖（通用机制，不是两例特判）
新增 `cli/light_unified.py` 的 `_iter_runtime_module_deps` + `_emit_runtime_modules`，
接在既有 `_emit_user_modules`（单 D 先例）旁边、`compile_with_src` 写产物之后：
- **依赖发现**：正则只匹配**行首（可带缩进）的真 import 语句**，两种形态
  `from X import …` / `import X` 都认；命中集合再与 `L3_MODULES` 白名单求交。
  注释里、字符串中间提到模块名都不会误命中（有回归用例钉住）。
- **白名单是硬边界**：不在 `L3_MODULES` 里的名字**一律不碰**。不能改成「凡 import
  不到的就复制」——那等于允许把任意路径的文件往产物目录搬。`src/` 里有
  `errors.py`/`version.py`/`tokens.py` 这类泛用名，尤其不能进。
  白名单里将来新增 `l3_*` 模块，本机制自动覆盖，无需再改代码。
- **落盘**：用 `importlib` 定位模块 `__file__` 再 `shutil.copyfile` 到产物**同目录**
  （不拼 `<repo>/src/`，这样开发模式与 `pip install` 安装模式都成立）。
  Python 跑脚本时 sys.path[0] 是脚本所在目录，于是 import 自然解析。
- 复制失败/模块加载失败**明确告警**（`[警告] …产物将不自包含`），不静默产出半残产物。

**为什么不选另两条路**：
- 「产物引导段补 `src/` 一档」只是**原地自举**——产物拷到没有本仓库的机器上照样炸，
  「产物可独立运行」只兑现一半；且把整个编译器目录塞进用户产物 sys.path 有遮蔽
  第三方/标准库同名模块的风险。

### 31-D · `_skip_compound_safe_and_match` 返回值失配（正面修复）

**范围**：只改 `src/lexer.py` 一处（`:1104` 内层命中非 `之` 时的返回值），

不动 `E2E_EXCLUDED`。这是 31-B/31-C 里反复标注「阻塞于返回值失配」的那个本体缺陷。

**缺陷机理**：`_match_keyword` 自己的文档串（`src/lexer.py:1021-1023`）承诺
「匹配长度恒等于 `len(kw)`，且 `kw` 恒等于 `text[pos:pos+长度]`」。
`_skip_compound_safe_and_match` 命中 compound-safe 单字后递归到 `pos+1`；旧实现在递归
找到关键字（且不是 `之`）时把**内层的 `(kw, l)` 原样上报**。但内层的 `kw` 取自
`text[pos+k : pos+k+l]`、`l` 也以 `pos+k` 为基准，而**六处调用方**（`:2040/:2244/:2365`
等）按 **`pos`** 消费 `l` 个字符、同时把 `kw` 的字面 emit 出去。于是 `pos` 处那个字被
丢掉、内层关键字被吐两次。实测形态（全部经 HEAD:src vs 工作树双跑核对）：

```
等于空那么     → 等于 那么 么      （`空`丢、`么`凭空）
种类等于       → 种 等于 于        （`类`丢、`于`吐两次）
索引等于       → 索 等于 于
除类型错误     → 类型 型错误       （`除`丢、`型`凭空）
对于 项 之 …   → 于 于 项 之 …     （`对`丢、`于`吐两次）
是否为空       → 为 为 为 空       （`是否`被压成 `为为`）
10的幂         → 幂 幂             （`的`丢、`幂`吐两次）
```

**三种候选语义，为什么选 `(None, 0)`**：

- `return kw, l`（旧）——失配本体，见上。
- `return candidate, length`——即断言 `pos` 处这颗 compound-safe 单字就是词。**单 B 试过**，
  会让 `除`/`幂`/`于` 作为运算符浮现，把 `去除空格`/`对于`/`10的幂` 之类整词切碎；
  全仓 A/B 实测 **100+ 处漂移、42 文件受影响**，故当年收窄到只认 `之`。
- `return None, 0`（本单）——「这颗单字后面还接着关键字料，别让它在这里成词」，正是
  compound-safe 这套启发式本来要表达的语义；契约由 `kw is None` 平凡满足。下游行为不变
  的原因：调用方拿到 `None` 后把 `pos` 处的字当标识符料继续扫，扫到内层那个位置时会
  **在正确的 `pos` 上**重新问一次，得到诚实结果，再由既有 compound-safe 跳过逻辑决定
  整词保留还是切开。

- 语料：代码侧词首 106 / 词内 444（208 文件）；注释侧 56 / 387。词内大头是

#### 31-E-2 · 复合词保护盘点：`异常` 未受长度-2 保护，`常` 与 `异` **不得同批落地**

按 31-A `断`（`断言*` 族靠 `断言` 这个既有关键字获得最长匹配保护）的经验，逐个查了候选字
所在高频复合词**是否本身就在 `ALL_KEYWORDS` 里**（在表里 ⇒ 最长匹配先命中，词不会被撕开）：

```
异常  False   ← 未受保护
常量  True
公有  True
异步  True
接口  True
小写  False
大写  False
公式  False
写入  False
契约  False

```

由此得到两条硬约束：

1. **`常` 与 `异` 都会撕 `异常`，且 `异常` 不在关键字表里**。上面两字的 SPLIT 合计 4 例
   全部就是这一种形态。若要走范式 B，**先把 `异常` 加进关键字表（或等价的最长匹配保护）
   再落单字**，参照 `等于`/`等待` 保护 `等` 的既有做法。
2. **两字更不能放在同一批里改**：同批注入时 `常` 与 `异` 会在 `异常` 上互相干扰，
   A/B 的四档归类会失去可读性（一次改动同时从两侧切同一个词）。**必须串行、逐字重跑预筛。**

`写` 的 `大写`(99)/`小写`(80) 同样无保护，这是范式 C 相对范式 B 的又一条优势。
