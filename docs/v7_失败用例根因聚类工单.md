# v7 合并后失败用例根因聚类工单

- 基线 commit：`7593616b`
- 跑分：`144 failed / 3239 passed / 99 skipped / 6 errors`（3482 收集）
- 复现命令：`python -m pytest tests -q --no-header -p no:cacheprovider --tb=short -rf`
- 背景：段言(duan)/光明(light) 两库合并。**绝大多数失败是「duan 带进来、从未在 light 编译器上跑过」的测试，不要假设它们曾经通过过。**

## 全局硬规则（分发时必须随单转达）

1. **禁止改断言让测试变绿。** 若断言确实写错，必须写明错在哪、正确期望是什么、依据（引规范文档 `文件:行号`）。
2. **禁止改被测输入去迁就编译器。** 例如不要改 `bootstrap/bootstrap_level5.light` 来绕过 parser——它是被测输入。
3. **每张单收尾必须跑全量回归**，不能只看本簇转绿。词法/代码生成类改动尤其容易打穿现在绿着的用例。
4. **PowerShell 5.1 环境**：没有 `&&`（用 `;`），没有 heredoc；pytest 中文输出会被 GBK 解码成乱码，必须 `| Out-File -Encoding utf8 <文件>` 落盘再读。
5. 临时文件写 `.scratch/`（已 gitignore），用完删除；提交前 `git status --short` 必须干净。
6. 跑自举测试会重新生成 `bootstrap/bootstrap_level3.py`、`bootstrap_level4.py`（被 git 跟踪）。跑完用 `git checkout -- <文件>` 还原，**不要留下未提交的产物改动**。

## 已定口径（用户裁决，执行者不得自行更改）

- **遍历循环语序消歧：按连接词区分。** 前置工作是先收窄 `之` 的用法——目前 `之` 在 L0 和 L1 都能用，是消歧的障碍。必须先定「哪个连接词归哪种语序」，再动 parser。
- **类型检查 VARIABLE 档语义：以 light 现行实现为准**，即只在「注解与推断类型冲突」时告警（`V001`），对未注解变量不发声。因此 `tests/test_level6_types.py` 里期望「缺注解 → 告警」的断言**需要重写**，且必须在提交信息里留痕说明这是口径变更、依据是本决策。

## 单 02 · 紧凑写法（无空格）分词族（15 例）

**受影响**：`tests/test_level6_indent.py` 4 + `tests/test_level6_lexer.py` 3 + `tests/test_lexer.py` 1 + `tests/unit/test_lexer.py` 1 + `tests/unit/test_parser.py` 1 + `tests/_test_null_safety.py` 1 + `tests/e2e/test_e2e_chain.py` 4

实测 实际 vs 期望：

- `设x为10` → `IDENTIFIER '设x'` + `为` + `10`；应为 `设`(KW) `x`(ID) `为`(KW) `10`(NUM)
- `如果x大于0` → `IDENTIFIER '如果x'` + …；应切开
- `遍历i从1到10` → `IDENTIFIER '遍历i'` + …
- `打印x` → `IDENTIFIER '打印x'`
- `left自right` → `IDENTIFIER 'left'` + `IDENTIFIER '自right'`
- `甲加1。` → `IDENTIFIER '甲加1'` + `PERIOD`（期望 4 个 token，实得 2）
- `n乘阶乘(n-1)` → `n` + `IDENTIFIER '乘阶'` + `KEYWORD 乘` + …（`tests/unit/test_parser.py:65`：`'n乘阶' != 'n'`）

**根因（单点）**：`src/lexer.py:1309-1315`，`_tokenize_identifier_or_keyword` 的「汉字后紧跟 ASCII」后缀合并分支——`_tokenize_chinese_sequence` 已经正确切出 `KEYWORD 设/如果/打印/自`，这个分支又把紧邻 ASCII 后缀无条件粘回去，并把 token 类型从 KEYWORD 降级成 IDENTIFIER。

第二个缺口：纯汉字序列不在内部运算符动词处切分（`甲加`、`乘阶乘`，`加`/`乘` 在 `src/keywords.py` 的 `VERB_ARITY` 里）。

**规范依据**：`docs/superpowers/specs/2026-07-01-level6-type-annotation-design.md`（light 自己的规格，非 duan）2.1 节「最长前缀匹配」、2.2 节把 `设/为/如果/遍历/加/减/乘/除` 全列为支持无空格分词、2.4 节逐 token 给出期望，与 `tests/test_level6_lexer.py:41-53` 断言完全一致。另 `docs/bug_fixes_compact_notation.md` 记录 duan 侧修过同族问题（Bug 1、Bug 4），其修复要点在 light 的 `src/lexer.py:1383-1397` 与 `:500-508` 都还在 —— **不是机制缺失，是 1309-1315 这个后加分支把已修好的路径推翻了一半**。

**重要澄清**：`tests/test_level6_indent.py` 那 4 例**不是缩进问题**。INDENT/DEDENT 生成正确（同文件 2 例通过），4 个失败全部卡在 `tokens[indent_idx+1].type == KEYWORD` 而该位置是 `打印x`/`打印i`/`打印c`。缩进代码一行都不用动。

**风险提示**：1313 行那个合并是为 `分割Pointer_内部`、`读取LSP消息`、`阶段1标题` 这类混排名字加的。收窄条件时必须让 `user_definitions`（`src/lexer.py:500-508` 已预扫描）当唯一放行依据。

**难度**：中等。**必须带全量回归**（`test_lexer.py`、`tests/unit/`、`test_level6_*`、e2e 产物链一起跑）。

**附带**：`tests/_test_null_safety.py::TestNullSafetyArithmetic::test_operation_without_unwrap`（:123）属同一根因。测试输入 `设值为空。设结果为值加1。` 无空格，RHS 被并成单个标识符 `值加1`，不生成 BinaryOp，所以可空运算检查无从触发。检查逻辑本身正确（`src/type_inferencer.py:1800-1823`，加空格后正常报错）。本单修好后此例自动转绿。

## 单 05 · `TypeChecker` / `GradedTypeChecker` 符号错位（13 例，最高性价比）

**受影响**：`tests/test_level6_types.py` 9（`:438/455/468/482/505/1783/1791/1801/1811`）+ `tests/test_core_coverage.py` 4（`:287/294/301/308`）

- `:819` `class GradedTypeChecker` —— 注释「分级类型检查器（编译器集成用）」，`__init__(self, config)`，`check(self, module, inferencer=None)`，`:847-856` 按 `TypeCheckLevel` 逐级 gate

## 单 07 · `等待`(await) + 成员访问解析崩溃（6 例）

**受影响**：`tests/test_context_manager.py` 的 `test_async_with_basic`(:99)、`test_async_with_await`(:108)、`test_async_with_return`(:127)、`test_ast_async_with`(:163)、`test_codegen_async_with`(:214)、`test_async_with_file`(:242)

**报错**：`parser_core.ParseError: 无法识别的语法元素：'.'`

**隔离实验结论**（决定性）：

- `使用 异步 … 为 f:` + 体 `输出(f)`（无 await）→ OK，生成 `async with open("t") as f:`
- `等待 读取(f)`（await + 普通调用）→ OK
- `等待 f.读取()`（await + 成员访问）→ **FAIL**
- 无 with 的裸 `等待 f.读取()` → 同样 FAIL

**所以 `async with` 完全实现、`await` 也实现，崩溃点是 `等待` + 成员访问的组合，与 with 无关。**

**根因**：`src/parser_expr.py:340-355`

```python
if tok.type == KEYWORD and tok.value == '等待':
    next_tok = self._peek(1)
    if next_tok and next_tok.type == IDENTIFIER:
        peek2 = self._peek(2)
        if peek2 and peek2.type != TokenType.LPAREN:   # ← bug
            # 合并成复合标识符 等待f，只吃两个 token，.读取() 被丢下
```

该启发式只认「`等待 标识符(`」一种形状，漏了「`等待 标识符.成员`」。

**修法**：`peek2` 为 DOT（及其它后缀 token）时应走 `AwaitExpr(self._parse_expr())`，而非折叠为复合标识符。注意别破坏既有「等待价值」复合标识符用例，加单测回归。

**难度**：中低。建议与单 03 交同一人（都涉及 `f.读取()`，一个在解析层、一个在生成层）。

## 单 10 · `bootstrap_level5.light` 的 `结束` + DEDENT 配对（7 例）

**受影响**：`tests/test_self_host_bootstrap.py` 5（`:667/715/779/851/870`）+ `tests/test_e2e_full_coverage.py` 2（`:65/:82`）

**线索纠正**：只有 level5 挂。level3、level4、`bootstrap_v3.light` 都过（该文件 57 passed / 2 skipped）。

**报错**：`位置: 行 973, 列 1 / 原因: 无法识别的语法元素：'2'`

**核心发现**：那个 `'2'` **不是源码里的数字，是 DEDENT token 的 value（缩进宽度 2）**。tokenize dump：

```
line=972 col=1 type=DEDENT     value=4
line=972 col=5 type=IDENTIFIER value='结束'
line=973 col=1 type=DEDENT     value=2      ← 报错的就是它
line=973 col=3 type=IDENTIFIER value='结束'
```

对应源码 `bootstrap/bootstrap_level5.light:971-974`：

```
      返回 列表创建(out, try_end 加 1)
    结束          ← DEDENT(4) + 结束
  结束            ← DEDENT(2) + 结束，parser 在这里死
```

**根因**：`结束` 被词法器当 IDENTIFIER（非 KEYWORD），而 level5 是「缩进 + 显式 `结束`」双轨块结构。连续两个递减缩进的 `结束` 时，parser 消掉了 `结束` 却没消掉配对的 DEDENT，第二个 DEDENT 落到语句起始位置报错。

**辅证**：全文件「以 `：` 结尾的块开启行 = 427」，「单独成行的 `结束` = 392」，差 35 —— 两种闭合风格混用，parser 只按一种规则平衡。

**两步走**：

1. 先修 `src/parser_stmt.py:561` 的报错文案 —— INDENT/DEDENT token 必须打印类型而不是 `value`，否则后来人一样被 `'2'` 带偏
2. 真修在 `src/parser_core.py` 的 `结束` + DEDENT 配对逻辑

**难度**：中高，自成闭环（只碰 parser + 一个输入文件），适合独立分发。
