### AI 辅助编程降本长期项（L1-L5，3-6 个月）

> 来源：R127/R129 对 AI 写光明代码 retry 成本的实测分析。
> R129 任务计划见 [R129_AI辅助编程降本_M1-M5任务计划.md](R129_AI辅助编程降本_M1-M5任务计划.md)。
> 以下五项是编译器/架构级改造，R129 不动，按版本排期推进。

| 编号 | 目标 | 当前基线 | 目标 | 说明 |
|------|------|----------|------|------|
| **L1** | 原生腿（native/llvm-typed）模块覆盖率 | **可编 71/81 = 87.65%**（2026-10-09 实测，commit `c0e26e753`）<br>可跑率见 `tools/ci/native_run_readiness.py` | 60%（**数字判据已达成**） | 按 R10-10 阻断分类逐模块补；解锁 `light run --backend native` 一条命令跑通真实项目，不再回退 Python runtime。**剩余工作不是凑数字，而是把「可编」升级为「可跑且跑得对」** |
| **L2** | 编译器自举率（stdlib 光明模块占比） | 41.57%（37/89 文件，2026-09 旧数） | **93/123 = 75.61%**（bootstrap_rate.py 实测，R132-D 刷新基线）<br>同名 .py 影子数 76/123（只许降不许升）<br>关键路径自举率 24/24 = 100%（子指标，只升不降） | ✅ **已达成**（超过 60% 目标） | 47 个文件"有实现且有影子"需人工核验算法可见性（不设门禁）；行维度 decl/code = 2024/21759 = 9.30%（仅供参考、不许引用） |
| **L3** | 原生腿语义正确性（可编≠跑得对） | 旧目标"段参数传值改引用语义" | 已实测抓到 2 个真 bug：① **L-182 原生腿段参数遮蔽失效**（R128：`写JSON(路径,字典)` 段内参数被全局同名变量穿透，静默写错文件）；② **`isinstance()` 对原生标量恒返回假**（R123：影响 4 个纯光明模块共 34 处判型，根因在 `runtime_typed.c:5133-5145`） | 🔴 **进行中**（R130-C native 线正在跑） | R131 起增设第二把尺子 `tools/ci/native_run_readiness.py`（可跑率+对拍覆盖率）。L1 数字已达标，但 L3 是"可编≠可跑≠跑得对"的真实缺口，修法在 `src/llvm/runtime_typed.c` 和 `codegen_typed.py` |
| **L3** | 原生腿语义正确性（可编≠跑得对） | 顶层容器参数**已是**引用语义（R132 实测双腿对拍：段内 `列表追加(表,1)` / `表.追加(2)` / `表[0]=7` / `字典设置(字典,"k",1)` 全部与 Python 腿一致） | **L-188 嵌套下标读-改-写回**（R132-B 已修）/ **L-189 列表别名赋值深拷贝**（R132-B 裁定不修，登记跨腿分叉）/ **L-190 带参 `.弹出(i)`**（R132-B 已修）/ **L-192 A 线翻面让 stub 顶掉 `.py`**（R132-D 已修：`集合操作.light` 回调函数真实现 + `集合.light` 裸 `追加` 修复） | 🔴 **进行中**（R132-B 修 2 留 1；R132-D 修 A 线翻面回归） | **原文「段参数传值是传值（跨段变异不生效）」在 R132 起草前实测已不成立**——顶层参数语义正确，不需要改整体调用约定；真残余是上述三条精确缺陷，其中 L-189 需引用计数/写时复制架构级改造，另立轮次 |
| **L4** | light-translator 模型 few-shot 语料扩充 | 881 条 Python↔光明对照（v3.2 风格） | 加入 lightharness 300 个工程体 .light 文件 | 让 7B 小模型翻译时见过真实工程体写法（`尝试/捕获/读取文件/序列化JSON`），而不是只见过教学体 |
| **L5** | SemanticAnalyzer 统一（known_issues G1） | 各后端语义分析分散 | 统一语义分析器 | 解锁 `light ai check` 做真正的类型级诊断，而不只是后端兼容检测；排期见 known_issues G1 |

> **L1 口径说明（2026-10-09 R131 核实，勿再引用旧数）**
>
> - 旧基线「18%（16/89）」是 **2026-09-05 R10-11c 批次**的值（见 `docs/known_issues.md` R10-11c 条目），早已被后续 R11A/B/C、R12A/B/C、R128、R129、R130 等批次大幅推进，本表此前未跟随更新。
> - **权威度量 = `tools/ci/llvm_stdlib_readiness.py`**（多模块 `compile_light_typed` 口径）：分母 **81** = `stdlib/` 下带「纯光明实现」魔数的 `.light`（全量 122 个 `.light` 中 81 带魔数、41 无魔数），与 M23 判据原文「`stdlib` 纯光明模块的原生可编译比例 ≥60%」**同口径**。
> - 分母为何从 89 变 81：89 是 2026-09 时点的 stdlib `.light` 全量数（含空壳/影子），现行口径只统计「声明了纯光明实现」的模块，与判据原文一致。
> - ⚠️ **可编 ≠ 可跑 ≠ 跑得对**：上表分母只保证「能编出 IR」。实测 `light run --backend native` 能跑通中等复杂度样例，但同时抓到真缺陷（L-186 `列表排序` 不写回、L-187 异常栈追踪串台）。故 R131 起增设第二把尺子 **`tools/ci/native_run_readiness.py`**（可跑率 + 对拍覆盖率），**判 L1 是否真完成要看这两把尺子，不能只看可编率**。

> **M2 lambda 状态修正（2026-10-10 复核）**
>
> R129 计划书里 M2（lambda 语法糖）原列"待做"，实际 **G2 已由 R129-C 修复**（known_issues.md 已登记"G2 已由 R129-C 修复，保留该行存证"）。AI 指南第六章错误 #13 的"lambda 不支持"描述需在 R132 后同步更新。
>
> **M3 with 状态半支持**：原生腿 capability matrix 显示 `WithStmt | 使用 … 为 X：` 三层齐备、实测 11766 字符（supported）；但 known_issues §9.3 仍说 `runtime_typed.c` 没有上下文管理协议所需 dv 函数（无 `__进入__`/`__退出__` 对应物）。即 codegen 分派已通、runtime 协议未接，落地仍需扩 runtime。
