## 坑 01：POSIX 原生原语缺链接库 → 整条原生腿 `链接失败`

**影响范围**：`src/llvm/runtime_typed.c` 新增任何依赖系统库（pthread / dl / 其它）的原语时。
**首次暴露**：R151-D1 线程原语（`dv_thread_spawn` / `dv_fs_watch_start` / 目录监控）上 0.82 全量门。

### 症状
0.82 全量门出现**几百条**原生腿红，报错形如：

```
RuntimeError: 链接失败:
ld.lld: error: undefined symbol: pthread_create
>>> referenced by runtime_typed.c
>>>               .../产物_runtime.o:(dv_thread_spawn)
>>>               .../产物_runtime.o:(dv_fs_watch_start)
clang: error: linker command failed with exit code 1
```

### 根因
在 `runtime_typed.c` 里加了 POSIX 线程原语，走了 `pthread_create` / `pthread_join`，
但 `src/llvm/compiler.py` 的 `get_link_libs()` 的 POSIX 分支只返回 `['-lm']`，
**FreeBSD 的 `ld.lld` 不会自动链 libpthread**（Linux 多数发行版也需显式 `-pthread`）。
链接器在 `runtime_typed.c` 的目标文件里找到 `pthread_create` 的引用却找不到定义 → 整条原生腿链接失败。

### 隐蔽性（最坑的一点）
这条错误**极易被编译错误掩盖**。R151 同批还有一个 `static` 函数 `dv_mkdir_p`
「先调用后定义」导致的 `conflicting types` 编译错误，使得原生腿先报「运行时库编译失败」；
编译错误修掉之后，才轮到链接错误浮出水面——门红从「编译失败」变成「链接失败」，
乍看像修复引入新问题，其实是**同一个批次里藏着的第二个独立 bug**。

### 修复
1. `get_link_libs()` 的 POSIX 分支改为 `['-lm', '-pthread']`。
   `-pthread` 在 Linux / BSD / macOS 均安全（macOS/libc 已含 pthread，该标志为 no-op）。
2. `src/package_manager.py` 里**另抄的一份硬编码 `-lm` 链接命令**也改回调用 `get_link_libs()`。
   该文件原本自己 `link_args.append('-lm')`，绕过了唯一真相源——这正是
   `get_link_libs()` docstring 警告的「第二份拷贝会在另一个平台炸」陷阱。

### 规避守则（动原生后端前必读）
1. **加 `#include` ≠ 能链接**。头文件只解决「声明」，链接还需「库」。
   任何依赖系统库的原语（线程、动态加载、加密……）必须同步在 `get_link_libs()` 加对应链接标志。
2. **链接库参数的唯一真相源是 `get_link_libs()`**。全仓（生产 3 处链接点 +
   测试侧 `tests/llvm运行时.py` / `tests/unit/test_link_libs_guard.py`）都转调它，
   **绝不在别处硬编码 `-lm` / `-lpthread`**。改链接库只改这一处。
3. 改完 `runtime_typed.c` 后**先本机 `clang -c` 复编**确认 0 error，再上 0.82 门。
   若门红从「编译失败」转为「链接失败」，第一反应查 `ld.lld: error: undefined symbol: xxx`——
   缺的就是那个 `xxx` 对应的链接库。
4. 一次只动一条线（`src/` 是瓶颈）；`runtime_typed.c` 是 C 文件，编辑务必保留 CRLF
   （用 `open(p, encoding='utf-8', newline='')` 字节级改写，Edit 工具在 CRLF 上容易失手）。

## 坑 03：判空不判「相」—— 无相的尺子量器相，尺子说不空

**影响范围**：任何写 `是空(x)` / `长(x)==0` / `x == 空` / `字典包含键` 的地方。
**首次暴露**：R152 B1（`test_展开用户目录` 红）、R153（`文件系统.light:367`）。
**复发次数**：≥ 8 个轮次（R42 / R55 / R59 / R27 / tmux / 客户端 / 终端 / R152 / R153）。

### 症状
HOME 兜底被跳过、创建临时目录返回**裸相对名**、软删除后对象被当成不存在、
或反过来把空容器误判为 null。症状离根因通常很远，报错点完全不相干。

### 根因
中文「空」一字**双相**：**无相**（`空`，什么都没有）与**器相**（`""`/`[]`/`{}`，有器无物）。
`环境变量()` 缺 key 返 `""`（器相），而 `是空` 当时只认无相 ——
**拿无相的尺子量器相，尺子说「不空」**，兜底逻辑被跳过。
另一条隐藏路径是**置空 ≠ 删除**：`设 字典[键] 为 空` 把值（色）转空，键（器）未灭，
`字典包含键` 仍为真 —— 误把「色已空」当成「器已灭」。

> **R154 更新**：`环境变量()` 缺 key 的返回值已由 `""` 改为 **null**（L-213 已修，
> 见坑 04）。此处“缺 key 返 `""`”是 R152/R153 时点的历史成因，**保留以说明当时为何中招**；
> 当前实际行为以 `docs/空值语义规范.md` §9 为准。

### 隐蔽性（最坑的一点）
1. ~~**同名双轨**：`从 类型工具 导入 是空` 会让 `是空([])` 从假变真，**零提示**（L-214）。~~
   ⇒ **已修（R154-B）**：宽口径函数已改名 `皆空`，旧名 `从 类型工具 导入 是空` 现为**响亮
   ImportError**。仍请按守则 2 执行（不要写那行 import）。
2. 仓里曾同时存在**四套互相矛盾的文档口径**，查文档得到什么答案全看运气。
3. 两腿布尔 repr 不同，对拍测试还会制造假红，把真问题盖住。

### 修复
R153 已把 `是空` 统一定义为 **`null 或 ""`**（两腿 16 处定义点），
B1 绕开回归统一语义，`文件系统.light:367` 回落 `当前目录()` 返回绝对路径。

### 规避守则（判空前必读）
1. **判空先分相**：问「存在吗」用严格 null；问「有内容吗」用 `长(x)==0`；
   问「键在吗」用 `字典包含键`。**不要**靠值判键的存在。
2. **不要 `从 类型工具 导入 是空`**（该导出已于 R154-B 改名 `皆空`，旧名会响亮报错；
   宽口径要用就显式 `从 类型工具 导入 皆空`，语义与地板内置不同名不同口径）。
3. **判空一律看 `docs/空值语义规范.md`** —— 那是唯一权威，含速查卡与决策树。
4. 写 `.light` 时对下游返回值先确认它**缺值时返哪一相**（null 还是 `""`），
   R152 的病根就是没确认。
5. 置空软删除后，取值处必须补判空；要真删键用 `字典弹出` / `字典删除`。

## 坑 04：缺失 ≠ 空值 —— 拿空串当“没有”的哨兵，三态必然塌成两态

**影响范围**：任何“取不到 / 不存在”与“存在但为空”必须区分的接口
（环境变量、字典取值、配置读取、可选字段）。
**首次暴露**：R154-A（L-213，`环境变量()` 缺 key 两腿分歧 + `default` 被静默丢弃）。
**复发风险**：高 —— 这是“用返回值表示缺失”这一类设计的通病，不是单点 bug。

### 症状
1. **默认值静默失效**：`环境变量("缺的key", "默认")` 返回 `""` 而非 `"默认"`，
   且**没有任何报错**。`stdlib/os.light:getenv(名, 默认)` 因此永远走不到默认分支。
2. **两腿分歧**：src 腿（真 Python）返 `None`，原生腿返 `""`，同一段代码换个后端行为就变。
3. **连带损伤隐蔽**：`如果 值 == 空: 返回 默认` 写法在缺 key 时**看起来对**
   （因为 `""` 也满足某些判空），只有拿到非空默认值时才暴露。

### 根因
**用返回值的内容表达“缺失”**。`""` 是**合法**的环境变量值（`export X=` 之后
`X` 存在且为空），与“`X` 根本不存在”是两种状态。旧实现两条路都返 `dv_strdup("")`，
信息在 C 侧就已经丢失 —— codegen 再怎么改也补不回来，因为**根本没拿到区分依据**。

```c
/* 旧：两种状态压成一个值 */
char* dv_getenv(const char* name) {
    if (!name) return dv_strdup("");
    const char* val = getenv(name);
    return dv_strdup(val ? val : "");   /* 缺 key 与空值都成 "" */
}

/* 新：缺失用 NULL 指针单独表达 */
char* dv_getenv(const char* name) {
    if (!name) return NULL;
    const char* val = getenv(name);
    return val ? dv_strdup(val) : NULL;
}
```

### 隐蔽性（最坑的一点）
1. **最常被误改的那一行**：`值 == 空` 看着“不优雅”，很容易被"顺手优化"成 `是空(值)`。
   但 `是空` 的口径是 **null 或空串** —— 它会把“存在但值为空串”也吞进缺失分支，
   **制造新分叉**（实测：src `<empty>` vs 原生 `DEF2`）。R154-A 用探针证伪了这条候选修法，
   `stdlib/os.light` 与 `节点网络.light:取环境` 两处同形代码**都保持 `== 空` 不动**。
2. **arity 丢弃无提示**：`codegen` 只取了 `args[0]`，第 2 个实参从未到达 C 侧。
   多传一个参数、什么都没发生、也不报错 —— 只能靠探针发现。

### 修复
R154-A：C 侧缺 key 返 **NULL**；codegen 侧据 `icmp ne ptr out, null` 分流三态 ——
命中 → 变量值；缺失且有默认值 → 实参默认值；缺失且无默认值 → `dv_null`。
见 `_R154_A线交付报告.md`、缺陷账 §十六 L-213。

### 规避守则（写“取值”类接口前必读）
1. **缺失与空值必须用两种载体表达**。C/Rust 用指针/`Option`；Python 用返回值 + 哨兵对象；
   **绝不用空串/空容器/0 兼任“没有”**。
2. **判“取不到”用 `== 空`（严格 null），不要用 `是空`**（后者含空串，会吞掉合法空值）。
3. **多参内置的每个实参都要有到达路径**——加参数时先确认 codegen 侧真把它传下去了，
   再写测试（`args[1]` 静默丢弃就是这么活了很久的）。
4. 新增/修改“取值”类原语，测试必须覆盖**三态**：命中 / 缺失有默认 / 缺失无默认，
   且**两腿逐行对拍**（`tests/unit/test_R154_L213_环境变量口径.py` 是模板）。

## 坑 05：分派判定的 fail-open 兜底会造出误导性报错

**影响范围**：任何“先判定再分派”的开关（如“有无模块级导入”决定走多模块还是单模块快速路径）；以及任何 `try/except` 后**静默返回默认值**的分派函数。
**首次暴露**：R157-A（L-079，`test_O0_行政区划代码_对拍与扩展` 0.12s 秒挂）。
**复发风险**：高 —— 这是“分派判定”这一类设计的通病，不止 `_module_has_imports` 一处。

### 症状
同一个用例**偶尔**（并发/负载下更易触发）在**编译刚开始就炸**，耗时只有正常路径的几十分之一（实测 0.15s vs 正常 11s），报错却指向一个**与真因无关**的语义错误——例如 `NotImplementedError: 未定义的段落：获取行政区划代码`，并提示“本模块已定义：主”。

### 根因
编译决策分两步：先判“源码含不含模块级导入”，再据此选路径。

```python
def _module_has_imports(source):          # 旧实现（fail-open）
    try:
        v3_module = LightParser().parse(source)
        module = AstAdapter().convert_module(v3_module)
        return bool(getattr(module, 'imports', None) or [])
    except Exception:
        return False                       # ← 静默降级成“没有导入”
```

`compile_light_typed` 据此分派：

```python
if _module_has_imports(source):
    return compile_light_project(...)      # 多模块：stdlib 导出名全部注册
# 单模块快速路径：stdlib 导出名全部未注册
```

一旦 `parse`/`convert` 偶发抛异常，`except: return False` 就把“源码明明有导入”吞成“无导入”→ 走单模块路径 → 任何 stdlib 调用都被 codegen 的 `_reject_unknown_call` 以“未定义的段落”拒绝。**报错发生在编译决策阶段，而不是真正缺失实现。**

### 隐蔽性（最坑的一点）
1. **报错指向错误的方向**。它看起来像“光明原生腿不支持 stdlib”，引导人去查 codegen 或 `.light` 实现，实际问题是“分派判定被静默降级”——查错方向会浪费整轮。
2. **偶发**。解析器状态/并发时序异常不是每次触发，同一轮里多数跑绿、偶发秒挂，极易被归因成“flaky 测试”或“编译缓存竞争”，从而被 `retry` 装饰掩盖。
3. **默认值看着“合理”**。`return False` 单独看没错——它想表达“解析不了就当没导入”。问题在于**这个默认值指向一条错误的代码路径**，而错误路径的报错比原始异常更“像回事”。

### 修复
R157-A：`_module_has_imports` 改为 **fail-closed** + 文本级兜底 `_text_has_imports`：

```python
    except Exception:
        if _text_has_imports(source):     # 源码字面含“导入”
            raise                          # fail-closed：宁可真报错，不许静默走错路径
        return False                       # 文本兜底也未命中：真没有导入，走快速路径合法
```

`_text_has_imports` 逐行扫描，忽略以 `#` 开头的注释，命中独立 token `导入` 或 `从 X 导入 Y` 结构即返回真。它只在 `except` 分支被调用，正常路径零开销。

### 规避守则（写“分派判定”类函数前必读）
1. **分派判定的 `except` 默认值必须指向“与真值一致”的路径**。若默认值会让下游走错路（这里是从多模块退到单模块），就不能静默——要抛原始异常，或给出可判别的失败信号。
2. **报错文本要能区分“真·能力缺失”与“判定失败”**。见坑 06。
3. **反跑有牙**：改分派逻辑时，用 monkeypatch 强制分派函数抛异常，验证是 fail-closed 报原始异常、还是 fail-open 走错路径（R157 反跑实测：前者 0.007s 抛原始异常，后者 0.147s 秒挂 NotImplementedError）。
4. **偶发 flaky 先查“决策分派”再查“执行”**：秒挂（耗时异常短）+ 报错看似能力缺失，多半是分派判定被静默降级，不是执行路径真不支持。

## 坑 06：报错文本“原生后端暂不支持”在分派失败场景是假提示

**影响范围**：`src/llvm/codegen_typed.py::_reject_unknown_call` 等“能力缺失”类报错。
**首次暴露**：R157-A 定位 L-079 秒挂时确认（同一报错文本，两条完全不同的成因）。
**状态**：**登记待评估（未修）**——区分两类成因需要改动报错文本，属语义诊断，交由后续轮评估。

### 症状
用户看到 `NotImplementedError: 未定义的段落：获取行政区划代码 …… 原生后端暂不支持，请用转译后端（python -m cli.light_unified run）`。这条提示的潜台词是“光明原生腿不支持这个调用”，而实际**原生腿明明支持**（同一源码在正常路径 6.5s 编译成功、运行 rc=0）。

### 根因
`_reject_unknown_call` 的报错文案是**单一日径**：凡遇到未注册的段落调用，一律提示“原生后端暂不支持”。但“未注册的段落调用”至少有两类截然不同的成因：

| 成因 | 真实含义 | 应给出的提示 |
|---|---|---|
| A. 真·语言/能力不支持 | codegen 真的没实现该调用（拼错名、未实现内置） | 保留“原生后端暂不支持” |
| B. 编译路径分派失败 | 模块级导入被静默降级，stdlib 导出名根本没注册（坑 05） | 提示“疑似编译路径分派失败，查模块导入” |

两类成因的**报错文本一字不差**，用户和开发者都无法从报错本身区分，只能靠额外排查。

### 隐蔽性（最坑的一点）
1. **假提示比没提示更坑**。它会主动把排查方向引向“原生腿不支持”——而真相是“编译决策出了错”。排查者按提示去查 `.light` 实现或 codegen，查完发现两者都没问题，再回头找，一轮时间就没了。
2. **文本里的“转译后端”建议也失效**。用户照提示改用 `python -m cli.light_unified run` 想绕开，但成因 B 下换后端**治标不治本**——问题在编译分派，不在原生腿能力。

### 修复
**本轮未修**（属语义诊断，需评估改动风险后由后续轮落地）。候选方向：
1. `_reject_unknown_call` 增加成因分类参数（由调用方传入“是否可能属分派失败”），成因 B 时改写提示为“疑似编译路径分派失败：请检查模块导入是否被静默降级”。
2. 或由 `compile_light_project` 侧在 catch 到“未定义段落”时二次判读：若该段落名能在 stdlib 模块的导出清单里找到，则改写提示为成因 B。

### 规避守则（写“能力缺失”类报错前必读）
1. **报错文本要能自证成因**。凡是“看似不支持 X”的报错，先问自己：X 有没有可能其实支持、只是没被正确加载/分派？能，就必须让报错带上区分信息。
2. **提示里的“绕行方案”必须是真绕行**。成因未分清就建议“换后端”，等于把排查责任转嫁给用户。
3. **登记而非静默改**：涉及报错文本口径的改动，先登记成因分类方案再实施，避免把一种成因的提示改成另一种后造成新的误导。
