# 光明语言错误码规范（v1 · T-0316）

> 本文是 `src/diagnostics/` 的规范性说明：**码段划分、字段语义、新增码流程、兼容承诺**。
> 码表的唯一实现是 `src/diagnostics/registry.py::RULES`；本文与之对拍，改码表必须同步改本文。
>
> 外部评审（DeepSeek，2026-11）把「报错质量」列为 AI 友好与人类友好的共同第一道门槛：
> AI 最怕模糊报错，而「**错误码 + 原因 + 候选修复**」三元组比任何语法糖都更能提升可诊断性。

## 1. 码段划分

错误码格式固定为 `L[1-5]\d{3}`（正则见 `registry.py::CODE_PATTERN`）：首位是码段号，后三位是段内序号，从 `001` 起顺排。

| 码段 | 含义 | 典型 stage | 本版条数 |
|------|------|-----------|----------|
| `L1xxx` | 词法 / 语法 | `词法` / `语法` | 7 |
| `L2xxx` | 类型 | `类型` | 3 |
| `L3xxx` | 运行时 | `运行时` | 4 |
| `L4xxx` | 模块 / 导入 | `模块` | 2 |
| `L5xxx` | 后端差异 | `代码生成` | 3 |
| **合计** | | | **19** |

`stage` 取值集合为 `词法 / 语法 / 类型 / 运行时 / 模块 / 代码生成`，与 `src/errors.py::ErrorEntry.stage` 的既有口径对齐（后两者是新增细分）。
`explain(message, stage=...)` 的 `stage` 参数是**过滤器**：给定后只在该阶段的规则里匹配，不给则按码表顺序全表匹配、取第一条命中。

## 2. 字段语义

`Diagnostic` 的字段集合与 `to_dict()` 的输出顺序**完全一致**（`model.py::DIAGNOSTIC_FIELDS`）：

| 顺序 | 字段 | 类型 | 默认值 | 语义 |
|------|------|------|--------|------|
| 1 | `code` | `str` | 必填 | 形如 `L2001`；必须是码表里的已发布码 |
| 2 | `severity` | `str` | `"error"` | 仅 `error` / `warning` / `info` 三值 |
| 3 | `stage` | `str` | `""` | 阶段，取值见 §1 |
| 4 | `line` | `int` | `0` | 行号；**0 = 位置未知** |
| 5 | `column` | `int` | `0` | 列号；**0 = 位置未知** |
| 6 | `message` | `str` | `""` | 编译器给出的**原始报错文本**，不改写 |
| 7 | `hint` | `str` | `""` | 该错误码对应的通用原因说明 |
| 8 | `fixes` | `list[str]` | `[]` | 人类可读修复建议，**≤ 3 条**（`MAX_FIXES = 3`） |
| 9 | `candidates` | `list[str]` | `[]` | 机器可读候选写法，可直接贴进源码或喂给 AI；条数不限 |
| 10 | `provisional` | `bool` | `False`（`Diagnostic`） | 是否「推断态」，见 §2.2 |
| 11 | `docs` | `str` | `""` | 规范文档路径；`explain()` 产出统一为 `docs/错误码规范.md` |

### 2.1 位置不许编造

`line == 0` 表示位置未知，序列化时**原样保留 0**，不换算成 1、不从报错文本里猜行号。
这与 `src/llvm/codegen_typed.py::_stmt_source_line` 的「不许伪造」纪律同源。
`ErrorEntry.format()` 在 `line == 0` 时本来就不打印「位置」行，所以兼容层无需特判。
真实坐标由调用方（T-0317 / T-0318）在拿到编译器异常对象后填入，不由 `explain()` 猜。

### 2.2 推断态 `provisional`

本卡只交付码表与框架，`explain()` 目前是**自由文本正则推断**，因此它产出的诊断一律
`provisional=True`（`Rule.provisional` 默认 `True`）。等编译器内部异常直接携带错误码后，
由接入方改填 `False`。消费者应把 `provisional=True` 理解为「这条码是推断出来的，坐标与归因待确认」。

### 2.3 `to_dict()` / `from_dict()`

- `to_dict()` 按上表顺序构造 dict，列表字段返回副本；`json.dumps(..., ensure_ascii=False)` 结果可直接 diff。
- `from_dict()` 识别同样的 11 个字段，**未知字段忽略**（前向兼容），缺失字段走默认值。
- 二者满足 `Diagnostic.from_dict(d.to_dict()) == d` 的往返相等。
- `Diagnostic.line/column` 必须是非负整数；`fixes` 超过 3 条、`severity` 非法都会在构造时抛 `ValueError`。

## 3. `explain()` 契约

```python
explain(message: str, stage: str | None = None) -> Diagnostic | None
```

1. 按码表顺序用 `re.search(rule.pattern, message)` 匹配；`stage` 给定时只匹配该阶段的规则。
2. 命中返回 `Diagnostic`，其中 `message` 是**原样传入的报错文本**，`line/column` 恒为 `0`，
   `provisional=True`，`fixes/candidates/hint/severity/docs` 来自命中的 `Rule`。
3. **未命中返回 `None`，绝不造兜底假码**。`message` 为空串或非 `str` 同样返回 `None`。
4. `get(code) -> Rule | None` 精确查询；`all_codes()` 返回全部码；
   `duplicate_codes(rules)` 用于检测同一码被两条规则占用。

示例（均为仓库里真实报错模板）：

| 真实报错（`source`） | 命中码 | fixes[0] |
|----------------------|--------|----------|
| `参数数量错误: 段落「加法」期望 2 个参数，实际传入 3 个`（`src/errors.py:636`） | `L2001` | 对照段落定义补齐或删掉多余实参 |
| `该函数来自『字符串处理』模块（不是未定义变量），请在文件顶部加一行：从 字符串处理 导入 子串位置`（`src/enhanced_errors.py:892`） | `L4001` | 按提示在文件顶部补 `从 <模块> 导入 <名字>` |
| `原生后端暂不支持语句类型「YieldStmt」…`（`src/llvm/codegen_typed.py:6841`） | `L5001` | 按报错里的回退指引改用转译后端 |
| `「空」是保留字（值类型），不可作标识符（变量名/下标名）。…`（`src/keywords.py:684`） | `L1006` | 把作变量名的保留字换成别的名字 |

## 4. 兼容层 `to_legacy_entry()`

`to_legacy_entry(diag) -> src.errors.ErrorEntry`，只搬运 5 个字段：

| Diagnostic | ErrorEntry |
|------------|------------|
| `stage` | `stage` |
| `message` | `message` |
| `line` / `column` | `line` / `column` |
| `fixes` | `fix_suggestions` |

- **不把 `code` 拼进 `message`**：错误码由 T-0318 的 JSON 输出承载；塞进文本会破坏「现有文本输出逐字不变」。
- 不传 `source_line` / `exception`，保持 `ErrorEntry` 默认值。
- 因此 `to_legacy_entry(diag).format()` 与用同样 5 个字段直接构造的 `ErrorEntry(...).format()` **逐字相等**。

## 5. 新增一条码的流程

1. **先找出处**：必须有 `docs/` 或 `src/` 里可复核的文档/代码依据；没有依据的问题不许进码表。
   「为凑够条数编造语言里不存在的问题」是本卡禁止行为。
2. **定码段**：按 §1 归类，取该段当前最大序号 +1；**不得复用已发布或已废弃的码**。
3. **写 `Rule`**：在 `RULES` 对应码段追加，填齐 `code/title/pattern/stage/hint/fixes/candidates`，
   并在定义处写 `# source:` 注释、填 `source` 字段（两者一致）。
   - `pattern` 要能命中真实报错文本，并给得出**反例**；避免过宽正则造成误命中。
   - `fixes` ≤ 3 条；`candidates` 给可直接使用的写法。
   - 若该问题在现有系统里是 warning / 合法语法 / 静默差异，`severity` 必须保持 `warning`，不许升级成 error。
4. **补测试**：在 `tests/test_diagnostics_registry.py::CASES` 增加一组 `(code, 正例, 反例)`，
   正例要命中该码、反例要全局不命中；`CASES` 与 `RULES` 的码集合由测试强制对拍。
5. **同步本文**：更新 §1.1 码表与条数统计。
6. **跑判据**：`python -m pytest -q tests/test_diagnostics_registry.py` 全绿。

## 6. 兼容承诺

1. **码一旦发布，永不复用、永不改变含义。** 某条问题被修掉或不再适用时，保留码并把规则标为废弃
   （当前实现尚无废弃字段，接入时以「保留码 + 不再命中」处理），不得把该码分配给别的问题。
2. **码 → (码段, 标题, 严重度, 修复建议) 的映射是稳定契约**：下游（CLI、LSP、AI 工具、文档）
   可以按码缓存修复建议。允许新增字段，不允许删除或重排 `Diagnostic.to_dict()` 的既有 11 个字段顺序。
3. **文本输出零变更**：在 T-0317 / T-0318 接入前，`src/errors.py::ErrorEntry.format()` 的输出
   逐字不变；`to_legacy_entry()` 是唯一的桥。
4. **severity 只降不升**：既有 warning 规则不得改成 error；确需提高严重度时，发新码并保留旧码语义。
5. **`explain()` 的 `None` 是稳定契约**：匹配不上就是匹配不上，不允许以后加「兜底码」把 `None` 变成假诊断。
6. **推断态显式**：`provisional=True` 会一直保留到编译器内部异常真正带码为止；下游不得把它当成精确归因。
