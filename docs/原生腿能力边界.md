## 0. 一句话

原生腿（LLVM）**只认它分派链里列出的节点**。链尾一律 `NotImplementedError`
带源码行号 + 转译后端指路；拼错名字的段落调用会列出本模块已定义候选。
**没有任何「编译成功、产物行为错误」的静默降级留在表达式层。**

网络层（B1-B4）同样遵循此原则：POSIX TLS 不支持时返回明确错误码，不静默失败。

| `PrintStatement` | `打印 …` |
| `TryStatement` / `ThrowStatement` | 异常 |
| `ExpressionStatement` | 表达式语句（含适配层 `<unknown:XXX>` 揭穿，见 §4） |
| `ImportStatement` | 单文件快路径不出现；**含导入时整源委托 `compile_light_project` 多模块编译**（B9 S1 2.3，见 §9），不再是 no-op |
| `AsyncScope` | `异步 作用域` |
| `YieldStatement` | `生成 X`（含 `生成 的段` 只报错不落静默；**R10-11b 新增**） |
| `ScopeDeclaration` | `全局 X。`（**R114-S1 新增**）：把 X 挂到模块级全局槽 `@__var_X`，语义等价于转译腿的 Python `global`；`外层` / 模块级 `全局` 均明确拒绝。全局**容器**的原地修改（`字典设置` 等）自 R114-S2 起同样生效 |
| `MatchStatement` | `匹配 X：情况 …：`（**R115-A 新增**）：只支持**字面量模式**（整数/字符串/布尔/空）与 `情况 _：` 通配；按源码顺序逐条 `dv_eq` 比较，命中即跳出，全不中且无通配则 no-op。`情况 乙：`（变量绑定）、守卫 `情况 _ 如果 …`、序列/结构/类型模式一律明确拒绝，绝不静默当成默认分支 |
| `DestructuringAssignment` | `设 [甲, 乙] 为 …` / `设 甲, 乙 为 …`（**R115-A 新增**）：按位置解包（`dv_len` + `dv_foreach_get`）；目标先置 null 再赋值，**个数不匹配抛运行时异常**（与转译腿 Python 解包的 ValueError 同口径），绝不静默少赋 |
| `AssertStmt` | `断言 <条件>。` / `断言 <条件>, <消息>。`（**R116-A 新增**）：条件为真 → no-op（不生成 IR）；条件为假 → 抛 AssertionError（复用 `dv_create_exception_with_cause`）。消息只支持字符串字面量，其它情况回落空串；不接受静默降级成表达式语句 |
| `WithStatement` | `使用 X 为 Y：`（`**R116-A 新增**`，本轮放行 `runtime_typed.c`）：进入调 `X.__enter__()` 并把返回值绑给 `Y`，执行体，离开调 `X.__exit__()`；**体抛异常也走 `__exit__`** 再重抛（与转译腿 Python `with` 对齐）。`__enter__`/`__exit__` 经既有通用方法调用 `dv_call_method` 发起，无需新增 runtime 函数。已知限制：原生腿无类型推断，无法编译期确认 `X` 真有这两个方法——缺方法时由运行期 `dv_call_method` 查找失败暴露，而非编译期 `_reject_unsupported_stmt` |
| `RunAsyncStmt` | `异步 运行 X()。`（`**R119-A 新增**`，转正 R116-A 砍线）：顶层启动异步段——求值 `X()`（一个 `异步 段落`）得到协程句柄（LightValue type=100, ptr_val=coro*），交由 runtime 调度器 `dv_coro_run_to_completion` 阻塞驱动至完成；与转译腿 `asyncio.run(X())` 同语义。runtime 已有完整协程状态机 + 调度器（dv_coro_create / dv_coro_resume / dv_scheduler_run），**无需新建异步运行时**。只能在模块层 / 同步段调用；协程内调用会显式拒绝（与 Python `asyncio.run` 不能写在 async 函数内同口径） |

模块层（`generate`，`:714`）额外支持：类定义（`_collect_class`，`:2501`）、
接口定义、段落定义、导出别名。

### 1.2 已支持运算符（`_gen_typed_binary_op`，`:959` 起）

## 4. 适配层伪装揭穿

`AstAdapter`（`src/compiler.py`）对它不认识的 v3 节点包成
`Identifier("<unknown:XXX>")`。原生腿在**语句位**（`_gen_statement`
`ExpressionStatement` 分支）与**表达式位**（`_gen_expression` `Identifier` 分支）
都用 `_ADAPTER_UNKNOWN_PREFIX`（`:2680`）拆开，报出原 v3 类型名——`<unknown:DictLiteral>`
不会报成「未定义变量」。

## 7. B3 事件循环（runtime_typed.c:4858-5074）

### 7.1 能力面

`dv_scheduler_run_event_loop`（:5004）是原生腿的真事件循环，实现：

1. **IO 等待队列**（:4858-4920）：协程挂起等待 fd 读写时入队，poller 返回就绪后唤醒。
2. **定时器最小堆**（:4922-4970）：`dv_coro_sleep` 注册的定时器按到期时间排序。
3. **事件循环主体**（:4975-5074）：循环 `dv_poller_wait` → 检查定时器 → 唤醒就绪协程 → 检查退出条件。

### 7.2 协程模型

- **最大协程数**: 4096（`DV_MAX_COROUTINES`，:4047），不是 256。
- **实现方式**: 单线程 Duff's device，codegen 发 IR。
  - 入口 switch：`codegen_typed.py:3459-3475`
  - 挂起点：`codegen_typed.py:3634-3651`
  - **注意**: Duff's device 在 codegen 层，不在 runtime 层。
- **线程模型**: 单线程，无 pthread。
- **`await_io`**: 协程挂起等待 IO 就绪（`dv_coro_await_io`）。
- **`sleep`**: 协程挂起指定毫秒后恢复（`dv_coro_sleep`）。

### 7.3 内置函数入口

`运行事件循环`/`run_event_loop`（:1844）、`睡眠`/`sleep`（:1848）、`await_io`（:1852）。

### 7.4 真跑判据

`tests/test_llvm_async.py` 以真编译 + 真运行验证协程调度与事件循环。
`tests/test_llvm_net.py` 验证 socket + 事件循环联合工作。

## 8. B2-4 TLS（runtime_typed.c:5076-5779）

### 8.1 平台裁决（B7 首日裁决，2026-08-24）

**取「显式降级」方案**：

- **Windows**: Schannel 后端，真实现（:5111-5745）。
- **POSIX**: **不支持 TLS**。`dv_tls_*` 返回 `DV_TLS_ERROR` (-1) 并设置 `g_tls_error`
  错误文本为「本平台未实现原生 TLS：当前只有 Windows Schannel 后端（POSIX 待补 mbedTLS）」。
  `dv_tls_backend()` 返回 `"none"`。

**不静默失败**——调用方会拿到明确的错误码和可读错误文本。

**2026-08-24 Linux 实机复核（`docs/POSIX验证报告_Linux.md` §C.2、§4 #L2）**：此前这一节只有
读码结论，现已在 Ubuntu 22.04.5 + clang-18 上实测——`dv_tls_backend()` 真返回 `none`、
`dv_tls_wrap` 真返回 `NULL`，且 `dv_tls_last_error()` 在 POSIX 上**确实可用**
（定义在 `runtime_typed.c:5107`，位于 `#ifdef _WIN32` 之前，无条件存在），
返回上面那句错误文本。所以「TLS 可用」这句话在任何文档/清单里都只对 **Windows** 成立。

改选引 OpenSSL/mbedTLS 必须先拿用户裁决（依赖红线）。

### 8.3 POSIX 降级桩（:5747-5778）

`dv_tls_unsupported()`（:5747）写入 `g_tls_error` 错误文本，所有 POSIX TLS 函数桩

## 9. B9 多模块导入与名字修饰（2026-08-24）

### 9.1 入口与分派

`compile_light_typed` 检测到**模块级导入**（`_module_has_imports`，`compiler.py:459`）
时，不再走单文件快路径，而是委托 `compile_light_project`（`compiler.py:987`）：
`ModuleResolver` 递归收集依赖 → `compile_modules_typed`（`compiler.py:835`）用**一个**
`TypedLLVMCodeGen` 实例编译所有模块、合并成单份 IR → clang 编译链接。判据见
`tests/test_native_import.py`（单层 / 两层传递 / `从 X 导入 Y` 别名，均真编译真跑）。

`run`/`compile --backend native` 走同一条生产路径（`compile_light_typed`），
故命令行触发的多模块编译与库调用等价。`native` 是 `llvm-typed` 的一等别名（B9 S1 2.2）。

### 9.2 掩码拒绝：同名 `.py` 影子不许静默降级

原生腿不加载 Python。`compile_light_project` 收集依赖时（`compiler.py:1028`的
`collect_modules`）遇下列情形抛 `NativeImportError`（`compiler.py:42`），给出可读
错误（点出模块名 + 缺什么），**绝不留一个「跑起来就崩」的产物**：

- 依赖解析到 `.py`（无 `.light` 实现）→「原生腿不加载 .py」。
- `.light` 与同名 `.py` 都在，但 `.light` 是 decl 0 空壳（`_is_decl0_shell`，
  `compiler.py:48`，无段落无类的纯导出清单）→「decl 0 空壳，实现在同名 .py」。

### 9.3 名字修饰规则（跨模块段落符号）

| 符号 | 原生 LLVM 名 | 出处 |
|---|---|---|
| 寄存器 / 局部变量 | 中文名 → ASCII `v{counter}` | `_safe_var_name`（`llvm/core.py:103`，`:`110 是调用点） |
| 本模块段函数 | 裸名收集，函数 `@_seg_f{N}`（`f{N}` 按收集顺序） | `_collect_segment`（`codegen_typed.py:2484`）、`_safe_func_name`（`core.py:116`） |
| 跨模块可见别名 | `{模块名}_{段落名}` → `@_seg_f{M}` | `_gen_exported_aliases`（`codegen_typed.py:787`） |
| 导入侧调用目标 | `{模块名}_{Y}`（`从 模块 导入 Y` 取 Y 所在模块名） | `_process_imports`（`:767`）、`_gen_imported_segment_call`（`:1170`） |

要点：
1. **源头商责**：每个模块为导出的段（无显式导出则全部）注册 `{模块名}_{段落名}`
   前缀别名（`_gen_exported_aliases:808`），跨模块撞车身由前缀消解。
2. **调用侧做同名前缀解析**：`从 模块 导入 Y` 记入 `_imports[Y]=(模块名,Y)`，调用时
   按 `{模块名}_{Y}` 取目标（`_gen_imported_segment_call:1173`）。
3. **单 codegen 全局收集的已知限制**：`self._segments` 以**裸段落名**为键
   （`_collect_segment:2488`），两个模块若定义**同名段落**，后收集的模块覆盖先者
   （后写胜）。`{模块名}_{段落名}` 前缀能区分「去重后仍需被 import 的名字」，但
   同名裸段的覆盖是 M23 级已知限制，导入方不应依赖「同一裸名在不同源实现不同」。
4. 中文模块名/段落名经 `_safe_func_name` 统一映射为 ASCII `f{counter}`，保证
   LLVM 标识符合法；同源非 ASCII 名不会撞 LLVM 保留字。

## 10. 模块解析边界（2026-08-29 补登，v7.0.0 实测）

> 本节补登两条**实测发现**的边界。§9.2 的 `NativeImportError` 只覆盖了
> 「依赖解析到 `.py`」这一种情形；下面两条会走到 `ModuleResolver` 的通用
> `ModuleNotFoundError`，报错信息与真实原因不符，排查时容易误判。

### 10.1 不区分「外部 Python 生态模块」与「light 模块」

`导入 asyncio` / `导入 codecs` 这类**引用 Python 标准库或第三方包**的语句，
原生腿一律当作 light 模块去找文件，找不到就抛
`模块未找到`，并逐级向上搜索到盘符根目录。

最小复现（`_speedcheck/nativetest/t_asyncio.light`）：

```light
导入 asyncio

段落 主:
  打印 "ok"

主()
```

```
$ light compile t_asyncio.light -o t_asyncio.exe --backend native
原生（native）编译错误: 模块未找到: 'asyncio'
搜索路径:
  - G:\...\nativetest\asyncio.light
  - G:\...\nativetest\asyncio.py
  - G:\...\_speedcheck\asyncio.light
  ...
  - G:\asyncio.light          ← 搜到盘符根目录
  - G:\asyncio.py
  - G:\...\light-merge\stdlib\asyncio.light
  - G:\...\light-merge\contrib\asyncio.light
```

**三条问题叠加**：

1. 没识别出 `asyncio` 是 Python 生态模块，错误信息不点出真实原因；
2. 搜索路径逐级上溯到盘符根（`G:\`），输出 16 条几乎无用的候选；
3. 未触发 §9.2 的 `NativeImportError`（那个只处理「找到了 `.py`」的情形），
   因此没有「原生腿不加载 .py」这类可读提示。

**影响面**：任何依赖 Python 生态的项目，原生腿当前**必然失败**。
实测 `lightharness/src/总入口.light` 即因此编译不过（`客户端.light:17` 有 `导入 asyncio`）。

**对照**：纯 light、无外部导入的模块可正常编译
（`_speedcheck/nativetest/t_clean.light` → rc=0）。

### 10.2 项目 `stdlib/` 默认不在搜索路径内

`src/module_resolver.py:263` `find_module` 的搜索顺序是
`from_dir` → `self.search_paths` → 环境变量 `LIGHT_PATH`。
项目自身的 `stdlib/` **不在**默认的 `search_paths` 里。

实测（lightharness）：

```
$ light compile src/总入口.light -o 总入口.exe --backend native
原生（native）编译错误: 模块未找到: 'SSE'
搜索路径:
  - lightharness\src\SSE.light
  - lightharness\src\SSE.py
```

而 `SSE.light` 实际位于 `lightharness/stdlib/`。

**绕过方式**：显式设置 `LIGHT_PATH`（`os.pathsep` 分隔多路径）：

```bash
LIGHT_PATH="lightharness/stdlib;light-merge/stdlib" \
  light compile src/总入口.light -o 总入口.exe --backend native
```

注意：**这只是绕过 10.2，随后仍会撞上 10.1**（下一关报 `模块未找到: 'codecs'`）。

### 10.3 待办

| 优先级 | 事项 |

### 11.2 与 CPython 的已知差异（**不是 bug，是边界；不许静默降级**）

| 项 | 原生腿行为 | CPython | 登记理由 |
|---|---|---|---|
| `callable(段名/类/lambda)` | **恒为假** | 真 | LightValue 无一等函数值类型（§1.4 桶③）。唯一为真的形态是「对象所属类注册了中文 dunder `__调用__`」。C 线翻魔数时若把 `断言可调用` 写成 `如果 callable(值) == 假：断言失败(…)`，原生腿会**恒失败**，须保持降级实现 |
| `是函数(值)` | 仅当 value 为**一等函数值**（LV_TYPE_FUNCTION，即段名封成的函数值）为真；可调用对象（含注册 `__调用__` 的实例）**为假** | 对任意 callable 对象为真（含类实例、`__call__` 对象） | 原生腿以 R118-A 引入的 LV_TYPE_FUNCTION 为「函数」唯一判据，不识别 CPython 的对象可调用性。需对「可调用对象」做判定的场景应改用 `callable`（dv_is_callable） |
| `随机字节(n)` | 返回 **n 个 0..255 整数的列表**（原生无 bytes 类型），熵源是 **MT19937**（`dv_rand_genrand`） | `bytes`，`os.urandom`（密码学安全） | 用于 UUID / nonce 时**强度低于转译腿**。要对齐需给 runtime 接平台 CSPRNG（Windows `BCryptGenRandom` / POSIX `getrandom`） |
| `异步睡眠(x)` | `dv_sleep(x)` —— **真睡 N 秒** | `asyncio.sleep(x)` —— 让出控制权给事件循环 | 原生腿无事件循环；`等待`（AwaitExpression）在非协程内退化为直接求值，故整句可编可执行，但**没有并发让出**语义 |
| `getattr` 两参缺失 | 返回 `空`（null） | 抛 `AttributeError` | 表达式位生成「条件抛异常」需额外的分支与 `dv_throw` 编排，本轮不做；三参形态（带默认值）才是 stdlib 实际用到的 |

## 12. R122-A1：`_light_bytes_split` 补齐与「bytes」边界（2026-10-08）

### 12.1 缺口与落地

`_light_bytes_split(内容, 分隔)` 是**编译器内嵌 helper**（与转译腿
`src/code_generator.py:1483` 同名同语义），**不是** stdlib 导出函数。光明 parser
拒绝 `b'...'.split(...)` 这种「bytes 字面量后跟 `.方法`」的成员调用（句号被当语句
结束符，R72-E · L-175），所以纯光明侧的字节分帧只能走这个 helper；**原生腿此前
完全没有对应实现**，`stdlib/字节缓冲.light` 编译报
「未定义的段落：_light_bytes_split」。

| 层 | 落点 |
|---|---|
| runtime | `src/llvm/runtime_typed.c` 新增 `dv_bytes_split(LightValue*, LightValue*, LightValue*)` |
| IR declare | `src/llvm/codegen_typed.py` `declare void @dv_bytes_split(ptr, ptr, ptr)` |
| 内建分派 | `src/llvm/codegen_typed.py::_gen_typed_builtin` 新增 `name in ('_light_bytes_split',)` |

语义**严格对齐**转译腿 helper（`_b`/`_sep` 非 bytes 或 `_sep` 为空 → `[_b]`；
否则按 `_sep` 逐字节切分、不含分隔符、尾部空段保留）。注意与 `dv_str_split`
的「异常输入返回空列表」**不同**，别照抄。

真跑判据（O0 编译 + 执行，与 Python `bytes.split` 逐例对拍 5/5 一致），守在
`tests/unit/test_llvm_bytes_split.py`：多段+尾部空段 / 空分隔 / 无分隔符 /
连续分隔符 / 跨 chunk 切帧+残余保留（`stdlib/字节缓冲.light` 端到端）。

### 12.2 与 CPython 的已知差异（**边界，不是 bug；不许静默降级**）

| 项 | 原生腿行为 | CPython / 转译腿 | 登记理由 |
|---|---|---|---|
| bytes 的表示 | 字节串字面量 `b"..."` 落成 **STRING（type=3）**，`str` 字段存原始 UTF-8 字节；`dv_bytes_split` 按字节 `strstr` 切分，元素仍是 STRING | 一等 `bytes` 对象，`bytes.split` 返回 `bytes` 列表 | 原生腿**无一等 bytes 类型**。ASCII/UTF-8 可打印场景下逐例对拍一致；注意这与 `随机字节` 用「0..255 整数列表」表示字节序列是**两套既有口径** |
| 内嵌 NUL（`\x00`） | C 字符串以 NUL 为串尾，`b"a\x00b"` 会被截断 | `bytes` 可承载任意字节 | STRING 的既有边界，非本次引入。要真正对齐须先引入一等 bytes 类型 |
| `_b` / `_sep` 的类型判定 | 只要是 STRING 就参与切分，**无法区分 str 与 bytes** | `bytes.split` 只对 bytes 生效，str 走 `str.split` | 同上：类型不可分辨是「无一等 bytes 类型」的直接后果 |

### 12.3 顺带发现（**既有行为，非 R122 引入**，两条均为 **R123 候选**）

- **成员调用撞内置 mutating 名**（`清空`/`追加`/`设置`/`插入`/`删除`/`移除`/`弹出`/`弹栈`）：
  原生腿把「用户类方法」误当内建 mutating 处理。实测**两套机制**：
  - **截胡型**（名字在 `_gen_typed_builtin` 有分支：`追加`/`设置`/`插入`/`删除`/`移除`/`弹栈`）
    —— 成员调用先命中内建，类方法根本不跑；
  - **写回型**（名字只在 `mutating_methods`、无内建分支：`清空`/`弹出`）
    —— `codegen_typed.py:5253-5259` 的语句级写回把**方法返回值**覆盖接收者绑定。
  `字节缓冲.light:清空()` 即写回型：方法以赋值结尾、无返回 ⇒ 返回 `空` ⇒
  `缓冲` 绑定被覆盖成 `空`（实测 `取全部()`/`字节长度()` 均返回 null，再推入也无法恢复）。
  ⚠️ **更正**：此前「走 `_gen_typed_builtin('清空') → dv_list_clear`」的描述**不成立**——
  `清空` 无内建分支、`dv_list_clear` 全仓仅 declare 无调用（grep 实证）。
  全仓受影响模块：`代理循环`(会话.追加) / `对象池缓存`(删除/清空) / `数据结构轻量`
  (栈.弹出/清空、队列.清空) / `字节缓冲`(清空)。修法：成员调用先判接收者是否用户类实例，
  是则走 `dv_call_method`；改动在成员调用主路径，须过 082 门 → **R123 候选**。
- **模块名 == 类名导致两腿解析不一致**（实测全仓 **8 个**模块：`HTTP服务端`/`事件总线`/
  `代理循环`/`大模型客户端`/`字节缓冲`/`插件`/`路径护栏`/`进程树`）：
  原生腿 `新建 X()` 解析到**类**；转译腿 `导入 X` + `新建 X()` 解析到**模块**，报
  `TypeError: 'module' object is not callable`（是否真炸取决于消费形态，`从 X 导入 X` 则不炸）。
  修法：统一转译腿 `新建 X()` 的名字解析（L-019 一带，`src/code_generator.py:81-89`）；
  **不建议**靠改类名/模块名绕过。→ **R123 候选**（不影响就绪度口径——本模块无同名 `.py`，
  翻魔数对 Python 腿零影响）。

### 13.1 三集合定义

| 集合 | 含义 | 落点 |
|---|---|---|
| 原生腿分派名集 | 原生（LLVM）`codegen_typed.py::_gen_typed_builtin` 实际能分派的名字 | `src/llvm/codegen_typed.py` |

### 13.2 一致性要求

`.light` 实际调用的名字，**必须在两腿都可解析**：
- 若某名只在原生腿有（`_gen_typed_builtin` 注册）、转译腿缺映射 → Python 腿 `NameError`
  （R123-D2 实证：`时间格式化` / `随机位` / `睡眠秒`）；
- 反之若只在转译腿有、原生腿无 → 原生腿 `NotImplementedError`。
- 差集（原生腿有 − 转译腿可解析）即候选缺口；**每个候选必须实证**（真加载 `.light` 调用一次），

## 14. `isinstance` 原生腿语义（R124-C1 出框架；A1 填结论）

### 14.1 现状（R123 实测，2026-10-08 原生腿真跑 `_r123_scratch/native_诊断3.light`）

原生腿 `isinstance(值, 类型)` 当前**对一切原生标量恒返回假**，共 8 种形态全假：

| 探针 | 原生腿结果 |
|---|---|
| `isinstance("abc", str)` | 假 |
| `isinstance(42, str)` | 假 |
| `isinstance(42, int)` | 假 |
| `isinstance(3.5, float)` | 假 |

### 14.2 `type()` vs `isinstance()`：这是缺陷，不是设计差异

**必须写清**：`type(串) == str` 为真、而 `isinstance(串, str)` 为假，两者并存是
`src/llvm/runtime_typed.c` `dv_isinstance` 的**实现缺陷**（`obj->type != 3` 即 `return 0`，
该函数当前只服务类实例、走 `OBJ_PREFIX` 继承链），**不是原生腿的有意设计**。
后人排查时不要把它误判成「type() 看静态类型、isinstance() 另有意图」——R123-D 真编译真跑
已定位到行，R124-A1 负责修。

### 14.3 两条既有路径（A1 修复时的红线）

- **类实例继承链路径（现有正确，一个不许改）**：`obj->type == 3` 时 `dv_isinstance` 沿
  `OBJ_PREFIX` 走继承链判型——这条路径对自定义类实例是**正确的**，A1 修复只能**新增**
  原生标量判型分支，**不得改残**这条继承链（R124 要求补「自定义类 A、B 继承 A，
  `isinstance(B(), A) == 真`」用例防回归）。
- **原生标量路径（当前恒假，是缺陷本体）**：str/int/float/bool/list/dict/tuple 等原生标量
  一律落到 `return 0`。修复后应按值的真实类型分派为真，且**必须支持元组 class name**
  （`isinstance(整, (int, float))` 也要为真——R123 实测该形态同样全假）。

### 14.4 修复后原生标量判型规则（R124-A1 实测，2026-10-08）

> A1 已在 `src/llvm/runtime_typed.c` 的 `dv_isinstance` 完成修复：**新增**原生标量判型分支，

### 14.4a 本轮登记的边界（A1 实测，只登记不改）

- **原生腿无一等 `bytes` 类型**：`b"..."` 落成 STRING（type=3），因此
  `isinstance(值, "bytes")` 恒为假（不把普通 str 误判为 bytes）——与 `内置核心判型.是字节`
  在原生腿的语义一致（该段落在原生腿不可用，见 R124 收口）。
- **`内置核心判型.是字节` 在原生腿恒假 = 设计边界，不是缺陷（只登记不改）**：
  `stdlib/内置核心判型.light:47-49` 的 `是字节(值)` 段落实现为 `返回 isinstance(值, bytes)`，
  而**原生腿无一等 `bytes` 类型**（`b"..."` 落成 STRING（type=3），`dv_isinstance` 按 type
  分派时无 `bytes` 分支），因此该段落**在原生腿恒返回假**。这与 R124-A1 修 `dv_isinstance`
  时新增的原生标量分派表（int/float/str/list/dict/bool/tuple/generator/function/NoneType）
  **一致**：该表**本就不含 `bytes`**，故「修复后 `是字节` 仍假」是**结构性结果**，
  **不是 A1 修复残留的缺陷**。
  **后续排查提示**：任何人看到 `isinstance(值, "bytes")` 在原生腿为假，**不要把它当
  缺陷登记或修补**——`dv_isinstance` 要返回真就必须给 runtime 引入一等 `bytes` 类型
  （`dv_bytes_split` 已按字节 `strstr` 切分 STRING，见 §12.1），那是**独立的架构决策**，
  与本轮 `dv_isinstance` 标量判型修复**解耦**。要真正让 `是字节` 转真，须走「引入一等
  bytes 类型」这条路线，**不是**在 `dv_isinstance` 里加一个 `type==bytes` 分支（原生腿
  根本没有 `bytes` 这个 type 码）。
  **转译腿对照**：`是字节` 在 Python 腿（转译后 `isinstance(值, bytes)`）**返回正常**——
  缺陷不在 `.light` 真身，是**原生腿无 bytes 类型**这个设计边界。
- **`代理循环` 整模块仍不可编译**：它 `导入 threading`（Python 标准库），原生腿
  `NativeImportError`，落在就绪度基线的「其它错误」桶——A1 修 isinstance 不改变这一终局
  （任务书 §7 预期「本轮就绪度持平」已兑现）。
