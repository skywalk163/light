# stdlib 原生腿就绪度指标

> R115 任务线 C 交付 ｜ 2026-10-05 首跑基线 ｜ 脚本：`tools/ci/llvm_stdlib_readiness.py`

## 为什么要有这条指标

自举率（`tools/ci/bootstrap_rate.py`）回答的问题是：**stdlib 里有多少模块是用光明写成的**。
自从 `拼音转换`、`中文分词` 这批大模块挂上「纯光明实现」魔数之后，这个问题基本被答完了——
73 个带魔数的模块覆盖了绝大部分 stdlib。

但答完上一层问题，下一层问题立刻浮出来：**这些用光明写成的模块，有多少能被原生腿
（LLVM typed 后端）直接编译通过？** 这个数字此前没有任何指标在盯。魔数只说明
「运行期不再被同名 .py 遮蔽」，不说明「原生腿编得过」——实测里 73 个魔数模块有 27 个
会在原生腿上明确拒绝（大部分卡在 `未定义的段落`、`RunAsyncStmt`、`DestructuringAssignment`
这类缺口上），它们的原生腿可用性是零。

长期这个问题必须像自举率一样量化追踪，所以有了这条**就绪度指标**。

## 口径

- **分母**：`stdlib/`（递归）下首两行含「纯光明实现」魔数的 `.light` 模块。
  魔数识别**复用 `bootstrap_rate._是纯光明`**（与 `stdlib/_light_import_hook.py::_is_pure_light`
  同口径），不自造。
- **分子**：对每个模块真跑一次原生腿**编译**——`from llvm.compiler import compile_source_typed`，
  只编译、不链接、不 clang、不运行，快。编译必须在子进程里做（部分模块很大，
  拼音转换 2800+ 条字典设置），每模块一个子进程 + 默认 120s 超时，超时计入「其它错误」桶。
- **结果分三桶**：
  - `可编` —— `compile_source_typed` 正常返回 IR 文本；
  - `明确拒绝（含缺口类型名）` —— 抛 `NotImplementedError`（原生后端显式拒绝），
    名单里逐个标注缺口类型名（如 `RunAsyncStmt`、`DestructuringAssignment`、
    `未定义的段落：处理器`）；
  - `其它错误` —— 解析失败、导入失败、读不动、超时、子进程崩溃等，名单里给原因首行。
- **就绪度 = 可编 / 魔数模块总数**。三桶的完整名单都会打印出来，不许只给数字。

## 当前值（2026-10-05 首跑基线）

```
就绪度 = 可编 / 总数 = 46 / 73 = 63.01%
可编      46 个
明确拒绝  27 个（缺口集中在：未定义的段落、RunAsyncStmt、DestructuringAssignment、KeywordArg）
其它错误   0 个
```

基线落在 `tools/ci/llvm_stdlib_readiness_baseline.json`（`.gitignore` 已有
`!tools/ci/*_baseline.json` 豁免，能进仓）。27 个「明确拒绝」的逐模块缺口类型名，
正好是原生腿补能力时的**优先级清单**——它就是 R115 任务线 A 那三条语句的来源
（`大模型客户端` 卡 `DestructuringAssignment` 等）。

## 怎么跑

```bash
cd /g/dswork/duan-light-merge/light-merge

# 全量扫描：打印就绪度 + 三桶完整名单
MSYS_NO_PATHCONV=1 .venv/Scripts/python.exe tools/ci/llvm_stdlib_readiness.py

# 与基线对比，产出「新增不可编模块」清单；非空则 rc=1（闸门语义：就绪度只许升）
MSYS_NO_PATHCONV=1 .venv/Scripts/python.exe tools/ci/llvm_stdlib_readiness.py \
  --base tools/ci/llvm_stdlib_readiness_baseline.json

# 重新生成基线（只在合并点做，与自举率基线同纪律）
MSYS_NO_PATHCONV=1 .venv/Scripts/python.exe tools/ci/llvm_stdlib_readiness.py \
  --json tools/ci/llvm_stdlib_readiness_baseline.json

# 单模块调试：打印该模块的桶与完整报错（不截断）
MSYS_NO_PATHCONV=1 .venv/Scripts/python.exe tools/ci/llvm_stdlib_readiness.py --sample 拼音转换
```

退出码：`0` 正常（`--base` 时且无新增不可编）；`1` 有新增不可编或扫描失败；`2` 用法错误
（`--sample` 找不到模块）。判据是**下界式**的：单测（`tests/unit/test_llvm_stdlib_readiness.py`）
不止断言比例，还钉死了 `Base64`、`哈希`、`列表工具`、`拼音转换`、`JSON核心` 五个真实模块
必须一直在「可编」桶里，并当场逐个真编译——把模块换成空壳或改坏任何一个，测试立刻红。

## 与自举率的分工

| 指标 | 回答的问题 | 口径 |
|---|---|---|
| 自举率（`bootstrap_rate.py`） | stdlib 有多少模块用光明写成？ | 魔数 + decl ≥ 1 |
| **就绪度（本指标）** | **写成的模块有多少原生腿编得过？** | 魔数模块 × `compile_source_typed` |

两条指标是上下游关系：自举率涨了（更多模块挂魔数），就绪度不一定跟着涨——新挂魔数的
模块若用了原生腿不支持的语法，就绪度分母涨、分子不涨，**指标反而会降**。这正是它该疼的
地方：防止「挂魔数」变成刷自举率数字的动作，逼着新模块同时过原生腿编译这一关。

## 基线纪律

- 基线 JSON **只在合并点重建**（与自举率基线、能力矩阵基线同纪律），日常跑只做 `--base` 对比。
- 「可编」名单只许增不许减：对基线跑出「新增不可编」即 rc=1，必须查明是哪个改动把
  原本能编的模块改坏了。
- 魔数模块总数也是下界：缩水说明模块被删或魔数被摘，同样要查。
