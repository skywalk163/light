## 为什么要有这条指标

自举率（`tools/ci/bootstrap_rate.py`）回答的问题是：**stdlib 里有多少模块是用光明写成的**。
自从 `拼音转换`、`中文分词` 这批大模块挂上「纯光明实现」魔数之后，这个问题基本被答完了——
73 个带魔数的模块覆盖了绝大部分 stdlib。

但答完上一层问题，下一层问题立刻浮出来：**这些用光明写成的模块，有多少能被原生腿
（LLVM typed 后端）按真实依赖直接编译通过？** 这个数字此前没有任何指标在盯。魔数只说明
「运行期不再被同名 .py 遮蔽」，不说明「原生腿编得过」。R115 首版指标使用
`compile_source_typed` 单模块入口，不能解析模块级导入，因此把一批实际可编模块误记成
`未定义的段落`；R117 改走 `compile_light_typed` 多模块入口后才得到真实口径。

长期这个问题必须像自举率一样量化追踪，所以有了这条**就绪度指标**。

## 口径

- **分母**：`stdlib/`（递归）下首两行含「纯光明实现」魔数的 `.light` 模块。
  魔数识别**复用 `bootstrap_rate._是纯光明`**（与 `stdlib/_light_import_hook.py::_is_pure_light`
  同口径），不自造。
- **分子**：对每个模块真跑一次 `from llvm.compiler import compile_light_typed`，传入 `.light`
  文件路径和临时目录中的 `output_path`。该入口会递归解析依赖、生成 IR、经 clang 验证并链接；
  全部产物随临时目录清理，不污染 `stdlib/` 或仓内目录。编译在独立子进程里执行，最多 2 路
  并发，默认每模块 300s 超时，结果仍按模块名稳定排序。
- **结果分三桶**：
  - `可编` —— `compile_light_typed` 正常完成；
  - `明确拒绝（含缺口类型名）` —— 抛 `NotImplementedError`（原生后端显式拒绝），
    名单里逐个标注缺口类型名（如 `RunAsyncStmt`、`DestructuringAssignment`、
    `未定义的段落：处理器`）；
  - `其它错误` —— 解析失败、导入失败、读不动、超时、子进程崩溃等，名单里给原因首行。
- **就绪度 = 可编 / 魔数模块总数**。三桶的完整名单都会打印出来，不许只给数字。
  JSON 顶层的 `compile_entry` 固定记录本次测量入口，防止不同口径的基线被混用。

## 框架边界·终局登记（R120）

**结论**：R119 收口后「其它错误」桶残留的 10 个模块，**全部**因导入 Python 生态/标准库
（`socket` / `locale` / `threading` / `os` / `selectors` / `asyncio`）而命中 `NativeImportError`：
原生运行时是纯 C（`src/llvm/runtime_typed.c`），**不嵌 CPython、没有 Python 互操作层、
也没有可链接的 Python 符号**。这 10 个模块因此**结构性不可移植**——不是原生腿的实现缺口，
也不是 bug。

R120 把它们**从「待修遗留」改为「框架边界·终局登记」**：永久不计入就绪度分子（与既有口径一致，
非新口径），「其它错误」桶语义自此收敛为「框架级不可移植·终局」，不再作为待修 red 遗留。
数字不变（不计入分子本就是现行口径），本登记只是把「未决」正式结案，**不假绿**。

### 为什么是设计边界而非缺陷

- **与「明确拒绝」桶不同**：「明确拒绝」是原生后端显式抛 `NotImplementedError` 并给出缺口类型名
  （如 `RunAsyncStmt`、`未定义的段落：创建任务`），属**可被 `src/` 原生 codegen 逐条补齐**的能力缺口
  （R118/R119 即据此把该桶清零）。本桶是 `NativeImportError`，是**语言生态边界**：原生腿把光明源码
  编成纯 C 自然码、不嵌 CPython，凡依赖 CPython 运行时对象（`socket`/`threading`/`asyncio`/`selectors`/
  `locale`/`os`）的模块都无法链接。
- **消除这 10 条没有「改代码使其可编」的捷径**：要么在光明里重写等价的 socket/事件循环/线程原语
  （等于换实现，语义对齐成本高），要么引入「原生运行时 Python 互操作层」（独立大项，见下节）。
  二者**都不在 R120 范围**。
- **R120 不做任何假绿**：不删这 10 个模块的「纯光明实现」魔数、不改它们的 `.light`、不改 `src/`、不改测试。

### 口径影响

- 就绪度公式不变：**就绪度 = 可编 / 魔数模块总数**。这 10 个既不在分子，也不从分母剔除——
  它们确实挂了「纯光明实现」魔数，是有效分母。
- 「其它错误」桶自 R120 起**语义收敛**为「框架级不可移植·终局」，不再产出待修 red。

## R121 更新（2026-10-07 收口）—— 零风险分母扩军

### 立足点：为什么这批模块翻魔数是零风险的

`stdlib/_light_import_hook.py` 的接管判定：

```python
if _exists_exact(base, realname + '.py'):      # 有同名 .py 兄弟
    if not _is_pure_light(light_file):         #   未声明魔数 -> 不接管，走 .py
        return None
loader = LightLoader(...)                       # 无同名 .py -> 无论如何都加载 .light
```

即**「无同名 .py」的 .light，钩子不看魔数、本来就加载 .light**。给这类模块补魔数，
**对 Python 腿零影响、零回归风险**——与 R119/R120 踩坑的 `对象池缓存`（有同名 .py
且 `.light` 与 `.py` 语义不等价，装饰器 `返回 空`）是**完全不同**的风险等级。

这类模块本就是**纯光明唯一实现**，只是没声明魔数、因而**未计入分母**（分子分母都没算它）。
把它们补进分母是**测量口径补全**，且每个都必须先真过 `compile_light_typed` 才允许翻。

### 两档风险

判定键就是「旁边有没有同名 `.py`」（`stdlib/_light_import_hook.py::_exists_exact`）：

| 档 | 判定 | 补魔数对 Python 腿的影响 | 翻前必须 |
|---|---|---|---|
| **NO-PY（零风险）** | 无同名 `.py` | **零影响**——钩子本就加载 `.light`（见 `_light_import_hook.find_spec`：`.light` 在、`.py` 不在 → 无论魔数都接管）。补魔数只是把它「补进就绪度分母」的测量口径补全。 | 先过原生腿 `compile_light_typed` |
| **HAS-PY（高风险）** | 有同名 `.py` | **改行为**——未挂魔数时钩子让位给 `.py`；挂魔数后钩子改吃 `.light`。必须先逐模块证明 `.light` 与 `.py` **语义等价** + 自跑 082 全量门（R119/R120 `对象池缓存` 即此翻车：`.light` 装饰器 `返回 空` ≠ `.py`，phase10 `test_缓存装饰器` 新增红 1）。 | 语义等价证据 + 082 门 |

### 单调性约束（翻不可编 = 拉低就绪度）

就绪度 = 可编 / 魔数模块总数。翻一个**不可编**模块：分母 +1、分子不变 ⇒ 比例反降
（按 R122 基线：67/77 → 67/78）。所以：

- `flip_magic.py` 内置**前置可编闸门**——原生腿不可编一律拒绝翻（rc=1），不许靠翻不可编模块刷分母；
- `--allow-shadow`（HAS-PY）只是影子闸门的显式放行，**可编闸门照常拦截**；
- 只有翻「实测可编」的模块才单调上升：翻 k 个全可编 ⇒ `(67+k)/(77+k)` 与 67/77 交叉相乘差 10k > 0。

> **R122 真实实例（两条约束各踩一次）**：
> - **正向**：A1 补 `dv_bytes_split` 使 `字节缓冲` 可编 → B1 才敢翻 ⇒ 67/77=87.01%，单调上升；
> - **反向**：若 B1 单独翻（A1 缺席），`字节缓冲` 进分母但编不过 ⇒ **66/77 = 85.71%，反降 1.13pp**
>   → 故 A1 与 B1 **必须同批提交**。

## 与自举率的分工

| 指标 | 回答的问题 | 口径 |
|---|---|---|
| 自举率（`bootstrap_rate.py`） | stdlib 有多少模块用光明写成？ | 魔数 + decl ≥ 1 |
| **就绪度（本指标）** | **写成的模块有多少原生腿按真实依赖编得过？** | 魔数模块 × `compile_light_typed` |

两条指标是上下游关系：自举率涨了（更多模块挂魔数），就绪度不一定跟着涨——新挂魔数的
模块若用了原生腿不支持的语法，就绪度分母涨、分子不涨，**指标反而会降**。这正是它该疼的
地方：防止「挂魔数」变成刷自举率数字的动作，逼着新模块同时过原生腿编译这一关。

## 基线纪律

- 基线 JSON **只在合并点重建**（与自举率基线、能力矩阵基线同纪律），日常跑只做 `--base` 对比。
- 「可编」名单只许增不许减：对基线跑出「新增不可编」即 rc=1，必须查明是哪个改动把
  原本能编的模块改坏了。
- ⚠️ **跨口径不可直接比**：2026-10-06 起基线带 `compile_entry` 字段，换编译入口必须
  重建基线并写进「口径变更」小节，否则 `--base` 对比的是两个不同口径的数字。
- 魔数模块总数也是下界：缩水说明模块被删或魔数被摘，同样要查。
