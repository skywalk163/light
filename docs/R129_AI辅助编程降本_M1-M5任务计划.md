> 任务来源：R127 完成"AI 编程指南沉淀 + lightharness 惯用法提炼"后，
> 基于对 stdlib 541 条导出的全量盘点和 lightharness 300+ 生产文件的对照，
> 识别出 AI 写光明代码的 retry 成本大头。
> R127 已交付 S1-S5（纯文档/工具层，已落地）。
> R129 进入编译器与 stdlib 层，目标是**从根源上消灭 AI 写错函数名、写错语法的 retry**。

## 〇、背景：为什么是这五项

R127 实测发现，AI 写光明代码的 token 成本大头不是"汉字比英文 token 多"（只占 ~20%），而是：

| 成本源 | 占比 | 对应 R129 项 |
|--------|------|--------------|
| stdlib 函数名双轨/三轨（`读取` vs `读取文件`、`序列化` vs `序列化JSON`） | ~40% | M1 |
| lambda / with 缺失，AI 第一反应必错 | ~20% | M2 / M3 |
| 字典操作三套（下标 / `字典获取()` / `.包含()`） | ~10% | M4 |
| 教学体 vs 工程体关键字分歧（`试` vs `尝试`、`捕` vs `捕获`） | ~10% | M5 |

S1-S5 已经用文档把这些坑"说清楚"，但编译器层面还没"消灭"它们。R129 做 M1-M5，让 AI 就算忘了指南也能写对。

## 一、M1：stdlib 函数名统一（加别名层，不改语义）

### 目标
让 AI 写 `读取("f")` / `写入("f", s)` / `序列化(x)` / `解析(s)` 也能跑通，同时保留旧代码兼容。

### 现状（已核对 stdlib 真实导出）
| 模块 | 权威名（R127 指南推荐） | 另一套名（AI 容易写错） | 位置 |
|------|------------------------|------------------------|------|
| 文件 | `读取文件` / `写入文件` | `读取` / `写入` | `stdlib/文件系统.light` |
| JSON | `解析JSON` / `序列化JSON` | `解析` / `序列化` | `stdlib/JSON.light` vs `stdlib/JSON核心.light` |
| 文件存在 | `文件存在` / `目录存在` | `存在` | `stdlib/文件系统.light` |
| 字符串空白 | `去除首尾空白` | `去空白` / `去除空白` | `stdlib/字符串工具.light` vs `stdlib/中文NLP.light` |
| HTTP | `获取` / `POST`（网络请求.light） | `HTTP获取` / `HTTPPost` | `stdlib/网络请求.light` vs `stdlib/HTTP.light` |
| CSV | `读取CSV` / `写入CSV` | `CSV读取` / `CSV写入` | `stdlib/CSV读写器.light` vs `stdlib/CSV.light` |

### 方案
1. 在权威模块里**加薄别名导出**：例如 `stdlib/文件系统.light` 追加 `导出 读取 为 读取文件, 导出 写入 为 写入文件`。
2. 别名名字保留 **6 个月**兼容期，期间用 `--deprecated` lint 标记（不改运行时行为）。
3. 在 `src/keywords.py` 或 builtins 注册表里加 deprecated 映射，让 AI 就算写旧名字也不会报"未定义符号"。

### 验收判据
- `读取("f.txt")` / `写入("f.txt", "x")` / `序列化(x)` / `解析(s)` 在 src 后端直接跑通，不报 NameError。
- 既有 7912 个 CI 测试零回归。
- deprecated 别名列表写进 `docs/known_issues.md`。

### 工作量
- 估计 1-2 天。纯 stdlib 别名层，不动 parser / codegen。

## 二、M2：补 lambda 语法（known_issues G2，提前到 R129）

### 目标
让 AI 写 `排序(列表, key=lambda x: x["age"])` 不用改成"先定义段落再传段名"。

### 现状
- known_issues G2 明确记录 lambda 不支持。
- R127 指南 #13 错误条目给的替代写法是"先定义命名段落再传引用"——能用但啰嗦，AI retry 率高。
- Python 程序员最常用 lambda 的场景：排序 key、回调、`map`/`filter`/列表推导的高阶函数。

### 方案（语法糖，不引入新语义）
```光明
# 推荐语法（白话体）：
设 翻倍 为 匿名(x): x * 2
排序(列表, 键 = 匿名(x): x["年龄"])

# 等价于：
段落 __匿名_1(x):
    返回 x * 2
设 翻倍 为 __匿名_1
```
1. parser_expr.py 加一个 `匿名(...) : expr` 产生式，desugar 成模块级/局部段落定义。
2. 不引入捕获语义变化（仍受 B7 闭包不能重绑外层变量约束）。
3. 只支持**单表达式** lambda（不支持多行体），多行体继续用命名段落。

### 验收判据
- `排序([{"年龄":3},{"年龄":1}], 键=匿名(x): x["年龄"])` 返回 `[{"年龄":1},{"年龄":3}]`。
- `map(匿名(x): x*2, [1,2,3])` 返回 `[2,4,6]`。
- 既有测试零回归；新增 `tests/unit/test_lambda.py` ≥ 10 个用例。
- known_issues G2 标记为已修复。

### 工作量
- 估计 3-5 天。parser + desugar + 测试。

## 三、M3：补 with 语法（known_issues G3，提前到 R129）

### 目标
让 AI 写 `与 打开(f) 为 fh:` 不用手写 try/finally。

### 现状
- known_issues G3 明确记录 with 不支持。
- R127 指南 #14 错误条目给的替代写法是 `尝试/最终: fh.关闭()`——AI 经常忘写 finally 或漏关资源。
- Python 的 `with` 在文件 I/O、锁、socket 场景几乎是默认写法。

### 方案（语法糖，desugar 成 try/finally）
```光明
# 推荐语法：
与 打开文件("f.txt") 为 fh:
    设 数据 为 fh.读取()

# desugar 成：
设 fh 为 打开文件("f.txt")
尝试:
    设 数据 为 fh.读取()
最终:
    fh.关闭()
```
1. parser_stmt.py 加 `与 表达式 为 名字: 块` 产生式。
2. 要求被管理对象有 `关闭()` 方法（鸭子类型，不强制协议）。
3. 支持多资源：`与 a() 为 x, b() 为 y:`（链式 with）。

### 验收判据
- 文件读、文件写、`互斥锁` 三种场景下资源正确释放（异常路径也要释放）。
- 新增 `tests/unit/test_with.py` ≥ 8 个用例。
- known_issues G3 标记为已修复。

### 工作量
- 估计 2-3 天。比 lambda 简单，因为就是 try/finally 包装。

## 四、M4：字典操作三轨收敛

### 目标
消除"下标 / `字典获取()` / `.包含()` 方法"三套写法的选择负担，给 AI 一个明确首选。

### 现状（R127 已盘点）
```光明
设 d 为 {"a": 1}
v = d["a"]                        # 下标读
设 d["b"] 为 2                    # 下标写（必须 设…为…）
v = 字典获取(d, "k", 默认)         # 函数式带默认值
如果 d.包含("k"): ...              # 方法判键
如果 字典包含键(d, "k"): ...       # 函数式判键
```
三套都能跑，AI 不知道用哪套。

### 方案
1. **不改语言**，只在 lint 层和文档层收敛：
   - 首选：下标 `d[k]` 读 + `设 d[k] 为 v` 写。
   - 带默认值：`字典获取(d, k, default)`。
   - 判键：`d.包含(k)` 方法形式。
2. `字典设置()` 函数保留但不推荐新代码使用。
3. 在 AI 指南"十一-B"章已经写了推荐写法（R127 完成），R129 加一个 `light ai lint` 规则检查"用了 `字典包含键` 函数形式就提示改用 `.包含()` 方法"。

### 验收判据
- R127 指南"十一-B"章的推荐写法与 linter 规则一致。
- linter 对既有 stdlib 扫描给出 deprecation 报告，但不阻塞 CI。

### 工作量
- 估计 1 天。主要是 linter 规则。

## 五、M5：教学体/工程体收敛（linter，不改 parser）

### 目标
消除"试 vs 尝试"、"捕 vs 捕获"、"读取 vs 读取文件"、"初始化 vs 构造"的文体分歧。

### 现状（R127 已盘点对照表）
| 语义 | 教学体（L1 白话） | 工程体（lightharness src/） |
|------|------------------|----------------------------|
| try | `试:` | `尝试:` |
| except | `捕 错误 为 e:` | `捕获 错误:` |
| 构造 | `段落 初始化 接收 x:` | `段落 构造(x):` |
| 文件读 | `读取(path)` | `读取文件(path)` |

两种 parser 都接受（R127 实测），但 AI 每写一个文件要猜用哪套。

### 方案
1. **不改 parser**（两种都接受，向后兼容）。
2. 在 `light ai lint` 加一个 `--style=工程体` / `--style=教学体` 选项：
   - 工程体项目：发现 `试:` 提示改为 `尝试:`。
   - 教学体项目：发现 `捕获 错误:` 提示改为 `捕 错误 为 e:`。
3. 项目根加 `light.toml` 配置项 `style = "工程体"` 固定项目文体。

### 验收判据
- `light ai lint --style=工程体` 能对 lightharness/src/ 全量扫描，0 个风格告警（因为本来就是工程体）。
- `light ai lint --style=教学体` 对 examples/ 扫描，0 个告警。
- linter 不阻塞 CI，只提示。

### 工作量
- 估计 2-3 天。linter 规则 + light.toml 解析。
