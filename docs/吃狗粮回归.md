## 1. 怎么跑

```bash
cd <light 仓根>
python -m pytest -q tests/dogfood/
```

本机预期（Windows 11 / Python 3.13.14）：`18 passed, 9 xfailed`，rc=0，约 75~105 秒。
9 个 xfail = 8 条基线欠账 + 1 个 xfail 场景；xfail **不是通过**，是挂账。

### 1.1 环境变量

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `LIGHTHARNESS_DIR` | 依次探测 `../lightharness` → `../../lightharness`（hive worktree 布局）→ `./lightharness` | 显式指定优先；都不存在则**全 skip** 并打印「未找到 lightharness，跳过（不是通过）」，rc=0 但不算通过 |
| `LIGHT_DOGFOOD_LIMIT` | `20` | 按相对路径排序取前 N；**禁止随机** |
| `LIGHT_DOGFOOD_HASH_SEED` | `0` | 固定子进程的 `PYTHONHASHSEED`，原因见 §7-A |

```bash
# 扩大抽样（会撞见基线外的新失败，用来验证门禁，见 §5）
LIGHT_DOGFOOD_LIMIT=21 python -m pytest -q tests/dogfood/

# 无 lightharness 的机器
LIGHTHARNESS_DIR=C:/path/does/not/exist python -m pytest -q tests/dogfood/   # 8 skipped, rc=0

# 装了 pytest-xdist / pytest-timeout 的机器，可显式用仓库级 addopts
python -m pytest -c pyproject.toml -q tests/dogfood/
```

### 1.2 为什么目录里有一份 `pytest.ini`

仓库根 `pyproject.toml` 的 addopts 是
`--tb=short --durations=15 --ignore=tests/archive --timeout=60 -n 4 --dist=loadscope`，
其中 `--timeout` / `-n` / `--dist` 分别依赖 `pytest-timeout` / `pytest-xdist`。本机没装，
`python -m pytest -q tests/dogfood/` 会在解析命令行阶段就报
`unrecognized arguments: --timeout=60 -n --dist=loadscope` —— 与产物无关，别怀疑测试。
pytest 9 还禁止普通 `addoption` 注册小写短选项（`-n` 报 `lowercase short options are reserved`），
所以「占位注册」也兜不住 `-n`。本卡不能改 `pyproject.toml`，于是两层处理：

1. `tests/dogfood/pytest.ini`：目录级最小配置，rootdir 局部化，不继承仓库级插件依赖；
   `-p no:cacheprovider` 避免在受限目录建 `.pytest_cache` 触发写权限告警。
2. `tests/dogfood/conftest.py::pytest_load_initial_conftests`：兜底剥掉本机无插件支撑的那几个
   addopts 参数（含 `-n 4` 的取值），其余 addopts 原样保留。

插件已安装的机器上两层都是 no-op，xdist / timeout 照常接管。用例内部每个 CLI 子进程
自带 `subprocess` 超时（90s），不依赖 pytest-timeout。

## 2. 抽样与判据

- **范围**：`lightharness/src/**.light` + `lightharness/stdlib/**.light`，共 **354** 个工程体模块。
  `examples/` 是场景与复现载体、`docs/` 是历史探针和**故意写坏的负例**，按路径排序会排在
  最前面，若纳入抽样只会得到一堆假欠账，故不入 check 抽样。
- **确定化**：相对路径统一成 `/` 分隔，Python `sorted()` 按 Unicode 码点升序取前 N —— 与平台
  locale 无关、无随机、无 `random`。参数化用例 id 直接是模块路径。
- **check 层**：`python -m cli.light check <绝对路径>`（纯语法/类型检查，不执行副作用代码），
  cwd = light 仓根，记录 rc、stderr 首行、stdout 错误首行、耗时。
- **场景层**：`python -m cli.light run <绝对路径>`，断言 **rc=0 且 stdout 含业务收尾标志**。
  只看 rc 会把「空跑」也算通过，所以每个场景都有 `expect` 收尾字符串。
- **可重复性**：子进程固定 `PYTHONHASHSEED=0`。light 的类型推断结果会随 hash seed 变化
  （§7-A），不固定则同一文件忽红忽绿，基线无法落地。

## 3. 报告：`build/dogfood_report.json`

运行产物，`build/` 已被仓库 `.gitignore` 忽略，不入库；每次 `pytest` 的 session 结束由
master 汇总落盘。`build/dogfood_parts/*.json` 是每用例一个分片，xdist 多 worker 并行也不会
互相覆盖；session 开始由 master 清空。

| 字段 | 含义 |
| --- | --- |
| `schema` / `task` / `generated_at` | 版本、任务号、生成时间 |
| `platform` / `python` / `env` | 平台、解释器版本、`PYTHONHASHSEED` 与固定原因 |
| `lightharness_dir` / `lightharness_found` / `status` | 探测到的只读目录；缺失时 `status=skipped` |
| `sample{limit,scope,total_modules,sampled,rule}` | 抽样上限、范围、总体数、实际抽样数、排序规则 |
| `modules[]` | `module`、 `rc`、`elapsed_sec`、`stderr_first`、`error_first`、`detail_first`、`stdout_first`、`stdout_last`、`command` |
| `scenes[]` | `scene`、`entry`、`desc`、`xfail`、`reason` + 同 modules 字段 + `stdout_excerpt` |
| `baseline{file,debt,failed_now,new_failures,removable,policy}` | 欠账数、本次失败清单、新增失败、可缩减项 |
| `summary` | `sampled` / `passed` / `failed` / `baseline_debt` / `new_failures` / `baseline_removable` / `scenes_*` / `run_through_rate` |

> `error_first` / `detail_first` 从 **stdout** 提取：light CLI 把类型错误打在 stdout，
> `stderr` 常为空（§7-B）。`stderr_first` 仍如实记录，通常为空字符串 —— 这本身就是欠账证据。

## 4. 五个场景

| # | 场景 | 入口（lightharness，只读） | 判据 | 本机结果 |
| --- | --- | --- | --- | --- |
| 1 | JSON 序列化与解析往返 | `examples/冒烟.light` | rc=0 + `自包含 stdlib 冒烟测试通过` | PASS |
| 2 | 字典存取与条件判定 | `examples/test_字典.light` | rc=0 + `--- 字典方法测试通过 ---` | PASS |
| 3 | 类实例与列表增删 | `examples/test_空表.light` | rc=0 + `--- 测试结束 ---` | PASS |
| 4 | 事件表构建与追加 | `examples/test_事件表.light` | rc=0 + `--- 测试2结束 ---` | PASS |
| 5 | 真实 HTTP 请求并解析响应 | `examples/test_R41_真实网络IO.light` | `xfail(strict=True)` | XFAIL |

场景 5 覆盖的目标：本机起 web 服务 → `GET /health` → `POST /v1/chat/completions` → 解析
200/401 响应，正对应评审举的例子。挂 xfail 的两个原因：

1. **需要真实网络 IO**：本卡禁止联网；该场景还要本机起 HTTP 服务端/客户端。
2. **跨仓模块引导缺失**：lightharness 的 `src/*.light` 模块名（如 `总入口`、`web服务器`）
   靠 `运行.py` 在**同进程**里 `sys.path.insert` + `_light_import_hook.install([SRC, STDLIB, ROOT])`
   才能解析（`运行.py:109/120/154/158`）。独立 `python -m cli.light run` 子进程拿不到这套引导，
   报 `No module named 'web服务器'`；实测追加 `PYTHONPATH` 和 `--stdlib-dir` 也无效。
   本卡禁止改 lightharness、也不修 light 本体，所以不绕过、不假造通过。

`strict=True` 的含义：若将来该场景意外跑通，会以 **XPASS 判红**，提醒把它升级成正式断言并
销账 —— 防止 xfail 永远挂着。

## 5. 基线机制与更新规则

`tests/dogfood/baseline.json` 首次落地时如实登记**当前 8 个失败模块**（不是清零、没挑好用的
模块），每条带 `rc` / `first_error` / `detail`。仓库根 `.gitignore:46` 有全局 `*.json` 忽略，
本目录的 `.gitignore` 用 `!baseline.json` 豁免，保证基线随分支入库 —— 否则 checkout 后
`test_环境预检` 会因缺基线直接失败。测试里有三重判定：

1. `本次失败集合 ⊆ failed_modules` —— **新增失败即红**。
   实测 `LIGHT_DOGFOOD_LIMIT=21` 时第 21 个 `src/webhook会话.light` 触发
   `2 failed / rc=1`（「新增失败（不在 baseline.json）」+ 集合级断言），门禁确实有效。
2. `failed_modules ⊆ initial_failed_modules` —— 基线**不得新增条目**，防止把新失败塞进
   基线来消红。`initial_failed_modules` 是首次落地清单的快照。
3. 基线里本次已通过的条目会打印「可从 `baseline.json` 删除」并列出路径，**不判红**。
   未抽样到的基线条目只提示「保留观察」，不自动建议删除（没验证过就不该销账）。

更新规则：

- **只能下调（常规）**：删掉已通过的条目即可，git diff 可见，删完再跑一次确认全绿。
- **上调需说明理由（例外）**：确有平台差异或新模块时，必须 ① 同步更新
  `initial_failed_modules` 快照；② 在下方变更记录表追加一行（日期 / 模块 / rc / 错误首行 /
  理由 / light 缺陷卡号）；③ 经评审。**没有缺陷卡号不得上调，不得为让测试变绿而调大。**
  上调是一次显式、可 review 的改动，不是悄悄改数字。

## 7. 发现的 light 缺陷：建议开卡清单

以下都**没有在本卡修复**，只给定位与最小复现。`@` 行号为 light 仓（本 worktree）当前 main。

### A. 类型推断结果随 `PYTHONHASHSEED` 变化（非确定性，最高优先）

- **文件 + 行**：`src/type_inferencer.py:138-139`（`_segment_cache`）、`:542-591`（缓存命中/失效）、
  `:2263-2264`（可空参数报错处）；同类 `src/type_checker.py:1002`。疑点集中在集合/字典迭代
  顺序影响类型变量实例化与缓存命中的路径。
- **现象**：同一文件 `lightharness/src/mock大模型服务器.light`，`PYTHONHASHSEED=1` 稳定 rc=1
  （`函数 '造HTTP响应' 参数类型不匹配: 期望 T0'0，实际 列表[任意]`），`seed=0/2/42` 稳定
  rc=0；不固定 seed 时 8 次里 6 通过 2 失败。`src/office转PDF.light`（3↔2 条）、
  `src/ssh连接配置.light`（6↔9 条）的错误条数也随 seed 变化。
- **最小复现**：
  ```bash
  cd <light 仓根>
  PYTHONHASHSEED=1 python -m cli.light check <lightharness>/src/mock大模型服务器.light   # rc=1
  PYTHONHASHSEED=0 python -m cli.light check <lightharness>/src/mock大模型服务器.light   # rc=0
  ```
- **影响**：CI 判据不可重复；本套件被迫固定 `PYTHONHASHSEED=0` 才能落基线。

### B. `check` 的错误输出写 stdout、stderr 为空

- **文件 + 行**：`cli/light.py:1152-1165`（`type_errors` 打印 + `sys.exit(1)`）。
- **现象**：rc=1 但 stderr 0 字节；任务要求的「stderr 首行」判据拿不到任何信息，
  8 条欠账的 `stderr_first` 全是 `""`。
- **最小复现**：
  ```bash
  python -m cli.light check <lightharness>/src/JSONRPC传输.light >out.txt 2>err.txt
  # rc=1；err.txt 为 0 字节，❌ 类型错误 (6 个) 全在 out.txt
  ```
- **建议**：错误信息同时写 stderr（至少首行），或明确文档化 stdout 契约并让下游适配。

### C. 可空参数误报（`空` 字面量 / Optional 传播）

- **文件 + 行**：`src/type_inferencer.py:2263-2264`（另见 `:1817`、`:1824`）。
- **现象**：给未标注形参传 `空` 时一律报「函数 X 第 N 个参数类型不可空，但传入可空类型 空，
  需要先使用 '!' 或 unwrap() 解包」；`lightharness/src/ssh协议.light:47-84` 的
  `建立远程操作错误(消息, 空)` 被重复报 **49** 次。
- **最小复现**：
  ```bash
  python -m cli.light check <lightharness>/src/JSONRPC传输.light
  # 6 个类型错误；载体调用点 src/JSONRPC传输.light:59,71,204,225,379,400 的 归一化参数(参数)
  ```
- **建议**：区分「形参未标注（不该强制非空）」与「实参为 空 字面量」；同因同点错误去重。

### D. 条件表达式类型误判为 列表 / 字典

- **文件 + 行**：`src/type_checker.py:1002`、`src/type_inferencer.py:1385`、`:2125`。
- **现象**：`lightharness/src/acp内容.light` 报「条件表达式类型应为布尔，实际为 列表」；
  `src/mcp客户端.light`、`src/toolcordis.light`、`src/typert生成器.light` 报「实际为 字典」。
- **最小复现**：
  ```bash
  python -m cli.light check <lightharness>/src/acp内容.light
  # 1 个类型错误；该文件的 如果 条件见 :28/:34/:41-52（列表包含 / 匹配正则 / == 假 等）
  ```
- **建议**：核对容器方法返回值（如 `列表包含`）与比较表达式的推断传播。

### E. CLI 独立进程缺跨仓模块搜索路径（跨仓引导契约，非语法缺陷）

- **文件 + 行**：`cli/light.py:795-838`（`cmd_run`）；对照只读的
  `lightharness/运行.py:109/120/154/158`（进程内路径注入 + 导入钩子）。
- **现象**：`python -m cli.light run <lightharness>/examples/test_总入口.light` 报
  `错误: 模块未找到 / No module named '总入口'`；即使给子进程加 `PYTHONPATH`
  （`lightharness/src`、`stdlib`、根）与 `--stdlib-dir` 仍失败，只有 `python 运行.py ...`
  同进程注入钩子才找得到。这是场景 5 xfail 的第二个原因。
- **最小复现**：
  ```bash
  cd <light 仓根>
  python -m cli.light run <lightharness>/examples/test_总入口.light
  ```
- **建议**：CLI 支持 `--module-dir` / `LIGHT_MODULE_PATH` 透传并自行安装导入钩子；
  或由 lightharness 提供可复用引导 shim（需另开 lightharness 卡，本卡禁止改它）。

## 8. 如何把新发现转成 light 缺陷卡

1. 跑 `python -m pytest -q tests/dogfood/`，从 `build/dogfood_report.json` 的 `modules[]`
   取 `module` / `rc` / `error_first` / `detail_first` / `command`。
2. 用 `command` 原样复现一次，确认不是 `PYTHONHASHSEED` 抖动（§7-A）或平台判据假失败（§1.3）。
3. 在 light 仓定位到具体文件 + 行（参照 §7 的坐标），写清「现象 / 期望 / 影响面」。
4. 开卡模板：

   ```text
   标题：[dogfood] <模块路径> check 失败：<error_first>
   现象：rc=<rc>；<detail_first>；stderr 首行=<stderr_first>
   最小复现：cd <light 仓根> && python -m cli.light check <lightharness>/<模块路径>
   证据：build/dogfood_report.json → modules[] 对应项
   期望：...
   不要：不要改 lightharness；不要把模块塞进 baseline.json 消红
   ```

5. 卡修好后：先跑默认验收确认该模块通过 → 测试会打印「可从 `baseline.json` 删除」→
   **删条目**（基线缩小）→ 再跑一次确认全绿。若新增了别的失败，回到第 1 步，不要调大基线。
