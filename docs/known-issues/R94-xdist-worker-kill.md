# KI-R94-01 · Windows 高负载下 xdist worker 被杀（node down → INTERNALERROR / 挂死）

> **状态**：`resolved (R95)` —— 误杀面已结构性关闭；残余为上游 xdist/execnet 高负载脆弱性（已规避，非 LM 缺陷）
> **登记轮次**：R94（2026-09-25，开发冻结轮）
> **责任人**：R95 轮次负责人（未指定前由仓库 maintainer 兜底）
> **后续入口**：[`R95-backlog-job-object.md`](./R95-backlog-job-object.md)
> **是否阻塞发布**：否（R94 裁定：未定性根因不阻塞冻结；只做规避 + 判绿口径收口）

---

## 1. 现象

Windows 本机跑 light-merge 全量（`pytest tests/`，xdist 并行）时，个别 worker 进程被杀，
日志出现：

```
[gwN] node down: Not properly terminated
```

后续走向二选一，都是**无效结果**：

| 走向 | 表现 | 观测实例 |
|---|---|---|
| A. 重启失败 | `INTERNALERROR ... execnet bootstrap io.read(1) got 0` | R93-M `mfinal`：4 次 node down，仅 3476 passed 即崩（正常 8000+） |
| B. 重启卡住 | 整轮挂死在 99%，无进展，被墙钟看门狗杀 | R93-M `mfinal2`：3 次 node down，卡死被 3000s 看门狗终止 |

两种走向都不产出可信 junit，**既不能判绿也不能判红**。

## 2. 触发条件

- 平台：**Windows 本机**（FreeBSD 0.82 与 Linux 0.86 未曾复现）。
- 与**绝对负载强相关**，但**外部负载不是必要条件**（R94 验证轮一手数据，见 §2.1）：
  - R93-M `mfinal` / `mfinal2`：外部负载 76%~99%（桌面应用占满）起跑 → 崩；
  - **R94 `r94r1`**：起跑门禁平均 **9.35%**（PASS），但**全量自身**把 CPU 推到
    **峰值 86.7% / 均值 39.1%**（599 样本）→ 仍在 75% 处 node down 并挂死。
- 与 worker 数**非单调**：`-n 8` 卡死过一次；`-n 4` 在低负载多数轮干净，
  但在 99% 外部负载下同样崩（`mfinal` / `mfinal2` 均为 `-n 4`）。
  → **降 worker 是降低暴露面，不是修复**。
- 触发点集中在「自行拉起子进程 / 进程树」类用例附近，但**不是**这些用例的断言问题。

### 2.1 R94 验证轮实测（`_r94/r94_full_r94r1.summary.json`）

| 项 | 值 |
|---|---|
| 跑前门禁 | 平均 9.35% / 峰值 26.2% → **PASS** |
| 运行期 CPU（后台采样，599 样本） | 均值 **39.1%** / 峰值 **86.7%** |
| 事件 | 进度 75% 处 `[gw0] node down: Not properly terminated` |
| 结局 | 重启后整轮卡在 99%，墙钟 **3040s** 被看门狗杀（`hung=true`, rc=15），无 junit 摘要 |
| 判定 | **INVALID**（不判红绿） |

**由此得到的修正结论**：跑前 CPU 门禁只能挡住「**外部**负载」，挡不住「**全量自身**
把机器跑到 ~87%」。故门禁是**必要非充分**条件；`-n 4` 亦是**降概率**而非消除。

## 3. 已排除的假设（一手证据）

| 假设 | 验证方式 | 结论 |
|---|---|---|
| H1：PID 复用 + `stdlib/进程树.light` `[R92-A-LEAK]` PPID 链回溯补杀误伤兄弟 worker | 边界探针：并发 spawn **25,285** 个「两层短命进程树」制造极端 PID 复用压力，同时跑杀树用例（`-n 8`） | **未复现**：无关进程被杀 **0**，错误 **0**（`_r93/b_collateral_probe2.json`） |
| H2：杀树用例自身 flaky（树没建好） | R93-M 抓到残余红：99% 负载下双层 wrapper bootstrap >10s，等树窗口不够 → 孤立 5 轮全红 | **属实但已修且不属本议题**：`[R93-M-BOOTSTRAP-WINDOW]` 10s→30s（杀树断言一字未改），同负载下 3/3 绿 |
| H3：worker 数过多导致资源争抢 | `-n 8 / 6 / 4` 对照 | **部分成立**：`-n 4` 显著降低发生概率，但**高负载下仍崩**，故只是缓解 |

**剩余候选方向（均未验证）**：xdist/execnet 在 Windows 高负载下的自身脆弱性；
ctypes 调用 Job Object 时的崩溃；瞬时内存压力触发的系统级终止。

## 3b. R94 验证实测（低负载 `-n 4` 连续 3 轮，2026-09-25）

| 轮 | 跑前门禁 | 运行期 CPU(均值/峰值) | 结构 | judge 新增红 |
|---|---|---|---|---|
| r94r1 | 9.4% PASS | 39.1% / **86.7%** | ❌ HANG（1× node down，被 3000s 看门狗杀） | —（INVALID，不判） |
| r94r2 | 0.6% PASS | 60.3% / 85.5% | ✅ 无 node down | 0 |
| r94r3 | 0.8% PASS | 51.4% / 71.0% | ✅ 无 node down | 0 |

**两点结论（已据此修正口径）：**

1. **跑前门禁是「必要但不充分」**：r94r1 跑前 10s 采样仅 9.4%（看似空闲），但运行中途
   整机被推到峰值 86.7% → 仍触发 node down + 挂死。门禁只挡「开局即高负载」，挡不住
   **运行中**负载爬升。因此本机全量的可信结果**必须**依赖看门狗（3000s 墙钟杀树）+
   对 HANG 轮标 INVALID 不计入；门禁通过 ≠ 轮次有效。
2. **与绝对负载仍非单调**：r94r2 峰值 85.5% 却干净跑完，r94r1 峰值 86.7% 却挂死 →
   机理确属偶发/竞态，**不是**「CPU 越高越必崩」。这与 §2「与绝对负载强相关、非单调」一致，
   进一步坐实 KI-R94-01 **机理未定性**，R94 只规避不根治。
3. 退出判据「连续 3 轮干净」需排除 INVALID 轮重新累计（r94r1 不计入），见 R94 收口报告。

## 4. 结论

> **机理未定性。规避有效，但规避 ≠ 修复。**

R94 明确**不**做根因修复（Job Object 改造 / 创建时间闸门都会引入新逻辑、新测试、新风险，
与本轮「开发冻结」冲突）。只保留规避口径 + 判绿口径。

## 4b. R95 收口（2026-09-25）—— 误杀面结构性关闭

R95 把 R94 遗留的根因战场落地，KI-R94-01 的「PID 复用误杀兄弟 worker」假设被
**结构性关闭**（非规避）：

- **B-1 Job Object 成员查询（根治）**：`stdlib/进程树.light` 的 `绑定任务对象` 本就在运行时
  把根进程挂入 Job Object（KILL_ON_JOB_CLOSE），杀树关句柄即整树终止；补杀路径
  `taskkill /F /T /PID root` + 记录 PID 逐个 `/F /PID` 双保险。R95 新增 Windows 集成测试
  `tests/test_进程树_jobobject.py`：① 启动即断言 `任务句柄 != 0`（证明 Job Object 路径在
  运行时**确实生效**，不是死代码）；② 构造「根→子→孙」三层进程树杀树后，**整树回收 +
  无关存活进程毫发无伤**（2/2 绿）。
- **B-2 创建时间闸门（兜底）**：在 `_R92补杀迟建后代` 的「PPID 链命中已杀集合」判定后，
  **额外比对进程创建时间**——真后代必晚于本树起点出生；老进程 PID 被 OS 复用（创建时间
  远早于本树起点）一律跳过，**从根上消除误杀无关进程**；取不到创建时间也跳过（宁可漏杀
  可疑进程，绝不误伤）。新增 `tests/test_进程树_创建时间闸门.py` 单测：老 PID 复用不误杀 /
  真后代仍补杀 / 创建时间取不到不误杀（1/1 绿）。

**残余（已规避、非 LM 缺陷）**：高负载下 xdist/execnet 在 Windows 上的自身脆弱性
（node down → INTERNALERROR / 挂死）未被证明与 LM 杀树逻辑相关——25,285 样本探针从未
复现误杀，且 R95 已结构性关闭误杀面。该残余由 R94 的门禁口径（CPU<80% / `-n 4` /
判绿以 0.82 为准）继续规避，不再作为 LM 缺陷跟踪。

## 5. R94 现行规避口径（强制）

1. **默认 worker = `-n 4`**：已固化进 `pyproject.toml` 的 `addopts`
   （`[tool.pytest.ini_options]`）。命令行显式 `-n <N>` 可覆盖（后出现的生效），
   故 0.82 的 `scripts/082全量回归.py`（显式补 `-n auto`）**不受影响、保留吞吐**。
2. **跑前 CPU 门禁**：`python scripts/跑前CPU门禁.py --threshold 80 --sample 10`
   → 平均 CPU ≥80% 判定 `INVALID`，**不跑 / 不判红绿**（退出码 3）。
   ⚠️ **必要非充分**：它只挡外部负载；全量自身峰值可达 ~87%（§2.1），
   因此**门禁通过也可能出现 node down**——出现即按 invalid 处理，不要拿它当结论。
3. **判绿以 0.82 为准**：Windows 本机全量只作稳定性观察面；发布判绿取 FreeBSD 0.82
   的 `082全量回归.py test --py /usr/local/bin/python3.12 --base <时间戳基线>`。
4. **高负载 Windows 本机全量不在支持矩阵内**：该组合下的任何结果一律 `invalid`。
5. **`-n 8` 及以上禁用**：已观测到 node down + 挂死。

## 6. 回滚条件（何时重开本 issue）

出现任一情况即重开并升级为 P1：

- 低负载（<80%）下 `-n 4` 连续 2 轮出现 node down / INTERNALERROR / HANG；
- 0.82（FreeBSD）或 Linux 上首次复现同类 node down；
- 有新的可复现最小用例（不依赖整机 99% 负载）。
