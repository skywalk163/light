# R95-B1 · Job Object 杀树根治实施方案

> **类型**：实施方案（供下一轮直接开工；本轮只出文档，不改代码）
> **关联**：[KI-R94-01](./R94-xdist-worker-kill.md) · [R95 backlog B-1](./R95-backlog-job-object.md)
> **依据**：`stdlib/进程树.light`（工作区 1009 行版本）逐段核对；Win32 官方文档（见附录 B）
> **状态**：草案，**未实现、未实测**。文中标「待验证」的条目必须在开工第一周用探针定性，不得凭推断动手
> **适用面**：Windows 10/11 x64 为主；Windows 7 / Server 2008 R2 只保留降级路径

## 0. 结论摘要

- **现场核对结论（与任务卡描述有差异）**：`进程树.light` 并非「没有 Job Object」。`绑定任务对象`（L341-418）在启动时已把根进程挂进 Job 并设 `KILL_ON_JOB_CLOSE`；但全文**没有** `QueryInformationJobObject`、**没有** `TerminateJobObject`，杀树主体仍是「Toolhelp32 快照 + 裸 PID `taskkill`」。
- **误杀的真凶不是 PPID 回溯，而是裸 PID 执行**：`记录` 里的 PID 在 L599-601 被直接 `taskkill /F /PID`，`等待树清`（L650-667）还会在最长 **4 秒**内反复对同一批 PID 补杀。枚举与执行之间的 TOCTOU 一旦撞上 PID 复用，就会杀掉无关进程；PPID 回溯只是把这个问题扩大到「迟建后代」窗口。
- **目标态**：杀树 = `QueryInformationJobObject(JobObjectBasicProcessIdList)` 拿成员 → `TerminateJobObject` → `CloseHandle`。成员由内核按对象身份维护，**不经过 PID 查找**，从结构上消除复用误杀。
- **开关**：配置项 `杀树引擎` / 环境变量 `LIGHT_KILL_TREE_ENGINE`，取值 `job | toolhelp | auto`；默认 `auto`（Win8+ 走 job，Win7 或任一步失败降级 toolhelp）。
- **前置门禁**：仓库注释（L556-559）称孙进程会 breakaway 逃出 Job，但按 Win32 文档，未设 `JOB_OBJECT_LIMIT_BREAKAWAY_OK` 时 `CREATE_BREAKAWAY_FROM_JOB` 不应生效——两者矛盾。§4.4 的归因探针不出结论，**不得删除旧路径**。

> 一句话：B-1 的增量不是「引入 Job Object」，而是**把杀树判定从 PID 数字换成 Job 成员身份**，并给这条新路径装上可回退的开关。

### 1.2 现场核对：Job 已有，但只做了一半

核对本文件全部 1009 行后，可以得到三个确定事实：

1. **Job 绑定确实存在且在运行时生效**：`CreateJobObjectW`（L383）、`SetInformationJobObject`（L393）、`LimitFlags = 8192`（L392，即 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）、`AssignProcessToJobObject`（L409）都在；`tests/test_进程树_jobobject.py` 也已断言 `任务句柄 != 0`。
2. **但杀树没有以 Job 成员为准**：`杀树` 的 Windows 分支先做两轮 Toolhelp32 枚举（L573-598），再按 `记录` 里的 PID 逐个强杀（L599-601），最后才关 Job（L608-613）。Job 在这里只是「最后一道保险」，不是「唯一事实来源」。
3. **成员查询与显式终止完全缺失**：全文没有 `QueryInformationJobObject`，也没有 `TerminateJobObject`；`绑定任务对象` 只负责「把根挂进去」，之后不再读 Job 的成员表。

> 因此 B-1 的正确表述是：**把「Job 仅兜底」升级为「Job 为唯一成员事实源 + 显式终止」，并把旧路径整体降级为开关后的回退分支**。这比「从零引入 Job Object」更准确，也能解释为什么 R95 已有 Job 绑定却仍有 §1.3 的误杀面。

### 1.3 PID 复用为什么会误杀兄弟进程

现有实现有四处把「PID 数字」当成「进程身份」，复用一旦发生就可能误伤。按危险程度排序：

1. **快照与执行分离（L599-601）**：`记录` 在 L584-598 由快照生成，真正 `taskkill` 在 L599 之后。中间还要跑完两轮枚举（最多 1.2s，L582）和第二次 `/T` 杀（L607）。这期间某个后代可能已经退出，PID 被 OS 分配给并发 pytest worker 刚 spawn 的子进程；`taskkill /F /PID` 只认数字，直接杀掉无辜者。
2. **4 秒补杀循环（L650-667）**：`等待树清` 的截止是 `now + 4000ms`（L651），每 50ms 对 `记录` 中每个 PID 做一次 `OpenProcess`，成功就补一记 `taskkill`（L657）。这把「快照 PID 集合」的打击窗口从毫秒级拉长到 4 秒，PID 复用概率随并发度显著放大。**这是本文件里最长的裸 PID 打击窗口。**
3. **`已杀键` 被污染（L753-757、L810）**：`已杀键` 用 PID 字符串建集合；L810 每杀一个就把新 PID 并入。若某个数字已被复用，后续轮次会把「复用者的子进程」也当成树的后代（L785 链命中），形成级联误杀。
4. **创建时间闸门只挡老进程（L758-761、L799-806）**：闸门拒绝「创建时间早于本树起点 5s 以上」的进程，保护的典型是「PID 被复用给一个早就在跑的老进程」。但并发 worker 新 spawn 的子进程创建时间晚于本树起点，闸门**放行**。所以 B-2 不能替代 B-1：它降低老进程误杀，不解决「裸 PID 执行 + 新生兄弟进程」这一类。

**为什么 Job 成员身份能根治**：Job 的成员关系由内核对象引用维护；`QueryInformationJobObject` 返回的是「查询时刻仍在 Job 内的 PID」，`TerminateJobObject` 终止的是「当前成员」，即使某个成员刚退出、PID 立刻被复用，复用者也不是成员，不会被连带终止。关键纪律是：**Query 拿到的 PID 只能用于诊断/断言，不能再喂给 `taskkill`**（否则 PID 复用风险原样回来）。

### 1.4 影响面与不主张

- 现有 `tests/test_进程树_jobobject.py` 只有 1 轮三层树用例，能证明「Job 绑定生效 + 单次回收」，但**不能**证明 100 轮、25k 压力、降级路径、开关切换下的行为。
- R94 §3 的 25,285 样本探针**未复现**误杀（无关进程被杀 0）。本方案不主张「已证实 KI-R94-01 由 PID 复用导致」，只主张：**这是杀树路径上唯一无法用测试穷尽的身份混淆风险，Job 成员制能从结构上消除它**。KI-R94-01 的机理仍未定性（R94 §4）。
- 改造只动 Windows 分支；POSIX `os.killpg` 路径（L621-641）不碰，非 win32 全部 skip。

## 2. Windows API 清单

### 2.1 四个 API 的职责与调用位置

| API | DLL | 作用 | 本方案中的位置 | 失败返回 |
|---|---|---|---|---|
| `CreateJobObjectW` | kernel32 | 创建匿名 Job 对象，返回句柄（含 `JOB_OBJECT_ALL_ACCESS`） | 启动时一次；每个 `进程树` 实例独立一个 Job | `NULL` |
| `AssignProcessToJobObject` | kernel32 | 把根进程挂进 Job；之后其子进程默认继承 | 根进程 `CREATE_SUSPENDED` 期间、恢复前 | 0；`GetLastError()` 取原因 |
| `QueryInformationJobObject(JobObjectBasicProcessIdList)` | kernel32 | 读 Job 当前成员 PID 列表 | 杀树前（诊断/断言）、`Terminate` 后确认清空 | 0 |
| `TerminateJobObject` | kernel32 | 显式终止 Job 内全部进程（含子 Job），等价于对每个成员 `TerminateProcess` | 杀树主操作；替代「按 PID `taskkill`」 | 0 |
| `CloseHandle` | kernel32 | 关 Job 句柄，触发 `KILL_ON_JOB_CLOSE` 兜底 | `Terminate` 之后；所有失败路径也要关 | 0 |

> 说明：`CreateJobObjectW` + `SetInformationJobObject(KILL_ON_JOB_CLOSE)` 在现文件已存在（L383、L393），本方案复用；新增面只有 `Query` 与 `Terminate`。

### 2.2 调用时序

**启动（一次性）**

| 步 | 调用 | 关键参数 | 失败处理 |
|---|---|---|---|
| 1 | `Popen(..., creationflags=0x204)` | `CREATE_SUSPENDED` + `CREATE_NEW_PROCESS_GROUP` | 启动失败 → `开动故障`（现状 L324-327） |
| 2 | `CreateJobObjectW(NULL, NULL)` | 匿名，不具名 | 恢复挂起进程，`任务句柄=0`，降级 |
| 3 | `SetInformationJobObject` | class=9，`LimitFlags=0x2000` | 关 Job，恢复进程，降级 |
| 4 | `OpenProcess(0x0D01, FALSE, root_pid)` | `TERMINATE` + `SET_QUOTA` + `QUERY_INFORMATION` + `SUSPEND_RESUME` | 关 Job，恢复进程，降级 |
| 5 | `AssignProcessToJobObject(hJob, hProc)` | — | 关 Job + 关进程句柄，恢复进程，降级 |
| 6 | `NtResumeProcess(hProc)` | — | **无论 5 成败都必须调用**，否则根进程永久挂起 |
| 7 | `CloseHandle(hProc)`；成功则保存 `任务句柄` | — | — |

> 顺序可以保持现状（先 Popen 再 Create Job）：根进程处于 suspended，不会在 2~5 之间 spawn 后代，因此不存在「绑定前已逃逸」窗口。若要更保守，可把 2~3 提到 1 之前，但收益有限，且要处理 Popen 失败后的 Job 泄漏，建议保持现状。

**杀树（引擎 = job）**

| 步 | 调用 | 目的 | 备注 |
|---|---|---|---|
| 1 | `QueryInformationJobObject(hJob, 3, buf, len, &ret)` | 取成员 PID，写日志/供测试断言 | **只读，不用于杀** |
| 2 | `TerminateJobObject(hJob, 0xDEAD)` | 显式终止全部成员 | 退出码用非 0，避免与正常退出混淆 |
| 3 | 再 Query 一次（最多 500ms，50ms 间隔） | 确认成员数归零 | 若 `Terminate` 失败，此步可跳过 |
| 4 | `CloseHandle(hJob)`；`任务句柄=0` | `KILL_ON_JOB_CLOSE` 兜底 | 即使 `Terminate` 返回 0 也必须关 |
| 5 | `等待到死(宽限期)`（现状 L958-968） | 等根进程 `poll()` 非空 | 保留 |
| 6 | **不调用** `等待树清`、**不调用** `_R92补杀迟建后代` | 消除全部裸 PID 杀 | 这是 B-1 的核心收益 |

> 第 3 步的意义：`TerminateJobObject` 是同步语义（文档称「如同对每个进程调用 `TerminateProcess`」），理论上返回后成员已终止；保留一次短轮询是为了拿证据，而不是为了「多杀几次」。若 `Terminate` 返回 0 且 `GetLastError=5`（权限不足），第 4 步的关句柄仍可能由内核完成整树终止（`KILL_ON_JOB_CLOSE` 不依赖调用方的每进程 `PROCESS_TERMINATE`，**待验证**），因此关句柄不能省。

### 2.3 ctypes 签名草案

以下为 Python 侧草案；落到 `stdlib/进程树.light` 时需按光明语法改写（`设`/`如果`/`结束`，结构体用 `type()` 动态构造，参见现文件 L360-382）。

```python
import ctypes

k = ctypes.windll.kernel32

# 句柄一律 c_void_p：默认 c_int 会在 x64 截断高 32 位（R91-D-voidp 已踩过）
k.CreateJobObjectW.restype = ctypes.c_void_p
k.CreateJobObjectW.argtypes = [ctypes.c_void_p, ctypes.c_wchar_p]

k.SetInformationJobObject.restype = ctypes.c_int
k.SetInformationJobObject.argtypes = [
    ctypes.c_void_p, ctypes.c_int, ctypes.c_void_p, ctypes.c_uint32,
]

k.AssignProcessToJobObject.restype = ctypes.c_int
k.AssignProcessToJobObject.argtypes = [ctypes.c_void_p, ctypes.c_void_p]

k.QueryInformationJobObject.restype = ctypes.c_int
k.QueryInformationJobObject.argtypes = [
    ctypes.c_void_p, ctypes.c_int, ctypes.c_void_p,
    ctypes.c_uint32, ctypes.POINTER(ctypes.c_uint32),
]

k.TerminateJobObject.restype = ctypes.c_int
k.TerminateJobObject.argtypes = [ctypes.c_void_p, ctypes.c_uint]

k.CloseHandle.restype = ctypes.c_int
k.CloseHandle.argtypes = [ctypes.c_void_p]

k.GetLastError.restype = ctypes.c_uint32
k.GetLastError.argtypes = []
```

结构体（容量按需扩容，`容量` 是编译期常量或每次重建）：

**尺寸断言（开工第一件事）**：

- x64：`ctypes.sizeof(扩展) == 144`（现文件 L357 注释也是 144）；`ctypes.sizeof(ID列表) == 8 + 8 * 容量`。
- 32 位不适用上述数字，按 `ctypes.sizeof(ctypes.c_void_p)` 分支断言；本项目 Windows 侧以 x64 为主。
- 断言失败即停止实施，先修结构体布局；布局错会读出垃圾 PID，比不杀更危险。

### 2.5 已知坑（必须写进实现注释）

1. **`restype` / `argtypes` 必须显式声明**。`CreateJobObjectW`、`OpenProcess` 返回 64 位句柄，默认 `c_int` 会截断；现文件 L350-355、L384-385 已记录 [R91-D-voidp] 的两次踩坑。
2. **`GetLastError()` 要立刻取**。失败调用与 `GetLastError` 之间不能再插任何 ctypes 调用，否则错误码可能被覆盖；建议封装 `调用后立即取错误码` 的小函数。
3. **`ProcessIdList` 必须是 `c_size_t`（`ULONG_PTR`）**，不是 `c_uint32`。用错会导致 x64 上元素间距 4 字节、PID 全部错位。
4. **缓冲截断不能当全量**：`NumberOfAssignedProcesses` 是「应存数量」，`NumberOfProcessIdsInList` 是「实际返回」。后者小于前者 = 截断，必须按前者扩容重查（建议 `容量 = 已分配 + 8`，最多重试 3 次）；仍截断则记录 `[R95-B1-TRUNC]` 并降级，不得拿半张表去杀。
5. **不要给 Job 命名**。匿名 Job 不会被同机其它进程 `OpenJobObject` 打开；一旦被外部持有一个句柄，`KILL_ON_JOB_CLOSE` 的「最后一个句柄关闭」语义就可能不触发。
6. **`TerminateJobObject` 的 `uExitCode` 用非 0**（建议 `0xDEAD`）。测试若断言 `退出码 != 0`，用 0 会自相矛盾。
7. **`CloseHandle` 只能调一次**。杀树与析构都可能走到关闭逻辑，必须用「单 owner + 置 0」防重复关；重复关一个已复用的句柄值是灾难性的。
8. **`QueryInformationJobObject` 传 `hJob=NULL` 的语义是「查调用者自己的 Job」**，不是「查任意 Job」。本方案必须传自己的 `任务句柄`，不要图省事传 NULL。

## 3. 与现有路径的共存 / 切换开关

### 3.1 开关定义

| 项 | 设计 |
|---|---|
| 配置键 | `杀树引擎`（沿用现有中文键风格：`宽限期毫秒`、`空闲超时毫秒`、`编码`） |
| 环境变量 | `LIGHT_KILL_TREE_ENGINE`（大小写不敏感，读取后 `strip().lower()`） |
| 取值 | `job` / `toolhelp` / `auto`（未识别值按 `auto` 处理并记警告） |
| 优先级 | 配置键 > 环境变量 > `auto` |
| 作用域 | 每个 `进程树` 实例独立解析；不做进程级全局缓存，避免测试之间互相污染 |

### 3.2 取值语义

| 值 | 行为 | 典型用途 |
|---|---|---|
| `job` | 强制新路径。绑定失败时仍走旧路径，但 `降级原因` 必须非空；正常环境下的测试断言它为**空**（「强制 job 却降级」即测试失败） | 新路径验收、CI 强制门禁 |
| `toolhelp` | 强制旧路径（L573-620 原逻辑），完全不碰 `Query` / `Terminate` | 紧急回滚、A/B 对照 |
| `auto` | Win8+ 且 `任务句柄 != 0` → `job`；否则 `toolhelp` | 默认值，灰度 |

### 3.3 默认值建议与理由

**建议默认 `auto`**，而不是 `job` 或 `toolhelp`：

- 默认 `job` 的风险：Win7/2008 R2 不支持嵌套 Job，若 pytest 进程本身已在某个 Job 内（CI runner、任务计划、部分终端/沙箱），`AssignProcessToJobObject` 会直接失败（`ERROR_ACCESS_DENIED`），等于把「能杀」变成「绑定失败」；`auto` 让这类环境自动留在旧路径。
- 默认 `toolhelp` 的问题：旧路径正是要修的对象，默认旧路径等于 B-1 不生效，日常回归也覆盖不到新代码，缺陷会攒到强制 `job` 的验收轮才爆。
- `auto` 的失败是**可见**的：`降级原因` 非空即为一条结构化证据，可统计分布，再决定是否扩大 `job` 的适用范围。
- 灰度策略：合入时默认 `auto`；首周统计 `降级原因`，若 `assign:` 前缀占比 >1%，先查调用方环境（是否在 Job 内、是否 Win7），不要用改默认值来掩盖问题。

### 3.4 开关读取与选路草案（光明伪代码）

```text
段落 杀树引擎():
  设 指定 为 己.配置.get("杀树引擎", 空)。
  如果 指定 等于 空:
    指定 为 os.environ.get("LIGHT_KILL_TREE_ENGINE", "auto")。
  结束。
  设 名 为 str(指定).strip().lower()。
  如果 名 等于 "job" 或 名 等于 "toolhelp":
    返回 名。
  结束。
  返回 "auto"。

段落 选引擎():
  设 名 为 己.杀树引擎()。
  如果 名 等于 "toolhelp":
    返回 "toolhelp"。
  结束。
  如果 sys.platform 不等于 "win32":
    返回 "toolhelp"。
  结束。
  设 版 为 sys.getwindowsversion()。
  如果 版.major 小于 6 或 (版.major 等于 6 且 版.minor 小于 2):
    己.降级原因 为 "os_too_old"。
    返回 "toolhelp"。       # Win7 及更早：不支持嵌套 Job
  结束。
  如果 己.任务句柄 等于 空 或 己.任务句柄 等于 0:
    如果 名 等于 "job":
      己.降级原因 为 "forced_job_but_not_bound"。
    结束。
    返回 "toolhelp"。       # auto：绑定失败即降级
  结束。
  返回 "job"。
```

**建议新增的可观测属性**（实现时加在 `进程树` 上，测试与日志都依赖）：

| 属性 | 含义 |
|---|---|
| `杀树引擎配置` | 解析后的开关值（`job`/`toolhelp`/`auto`） |
| `引擎实际` | 本次实际走的路径（`job`/`toolhelp`） |
| `降级原因` | 空串表示未降级；否则为 `os_too_old` / `create_job:<err>` / `set_info:<err>` / `assign:<err>` / `open_proc:<err>` / `query:<err>` / `terminate:<err>` |
| `Job成员数` | 最近一次 Query 的 `NumberOfProcessIdsInList`（无则 0） |

### 3.5 可观测性

每次杀树至少落一条结构化记录（测试可直接读，不必依赖日志框架）：

```json
{"ts": "...", "engine": "job", "degraded": "", "members": 3,
 "terminate_ok": 1, "get_last_error": 0, "elapsed_ms": 12}
```

建议路径：`_r96/kill_engine.jsonl`（与 R94 探针目录同风格）。该文件不是产品运行时依赖，只作验收证据。

## 4. Job 嵌套与权限评估

### 4.1 版本差异

| 平台 | 嵌套 Job | `AssignProcessToJobObject` 对「已在 Job 内」的进程 | 本方案行为 |
|---|---|---|---|
| Windows 8 / Server 2012+（6.2+） | 支持；进程可属于多个 Job，形成父子层级；子进程默认加入整条链 | 允许（Job 需为空或处于已有 Job 的嵌套链上） | 走 `job` |
| Windows 7 / Server 2008 R2（6.1） | 不支持；一个进程只能属于一个 Job | 失败，`GetLastError = ERROR_ACCESS_DENIED(5)` | 走 `toolhelp` |
| Vista / 2003 | 同 Win7 | 同 Win7 | `toolhelp`；是否仍在支持面**待验证** |

补充（Win8+）：`TerminateJobObject` 会连带终止子 Job；`JobObjectBasicProcessIdList` 返回的是「本 Job + 其子 Job」的全部进程。因此若调用方把我们的 Job 再嵌进更大的 Job，终止范围仍以我们的 Job 为根，不会向上波及父 Job 的其它进程。

### 4.2 「进程已在别的 Job 里」的四种情形

| 情形 | 现象 | 处理 |
|---|---|---|
| A. pytest 进程自己在上层 Job 内（CI runner / 任务计划 / 沙箱） | root 创建时自动继承上层 Job | Win8+：再 `Assign` 到我们的 Job 形成嵌套，可正常终止；Win7：`Assign` 失败 → `auto` 降级 |
| B. 我们的 Job 里已有进程（实例复用/重入） | 文档要求 Job 为空或处于嵌套链上，否则 `Assign` 可能失败 | 每个 `进程树` 实例独立 `CreateJobObject`，禁止跨实例复用（现实现符合） |
| C. Job 正在 terminating | `Assign` 失败（文档明确） | 记录 `assign:<err>`，关 Job，降级旧路径 |
| D. 目标进程是更高完整性级别（管理员/系统进程） | `OpenProcess(0x0D01)` 或 `TerminateJobObject` 可能 `ACCESS_DENIED` | 记录错误；先 `CloseHandle` 触发 `KILL_ON_JOB_CLOSE` 兜底（**待验证**），再降级 `taskkill`（多半同样失败，需在日志中明确「无法终止」而不是静默成功） |

### 4.3 所需权限清单

| 操作 | 需要的权限 | 现状 | 失败表现 |
|---|---|---|---|
| `CreateJobObjectW` | 无特殊；返回句柄含 `JOB_OBJECT_ALL_ACCESS` | 已满足 | `NULL` |
| `SetInformationJobObject(KILL_ON_JOB_CLOSE)` | Job 句柄的 `JOB_OBJECT_SET_ATTRIBUTES`（`ALL_ACCESS` 覆盖） | 已满足 | 0 |
| `AssignProcessToJobObject` | `hJob` 的 `JOB_OBJECT_ASSIGN_PROCESS`；`hProcess` 的 `PROCESS_SET_QUOTA` + `PROCESS_TERMINATE` | L401 的 `0x0D01` 已含这两项 | 0；常见错误码 5 |
| `QueryInformationJobObject` | `hJob` 的 `JOB_OBJECT_QUERY` | `ALL_ACCESS` 覆盖 | 0 |
| `TerminateJobObject` | `hJob` 的 `JOB_OBJECT_TERMINATE`；文档还要求「Job 内每个进程句柄有 `PROCESS_TERMINATE`」 | 子进程句柄未显式持有；是否影响终止**待验证** | 0；是否部分终止**待验证** |
| 手动兜底 `OpenProcess`（仅 hybrid） | `PROCESS_TERMINATE`（`0x0001`） | — | 0 / 5 |

> 关键判断：`TerminateJobObject` 的权限语义必须在 Step 0 用探针确认（§6 待验证清单）。若它因某个高权限成员整体失败，则 `CloseHandle` + `KILL_ON_JOB_CLOSE` 是唯一可靠兜底；两者都失败时应显式报「未能终止」，不能让 `杀树` 返回成功。

### 4.4 breakaway 归因（Step 0，必须先做）

**已知事实 A（仓库）**：L556-559 注释 + 2026-09-03 实测称「Job 内仅根进程；关 Job 后孙进程仍存活」，归因为「Python 的 `subprocess.Popen` 检测到父进程在 Job 内，会自动加 `CREATE_BREAKAWAY_FROM_JOB`」。

**已知事实 B（文档）**：`CREATE_BREAKAWAY_FROM_JOB` 要求 Job 设置 `JOB_OBJECT_LIMIT_BREAKAWAY_OK`；而当前 L392 只设了 `0x2000`（`KILL_ON_JOB_CLOSE`），没有 `0x0800` 也没有 `0x1000`。

**矛盾**：若 A 的归因成立，按事实 B，子进程创建应当失败（或至少不能逃逸）；但实测孙进程确实存在。三种可能，必须用探针区分：

| 可能 | 含义 | 对方案的影响 |
|---|---|---|
| P1 | CPython 并未自动加 flag；逃逸另有机制（上层 Job 嵌套、句柄生命周期、观测口径） | 纯 `job` 模式可能已足够，先修正归因再谈 hybrid |
| P2 | flag 被忽略，子进程实际仍在 Job 内；「Job 内仅根进程」是观测错误 | 纯 `job` 模式可行，旧路径可退居降级 |
| P3 | 目标程序自己 breakaway（被测程序行为，与本模块无关） | 与本模块无关，但测试需排除这类用例 |

**探针设计（`_r96/a_breakaway_probe.py`）**：

1. 用 `进程树` 启动 root（Python），root spawn child，child spawn grandchild，各 sleep 20s。
2. 对 root/child/grandchild 分别调 `IsProcessInJob(pid, NULL, &结果)`（`NULL` 表示「是否在任一 Job」，**待验证**），再用 `QueryInformationJobObject` 取本 Job 成员，两路比对。
3. A/B 对照：临时给 Job 加 `JOB_OBJECT_LIMIT_BREAKAWAY_OK` 再跑一遍，看成员集合差异（只用于归因，**不得**进入产品路径）。
4. 记录 Windows 版本、Python 版本、`inspect.getsource(subprocess)` 中 `CREATE_BREAKAWAY_FROM_JOB` 的出现位置。
5. 结论写入 `_r96/a_breakaway_result.md`，作为「纯 job / hybrid」的准入依据。

**判定**：P2 → 纯 `job` 模式，删除杀树路径上的全部裸 PID 操作；P1 → 先修正归因并解释成员表差异，再决定纯 `job` 还是 hybrid（默认仍按纯 `job` 设计，但不得删除旧路径）；P3/真逃逸 → 只能 hybrid（§4.5），且 B-1 的收益要下调为「缩小而非清零 PID 杀」。

### 4.5 混合模式（仅当真逃逸，默认关闭）

- 杀前枚举（复用 L584-598）**只用于找出可能逃逸的 PID**，不用于杀。
- `TerminateJobObject` 后，仅对这些 PID 做「创建时间闸门 + 立即 `taskkill`」，**只做一轮**；不做 4s 轮询。
- 每轮重新取创建时间，与预期窗口不符即剔除；取不到创建时间也剔除（宁可漏杀可疑进程，不误伤）。
- 记录 `hybrid_hits`；若每轮都 >0，说明 Job 没兜住，应回到 §4.4 重新归因，而不是继续加补杀轮次。
- 该模式仍需开关（建议 `杀树引擎=hybrid`），默认不启用；原因：它把 §1.3 的 TOCTOU 风险重新引入，只是窗口比现状短。

### 5.1 现有覆盖与缺口

### 5.2 验收标准 A：单层/多层树 100 轮 0 漏杀

| 用例 | 设计 | 轮次 | 判定 |
|---|---|---|---|
| A1 单层 | root 跑 `sleep 30`；启动后 50ms 杀树 | 100 | root 在 3s 内 `能打开 == 假`；哨兵进程全程存活 |
| A2 三层 | root→child→grandchild（各 sleep 30）；杀前用 `枚举后代` 记录期望 PID（**只读**） | 100 | root + 全部期望 PID 在 3s 内 gone；哨兵存活 |
| A3 迟建 | child 每 50ms spawn 一个 200ms 短命孙进程，持续 2s；在 100–800ms 随机时刻杀 | 100 | 杀后 1s 内轮询进程表，不存在「PPID ∈ 本树已记录集合」的新进程 |
| A4 降级 | monkeypatch `AssignProcessToJobObject` 返回 0 | 20 | `任务句柄=0`、`降级原因` 非空、A2 仍整树回收 |
| A5 开关 | 同一台机分别 `toolhelp` / `job` / `auto` | 各 10 | `auto` 在 Win10 上 `引擎实际=job`；`toolhelp` 不调用 Query/Terminate |

**漏杀定义**：`杀树` 返回后 3s 仍 `能打开(pid)==真`。**误杀定义**：哨兵或任何未参与本树的进程被杀。
**失败留存**：任一用例失败即保存「引擎、降级原因、期望 PID、实际存活 PID、Job 成员数、GetLastError」。

### 5.3 验收标准 B：≥25k 短命树 PID 复用压力下无关进程被杀数 = 0

- **复用 R94 §3 H1 的探针口径**：`_r93/b_collateral_probe2.py`，并发 spawn **25,285** 个「两层短命进程树」，同时跑 A1/A2；建议 `-n 8`（与 R93 探针一致）。这是**定向探针**，不违反 R94「全量禁用 `-n 8`」的口径。
- **必须证明压力真实发生**：采样 `(pid, 创建时间)`，统计「同一 PID 出现两次且创建时间不同」的事件数。事件数 = 0 → 本轮 **INVALID**（压力不够），加 spawn 数或并发重跑，**不得直接判绿**。
- **判定**：无关进程被杀 = 0；杀树错误 = 0；漏杀 = 0；PID 复用事件 > 0；单次杀树 p99 ≤ 2s（调用方现有 0.8s 等待 + 3s 死亡确认窗口，p99 超 2s 即视为回归）。
- **证据**：`_r96/b_collateral_job.json`（样本数、复用计数、误杀数、p50/p99、引擎与降级分布）。

### 5.4 验收标准 C：全量 `-n 4` 低负载 3 轮无 node down

- **命令**：Windows 本机 `python -m pytest tests/ -n 4`；跑前 `python scripts/跑前CPU门禁.py --threshold 80 --sample 10`；3000s 墙钟看门狗。
- **有效轮**：无 node down、无 `INTERNALERROR`、无 HANG、产出 junit；否则 **INVALID**，不计入连续 3 轮（严格沿用 R94 §3b 口径）。
- **判定**：连续 3 个有效轮内 node down 总数 = 0，且 judge 对比基线「新增红 = 0」。出现 1 轮 INVALID → 补跑；**出现 2 个有效轮 node down → 失败**，不是「再跑几次看看」。
- **辅助记录**：运行期 CPU 均值/峰值（R94 已证明跑前门禁不充分），只作归因材料，不作判绿条件。
- **证据**：`_r96/full_r96r{1..3}.summary.json` + junit。

### 5.6 回归与反例

- **R1 强制 `toolhelp`**：A1/A2 各 10 轮仍绿，证明回退可用。
- **R2 注入 Assign 失败**：同 A4；重点是「降级后仍能整树回收」，不是「降级成功」本身。
- **R3 注入 Query 失败/截断**：返回 0 或 `NumberOfProcessIdsInList < NumberOfAssignedProcesses`；不得误杀、不得死循环，`降级原因` 可见。
- **R4 非 Windows**：全部 skip；POSIX `os.killpg` 用例不受影响（现有 CI 矩阵）。
- **R5 并发杀树**：同一进程内 4 个 `进程树` 实例同时杀，句柄不串、哨兵存活（验证 §6 的单 owner 设计）。
- **R6 开关非法值**：`LIGHT_KILL_TREE_ENGINE=JOB `（大写+空格）应解析为 `job`；`bogus` 应回落 `auto` 并记警告，不得抛异常。

## 6. 风险与回滚

### 6.1 新增风险

| # | 风险 | 触发条件 | 影响 | 缓解 / 检测 |
|---|---|---|---|---|
| R1 | ctypes 句柄截断 / 结构体错位 | `restype`/`argtypes` 漏设、`ProcessIdList` 用错类型 | 读到垃圾 PID 或崩溃（access violation） | 显式声明 + 启动期 `sizeof` 断言 + 探针脚本先跑 |
| R2 | Query 缓冲不足 | 成员数 > 容量（默认 256） | 成员表截断 → 若误当全量会漏杀 | 按 `NumberOfAssignedProcesses` 扩容重查（最多 3 次），仍截断则记录并降级 |
| R3 | `TerminateJobObject` 权限不足 | Job 内有高完整性进程 | 返回 0，部分或全部未终止 | 立即 `CloseHandle` 兜底（待验证）；仍失败则显式报错，不返回成功 |
| R4 | 后代 breakaway 逃逸 | §4.4 的 P3 | 漏杀（比误杀更隐蔽） | Step 0 归因；真逃逸才启用 hybrid；日志记 `hybrid_hits` |
| R5 | 句柄重复关闭 / 跨线程竞争 | 杀树与析构并发、`启动` 失败路径 | 关错句柄、Job 泄漏或进程被误杀 | 单 owner + 置 0 + 实例内锁；所有失败路径统一走「关闭并置 0」 |
| R6 | 上层 Job 的限额干扰 | 调用方 Job 设了 `ActiveProcessLimit` / 内存上限 | `Assign` 失败或子进程被上层 Job 杀 | `auto` 降级 + `降级原因`；文档提示 CI 环境检查 |
| R7 | `KILL_ON_JOB_CLOSE` 被外部句柄拖住 | 有人 `OpenJobObject` 持有句柄 | 关句柄不触发整树终止 | Job 匿名（不具名）；不导出句柄；不设 `bInheritHandle` |
| R8 | 新路径性能回归 | Query/Terminate 本身很慢 | 杀树超过调用方 3s 确认窗口 | 记录 `elapsed_ms`；p99 门禁 ≤2s；超时降级旧路径并告警 |
| R9 | 把 Query 结果再喂 `taskkill` | 实现者「顺手」补杀 | PID 复用风险原样回归，B-1 收益归零 | 代码评审硬门禁：`job` 路径禁止出现 `taskkill /F /PID` |

### 6.2 回滚步骤

1. **热回滚（无需改代码/重装）**：设 `LIGHT_KILL_TREE_ENGINE=toolhelp`（或配置 `杀树引擎=toolhelp`），重启 pytest 进程；确认 `引擎实际=toolhelp`。
2. **验证回滚生效**：跑 A1/A2 各 10 轮 + R1；确认 `任务句柄` 仍可非 0（绑定逻辑保留），但杀树走旧路径。
3. **代码回滚**：`git revert <R95-B1 commit>`（只回滚 `stdlib/进程树.light` 与新增测试；`B-2` 创建时间闸门与既有 `test_进程树_jobobject.py` 保留）。
4. **若 ctypes 导致解释器崩溃**（access violation / 0xC0000005）：先做第 1 步禁用新路径，再回滚代码；保留 WER dump 与 `_r96/kill_engine.jsonl`，不要在同一进程里反复重试。
5. **回滚后必跑**：A1/A2 100 轮 + 一次全量 `-n 4`（观察面，按 R94 口径判 INVALID/有效）；确认没有把旧路径改坏。
6. **状态清理**：本方案无持久化状态；Job 句柄随进程退出释放；无需迁移数据或清缓存。

### 6.3 什么情况下应启用 B-2 而非继续 B-1

| 条件 | 选择 | 理由 |
|---|---|---|
| Step 0 证明逃逸不可消除（P3），或必须支持 Win7 | **B-2 为主** | Job 无法覆盖整树，hybrid 仍要按 PID 杀，B-1 的「清零 PID 杀」收益不成立 |
| 残留误杀只是「老进程 PID 复用 + stale PPID」 | **B-2 已足够**（已落地 L758-806） | 创建时间闸门正是为这一类设计；再上 Query/Terminate 是重复建设 |
| 主要风险是「快照→taskkill 的 TOCTOU」与 4s 补杀窗口 | **B-1** | B-2 对新出生的无关进程无效（§1.3 第 4 条） |
| KI-R94-01 最终证明与杀树无关（xdist/execnet 自身） | **都不做** | 回到 R94 的规避口径，不为未定性机理扩大 ctypes 面 |
| 轮次预算不足 / 处于冻结窗口 | **B-2** | 零新增 ctypes；B-1 属功能改造，须独立轮次、独立门禁（backlog 明确） |

### 6.4 停止条件（出现即停，不硬推）

- Step 0 的 `IsProcessInJob` / `Query` 探针无法稳定复现「成员表 == 实际树」，且原因不明；
- `TerminateJobObject` 在目标 Windows 版本上出现「返回成功但仍有成员存活」；
- 任何一次 ctypes 调用导致解释器崩溃，且无法在 1 天内定位到具体签名/结构体；
- A1/A2 在 `job` 模式下漏杀率 >0 且 hybrid 也无法收敛。

> 停止后按任务规则写清阻塞点与下一步，不在同一轮里反复「调参试运气」。
