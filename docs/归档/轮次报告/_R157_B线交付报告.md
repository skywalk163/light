## 一、门禁设计与理由

### 1.1 要堵的洞
R153 的 `tests/test_R153_顶层collect门禁.py` 只挡**模块级** ImportError（collect-only，rc≠0 即红），其文档字符串明文登记了一个更深的洞：

> 函数内 ImportError 若发生在 `pytest.mark.xfail(strict=False)` 用例里，会被**吞成 xfail**，
> 即使顶层真跑起来也不红。

**本文件（B 线）= 那个「下一档」门禁。**

### 1.2 三层动作（无硬编码清单，全部动态）
1. **动态枚举**：AST 扫描 `tests/` 顶层全部 xfail 构造——
   - 声明式 `@pytest.mark.xfail(...)` 装饰的用例；
   - 命令式 `pytest.xfail(...)` 调用所在用例（辅助函数里的调用解析到同文件测试调用方）；
   - 静态吞点：`pytest.xfail()` 位于 `except (ImportError|ModuleNotFoundError|NameError|Exception)` 内（见 §四 吞点）。
2. **动态执行**：对枚举节点跑 `pytest --runxfail`（xfail 标记/命令式调用全部失效，用例按普通用例真跑，失败如实报 failed）。**判定必须动态，不许只扫不跑。**
3. **失败二分类**：
   - `ImportError` / `ModuleNotFoundError` / `cannot import name` / 收集错 = **门禁红**（正是要堵的洞，无欠账通道）；
   - 断言 / 语义 / 环境类失败 = **合法 xfail**，但必须登记进 `_已知欠账`（过期自动红，R153 体例）。

### 1.3 子进程跑法（含一条本机实测约束）
子命令**继承 pyproject addopts**（`--timeout=60 -n 4 --dist=loadscope`），并显式追加 `--timeout=300`（后置覆盖 60，遵守 R152-C2「逐例提限、不动全局」纪律）。

> ⚠️ 为什么不清空 addopts 跑串行：本机 Windows 沙箱实测，python 父进程嵌套一个**串行** pytest 子进程执行 `tests/` 用例会触发进程树 SIGTERM（与用例轻重无关，探针 G 实证）；继承 xdist（`-n 4`）后编译/执行落在 worker，父子树可正常存活。真实机（0.82/0.86）无此限制；若某台机器嵌套 xdist 资源紧张，可用环境变量 `R157B_CHILD_WORKERS=<n>` 覆盖子进程并发度。

### 1.4 边界（明确不做什么）
- 不跑顶层**非 xfail** 用例（「顶层全套真跑」属 E 线候选）；
- 不改 / 不删任何现有 xfail marker（只诊断 + 登记，修不修由业主裁）；
- 不覆盖 `tests/unit/` 下的 xfail（常规回归地盘，本轮登记不扩 scope）。

### 1.5 门禁自测（8 个用例，均 PASSED）

## 七、新发现（需业主裁定 / 关注的未决点）

### 7.1 要堵的洞目前是「空」的——但门禁必须留下
22 节点 --runxfail 真跑后 **0 个 import 类失败**。即 R153 文档描述的「函数内 ImportError 被 xfail 吞成 xfail 不可见」在当前代码库并未活现。B 线价值不在「修一个现红」，而在**永久守住此洞不再复现**——任何未来把 import 类失败藏进 xfail 的提交，将被本门禁在 CI 拦截。

### 7.2 D9 跨平台分叉（疑真实缺陷，Windows 特异性）
`test_path_guard_light.py::Test对抗用例_D9::test_链接指向沙箱外时经过链接的子路径也被拒_附变异反跑`：
- **Windows 失败**：junction 指向外部时，穿过链接的子路径未被路径护栏拒绝（实测 `assert True is False`）；
- **Linux 通过**：同节点 realpath 解析 symlink 后正确拒绝子路径。

→ 证明断言逻辑本身正确，缺口**只在 Windows 的 junction 解析路径上**。属 Windows 特异性 path_guard 缺口（或 Windows junction 语义处理差异），**不是跨平台通用缺陷**。建议业主裁定：修 Windows path_guard（真 bug）或维持 xfail+债（到期 2026-11-30）。

### 7.3 phase4 / phase13 的 xfail 环境分叉条件已陈旧
8 个通用失败（债#1~8）的 marker 多带 `_原生腿环境分叉_XFAIL = platform.system() != "Windows"` 这类条件。自 R152-C1 起 conftest 会话级安装光明导入钩子，**Windows 现在也加载纯光明腿并同样失败**——原条件假设「Windows 会过」已不成立：
- Linux：条件为真 → 预期 xfail（XFAIL，不红）；
- Windows：条件为假 → marker 失效 → 这些用例在**普通 Windows 套件里会变成真红（FAILED）**。

B 线边界是「只诊断、不修 marker」，故仅登记。建议业主裁定：把这些 marker 改为无条件 xfail（行为已跨平台一致失败），或从 .light 腿层面真修 bytes/编码契约（根因在 stdlib 的 .light 实现与 .py 契约差异）。

### 7.4 静态吞点 `_过A1缺口`
`test_distributed_eval_light.py` 中 `pytest.xfail()` 位于 `except NameError` 内，吞掉「节点网络.light 调 时间格式化，转译腿零映射」的 NameError。该吞并 `--runxfail` 无法透视（except 先接走异常，动态层只见下游二次失败），故门禁以**静态枚举**抓出并登记为债#10。根因修复（在 `src/code_generator.py` 补 A1 映射）后该吞点自动消失，届时可从欠账清单销账。
