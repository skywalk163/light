## 二、实现要点（与设计的偏差逐条说明）

### 2.1 丙：字面量零分配共享

- codegen 新增 `gen_immortal_string` / `_emit_immortal_pool`：全部字面量按内容去重后写入**单个** `@dv_immortal_pool`（`dso_local global`，**不带** `unnamed_addr`——避免被 LLVM 合并到池外导致区间判定失效），并发射 `@dv_immortal_size`。
- 运行时 `dv_is_immortal_ptr` 只做**整数区间比较**（`lo <= s < hi`），不读区间外内存。
- **与设计的偏差（必须记录）**：设计 §十三 R5 建议「常量走显式 `dv_str_immortal` + tag=1 的零长头或独立 range 判断」。本轮选**独立 range 判断**，并**不引入 extern 全局**，改为由 codegen 在首次字面量求值时把 `(pool, size)` 传给 `dv_str_immortal` **当场登记**。原因：`tests/test_llvm_c_runtime.c` 会独立链接 `runtime_typed.c` 而不带任何 codegen 产物，任何 extern 数据都会变成 `undefined symbol` 直接编译失败（实测 3 个 C 层用例红）。

### 2.2 乙：语句级临时表（**形态与设计不同，理由是实测**）

设计 §六.1 描述的是「缓冲头 tag + 语句边界 wholesale reset」。实现上采用：

- 每个字符串缓冲前加 `DvBufHdr { magic, tag, idx }`，`str` 指向头之后；
- **thread-local 指针数组**（`g_dv_tmp_ptrs/len/cap`）登记全部临时缓冲；`dv_mark()` 返回**当前长度**，`dv_reset(mark)` **截断**回该长度并释放区间内 tag=ARENA 的块。

> **为什么不是侵入式链表**：原实现用双向链表 + `mark` 存节点指针。逃逸提升会把链上任意节点改成 OWNED 并从链中摘除，**语句入口记下的 mark 节点可能就此消失** ⇒ `dv_reset` 走不到边界，把整条链（含调用方仍在用的缓冲）全 free。这是实测踩到的结构性缺陷。改成「下标向量」后：mark 是整数、提升只改 tag 不动数组、复位就是截断，**边界永远成立**。

### 2.3 逃逸：从「零拷贝 move」改为「私有副本」

设计 §6.2 E1 设想「具名变量存储 ⇒ `dv_own`（arena→malloc）零拷贝提升」。**实测否决**：

- move 让临时槽里的缓冲变成 OWNED ⇒ **逃过**语句末 `dv_reset`；而本仓没有可靠的单点释放者（形参写回、容器浅拷 C5、`%result` 都会合法共享指针），该缓冲永久泄漏。实测 P3' 拼接循环斜率 **20.9 MB/s**，正是这条路径。
- 改为 `dv_slot_set` **一律复制成私有 OWNED**：源临时值留在 ARENA 随 reset 回收，具名槽拿私有副本。代价是每次赋值多一次拷贝，换来**有界内存**。

由此确立不变量：**任一具名槽持有的 OWNED 串恰好只有它自己一个持有者** ⇒ 函数出口释放安全。

### 2.4 顺序纪律（本轮最贵的教训）

OBJ 缓冲（`"obj:"` 前缀，类实例）自本轮起也由 `dv_owned_alloc` 分配（带 header）。因此**所有**缓冲判定必须 **先判 OBJ、再判 magic**：

```c
if (dv_is_obj_str(s)) return;        /* OBJ 归 dv_obj_release_slot 协议 */
if (dv_is_immortal_ptr(s)) ...
if (dv_is_our_buf(s, &tag)) ...
```

违反顺序的后果（实测）：`dv_slot_release` 把 OBJ 当普通字符串 free ⇒ 后续 `dv_class_set_member` 的 free+realloc 撞已释放块 ⇒ **`导入 字节缓冲` 的程序在 `__light_init` 就 0xC0000374**。

同时：`dv_strdup` 统一改为**带头分配**。原因是 `dv_is_our_buf` 靠读 `s - sizeof(DvBufHdr)` 处的 magic 判定；若某缓冲**没有头**，`s-32` 落在别的 malloc 块甚至堆边界外——读到随机值不等于 MAGIC 只是侥幸，**读这一下本身就是越界读**，在 FreeBSD 严格堆布局上直接 SIGSEGV（实测 0.82：`客户端.请求` 路径 100% 段错误，本机 Windows 却不崩）。统一带头后 `s-32` 恒在合法块内。

### 3.2 收敛判据（设计 §10.1）

设计判据：537 采样点线性拟合斜率 `|k| ≤ 0.001 MB/s`。

- **未严格达标，如实记录**：修后 P1'/P2'/P3' 在 0.82 与 0.86 上的斜率均为 **+0.002~0.005 MB/s**，落在 ±0.001 带**之外**。
- 但**量级对比**：修前同一探针是 **+48 ~ +127 MB/s**，修后是 **+0.002~0.005 MB/s**，改善 4~5 个数量级；峰值从 **11~13 GB（OOM）** 降到 **3~4 MB 恒定**。P1' 在 0.82 上修后**跑满 2 亿轮 rc=0**。
- **残余斜率的来源**：见 §6.2（不是字符串路径；P1' 是纯字面量循环、P3' 是纯拼接，二者的残余同量级，指向机制本身的固定开销而非泄漏）。

> 口径声明：**本轮不宣称「收敛判据达标」**。若收口要求严格 `|k| ≤ 0.001`，需继续查这 ~0.004 MB/s 的来源（候选：`dv_slots_zero` 每次函数入口 memset 整池带来的 RSS 抖动、或临时表数组扩容）。

### 3.3 P5'（心跳同构混合，主判据）

**修前**：0.82 上 `客户端.请求` 路径 SIGSEGV，P5' 取不到任何采样（rc=-11，0 轮）。
**修后**：能稳定跑满窗口（100 采样点 / 278 万轮 / 峰值 13164.9 MB），斜率 +68.39372 MB/s。

斜率仍高不是字符串路径的问题（P1'-P3' 已归零），而是 P5' 载荷每轮构造容器字面量
（`{"节点":..., "轮":..., "数据":[1,2,3]}`）——即 §6.1 登记的**容器元素所有权残留**。
故 P5' 的收敛**依赖 R1 的完成**，本轮不能宣称主判据达标。

> 附带结论：修前 P5' 崩、修后 P5' 不崩，说明本轮对**网络路径**的间接修复是有效的
> （统一 `dv_strdup` 带头消除了越界读，见 §2.4）。

### 5.3 一个**测试隔离缺陷**（R159-E3 反跑用例，本轮发现并处置）

全量并行运行（默认 `-n 4 --dist=loadscope`）时，`test_R159_E3_容器布尔repr.py::test_反跑_改回depth不敏感_容器分歧复现` 会**临时改写全仓共享的 `src/llvm/runtime_typed.c`** 再还原。实测造成两类事故：

1. **假红**：并发 worker 在改写窗口内读该文件或调 clang 编译 ⇒ 读到/编到半改状态（「单跑绿、全量跑红」）。
2. **真损坏（严重）**：该 worker 若在改写中途被 xdist 超时/掉线杀掉，`finally` 不执行 ⇒ **源码永久停在 depth 不敏感的 bug 态**。本轮实测发生两次：全量跑完后 `case 5` 变成 `return dv_strdup(v->boolean ? "真" : "假");`，把 R159-E3 的修复抹掉了。

**处置**：

- 先尝试加跨进程文件锁（`_RTWriteLock`）——只能串行化「改写段」，挡不住「别的 worker 读文件/编译」和「worker 被杀」。
- 最终改为：**并行模式下跳过该用例**（检测 `PYTEST_XDIST_WORKER` 环境变量），由**串行运行**（`-n 0` / `-p no:xdist`）承担反跑验证。已验证：串行 5 passed（反跑执行）、并行 4 passed 1 skipped（源码不动）。
- **本线代码未因此改变**——这是既有测试的隔离缺陷，本轮只是把它暴露并修掉。

> 建议主 agent 收口时注意：**任何会改写共享源码的用例都不该在 xdist 下跑**。本仓目前只有这一处。

## 六、残留与新发现（登记，不擅自扩 scope）

### 6.1 残留 R1：容器字面量的元素所有权（P4'/P5' 斜率未归零）

- **现象**：P4'（JSON 序列化循环）在 0.82 上斜率 +68.50 MB/s，仅比修前（+80.77）改善 15%。
- **根因**：`{"i": i, "名": "心跳", "数据": [1,2,3]}` 这类**容器字面量**每轮新建 list/dict，其元素由 `dv_clone` 分配、由容器管理者释放；但容器本身作为临时值，其**元素数组**的回收依赖容器被 `dv_free`——而具名槽路径只释放**字符串**（`dv_slot_release` 明确只处理 type 3/26）。容器值在具名槽出口不释放。
- **为什么不本轮修**：① 设计 C5 明确「DICT 浅拷是 L-204 刻意契约（R146-A 回退教训）」，动容器释放会撞该契约；② 需要「容器私有深拷贝 + 出口释放」的独立所有权模型，属下一轮工作量。
- **已做**：`dv_str_tmp` 让 JSON 序列化的**结果字符串**进临时表（P4 的一部分已回收）；容器本身的元素数组仍未回收。

### 6.2 残留 R2：斜率未严格进入 ±0.001 带

见 §3.2。P1'/P3' 修后斜率 +0.003~0.005 MB/s。**如实登记为「未严格收敛」**，不按「改善百分比」粉饰。若收口要求严格达标，需按 R1 继续做容器所有权。

### 6.3 新发现 N1（建议立号 L-229）：`客户端.请求` 在 0.82 上 SIGSEGV（存量，本轮**已间接修复**）

- **现象（修前）**：`从 节点网络 导入 客户端` + `客户端(...).请求(...)` 在 0.82（FreeBSD）上 100% 段错误（rc=139）；同一程序在本机 Windows 正常。
- **归因**：用 **R160 基线树**（`444d765a9`，独立 worktree，零 L-217 改动）在 0.82 上复现同一崩溃 ⇒ **存量缺陷**。精确定位：`客户端(...)` 构造正常、多段落分发正常，只有 **`.请求(...)`** 崩。
- **本轮状态：已随 `dv_strdup` 统一带头而消失**。修后同一程序在 0.82 上正常（`t2 ok`，rc=0）；P5' 也从「取不到采样」变为「跑满窗口」。
- **机理（重要教训）**：旧 `dv_strdup` 返回**无 header** 的裸 malloc，而本轮机制靠读 `s - sizeof(DvBufHdr)` 处的 magic 判定缓冲身份 ⇒ 对无 header 指针而言这是**越界读**，在 FreeBSD 严格堆布局上直接 SIGSEGV、在 Windows 上侥幸不崩。统一带头后该越界读被结构性消除。
- **仍建议立号**：虽然现象消失，但「一个字符串分配器返回的指针形态随调用路径而异」这件事本身是脆弱设计，值得在缺陷账里记一笔（编号建议 L-229，需主 agent 收口时按铁律 14 确认未占用）。

### 6.4 新发现 N2：`dv_is_our_buf` 的越界读风险（本轮已从结构上消除）

- 见 §2.4：无 header 缓冲会让 `s-32` 读到堆边界外。本轮通过「`dv_strdup` 统一带头」消除。**教训**：任何「指针减固定偏移查 magic」的机制，必须保证**该偏移恒在合法分配内**，否则在严格堆布局平台上必然崩。

## 十一、过程事故记录（供后续轮次吸取）

### 11.1 `git stash` 做基线对比被中断

中途为对比基线，用 `git stash push` 暂存本线改动并跑基线测试；后台任务被中断，`stash pop` 未执行，改动留在 `stash@{0}` 里，工作树一度回到基线形态。

- **恢复**：先 `git stash show --stat` 核对内容（1252 insertions / 112 deletions，含 `dv_immortal_pool`、`dv_slots_zero` 等本线标记），确认是本线工作后 `git stash pop`。
- **正确做法**：用**独立 worktree**（`git worktree add ../lm-baseline 444d765a9`）跑基线，完全不碰工作树。本轮后半段即改用此法，`new_reds=0` 的对比就建立在它上面。
- **教训**：任何「临时改变工作树」的操作都不该与后台任务混用。

### 11.2 批量文本替换误伤既有逻辑

见 §5.3：`case 5` 的 depth-aware repr 被压平。**教训**：批量替换后必须与基线做 diff 复核，专门找「删除行里不含 alloc/free 关键词」的那些（`_r161_scratch/b_audit_diff2.py` 即此用途）。

### 11.3 「指针减固定偏移查 magic」的越界读

见 §2.4 / §6.4：无 header 缓冲会让 `s-32` 读到堆边界外，Windows 侥幸不崩、FreeBSD 必崩。**教训**：这类机制必须保证偏移恒在合法分配内；宁可让所有分配统一带头。

### 11.4 改写共享源码的测试在并行下会「永久损坏源码」

见 §5.3。R159-E3 的反跑用例在 xdist 下被中断时，`finally` 不执行，源码永久停在 bug 态。
本轮实测两次被它抹掉修复，最后改为「并行跳过、串行执行」。
**教训**：凡会改写仓库源码的测试，要么串行独占、要么不进并行套件——文件锁解决不了「worker 被杀」。
