### 3.5 机制级证据：插桩 trace + IR 对拍（决定性）

在 `dv_dict_find` / `dv_dict_set` / `dv_clone` / `dv_closure_env_clone` / `dv_deref_value`
打同一组 stderr trace（`_r161_scratch/t_bd.py`），两棵树对跑 DEC 探针：

| 观察点 | 真 R160 | R161 |
|---|---|---|
| 每次调用 `装饰(5)` 的 `dv_clone(FUNCTION)` | **0 次**（函数值解引用不克隆） | **每次 2 次**（`装饰` 与 `原函数` 各一次） |
| env 克隆来源 | — | `[T-ENVCLONE] env=0x…4000 n=2 [0]t=7 **sz=0** dd=0x…b000`（**源 env 永远 sz=0**） |
| 第 2 次调用 `字典包含键` 时 dict 状态 | `sz=1` → **HIT**（写回直达原 env） | `sz=0` → **MISS**（写回落在当次克隆体的 env 上，被丢弃） |
| `[T-SET-INS] sz=1` 后下次 FIND | `sz=1` 保持 | `sz=0` 复位 |

IR 侧（`_r161_scratch/t_be.py` / `dec_R160_f3.ll` vs `dec_R161_f3.ll`）：`包装`（`_seg_f3`）的
closure env **打包 / 解包 / 写回三段在两棵树逐指令一致**（含出口 `store %7 → env[1]` 写回）；
R161 的增量全在 L-217/L-231 侧（`dv_slots_zero` / `dv_move` / `dv_mark`+`dv_reset` /
`dv_slot_release` / `dv_str_tmp` / immortal pool / `dv_deref_value` 的 FUNCTION 深拷）。

**根因链（三句话）**：

1. R161-C（L-231）在 `dv_deref_value` 给 FUNCTION 值加了 `dv_clone` 深拷分支
   （原意：修协程里「形参槽 vs 解引用临时槽」的 DvClosure 双 free，0xC0000374）；
2. 生成码对**每个**函数值使用都先过 `dv_deref_value`（`_seg_f5` 主段：
   `dv_deref_value(%20, %4)` → `dv_call_value(%23, %20, …)`）⇒ 每次调用闭包都克隆出
   **新 DvClosure + 新 env 数组**（拷贝自永远 pristine 的源 env）；
3. 闭包对捕获容器（`缓存表` 字典）的跨调用修改依赖段函数出口的 **env 写回**，
   而写回只落在**当次克隆体的 env** 上（随调用结束丢弃）⇒ 原 env 的 `list_size` 永远是 0
   ⇒ 缓存/记忆化永久 miss。

附带损害：每次调用多漏一份 `DvClosure`+env 数组（`dv_slot_release`/`dv_temp_release` 均跳过
FUNCTION，无释放点）、多一次 O(N) env 拷贝。

### 3.7 修复与验证

**修复（`src/llvm/runtime_typed.c`，`dv_deref_value`）**：删除 FUNCTION 深拷分支，
恢复 R160 浅拷语义（`*result = *v` 后直接结束，FUNCTION 堆负载共享、env 归闭包自身——
即 R130-A 契约）。其原本修的协程双 free 由同轮两道既有机制覆盖，无需本分支：

1. **R161-C L-230**：协程 prologue 把 `args[i]` 拷进 `locals[形参]` 后立即
   `dv_null(args[i])`（codegen_typed.py:8862）⇒ `dv_coro_free` 的 args 释放循环成 no-op，
   不与 `locals[形参]` 双 free；
2. **R161-C 同轮 `dv_coro_free`**：对 locals 槽做 O(n²) 载荷指针去重
   （runtime_typed.c:6937-6950，ASan 实证）⇒「形参槽 vs 解引用临时槽」同 `str` 时后者置空，
   只释放一次。

## 4. CRLF 核对（#5、#8）

| 项 | 本机 Windows（light-merge 工作树） | 0.82 干净 clone |
|---|---|---|
| `git config core.autocrlf` | `true` | 未设置（`rc=1`） |
| `git ls-files --eol stdlib/协程.light` | `i/lf w/crlf` | `i/lf w/lf` |
| 实际字节 | 9723 B，CRLF 189 / LF 189 | 9534 B，**CRLF 0 / LF 189** |
| `git ls-files --eol` 全仓 | — | `i/lf 2470`、`i/-text 6`、`i/none 1`，**`w/crlf 0`** |
| 同一文件 `src/llvm/runtime_typed.c` | `i/lf w/crlf`，CRLF 12730 | R161 干净树为 LF（LF 版 `_FIX_LINE` 命中、`dv_to_string_depth(e, 1)` 计数 = 2） |

**判定**：git **索引里存的就是 LF**（`i/lf`），Windows 靠 `core.autocrlf=true` 在工作树转成
CRLF；FreeBSD 未设 autocrlf ⇒ 干净 clone 拿到 LF。因此：

- **#5（C1 纯 CRLF）**：测试判据 `crlf > 0 and crlf == 总LF` 在非 Windows/autocrlf 环境必然失败。
  C 线 `stdlib/协程.light` 内容本身没坏、没丢 CRLF —— **行尾 artifact**。真 R160 同样红。
- **#8（R159 depth-aware 锚点）**：测试的 `_FIX_LINE` / `_BUG_LINE` 常量**硬编码裸 `\r\n`**，
  对 `runtime_typed.c` 的**原始字节**做 `in` 断言 ⇒ LF 检出必失败。已实证：把行尾归一化为 LF 后
  `case 5` 的 depth-aware 形态**存在**、`dv_to_string_depth(e, 1)` 恰 2 处 —— **行尾 artifact**，
  非 D 线破坏。真 R160 同样红。

**建议（三选一，交给业主裁定，本轮不动代码）**：

1. **测试侧归一化（推荐，改动最小且不改变检出形态）**：把两处裸 `\r\n` 锚点改为对
   `\r\n|\n` 归一化后的文本断言（或读取后 `replace(b'\r\n', b'\n')` 再比）；C1 同口径改为
   「行尾一致」判据（`总LF > 0`），保留「纯 CRLF」仅在 Windows/autocrlf 检出形态下要求。
2. **`.gitattributes` 定点** `stdlib/协程.light text eol=crlf`：只对这一文件强制 CRLF 检出。
3. **`.gitattributes` 全局** `*.light text eol=crlf`：影响 2470 个文件的检出形态，**不推荐**
   （会改所有平台、所有机器的 checkout 结果，牵动面远超两个测试）。
