## 你的任务

修复 L-218：`stdlib/分布式/节点网络.light` 的 HTTP 头用**字符数**声明 Content-Length，
而 UTF-8 多字节键名（`节点ID`/`在跑任务`）实际字节数更大——严格 master 按 CL 截断体 → 解析失败。

## 做法要点

1. **声明侧**：`:371` → `转字符串(字节长度(字符串转字节(体)))`。
2. **解析侧**：`:445` 体切取改字节空间——
   `字节转字符串(截取(字符串转字节(剩余), 0, 内容长度 乘以 2))`（hex 每字节 2 字符）。
   `:430-431` 头区切取（纯 ASCII 区，字节==字符）**保持原样但加注说明为何安全**。
3. **护栏侧**：评估 `:418` 是否同步改字节口径——倾向改（同函数族口径统一），
   若保持则写明「字符口径仍有界（≤4 倍）」的理由。**结论进报告**。
4. **口径文档化**：文件头注 + `请求`/`解析响应` 注释写明
   「**本协议所有 Content-Length = UTF-8 字节数**；头区 ASCII，体可为多字节」。
5. **严格 master 探针（反跑锚点，scratch）**：写一个**按 CL 截断体**的严格 master
   （与 R158 迷你主控的 0.5s 抽干形成对照）——旧口径下**必然解析失败**，新口径下 round-trip 成功。
   放在 `_r159_scratch/b_*`（该目录 gitignored）。
6. **中文响应体用例（必测）**：master 返回含中文值的 JSON（如 `{"结果": {"消息": "中文测试"}}`）——
   旧口径 `解析响应` 会按字符下标切错，新口径正确。
7. **全链复核（A 线修复后，若时间允许）**：真实领任务 round-trip 下 CL 仍字节对齐。
