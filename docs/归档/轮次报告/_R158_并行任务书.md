### 1.2 B 线 · R157-E9 —— `floor_bootstrap.py` 证据窗口漂移（已查实，含 R157 停血现状）

- **现象**：地板自举扫描器 `tools/ci/floor_bootstrap.py` 报红 9 处判型内置
  （`是字母/是数字/是空/是空白/是布尔/是函数/是数值/字符串全数字/是负零`），其「±2 行文本窗口内找
  『既是定义行、又含该函数名』」证据失配。**代码定义完好、L1 判型类模块实测可编**——是**检测器口径漂移，不是功能回退**。
- **根因**：`stdlib/内置核心判型.light` 自 **R153** 起每个 `段落` 前增厚「对齐 `stdlib/builtins.py:xxxx`」注释 + 扩语义长注释，
  把定义行推出了 ±2 行检测窗口。
- **R157 已停血（不是根治）**：R157 收口补丁②（`eaad2ad32` 前一个 commit 同批）把 **9 条判型内置证据行更新到真实定义行**，
  地板自举率由误算 **59/96** 恢复为真实 **68/96 = 70.83%**（与文档口径一致）。**这是把尺子对准当前，尺子仍然脆**。
- **为何必须是本轮而不是「已修」**：R157 收口登记过 durable 教训——**改 `.light` 源文件会顶行号**：
  任何在 `段落 X(` 上方增删行的改动都会让 `任务书/自举地板清单.json` 的证据行再次失准，下轮跑 floor 门禁必红。
  真修法 = **检测器按「段落/函数定义行」语法级定位**（而不是文本 ±2 行窗口）+ **加回归门**顶住，才不再靠每轮手工改清单。
- **为何与 A 线同批**：与 E-1 是**同一类病——账/尺子与代码脱节**。只修账本不修尺子，下轮照错。
- 参照基线：`tools/ci/bootstrap_rate.py` 实跑 **75.61%（93/123）**、影子 **35**、关键路径 **24/24 = 100%**（`tools/ci/bootstrap_rate_baseline.json` version 3）。

### 1.3 C 线 · R157-E2 —— 分布式模块「每轮分配路径」内存画像（L-194 残余，独立深水轮）

- **L-194 主体已修（R144）**：`收全部` socket 无限拼接 OOM（~120 MB/s）已止血（0.82 实测孤立 `客户端.请求` 干净错误返回 rc=0）。
- **R119-B 协程回收已修（R156）**：`LightFuture` 加 `refcount`/`owner` + `dv_future_ref/unref/dv_coro_free`。
- **残余未定位**：完整 `节点 --sample`（真实链 `节点` → `节点核心.主` → `工人.运转` → `客户端.请求`）
  在 `ulimit -v 6000000` 下 **208s 涨至 5.99 GB → `rc=-11`（SIGSEGV）**，斜率 **~29 MB/s**（**R144 时点**测得）。
- **⚠️ R156 之后无人复测**：残余曲线是 R144 时点测的；R156 的协程回收修复**可能已改变该曲线，也可能没有**，
  **当前 HEAD 状态未知**。语言升级方向.md 明文：「必须先做 post-R156 复测这一步，再决定本轮修还是销账」。
- **为何阻塞发布（唯一真阻塞项）**：① `native_run_readiness` 可跑率卡在 67/68；② **任何把 `节点` 当库导入的
  原生腿程序都会挂死并吃满内存**——缺陷账定性「本轮唯一有『打爆机器』风险的现象」。
- **关键定性（memory 存档）**：~29 MB/s 无界增长 **≠** 协程泄漏（`DV_MAX_COROUTINES=4096` 封顶使协程泄漏有界）；
  **主导根因在分布式模块另一条每轮分配路径**（socket 收包/请求对象）。**根因未定位到行**。
- **必须远端跑**：本机 Windows 禁实跑（xdist `-n 4` 会 node down 级联，R154 教训；且 Windows 路径/内存语义与 0.82 不同）。

## 三、测试方案（科学配置 —— R157 明令「只允许一次 0.82 全量门」继续有效）

### 3.1 时间账（沿用 R157 实测）

- 0.82 全量门：**9333 用例 / ~21min** + sync（>120s，须后台）≈ **25min/次**。
- 0.86 full：4 核 4G，预估 40min+；fast 模式预估 10~15min。
- 本机 Windows 全量：**禁全量**（`-n 4` node down 级联，R154 教训）。
- ⇒ **本轮只有 C 线可能动 `src/llvm`/runtime ⇒ 只有 C 线需要 L1 权威全量门**；A/B 纯文档/脚本，**绝不触发全量门**。

### 3.2 四层测试（L0~L3）

| 层 | 机器 | 跑什么 | 耗时量级 | 判据 |
|---|---|---|---|---|
| L0 本机初筛 | Windows `.venv` | 每线新测试 + 波及面定向 | 分钟级 | 只判「没写崩」，**不作绿** |
| L1 权威全量门 | **0.82** | 收口跑 1 次全量（**仅当 C 线动了 `src/llvm`**） | ~25min | **new_reds=0**（diff 显式 `--base ../lightharness/reports/082_lightmerge基线_2026-10-17-014952.json`） |
| L2 平台并行批 | **0.86** | fast 模式全套 + B 线新门禁 + C 线（若在 0.86 有平台证据可跑） | 10~15min/批 | 全绿 + **Linux 平台证据** |
| L3 定向深水 | 0.82 | C 线内存画像 + 复测（`ulimit -v 6000000` 采样） | 采样轮 ~3~4min | RC=0 + 内存有界，或完整根因证据链 |

### 3.3 并行策略（墙钟取 max 不取 sum）

- **A / B 两线互不依赖**，且**互不触碰对方文件**（独占矩阵见 §五），可同时派单并行；两者只在 L0 本机 + L2 0.86 平台证据。
- **C 线独立深水**，独占 0.82 的 L3 采样窗口；与 A/B 并行（A/B 在 0.86 + 本机，C 在 0.82）。

- 每线「必跑」节写明该线用哪几层；**禁止任何线自行触发全量门**（要跑先问主 agent）。
