## 1. 根因

`docs/known_issues.md` G1 原文只说「`SemanticAnalyzer.__init__` 期望 `ast_unified.Module`，但
`light_parser_v3` 产出 `ast_nodes_v3.Module`（无 `add_scope`）」，容易被读成「差几个方法」。
探针（`_r135_scratch/probe_semantic.py` + `.out`）实测后确认真实差距是**两套独立体系**：

| | `ast_nodes_v3.py`（解析器真产出） | `ast_unified.py`（分析器期望） |
|---|---|---|
| 节点类数 | **102** | **36** |
| Module 形状 | `__slots__ = ('statements',)`，纯语句列表 | `functions`/`structs`/`globals`/`scopes` + `add_scope()` |
| 命名体系 | `VarDecl`/`IfStmt`/`ForeachStmt`/`Paragraph`/`ParagraphCall` | `VariableDeclaration`/`IfStatement`/`ForStatement`/`FunctionDefinition`/`FunctionCall` |
| 类设计 | 全族 `__slots__`（**写回属性即 AttributeError**） | `@dataclass` |

探针四的直接证据（`probe_semantic.out`）：

```
可直接派发: ['BinaryOp', 'Identifier', 'Module', 'NumberLiteral', 'StringLiteral']
落 visit_default: ['ForeachStmt', 'IfStmt', 'Paragraph', 'ParagraphCall', 'ReturnStmt', 'VarDecl']
```

即：**6/11 的语料节点名根本没有对应 `visit_*`**，派发全落 `visit_default` = 空跑。
任务书判定的「路线 1 单独不够」成立：只补 `add_scope()` 仍会因为派发落空而空跑。

## 2. 做了什么（路线 2a + 独立符号表）

### 2.1 `src/semantic_analyzer.py`（唯一被改的 `src/` 文件）

| 设计点 | 做法 | 为什么 |
|---|---|---|
| **独立符号表** | v3 模式用分析器自带的 `self.scopes` / `self._scope_stack`；不调 `module.add_scope()` | v3 Module 无需补任何接口，路线 1 的障碍一并消除 |
| **v3 独立分派** | `_v3_visit_<节点名>`，与既有 `visit_*` **彻底隔离**；`visit_Module` 在 v3 模式下自动路由 | 两套 visit 方法空间不重叠，unified 语义零回归、可独立回滚 |
| **不写回节点** | v3 路径**不向任何 v3 节点写属性**，分析结果只落符号表 | ast_nodes_v3 全族 `__slots__`，写回即崩 |
| **保守兜底** | 未覆盖节点走 `_v3_visit_unknown` 递归子节点，不报错 | 新增 v3 节点不会让语义分析抛异常 |
| **声明提升** | `_v3_hoist` 先把段落/类/导入名入表 | 光明允许前向引用，`bootstrap/` 与 `stdlib/` 大量依赖 |
| **单一判定入口** | `_v3_is_resolvable()` 是**唯一**的「未定义」判定函数，标识符与调用名都走它 | 早期两条路径口径漂移，导致 `parser.light` 误报 55 条 |
| **v3 关闭类型检查** | `check_types()` 在 v3 模式直接返回 | v3 的 `数`/`串` 只是粗标签，字面上会大面积误报 |

覆盖度：**102 个 v3 节点类中显式覆盖 67 个**（`_r135_scratch/A线_证据/v3_节点覆盖.md`），
其余走保守递归。`V3_TO_UNIFIED` 映射表 14 条登记在模块顶层。

## 4. 关键踩坑记录（供后续轮次复用）

1. **`then_body`/`else_body` 可能是单节点而非列表** —— 初版 `for` 直接抛
   `TypeError: 'IfStmt' object is not iterable`（332 个文件里 173 个中招）。
2. **两条路径口径漂移**：调用名的「未定义」判定曾绕过统一的放宽规则，导致
   `parser.light` 误报 55 条 `make_binary_op`。→ 收口成 `_v3_is_resolvable()`。
3. **v3 把成员访问压成单个 Identifier**：`己名称`、`宠物的长度` 不是结构化节点
   （`的` 只在 `_is_paren_dict_key` 留痕），`super()` 也是字面带括号的 Identifier。
4. **`引 Python:` / `引 模式 日期:` 引入块**：`language` 字段里可能带修饰词，
   末段才是引入名；块内 Python 的 `名 = 值` / `def 名` 对后续光明代码可见。
