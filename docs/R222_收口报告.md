### 3.3 #1 的根因（本报告最重要的技术发现）

`spec/build_spec.py::_stdlib_digest()` 对 `stdlib/*.light` + `stdlib/*.py` **按磁盘原始字节**算 sha256，
**没有做行尾归一**。而 `test_spec_is_rebuildable_byte_for_byte` 的注释明确写了要处理 `core.autocrlf`：

```python
current = f.read().replace("\r\n", "\n")   # 只归一了 spec 文件本身
```

归一的是 JSON 的**自身**行尾，没归一**输入文件**的行尾。同一棵树，四种检出算出的指纹各不相同（实测）：

| 检出形态 | `stdlib_汇总` |
| --- | --- |
| `spec/light.spec.json` 里记录的 | `5168681cc08ed6d5` |
| T-0383 工作树（158 文件全 CRLF） | `5168681cc08ed6d5` ← 生成时的形态 |
| `light-merge` 主工作树（153 CRLF + 5 LF 混合） | `eb5613aa62fa7302` |
| 从 git blob 取（全 LF，= 干净检出） | `d2318dc662cbb1aa` |
| 0.88 FreeBSD 快照（tar 保留 LF） | `7e7d995923a0a937` |

也就是说：

- Windows 上（`core.autocrlf=true`，检出 CRLF）**绿**
- 0.88 / Linux / CI（检出 LF）**必红**
- 本机 `light-merge` 主工作树因为 5 个文件恰好是 LF，**也红**（`--check` rc=1）

这不是「合并没刷新指纹」的一次性事故，而是**门禁本身对检出形态敏感**——同一份提交在任何一台
不是 Windows 的机器上都会红。修法是 `_stdlib_digest()` 与 `FINGERPRINT_FILES` 的 sha256 统一先
`replace(b"\r\n", b"\n")`（与 `test_spec_lockstep` 对 spec 自身的口径一致），或在 `.gitattributes`
里把 `stdlib/*.light` 标 `-text`。M 线不改代码，另开卡。

旁证：`spec/build_spec.py` 的 diff 输出标签写反了——`仓内:` 打的是重建值、`现状:` 打的是文件值，
排查时容易看错方向。
