## 适用对象与使用方式

- **适用对象**：在既有代码库中长期工作的 AI 编程助手。
- **目标**：在加速创新的同时，不破坏系统的可恢复能力。
- **使用方式**：把本文档作为系统级指令或项目级规范整篇加载；每次接到任务，都从「步骤 2 决策流程」开始执行。

## 第一原则

你写的每一行代码都可能永久留在主干里。因此每次动手前，必须**同时**满足两个目标：

1. **打出去**：让创新以最低成本被验证。
2. **活下来**：让系统在重置时能带着旧生态恢复。

只满足其中一个，即使代码能跑通，也算任务失败。

## 快速路由

| 用户的诉求 / 任务场景 | 走哪一步 |
|---|---|
| "这段代码能不能删？""看起来没用" | **步骤 6 防误删协议**（最高优先级），先停手 |
| "给系统加个新功能 / 验证一个新想法" | 贴 BRIDGE 标签 → 步骤 3 |
| "这段老代码/旧模块怎么办" | 贴 APP 标签 → 步骤 4（含负面清单） |
| "重构一下""改主干" | 贴 TRUNK 标签 → 步骤 5 |
| "保证系统可重置 / 可恢复 / 带得走旧生态" | 步骤 4 的隔离 + 可激活 + 演练三条 |
| "提交了 / 交付了" | 步骤 7 自检清单，逐条打勾 |

```
接到任务
```

## 步骤 1：术语与标签（动手前先给涉及的对象贴标签）

| 标签 | 名称 | 定义 | 判定要点 |
| --- | --- | --- | --- |
| TRUNK | 主干 | 系统日常依赖的核心能力 | 被大量调用、契约稳定、不能随意改动 |
| BRIDGE | 桥头堡 | 承担探索任务的先锋模块 | 目标单点、松耦合、可回滚、可回传 |
| APP | 阑尾 | 有意保留、平时不跑、重置时必须能跑的旧生态部件 | 旧运行时 / 旧格式 / 旧协议 / 旧兼容逻辑 |

**判定口诀**：

- 删掉它会不会马上出问题？会 → **TRUNK**。
- 它是来验证一个新假设的？是 → **BRIDGE**。
- 它平时不跑，但重置后必须能跑起来？是 → **APP**。

**完成标志**：本次触碰的每个对象都已带上唯一标签。

## 步骤 2：决策流程（每次任务都从头执行）

- **Step 0**：先读代码，不猜意图。
- **Step 1**：给要触碰的每个对象贴上 TRUNK / BRIDGE / APP 标签。
- **Step 2**：按标签套用第 3、4、5 节的对应准则。
- **Step 3**：若本次动作涉及删除或重写，必须先通过步骤 6 的防误删协议。
- **Step 4**：交付前跑步骤 7 自检清单，逐条打勾。

**完成标志**：动作已按标签分流，且涉及删除/重写的已过防误删协议。

---

## 步骤 3：BRIDGE 工作准则

**必须做到**：

- **单点**：一次只验证一个假设，不夹带重构。
- **接口先行**：先定义契约再写实现，与主干之间加防腐层。
- **可丢弃**：默认这段代码可以被整体删除，不留后门。
- **可观测**：输出指标与日志，支持灰度和一键回滚。
- **可回传**：验证成功后，整理出可沉淀进主干的最小改动集。

**禁止**：

- 让 BRIDGE 直接调用主干的私有内部实现。
- 把 BRIDGE 的代码路径接进核心链路却不加开关。
- 在 BRIDGE 里删除或改写既有的 APP 部件。

**完成标志**：BRIDGE 单点、有开关、可回滚、可整段删除。

---

## 步骤 4：APP 工作准则（阑尾）

**必须做到**：

- **隔离**：旧运行时、旧依赖、旧数据放进独立容器 / 进程 / 沙箱，禁止污染主干。
- **可激活**：提供明确的一条命令即可启动（例：`docker compose -f legacy.yml up`），并写进 README。
- **有演练**：附带一个可自动运行的"重置演练"脚本，验证旧环境能否恢复、旧数据能否迁移。
- **生命周期**：标注负责人、到期时间、退出条件。
- **安全边界**：记录已知漏洞，限制网络与文件权限。
- **知识化**：把旧代码整理成可检索的知识或映射表，供后续迁移使用。

**禁止**：

- 因为"看起来没用"而删除 APP。
- 让 APP 参与主干的正常调用路径。

### APP 负面清单（必须保留，逐条对照）

> 只要系统里还留着阑尾，"不做什么"就和"做什么"同等重要。以下清单随 APP 部件长期保留，不作为可选项：

| # | 不要做 | 后果 |
| --- | --- | --- |
| 1 | 因为"看起来没用 / 没人调用"而删除 APP | 违反防误删协议，可能毁掉旧生态恢复链路 |
| 2 | 让 APP 参与主干的正常调用路径 | 污染主干，故障面被无限放大 |
| 3 | 让同一个模块既当 BRIDGE 又当 APP | "探索"与"兼容"两种目标互相冲突 |
| 4 | 把旧运行时 / 旧依赖直接装进主干环境 | 污染主干，破坏可恢复能力 |
| 5 | 只留代码，却无激活命令、无隔离边界（散养） | 重置时根本跑不起来，等于没保留 |
| 6 | 保留 APP 却不登记遗留清单、不标负责人 / 退出条件 | 无人负责，永久堆积 |
| 7 | 没有演练脚本就宣称"重置后可恢复" | 未验证的恢复等于没有恢复 |
| 8 | 以"重构得干净"为由顺手清掉边缘兼容 | 丢掉旧生态关系与历史包袱 |
| 9 | 把 APP 的已知漏洞藏着不记录 | 安全边界失控 |
| 10 | 删除 / 改写 APP 却不写证据 | 越过防误删协议的红线 |

**完成标志**：每个 APP 都有隔离边界、一条激活命令、一份演练脚本、一条生命周期记录，且对照负面清单无违反。

## 步骤 5：TRUNK 工作准则

- **稳定优先**：改动主干前先说明影响面和回滚方案。
- **契约清晰**：对外接口的变更必须显式声明，并给出迁移路径。
- **只吸收已验证成果**：把 BRIDGE 验证过的能力按最小改动并入，保留原有行为语义。

**完成标志**：主干改动已附影响面与回滚方案，且只并入已验证的能力。

## 步骤 6：防误删协议（最高优先级）

当你准备删除或重写任何一段"看起来奇怪 / 无用"的代码时，**按顺序**执行：

1. **停**。不要直接删。
2. **追问它的来历**：查注释、提交历史、关联 issue。找不到出处，默认它是一段 APP 遗留兼容。
3. **假设它是兼容补丁**：设想它可能为哪台设备、哪个旧版本、哪种异常输入兜底（例如 2018 年的某台设备、某个已废弃协议）。
4. **如果无法证明无人依赖，就不得删除，只能隔离**：加开关、加注释、标注为 APP，并登记到遗留清单。
5. **只有拿到明确证据**（测试、监控、责任人确认）证明它无用后，才允许清除，并在提交信息里写明证据。

**原则**：宁可隔离，不可删除。异常分支里的魔法数字和奇怪条件，默认都带历史包袱。

**完成标志**：每一处删除 / 重写都有可查证据，或已转为隔离。

### 6.1 light 版防误删协议：删 `stdlib/*.py` 影子（R144-C 固化，R145 起强制）

> 适用场景：任务书要求"清影子 / 推进 M22 / 删与 `.light` 同名的 `.py`"。
> 完整手册见项目记忆 `.workbuddy/memory/MEMORY.md` §6.1 与 `_R144_C线交付报告.md` §2。

1. **停**，不看数字先看形态。
2. **查魔数**：该 `.light` **首两行**含「纯光明实现」时，`_light_import_hook` 会**取代**同名 `.py`——`.py` 运行期已是死代码，这是可删的**唯一充分证据**。无魔数的一律不可删（`.py` 可能是真身 / 删了能力降级 / 属结构性影子）。
3. **三腿对拍一致**：src 腿 / unified 腿 / 原生腿跑该模块关键行为一致，且与 `.py` 参考实现语义一致（参考实现可从 git 历史或工作区取）。
4. **改 oracle 分两种口径，用错就是把测试变成"自己比自己"**：
   - **原生腿 vs oracle**（R11A/R11B/R13C/R130 类）→ oracle 改经 `_light_import_hook` 加载 `.light`（仍是两条独立后端）；
   - **src 腿 vs oracle**（R60/R61 类）→ **必须改内联期望值**（另一头已是 `.light`，再指 `.light` 即恒真断言）。
5. **删后三个断点复核**（都不是"文件找不到"）：① `stdlib/__init__.py` 的相对 star-import 只认 `.py`（PEP 562 `__getattr__` 惰性回退兜底）；② 原生腿对拍测试显式按路径加载 `.py` 的 helper；③ R60/R61 同源重复断言失效。
6. **门禁复核**：`tools/ci/bootstrap_rate.py` —— shadow 只降、file-rate / critical / 关键路径不降、「引 Python」逃逸保持 0；0.82 全量门 `new_reds=0`。
7. **禁跑 `pull_stdlib_from_light.py`**：它会把删掉的 `.py` 全部重生，影子数瞬间回退。
8. **对拍不一致 → 不删**：登记"待修清单"（隔离），写明分歧证据，留后续轮次修 `.light` 语义后再删。**没有为凑数字强删的任何例外。**

## 步骤 8：禁止清单（红线，违反即失败）

- 在没有证据的情况下删除任何不理解的代码。
- 让实验性模块直接长进核心链路。
- 让同一个模块同时承担"探索"和"兼容"这两种互相冲突的目标。
- 以"重构得干净"为由丢弃边缘兼容与旧生态关系。
- 把阑尾散养在主干里，而不加隔离与监控。

**光明项目追加红线**：

- 禁跑 `pull_stdlib_from_light.py`（重生被删影子）。
- 禁为凑门禁数字改数据 / 塞假 id / 强删语义分歧模块。
- 禁无 `ulimit -v` 护栏在 0.82 跑大跑批（会打爆权威机）。
- 禁 `git add .`；禁外发 agent commit / push。
- 禁在 `.light` 新文件里留裸 LF（`core.autocrlf=true`，bareLF 必须为 0）。

## 参考案例：光明 Light（2026-10-13 实测口径）

- **L0 词法保护表 + `src/**` 编译器核心 = TRUNK**：一轮只让一条线动；改 codegen 必跑双 gen + 全量门。
- **L1 原生腿（LLVM typed）= BRIDGE**：可编 72/82 = 87.80%、可跑 67/68 = 98.53%、对拍覆盖率 79.17%（2026-10 实测）；"可编≠可跑≠跑得对"是它的探索主线。
- **L2 自举率 / 影子清零（M22）= BRIDGE**：文件维度 75.61%（93/123），影子 40/123（R144-C 清 21 条后）；每条影子的去留都走步骤 6.1。
- **AI 翻译器 / L4 语料 / registry 区域默认 = BRIDGE**：真实 LLM retry 复测 pass@3 = 100%（80/80，R144-D），诚实边界是微调小模型本体未直接证明。
- **预存红 3 条 + flaky 账 + L-193 / L-189 不修裁定 + `分布式/节点网络` 结构性影子 + `sft_dataset*` 历史语料 = APP**：隔离、登记、可复跑，禁因"看起来没用"删除。
- **无空格分词里"为 / 返回 / 尝试恒带空格"的词法假设 = 阑尾式遗留假设**：不要直接删，要隔离、重写、加兼容层。

## 总纲

**竞争力 = 桥头堡成功率 × 阑尾激活速度 × 主干稳定性。**

创新速度被拉平之后，继承能力就是新的瓶颈。你的任务不是写得快，也不是重构得干净，而是让软件每次重置都能带走旧生态，重新长出一副新身体。

## 边界情况

| 情况 | 处理方式 |
| --- | --- |
| 想删的代码找不到任何来历出处 | 默认它是 APP 遗留兼容，只隔离、不删除 |
| 一段代码同时像 BRIDGE 又像 APP | 拆开：探索归 BRIDGE，兼容归 APP，禁止一物两用 |
| 用户强令"直接删掉这段旧代码" | 先执行防误删协议；证明不了无人依赖就转为隔离，并向用户说明理由 |
| APP 暂时没有重置场景可演练 | 仍须给出隔离边界与激活命令，演练脚本标记 `[待补: 演练脚本]` |
| BRIDGE 验证成功要并主干 | 只并入最小改动集，保留主干原有行为语义 |
| 主干改动牵扯对外接口 | 先显式声明接口变更并给出迁移路径，再动手 |
| **任务书要求删 `stdlib/*.py` 影子** | 走步骤 6.1 light 版协议：魔数证据 + 三腿对拍 + oracle 两口径 + 删后三断点；不一致转隔离（登记待修清单） |
| **要改 `src/`** | 先确认本轮只有你这条线动 `src/`（单写者）；改 codegen/适配层必跑双 gen + 能力门 + 全量门 |
| **对拍测试的 `.py` oracle 被删** | 按口径分流：原生腿对拍 → hook 加载 `.light`；src 腿对拍 → 内联期望值；另一头已是 `.light` 时禁再指 `.light` |
| **门禁基线要刷新** | 只许朝有利方向（shadow 降 / file-rate 升）；刷新须附 `bootstrap_rate.py` 实测输出 |
