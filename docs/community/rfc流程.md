# RFC 提案流程

> 目的：让语言演进（语法、标准库、工具链、生态政策）有**公开、可追溯、可评审**的通道，而非只由核心维护者拍板。
> 适用：所有会改变「他人将要依赖的行为」的提案（语法变更 / stdlib API / 包管理协议 / 治理规则）。

## 一、何时需要 RFC

- 新增或破坏性修改**语言语法**；
- 新增 / 移除 **stdlib / lightpub** 公共 API；
- 修改 **包管理 / 注册协议**；
- 修改 **治理文件**（CONTRIBUTING / CODE_OF_CONDUCT / 本流程本身）；
- 对 **路线图** 提出与 `ROADMAP.md` 显著偏离的方向。

**不需要 RFC**：Bug 修复、内部重构、文档、示例（走常规 Issue / PR）。

## 二、流程（5 阶段）

```
1. 预热（可选）  ──▶ GitHub Discussions · ideas  收集动机与初步反馈
2. 起草 RFC      ──▶ 提 PR：新增 docs/rfcs/rfc-XXXX-<主题>.md（模板见下文）
3. 评审          ──▶ 标签 rfc + 至少 1 位核心维护者评审；公开讨论 ≥ 3 个工作日
4. 裁定          ──▶ 核心维护者给出 接受 / 拒绝 / 需修订；记录于 PR 结论
5. 落地          ──▶ 并入实现，关联 PR；完成后在 RFC 头部标 状态=已采纳/已发布
```

## 三、RFC 文档模板（最小）

```markdown
# RFC-XXXX：<一句话标题>

- 状态：草稿 / 评审中 / 已采纳 / 已拒绝 / 已发布
- 作者：@你的ID
- 创建：YYYY-MM-DD
- 关联：#Issue号（如有）

## 摘要
（2-3 句说清要改什么、为什么）

## 动机
（解决谁的什么痛点，现状为何不够）

## 详细设计
（语法 / API / 协议的具体形态，附最小示例）

## 兼容性影响
（是否破坏性；如何迁移；旧代码怎么办）

## 替代方案
（考虑过哪些，为什么没选）

## 验收标准
（怎样算落地成功）
```

## 四、编号与归档

- 编号由维护者在 PR 合并时分配（顺序值），文件命名 `docs/rfcs/rfc-XXXX-<slug>.md`；
- 已采纳/已发布的 RFC 永久保留，作为语言演进的历史依据。

## 五、快速提交入口

仓库已配置 Issue 模板 `rfc`（`.github/ISSUE_TEMPLATE/rfc.md`）用于**简短提案**；
正式 RFC 一律走上面的 PR 流程。
