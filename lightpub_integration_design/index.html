    lightpub 标准库集成方案¶

    版本: v1.0 日期: 2026-08-03 状态: 设计稿

    1. 现状分析¶

    1.1 lightpub 包仓库 (109 个包)¶

    路径: C:\dumatework\lightpub\packages\

    每个包结构: 

    packages/文件系统/
  段件.toml      # 清单文件（名称/版本/描述/依赖）
  源.light        # 主源码（FFI 声明 + 封装函数）
  源_cstyle.light # C 风格变体
  示例.light      # 使用示例
  测试.light      # 测试代码
  测试_v2.light   # 测试代码 v2

    语法特征: 使用旧版语法 — 令 赋值、使用 模块.* 导入、接收 参数、输出() 输出、外部 段落 FFI 声明。

    1.2 当前 stdlib (29 个核心模块)¶

    路径: C:\dumatework\light\stdlib\

    语法特征: 使用 v3.3+ 语法 — 设 x 为 赋值、导入 模块 导入、函数 名(参数) 定义、打印() 输出。

    1.3 差异矩阵¶

    维度 lightpub 包 当前 stdlib
    赋值 令 x = 值 设 x 为 值
    导入 使用 模块.* 导入 模块
    函数定义 函数 名 接收 参数: 函数 名(参数):
    FFI 声明 外部 段落 名 参数。 嵌入 C: ... 或 导入 C: ...
    输出 输出(...) 打印(...)
    语句结束 // 注释为主 。 句号

    2. 集成策略¶

    2.1 不直接合并，而是建立桥接层¶

    原因: - lightpub 包用旧语法编写，直接放入 stdlib 会导致语法不一致 - lightpub 包依赖 FFI（C 底层），当前 Python 后端没有完整的 FFI 运行时 - 109 个包需要逐个验证，不能一次性全量引入

    策略: 1. 在 stdlib/lightpub/ 下建立包索引和桥接模块 2. 桥接模块用新语法重写关键函数签名，底层调用 Python 实现或 FFI 3. 通过 导入 标准文件系统 语法访问（"标准"前缀路由到 lightpub 索引）

    2.2 分层架构¶

    光明代码
  ↓
导入 标准文件系统           ← 光明标准库入口
  ↓
stdlib/lightpub/文件系统.light  ← 桥接模块（新语法，声明 API）
  ↓
stdlib/builtins.py 或 FFI    ← Python 实现 / C FFI

    2.3 包名映射规则¶

    lightpub 包名 → 光明导入名: - 文件系统 → 导入 标准文件系统（或兼容 导入 文件系统） - JSON → 导入 JSON（已有，保持不变） - CSV → 导入 CSV（已有，保持不变） - 网络请求 → 导入 标准网络请求 - SQLite → 导入 SQLite

    "标准"前缀是可选的——用于消歧义和明确意图，不加也能工作。

    3. 实施计划¶

    阶段 1: 包索引和元数据 (先做)¶

    • 在 stdlib/lightpub/ 下创建 __index__.py，列出 109 个包的名称、路径、API 摘要
    • 在 stdlib/lightpub/ 下创建 __init__.py，实现包加载器

    阶段 2: 高频包桥接 (选 10 个最常用的)¶

    优先级: 1. 文件系统 — 已有 stdlib 实现，桥接到现有 2. JSON — 已有 stdlib 实现 3. CSV — 已有 stdlib 实现 4. HTTP客户端 — 需新建（基于 Python requests） 5. 正则表达式 — 已有 stdlib 实现 6. 日期时间 — 已有 stdlib 实现 7. 数学运算 — 已有 stdlib 实现 8. 加密 — 已有 stdlib 实现 9. Socket — 需新建（基于 Python socket） 10. SQLite — 需新建（基于 Python sqlite3）

    阶段 3: 全量迁移和语法升级¶

    • 用 tools/migrate_syntax.py 批量迁移 lightpub 包语法
    • 逐包验证 FFI 声明与新 导入 C: 语法的兼容性

    4. API 设计原则¶

    1. 函数式优先: 读取文件(路径) 而非 文件系统.读取(路径)，减少成员访问的歧义
    2. 中文命名: 函数名用中文动词+名词，如 创建目录、删除文件、解析JSON
    3. 零标点导入: 导入 标准文件系统 不需要点号或引号
    4. 向后兼容: 现有 导入 数学、导入 JSON 继续工作不受影响
    5. FFI 透明: 底层是 Python 实现还是 C FFI 对用户不可见

    5. 暂不实施的原因¶

    这个方案目前是设计稿，暂不实施的原因： 1. Trae 正在修改 src/parser_stmt.py（T1 深层链式赋值），我修改 stdlib 不会冲突但需要等 parser 稳定后再做包加载器 2. lightpub 包的语法迁移（令→设、接收→()、使用→导入）需要 migrate_syntax.py 升级支持 lightpub 特有语法 3. 109 个包的逐个验证工作量大，建议先做 10 个高频包的桥接验证可行性

    下一步: 等 Trae 完成 T1-T4 后，开始实施阶段 1（包索引）。
