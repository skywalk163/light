    版本: v1.0 | 日期: 2026-08-04 | 基于 v4.2.0 基准数据

    2. 目标定义¶

    阶段 目标规模 推断时间目标 触发条件

    3. 阶段 1：低风险优化（200–500 段）¶

    3.1 is_instance 改为 type_id 整数分派¶

    现状：type_inferencer.py 每次 type(node).__name__ 做字符串比较，占函数调用总次数的 25%。

    方案：为所有 AST 节点添加 _ast_type_id 整数常量，用 node._ast_type_id == AST_ID_RETURN_STMT 替代 is_instance(node, 'ReturnStatement')。

    改动范围： - ast_nodes.py：为每个节点类添加 _ast_type_id 类属性 - type_inferencer.py：_infer_statement 和 _infer_expr 中的 is_instance 调用替换为 _ast_type_id 整数比较

    预期收益：_infer_statement / _infer_expr 分发开销降低 60–70%，总推断时间降低 15–25%。

    风险：低。_ast_type_id 在类定义时静态赋值，不依赖运行时状态。

    3.2 TypeSubstitution.clone() 改为 Copy-on-Write¶

    现状：type_system.py 每次 _unify_type_var 调用 subs.clone() 创建新字典，TypeSubstitution.__init__ 被调用 617 次/100段。

    方案：TypeSubstitution 内部维护一个 _frozen 标记和版本号。clone() 返回一个"浅代理"对象，只在真正写入时才复制底层字典。

    class TypeSubstitution:
    def __init__(self, mapping=None, _parent=None):
        self._mapping = dict(mapping) if mapping else {}
        self._parent = _parent  # CoW 父对象
        self._dirty = set()     # 本层修改的 key

    def clone(self):
        return TypeSubstitution(_parent=self)

    def __setitem__(self, name, t):
        self._dirty.add(name)
        self._mapping[name] = t

    def __contains__(self, name):
        if name in self._dirty:
            return name in self._mapping
        if self._parent:
            return name in self._parent
        return name in self._mapping

    预期收益：TypeSubstitution 创建开销降低 80%，总推断时间降低 5–10%。

    风险：低。接口不变，仅内部实现优化。

    3.3 apply_substitution 单例短路¶

    现状：TYPE_NUMBER、TYPE_STRING 等单例类型在 apply_substitution 中仍走完整调用链，但实际永远返回自身。

    方案：在 Type.apply_substitution 基类中增加快速路径：

    class Type:
    def apply_substitution(self, subs):
        if not subs:  # 空替换直接返回
            return self
        return self  # 基类默认：单例类型无需替换

    _SingletonType 子类直接继承此行为，无需额外代码。

    预期收益：apply_substitution 调用开销降低 10–15%，总推断时间降低 3–5%。

    风险：极低。单例类型确实不需要替换。

    4. 阶段 2：结构性优化（500–2000 段）¶

    4.1 基于调用图的 HM 迭代优化¶

    现状：type_inferencer.py 固定两轮迭代所有段。对于无相互调用的段，第二轮是浪费。

    方案：在 _pre_scan_definitions 阶段构建调用图（段名 → 被调用段名集合），用拓扑排序确定迭代次数：

    • 无环子图：1 轮
    • 有环子图（相互递归）：2 轮
    • 深度嵌套链：按拓扑层级分组，逐层推断

    预期收益：对于无相互调用的大模块，推断时间降低 30–40%（省掉一轮迭代）。

    风险：中。需要正确处理间接调用（高阶函数）、动态分发等场景。

    4.2 增量推断缓存¶

    现状：每次 infer() 调用都重新推断整个模块，即使只有少数段发生变化。

    方案：为每个段维护 (源码哈希, 依赖段签名哈希) → 推断结果 缓存。仅重新推断发生变化的段及其依赖链。

    改动范围： - TypeInferencer 增加 _segment_cache: Dict[str, CacheEntry] - infer() 新增 incremental=True 参数

    预期收益：IDE 场景下（单文件编辑后重新推断），时间降低 50–80%。

    风险：中。需要正确处理跨段类型变量传播和缓存失效。

    4.3 unify 快速路径扩展¶

    现状：type_system.py 已用 _type_id 整数分派，但 GenericTypeInstance ↔ ListType/DictType 的跨类型合一仍需逐字段检查。

    方案：为常见合一模式（如 列表[T] ~ 列表[数]、T ~ 数）添加内联快速路径，跳过 apply_substitution + collect_type_vars 的完整调用。

    预期收益：unify 调用开销降低 15–20%。

    风险：低。增加分支但不改变逻辑。

    5. 阶段 3：架构级优化（2000+ 段）¶

    5.1 并行段推断¶

    现状：_hm_infer_module 中所有段按顺序推断。

    方案：对于调用图中无依赖关系的段，使用 concurrent.futures 并行推断。每个段在独立的作用域副本中推断，最后合并符号表。

    预期收益：多核环境下推断时间降低 40–60%（取决于并行度）。

    风险：高。需要确保 TypeSymbolTable 和 TypeSubstitution 的线程安全，以及 type_cache 的隔离。

    5.2 符号表索引优化¶

    现状：type_system.py TypeSymbolTable.lookup 逐层遍历作用域栈，O(d) 复杂度（d = 嵌套深度）。

    方案：为全局符号（类名、段名、枚举名）维护一个扁平化的 _global_index: Dict[str, TypedSymbol]，避免深层作用域穿透。

    预期收益：深层嵌套模块中符号查找开销降低 50–70%。

    风险：低。全局符号与局部作用域隔离，不会冲突。

    5.3 类型表达式解析缓存¶

    现状：TypeParser.parse() 每次重新解析类型注解字符串（如 列表[字典[串: 数]]）。

    方案：为 TypeParser 添加 LRU 缓存（@lru_cache(maxsize=512)），相同类型字符串直接返回缓存结果。

    预期收益：类型注解解析开销降低 90%（类型注解在模块内高度重复）。

    风险：极低。TypeParser.parse() 是纯函数。

    7. 风险与注意事项¶

    风险 影响 缓解措施
    优化引入类型推断精度下降 阶段 2、3 保持全量回归测试，任何精度变化视为失败
    并行推断的符号表竞争 阶段 3 使用不可变符号表快照 + 写时合并
    增量缓存失效逻辑错误 阶段 2 为增量模式增加 --no-incremental 全量回退开关
    过早优化浪费开发时间 所有阶段 严格按触发条件执行，不提前优化
