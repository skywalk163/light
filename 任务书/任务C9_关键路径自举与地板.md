- ❌ 把 `JSON.light` 从头写成 1147 行 —— 没必要，且大量能力（转 XML、JSONSchema）harness 用不到。
- ✅ **已有纯光明替身，做「收口 + 改名归位」**：`stdlib/JSON核心.light`（decl 25）、`stdlib/JSON编解码.light`（decl 22）已经是纯光明实现，`examples/harness/LLM通道.light:33` 已改用 `从 JSON核心 导入 序列化`。**但 `JSON.light` 仍是空壳** —— 也就是说前几轮是「换了个名字绕开指标」。本轮把 `JSON.light` 做成真正的门面：真实现（可以委托 `JSON核心`/`JSON编解码`，但**门面自己必须有 `段落` 定义，转发也算实现**）+ 首两行魔数 + 保证 `stdlib/JSON.py` 那些被 `examples/` 真实使用的导出名一个不少。

## 3. S1 同期：把地板拉进分母（新建 `任务书/自举地板清单.json`）

**这是本轮最重要的认知修正。** `stdlib/builtins.py`（1067 行、114 个函数）被 `src/code_generator.py:735-741` 用 `spec_from_file_location('light_builtins', …)` 注入进**每一份**生成产物（另见 `src/module_resolver.py:202-225 preload_builtins()`、`src/compiler.py:972,994`）。连自称「零导入零引 Python」的 `stdlib/文件流.light:4` 都站在它的 `读取文件`(`builtins.py:22`)/`写入文件`(`:53`)/`追加文件`(`:79`) 上。

**它没有同名 `.light`，所以不在任何指标的分母里。** 这是六轮来最大的度量盲区 —— 不建这份清单，「纯光明」永远是相对的。

**清单要求**：114 个函数逐个登记 `名字 / 职责 / 当前实现语言 / 目标落点 / 证据文件行`。分五类：
1. **必须留在 Python/C 的**（真系统调用边界：文件 I/O、环境变量、stdin/stdout、时间戳、随机源）→ 标 `native_required`，并注明「原生腿由 `runtime_typed.c` 的哪个符号对应」（这条同时是 B9 的输入）
2. **纯计算，能立刻搬**（字符串 30 余个、列表/字典操作、类型判定、统计/数学）→ 标 `movable`
3. 已有纯光明替身的 → 标 `has_light_impl` + 落点
4. 重复/死码（`builtins.py` 与 `stdlib/数学.py` 有重叠项：`阶乘/平均数/中位数/方差/标准差/圆周率`）→ 标 `duplicate`
5. 零调用点的 → 标 `unused`，S3 删

**「地板自举率」= 纯光明实现数 / (总数 − native_required 数)**，只升不降。分母要扣掉真边界，否则这个指标永远到不了 100% 而变成摆设。S1 末给出基线数值，G9 接管门禁。

## 4. S2：地板搬迁（目标 ≥40%）

按清单的 `movable` 类逐批搬。**做法**：新建 `stdlib/内置核心.light` 等纯光明模块实现，然后改 `builtins.py` 让它**转发**到光明实现（保持 API 不变，避免 4000+ 测试大面积红），最后删掉 Python 原实现。

**三条硬约束**：
1. **不许让性能崩。** `builtins.py` 是热路径（每个产物都注入）。搬迁前后各跑一次 `benchmarks/` 或 `benchmark.py`，把数字写进报告。若某个函数搬完慢 10 倍以上，退回并在清单里标 `perf_blocked`。
2. **不许出现自举循环**：光明实现的内置函数自己又依赖被搬走的内置。`bootstrap_rate.py:168-185 查自导入` 会抓一部分，但循环依赖它抓不到 —— 你要自己画一遍依赖图，放进报告。
3. **注入点只许改一个 hunk**（`src/code_generator.py:735-741` 及其失败兜底 `:744-764`）。这个文件是 A9 的主战场，你越界改会造合并冲突。
