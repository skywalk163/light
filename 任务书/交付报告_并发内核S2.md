## 2. §3.1 结构化任务组（done · 本轮提交 689a5c87）

**结论先行**：经实证，嵌套取消在**现有实现下已经成立**，本轮 §3.1 是**补判据测试收口「深度嵌套未测」**，未改动 `stdlib/并发.light`（零风险，python_direct_calls 保持 251 不变）。

### 2.1 根因实证（为什么不用改代码）

- `并发等待`（`src/code_generator.py:268`）= `asyncio.gather`。`asyncio.gather` 在被取消时会**级联取消其子任务并等其终结**（`return_exceptions=False` 语义）。
- 因此 `任务池` 内部 `等待 并发等待(包装列表)` 一旦所在任务被取消，gather 会把取消信号递归下沉到所有子/孙任务，天然实现「外层取消穿透到内层孙子」。
- 探针实测（修复前状态，即未改任何代码）：
  - **向内三层**（外层 `全或无 [慢1(跑中层池), 立即失败, 慢2]` → 中层池 → 内层池 `[叶A,叶B,叶C]`）：立即失败触发外层取消后，最内层三个孙子叶子全部 `-被取消`，`孤儿数 = 0`。
  - **向外传播**（外层 `[A, B(跑内层池), C]`，内层 `B1` 失败）：`B1` 异常冒泡到外层 → 外层取消 `A`/`C`；捕获到的异常是内层 `B1` 的 `RuntimeError`（业务异常优先于 `CancelledError`），`孤儿数 = 0`。
- 故 S1 报告 §4「取消链的深度嵌套未测」是**测试覆盖缺口**，不是实现缺口。

## 3. §3.4 超时能真掐（done · 本轮提交 c06501f3）

**背景/裁决**：任务书 §3.4 指出 `examples/harness/评测驱动.light` 的「限时」包了 `asyncio.to_thread(...)`，`wait_for` 掐掉的只是「等待线程完成」的 Future，**线程里真正跑的阻塞调用不会被强杀**；且 `取消令牌`（事件总线.light:237 完整 AbortSignal）**全仓没有任何生产侧赋值入口**，`代理循环.light` 里 `取消令牌` 永远默认空、`是否已取消()`（代理循环.light:521）是死代码。A9 四条语言缺陷（见 §5）中第 2 条（裸 `捕获` → `except Exception`，抓不到 `CancelledError`）仍未修，故协作式取消**不能靠抓异常**，必须走显式 `是否已取消()` 布尔闸门。

**方案选型（用户拍板 = C / Hybrid）**：动 harness 架构前先说方案，给出两条路——
- A 进程隔离 + kill：每条 agent 丢子进程，超时 `进程.terminate()`(SIGTERM→SIGKILL)。能强杀死阻塞 syscall，但 harness 改动大、需 IPC 序列化、Windows/FreeBSD spawn 限制。
- B 真异步化 agent 循环：把 `代理循环.运行` 改真异步，LLM 走 `流式` 已搬进类内的 `协程读体` 等异步腿；超时 = wait_for 取消 + `取消令牌.取消()` 闸门。**改动最小、跨平台一致**，但协作式、不强制杀完全不 await 的死阻塞。
- **C Hybrid（采纳）**：以 B 为主（LLM 主路径真掐 + 取消令牌生产接入），额外在 agent 超时后调 `取消令牌.取消()` 并走「线程级 detach」（不再 re-await 已被取消的 to_thread 任务，worker 跑完即回收，事件循环不被阻塞）。覆盖超时场景绝大多数（LLM 多轮/多工具），改动面远小于 A。
