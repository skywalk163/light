### A3-2　协议等价的 mock DeepSeek server【P0，M4 的判绿点】

**文件**：新建 `tests/test_deepseek_mock.py`

现有 `tests/test_agent_loop_light.py:92-145` 的回放服务器**只按请求序号发帧，不看请求内容**。
新写一个**会读请求体的** mock：

- 真 HTTP/1.1 + 真 SSE 分帧，`bind(("127.0.0.1", 0))` 取回端口
- **先解析请求体 JSON 并断言**：`tools` 存在、结构合法、`tool_choice == "auto"`、
  `messages` 角色序列符合预期；**不合法就返回 400 + 明确错误体**，让测试红在「我们发错了」上
- 第一轮请求 → 回 `tool_calls` 分片（分两帧，`arguments` 切在 JSON 中间，
  沿用 `tests/test_llm_client_light.py:167-174` 已验证的分片形态）
- 收到含 `tool` 角色消息的第二轮请求 → **断言 `tool_call_id` 与第一轮下发的 id 一致**，
  再回最终文本
- **无 skip，任何机器上都必须绿**

这条用例的价值：它是唯一能在没有 API key 的机器上证明「我们的请求协议是对的」的东西。

### A3-6　token 预算截断【P1】

**文件**：`stdlib/代理循环.light`

现状 `:46-71` 的 `截断` 按**消息条数**（默认 20 条，`:81`），全 stdlib 搜
`token` / `词元` / `max_tokens` **零命中**。这在真实 harness 里必然炸——
一条 50KB 的文件读取结果和一条「好的」占同样一格。

- 加一个**可插拔的估算器**：默认用「字符数 / 系数」的粗估
  （中文 ≈ 1.5 字符/token，英文 ≈ 4 字符/token，写成常量并注明是粗估），
  留出 `设 己.计数器 为 <可调用>` 的注入口，将来接真 tokenizer
- 截断策略：**保前导连续 system**（现状已有）+ 保最近若干轮完整
  + **绝不切开 assistant.tool_calls 与其配对的 tool 消息**（切开会让服务端 400）
- 单条消息本身超预算时：**截断该消息内容并留明确标记**
  （如 `...[已截断 N 字符]`），不许静默丢整条
- **判据**：一条用例构造超预算历史，断言 ①总估算 ≤ 预算 ②tool_calls/tool 配对没被切开
  ③system 还在 ④被截内容带标记

### A3-7　事件总线不许吞签名错误【P0，这是一条活的假绿】

**文件**：`stdlib/事件总线.light`、`tests/test_agent_loop_light.py`、`tests/test_event_bus_light.py`

实测到的活案例：

- `stdlib/事件总线.light:143` 用 `处理器(事件名, 载荷)` **两参**调用
- `tests/test_agent_loop_light.py:243` 订阅的是 `lambda payload:` **一参**
- TypeError 被 `stdlib/事件总线.light:152` 的 `捕获 错误` 吞掉
- → `events` 恒为空 → `:243` 附近的 `assert len(events) <= 3` **空转通过**

改法：

- `捕获 错误` 收窄。只吞「处理器内部的业务异常」，
  **签名不匹配（TypeError/参数个数错）必须抛出来**。
  实现上可以在订阅时校验可调用的参数个数（`inspect` 或 try 一次探测调用），
  或者在捕获后判别异常来源——**方案自选，但必须有用例证明「一参 lambda 订阅会立刻响亮失败」**
- 修 `TestMaxRounds`：签名改两参，并把 `assert len(events) <= 3` 换成
  **正向断言**（`len(events) == 期望值` + 事件名序列相等）。
  `<=` 这种上界断言在集合为空时恒真，是假绿的常见形态，**本轮起一律换成等值断言**
- 顺查 `tests/test_event_bus_light.py` 有没有同类上界断言，一并换掉
- **事件名冻结**照 `第三轮总纲.md` §4.4，签名保持两参，**不许为了迁就测试改成一参**
