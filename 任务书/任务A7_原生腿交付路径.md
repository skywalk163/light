## 0. 开工首日必须先定的一件事

**优化管线怎么修？** 现状（`src/llvm/compiler.py:169-185`）把 legacy pass 名塞进 `-mllvm`：
`-inline`(`:171`)、`-mem2reg`(`:172`)、`-loop-unroll/-loop-rotate/-gvn`(`:176-178`)、
`-loop-vectorize/-slp-vectorize/-licm/-simplifycfg`(`:182-185`)。clang 22 的新 PassManager
不认这些名字，于是 **O1/O2/O3 全部编译失败，而 `compile --backend llvm-typed` 默认就是 O2**
（`cli/light.py:1361`）。实测：

```
python -m cli.light compile hw.light --backend llvm-typed -o hw.exe
→ LLVM (typed) 编译错误: 运行时库编译失败:
  clang (LLVM option parsing): Unknown command line argument '-inline'.
python -m cli.light compile hw.light --backend llvm-typed -o hw0.exe --optimize O0
→ 成功；hw0.exe → hello world, rc=0
```

三条路线：
- **(a) 去掉 `-mllvm` legacy 名，直传 `-O0/-O1/-O2/-O3` 给 clang**（**默认取这条**）。
  理由：clang 自己的 `-O2` 就是一整套新 PM 管线，我们手动塞 pass 名本来就是在重复它，
  而且做得更差。代价是失去「精细控制 pass 顺序」这个从未被验证过的能力。
- (b) 按 clang 版本探测分支保留 legacy 名。**不取**：会把版本矩阵引进来，本机是 clang 22、
  CI 是 FreeBSD 另一套，两边行为分叉的成本远高于收益。
- (c) 自建 pass 白名单。**不取**：等于自己维护一份 LLVM 版本兼容表。

裁决结果写进交付报告第 1 项。**换路线要重贴四档实测。**

**同时要裁决的第二件事：O1+ 与 Duff's device 互斥怎么解。**
`tests/test_llvm_net.py:449` 注释明写「用 O0 跳过优化管线，避免优化器合并协程 yield 基本块」。
协程的挂起点是「写回 `resume_point` → `dv_coro_await` → `ret void` → 落 `resume_N:` 标签」
（`src/llvm/codegen_typed.py:3634-3651`），入口 switch 在 `:3459-3475`。
优化器一旦合并/重排这些基本块，`resume_N` 标签就对不上了。

- **默认方案**：给协程函数打 `optnone` + `noinline` 属性，让优化器整体跳过它们，
  其余函数照常优化。
- **如果属性必须在 codegen 侧发射**（即无法只在你的文件里加）：**立刻移交 B7，不许自己改
  `src/llvm/codegen_typed.py`**（越界即停）。移交要写清「需要在哪个函数、发什么属性、
  为什么不能在优化侧解决」。
- 无论走哪条，**M16 判据 2 必须包含「协程用例在默认优化档下真跑通过」**。
  如果最终结论是「协程只能 O0」，那就是**降级**：必须在 `docs/原生腿能力边界.md`
  （移交 B7 写）与 CLI 帮助里登记，并且 `run --backend llvm-typed` 遇到含协程的源码时
  **显式告知用户降档，不许静默降档**。
