## 1. S1 必做（两条，都是别人的阻断）

### 1.1 类体接受 `异步 段落`

**现状证据**：`stdlib/流式.light:345-348` 原文写着「光明的类体不接受 `异步 段落`，parser 直接报错……已登记移交 B5」，于是四个异步读腿 `协程收/协程读体/协程读分块/协程按行读取`（`:367/:396/:421/:447`）**全部落在模块级**，`stdlib/大模型客户端.light:186-196` 的 `流式对话2` 只能做个同步方法去调模块级的 `异步 段落 流式对话`（`:348`）。E9 要做结构化并发、F9 要写异步服务端，都会再撞一次。

**要求**：
- 类体内 `异步 段落 名字 接收 …：` 正常解析，转译成 `async def` 方法（含 `己.` 属性访问、`等待` 上下文检查照旧生效）。
- 名字限制的既有裁决仍有效（名字不许以「异步」开头），别顺手放开。
- 类内裸调用被隐式改写成 `己.同名` 这条既有行为，在异步方法里必须一致。
- 判据：新建 `tests/test_async_class_method.py`，至少四例：① 类内异步方法 + `等待` 真跑；② 类内异步方法调另一个类内异步方法；③ 类内异步方法读写 `己.` 属性；④ **反跑**：把 `异步` 去掉后 `等待` 应报「不在异步上下文」。

### 1.2 真 `最终`（finally）语义

**现状证据**：`stdlib/代理循环.light:699-710` 用「预置槽位 + 哨兵文本」兜住工作线程猝死，注释写明理由是**光明没有可依赖的 finally**；`stdlib/并发.light:65-73` 的 `带限流` 只能在成功/失败两条路径各写一次 `信号量释放`。第八轮还因为 `捕获` 折叠 bug，被迫把 `组装单模成功/组装单模失败` 抽成同步段落规避。

**要求**：
- `尝试 / 捕获 / 最终` 三段完整，`最终` 在正常返回、异常抛出、`返回` 提前退出三种情况下都执行。
- 同时修 `捕获` 折叠 bug（第八轮实测：在 `捕获` 体里写多段落调用会被折叠，只能靠抽同步段落绕）。**先写一条能复现折叠的最小用例，再修**，用例留在仓库里。
- 异步段落里的 `最终` 同样成立。
- 判据：`tests/test_try_finally.py`，六例：正常路径 / 异常路径 / `返回` 提前退出 / 嵌套 / 异步 / **反跑**（把 `最终` 体删掉，断言资源未释放的那条断言必须立红）。

## 2. S2（原生腿表达式补齐，至少两类）

`src/llvm/codegen_typed.py` 目前只支持 **16 个语句节点 + 19 个表达式节点**（清单见 `docs/原生腿能力清单.json`）。实测拒绝：

```
输出(表[0:2])
→ 原生编译失败: 原生后端暂不支持切片表达式（SliceExpr）…请改用 截取/子串 或转译后端
设 双 为 接收 x：x 乘 2
→ 原生编译失败: 原生后端暂不支持表达式「LambdaExpression」…
```

未支持全清单（`docs/原生腿能力边界.md:57-104`）：语句层 `ScopeDeclStmt`/`YieldStmt`/`TypeAlias`/`DecoratedFunction`/`AssertStmt`/`RunAsyncStmt`/`EmbedBlock`/`ClassDefinitionWithNested`/`SetLiteral`；表达式层 `ListComprehension`/`DictComprehension`/`SetLiteral`/`TupleLiteral`/`LambdaExpression`/`UnwrapExpression`/`Pipeline`/`SliceExpr`/`DictExpand`。

**优先级按「stdlib 里实际用了多少」定，不按难度定**：开工时先跑一遍统计（哪些节点出现在 `stdlib/*.light` 里、各多少次），把结果写进交付报告，再挑前两类实现。当前预判前三是 `SliceExpr`、`ListComprehension`、`LambdaExpression`（第五轮已把「一等函数值」落地，lambda 在 stdlib 里应该有量）。

**每实现一类，必须同步三处**（否则 `tests/unit/test_native_leg_capability.py` 会双向咬合失败）：分派链、`docs/原生腿能力清单.json`、`docs/原生腿能力边界.md`。注意那份测试是**双向互含**（防腐烂 + 防吹牛），只加代码不改清单会红，只改清单不加代码也会红。
