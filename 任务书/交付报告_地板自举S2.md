## 1. 为什么切成 5 个模块，而不是任务书说的一个 `内置核心.light`

三条理由，前两条是实测出来的：

1. **并行开发的物理前提**。本轮四路并行（字符串 / 判型 / 列表 / 字典+转换）同时写码，
   一个文件会让四路互相踩。按域切分后每路各写各的文件，零冲突。
2. **`导出` 多行会让 `__all__` 只剩最后一行**（实测的 codegen 缺陷，见 §6-B）。
   47 条塞进一个模块，`导出` 必然多行或单行超长；分模块后每个模块的导出面都能一行写完
   （`内置核心字符串.light` 例外，保留了 4 行 `导出` 与范本 `字符串工具轻量.light` 一致，
   因为地板转发走属性访问、不受 `__all__` 影响）。
3. **域内聚**：门禁把「替身已就位但未转发」按模块点名，分模块后进度条读起来是
   「哪一域搬完了」而不是「一个大文件搬了几成」。

模块与条数：

- `stdlib/内置核心字符串.light` —— 17 条（85 行）
- `stdlib/内置核心判型.light` —— 9 条（57 行）
- `stdlib/内置核心列表.light` —— 10 条（56 行）
- `stdlib/内置核心字典.light` —— 8 条（46 行）
- `stdlib/内置核心转换.light` —— 3 条（31 行）

五个模块都**无同名 `.py`**（不遮蔽任何既有模块）、首两行都挂魔数「纯光明实现」、
**零 Python 模块导入**（`python_direct_calls.py` 对新 `.light` 基线为 0，实测新增 0 行）。

## 2. §4.4 循环依赖：设计答案

问题：用光明写 `列表追加`，而「往列表加元素」本身可能又得调同名内置 → 无限递归，
而地板门禁只做静态 `import` 检查，抓不到这种退化。

**答案：本轮 47 条全部只用「语言级语法 + Python 内置直通」表达，一条都不回调同名内置。**
判据是逐条看生成的 Python：只要生成物里不出现 `_light_builtin.<同名>`，就不存在回路。

三类可用的表达手段（都实测过，见 §6 手册摘要）：

- **语言层直发 Python 内置**：`长(x)`→`len(x)`、`类型(x)`→`type(x)`、`范围`→`range`。
  不经 `_light_builtin`，所以 `列表长度` 写 `返回 长(表)` 不会回调 `_light_builtin.列表长度`。
- **中文方法名映射**：`表.追加(x)`→`.append`、`映射.获取(k,d)`→`.get`、`文本.替换(...)`→`.replace`、
  `文本.包含(子串)`→`(子串 in 文本)`。作用在对象上，与同名内置无关。
- **纯 ASCII 标识符原样透传**：`isinstance` / `str.isalpha` / `int` / `float` / `str` / `list`。

**哪些做不到、因此没接**（详见 §4）：`显示宽度` 需要 `unicodedata`（会破 Python 直调门禁）；
路径 6 条需要 `os.path` 的平台相关词法；`求和` 需要 Neumaier 补偿求和；JSON 3 条卡在
编译器缺陷。这些都不是「语言级语法不够」，而是「真依赖 Python 模块 / 有算法精度或语义前置」。

**这层判据不只靠静态**：`tests/test_pure_light_hook.py` 的 `_已转发` 表已从 7 条扩到 **54 条**，
每条都跑「把光明段落换成返回哨兵的替身，再调 `builtins` 同名函数，拿不到哨兵即红」。
54 条全绿（`63 passed, 1 xfailed`）。递归若存在，这条测试会直接栈溢出而不是假绿。

### 3.5 三条冻结契约（口径差，已显式对齐并被测试钉住）

1. **默认值只留在 `builtins.py` 的 Python 签名里**。光明侧写不了负数/表达式默认参数
   （`接收 x, y=-1:` 解析失败：期望冒号得到减号）。受影响 5 条：`替换字符串次数(count=-1)`、
   `列表弹出(索引=-1)`、`列表排序(反向=False)`、`字典获取(默认值=None)`、三个对齐的 `fillchar=' '`。
   转发时**显式把默认值传下去**，光明段落收满参。
   `test_默认参数只留在Python签名侧` 正面钉住这条差（Python 版少传参走默认，光明版少传参 TypeError）。
2. **`是空` 用 `类型(值) == 类型(空)` 表达 `值 is None`**。`值 is None` 在光明里生成非法 Python；
   `值 == 空` 会被 `__eq__` 恒真的对象骗过（放宽口径）。实测：`__eq__` 恒真对象两版都判 False。
3. **`是字母/是数字/是空白` 用类方法形态 `str.isalpha(字符)`**。写成 `字符.isalpha()` 时，
   非 str 入参抛 `AttributeError` 而 Python 版抛 `TypeError` —— 那是改写错误口径。

## 4. 没接的条目与实测理由（照上一棒格式，给下一棒省事）

### 4.1 上一棒留的 5 条，本轮维持不接（理由复核过，未重新评估）
- **`解析JSON` / `序列化JSON` / `美化JSON`**：落点 `JSON核心.light` 里 7 处 `抛出 新建 异常(...)`
  运行期 `NameError`。根因本轮再次实测确认仍在：`exception_name_map` 只在 `_generate_throw_stmt`
  的 `Identifier` / `ParagraphCall` 两条分支查表，`新建 X(...)` 是 `ClassInstantiation`，
  落到通用分支发射未绑定的 `_light_exc = 异常(...)`。属编译器车道。
- **`求和`**：CPython `sum` 走 Neumaier 补偿求和，光明朴素循环有精度回退。要接必须先在光明侧
  实现补偿求和并证等价。
- **`连接字符串`**：光明版对非字符串元素自动 `转字符串`，把 Python 的 `TypeError` 变成静默拼接
  —— 放宽错误口径，需裁决。

### 4.2 本轮新增的不接项
- **`显示宽度`**：需要 `unicodedata.east_asian_width`。光明侧要 `导入 unicodedata` →
  新 `.light` 的 Python 直调基线是 0，一行就判红。**真边界的邻域，但不是 native_required**
  （分类未动，仍是 movable）。建议下一棒等原生腿或 stdlib 有宽度表后再接。
- **路径 6 条（`连接路径 / 目录名 / 文件名 / 扩展名 / 分割路径 / 分割扩展名`）**：任务书把它们
  列为「最好下手」，我**不同意并且没接**。理由：`os.path` 是**平台相关词法**（Windows 走 ntpath：
  盘符、UNC、`\` 与 `/` 混用、`altsep`；POSIX 走 posixpath）。用纯光明写出与两套 `os.path`
  逐条等价的实现，等于在光明里重写 ntpath + posixpath 并做平台分派，而平台分派本身要读
  `os.name` —— 又回到 Python 直调。**本机能对齐 ≠ CI（FreeBSD）能对齐，而我无法实测 FreeBSD**，
  接了就是拿假绿换指标。建议主线先裁决「路径语义按哪套口径」再动。
- **`duplicate` 13 条数学类**：删码是 S3 的活，本轮未动。

## 6. 实测出来的编译器/语言层事实（新增记账，供下一棒与主线）

标 **A** = 静默错译（会造出错结果而不报错），标 **B** = 硬报错（不会造假）。

- **A：`文本[::-1]` 步长切片被静默错译**。实测 `"abcd"[::-1]` 得到 `"a"`（相当于 `[0:1]`）。
  这是本轮最危险的一条：它不报错，直接给错值。`字符串反转` 因此写成 `当` 循环逐字符倒序拼。
  **建议主线立项修 codegen 的 slice 省略端处理**。
- **A：裸 `捕获 值错误:` 被解析成「无类型 + 变量名」**，生成 `except Exception as 值错误`
  —— 把 `TypeError` 一起吞掉并改型成 `RuntimeError`。**必须写带括号的 `捕获 (值错误):`**
  才生成 `except ValueError:`。这条会把「只捕 ValueError」静默放宽成「捕获一切」。
- **A：多行 `导出` 会让 `__all__` 只剩最后一行**（每条 `导出` 各生成一句 `__all__ = [...]`，
  后者覆盖前者）。存量受害者：`stdlib/字符串工具轻量.light`（5 行导出 → `__all__` 只剩 4 个名字）。
  只有 `import *` 的消费方会踩到；地板转发走属性访问，不受影响。**建议 codegen 改成累加**。
- **A：`抛出 新建 异常(...)` 运行期 NameError**（§4.1 的根因，第三轮起就在账上）。
- **B：`A 并且 not B`** → 代码生成错误 `未知语句类型 (FunctionCallExpr)`。改两段式。
- **B：`非 X` 用在表达式里** → 「『非』是保留关键字，不能直接作为语句开头」。
- **B：`值 is None`** → 生成非法 Python（SyntaxError）。用 `类型(值) == 类型(空)`。
- **B：负数默认参数 `接收 x, y=-1:`** → 解析错误。
- **B：裸 `映射[键] = 值`** → 「赋值需要使用『设』或『令』」。写 `设 映射[键] 为 值`。
- **B：`删除 映射[键]`** → 运行期 `NameError: name '删除' is not defined`（`删除` 不是语句关键字）。
  删键写 `如果 映射.包含(键): 映射.pop(键)`。
- **B：`新建 列表()` / `新建 字典()`** → 生成 `列表()`，运行期 NameError。用 `[]` / `{}`。
- 另：编译器已把 `段落 名 接收 参数` 标为**废弃**（`src/parser_stmt.py:433` 每编译一个段落发一条
  DeprecationWarning）。本轮五个模块仍用 `接收`，与范本 `字符串工具轻量.light` 一致。
  **建议主线单独立一轮全 stdlib 统一换写法**，不塞进地板搬迁。

### 11.3 `求和`：光明侧 Neumaier，与 `sum()` 逐位等价

CPython 自 3.12（gh-100425）起 `sum()` 对浮点走 Neumaier 补偿求和，
所以原来那个朴素左到右累加的光明替身**本来就不等价**，直接转发是埋静默数值分叉。实测分叉：
`[1e16,1.0,-1e16]` sum=1.0 / naive=0.0；`[0.1]*100` sum=10.0 / naive=9.99999999999998。

`stdlib/列表工具.light:69` 重写成三段结构（对齐 `Python/bltinmodule.c: builtin_sum_impl`）：
整数快路径（全 int 回 **int**）→ 只有切出结果**恰好是 float** 才进补偿路径 → 其后一律朴素 `+`。
`补偿收敛`（:22）复刻 `cs_to_double` 的两个判据（补偿为 0 不加，保 `-0.0` 符号；补偿为 inf/nan 不加，
否则 `[1e308,1e308,-1e308]` 会把 inf 污染成 nan）。Neumaier 的**内层括号不许省**，
`补偿 + (高位 - 临时) + 参量` 会因左结合多一次舍入。

**一条真不等价，已按平台钉住**：CPython 整数快路径的单项溢出判据是 **C long**，宽度平台相关
（LP64 是 2**63-1，Windows/LLP64 是 2**31-1），光明侧问不到 `sizeof(long)`
（那要 struct/ctypes 直调，本文件不许有）。故做成显式第二参 `长整上限`，默认 LP64；
`builtins.py` 侧用 `struct.calcsize("l")` 算出本平台上界后显式传入，**两个平台都逐位等价**。
差异窗口：`|int 元素| ≥ 2**31` 且其后还有会抵消的浮点，例如 `[2**31, 1e16, 1.0, -1e16]`。

**第二条真不等价（跨版本），CI 打出来后补上**：`sum()` 的浮点语义**自 3.12 起**才是补偿求和，
3.11 及更早是朴素累加。第一版把宿主假设成 3.12+（开发机 3.14.7），于是 CI runner（3.11.14）
上 36 条判据红。修法与平台参数同构：加显式第三参 `启用补偿`（默认真 = 3.12+ 语义），

- `_探平台长整上限` 用 `sum()` 输出反推 C long 宽度 —— 3.11 下补偿量根本没留住，两种宽度
  都给 `2147483648.0`，探针无判别力。改成 3.11 宿主走 `struct.calcsize("l")`，

- 窗口样本第三列原本写「LLP64 上默认参数是否与本机 sum 分叉」（叠了宿主版本），改成
