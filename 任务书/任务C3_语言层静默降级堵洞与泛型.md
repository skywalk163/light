## 0. 一句话

**第二轮在 LLVM 语句层加了兜底，洞搬到了表达式层。这一轮把它堵完，并把「能力边界」从猜变成查表。**

---

## 1. 为什么

第二轮 A2 做对了一半：`src/llvm/codegen_typed.py:2644-2646` 给语句分派加了 else 兜底，
`_reject_unsupported_stmt`（`:2580-2585`）抛 `NotImplementedError` 带源码行号，
还加了「揭穿适配层伪装」的机制（`:2621-2628`，把 `AstAdapter` 包出来的
`<unknown:XXX>` 拆开报出原 v3 节点类型名）。`全局`/`外层`/`生成` 现在**响亮报错**，
不再静默编成一次标识符取值。这些都是真的，别推翻。

**但表达式层原封不动**：

```python
# src/llvm/codegen_typed.py:885   —— _gen_expression 链尾
return self._create_int_dv('0'), 'dv'

# src/llvm/codegen_typed.py:859-861 —— 未知 ParagraphCall
if expr.name in self._segments:
    return self._gen_typed_segment_call(expr.name, args)
return self._create_int_dv('0'), 'dv'
```

于是这些东西在原生腿**编译成功、产物行为错误**：
字典字面量（`DictLiteral`）、Lambda、字符串插值（`StringInterpolation`）、
列表/字典推导、切片（`SliceExpr`）、`RangeExpr`、`UnwrapExpression`、`Pipeline`、
**以及任何拼错名字的段落调用**。

最后一项特别恶劣：`结果 为 计算总和(表)` 里 `计算总和` 打错一个字，
原生腿会编成 `结果 = 0` 并且**编译成功**。语句层的口径没有传导到表达式层。

## 2. 要做的

### C3-1　表达式层 else 兜底【P0，本任务的核心】

**文件**：`src/llvm/codegen_typed.py`

- `_gen_expression`（`:820-885`）链尾的 `return self._create_int_dv('0'), 'dv'` 换成
  `_reject_unsupported_expr(...)`，抛 `NotImplementedError`，**必须带源码行号**
  （复用 `_reject_unsupported_stmt` 的行号获取逻辑，`:2570-2578`：
  取不到行号时明说取不到，**不许伪造 0**）
- `ParagraphCall` 分支（`:854-861`）的未知段落名同样报错，
  错误文本要区分两种情况：
  - 名字不在 `self._segments` 里 → **「未定义的段落：X。本模块已定义：A, B, C」**
    （列出候选，这是最省调试时间的一句话；候选多时截断到前 10 个 + 总数）
  - 名字在但类型推断失败 → 说明是类型问题，不是名字问题
- 同样接上「揭穿适配层伪装」：`AstAdapter` 也可能把未知**表达式**节点包成
  `Identifier("<unknown:XXX>")`。`Identifier` 分支要先查前缀
  （`_ADAPTER_UNKNOWN_PREFIX`，`:2565`）再报原 v3 类型名，
  否则会报成「未定义变量 `<unknown:DictLiteral>`」，把线索藏起来了

**这一改必然打红一批原生腿用例**——那正是它的作用：
把「静默错编」变成「显式失败」。逐条判定每一条新红：

- 属于「原生腿确实不支持该语法」→ 用例改成 `pytest.raises(NotImplementedError)`
  并断言错误文本含语法名，**或者**把用例改用原生腿支持的写法
- 属于「本来该支持、只是走漏到兜底」→ 补实现（见 C3-2）
- **不许为了让红转绿而把兜底改回返回 0**

### C3-2　按性价比补几个表达式（P1，量力而行）

补哪些，按「harness 复刻会不会用到」排：

1. **`DictLiteral`（字典字面量）**——`[键: 值]` 形态。
   harness 的消息/载荷全是字典，这是原生腿承载 harness 的硬前提。
   runtime 侧字典能力已有（原生腿支持 `IndexAccess`，说明有字典读写原语），
   缺的只是字面量构造。**这一条优先做**。
2. **`StringInterpolation`（字符串插值）**——日志/错误信息到处在用。
   可以降级实现为「拆成若干段 + 字符串拼接」，不必真做 format 机制。
3. **`SliceExpr` / `RangeExpr`**——循环与切片，常用。
4. **Lambda / 推导式 / `Pipeline` / `UnwrapExpression`**——这一轮**明确不做**，
   但要在 `docs/` 的能力边界表里写清「不支持，用 X 替代」。

**做不完的一律走 C3-1 的报错路径 + 写进边界表。**
`第二轮总纲` §5 明令禁止「只有壳的东西」——**加名字必须同时加实现或映射**，
反过来也成立：**不实现就必须报错，不许留静默降级**。

### C3-3　原生腿能力边界表（P0，这是给 A3/B3 与后来者的地图）

**文件**：`docs/` 下新建（或在既有语法文档里加一节）

第二轮的能力边界是靠读源码猜出来的。这轮把它变成**源码级守单点**：

- 一张表列出原生腿**支持 / 不支持**的语句与表达式，逐项标注证据行号
- 已核实的现状（改动前）如下，你改完要更新：
  - **语句层支持**（`_gen_statement`，`:2595-2646`）：
    `VariableDeclaration` `Assignment` `SelfAssignment` `CompoundAssignment`
    `IfStatement` `ForeachStatement` `WhileStatement` `ReturnStatement`
    `BreakStatement` `ContinueStatement` `PrintStatement` `TryStatement`
    `ThrowStatement` `ExpressionStatement` `ImportStatement`(当 no-op，`:2641 pass`) `AsyncScope`
  - **模块层额外支持**（`generate`，`:726-750`）：类定义（`_collect_class`，`:2437`）、
    接口定义（`:2441`）、段落定义、导出别名
  - **语句层不支持（已会报错）**：`全局`/`外层`(ScopeDeclStmt)、`生成`(YieldStmt)、
    `类型 X = Y`(TypeAlias)、装饰器(DecoratedFunction)、`断言`(AssertStmt)、
    嵌入块(EmbedBlock)、`异步 运行`(RunAsyncStmt)、集合字面量语句
  - **表达式层支持**（`:820-885`）：`NumberLiteral` `StringLiteral` `BooleanLiteral`
    `NullLiteral` `Identifier` `BinaryOp` `UnaryOp` `FunctionCall` `ParagraphCall`
    `IndexAccess` `ListLiteral` `ConditionalExpression` `PropertyAccess`
    `ClassInstantiation` `NewExpression` `AwaitExpression`
- **必须有一条源码级断言的测试守住这张表**（按本项目「判据表靠源码级断言守单点」的既定口径）：
  用例读 codegen 的分派表 / `isinstance` 链，与文档里的清单比对，
  **加了新节点忘了更文档就打红**。别写成手抄两份然后漂移

### C3-4　`AstAdapter` 覆盖率补全（P1）

**文件**：`src/compiler.py`

`AstAdapter._node_converters`（`:241-292`）缺了一批键：
`ScopeDeclStmt` `YieldStmt` `TypeAlias` `DecoratedFunction` `AssertStmt`
`EmbedBlock` `SetLiteral` `RunAsyncStmt` `PassStmt` …
所以它们全走 `:307` 变成 `<unknown:XXX>`。

- 现在这条链路的**行为**是对的（会被揭穿并报错），但**诊断质量**取决于
  `<unknown:>` 前缀有没有被正确拆开。C3-1 改完后补一条用例：
  **每一个未支持节点类型都能在错误文本里看到自己的真名**
  （参数化测试，一个类型一条，别只测一个）
- `PassStmt` 这种**语义上就是 no-op** 的，直接加个转换器编成空操作，
  别让它走报错路径——报一个「不支持 `略过`」的错很荒谬

### C3-5　泛型形参注解发射【P1】

**文件**：`src/code_generator.py`

现状（实测）：`generic_params` 已被引用，`类 栈[T]` → 头部 `T = TypeVar('T')`
+ `class 栈(Generic[T])`（`:919-930`、`:1820-1826`），这部分是真的。

**但形参注解丢了**：源码 `段落 压入 接收 值: T：` 产出 `def 压入(self, 值):`。
`:1442-1447` 的注释说目的是「让形参/返回值注解里的 T 有定义可指」——
**这个目的没达到**，因为注解根本没发射出去。

- 让形参与返回值的类型注解真发射：`def 压入(self, 值: T)`
- 段落级泛型（`段落 首个[T] 接收 表：`）：`:1442-1447` 刻意不在 `def` 头上发
  `[T]`（那是 Python 3.12 语法，产物要能在更老解释器上跑）——**这个决策保留**，
  但注解要发出去，否则 `T = TypeVar('T')` 就是一个孤立的无用声明
- 加真跑用例：断言产物里注解在位，**并且 `exec` 一遍产物证明它真能跑**
  （`typing.get_type_hints` 能解析出 `T`）。
  **不许只断言 `'T' in py_code`**——那正是第二轮明令禁止的「字符串断言式假测试」

### C3-6　`对于 每个 X 在 [...]` 的语法坑【P1】

实测：`对于 每个 i 在 [1, 2, 3]：` 在**冒号处**报「无法识别的语法元素」，
而 `遍历` 语法可用。

- 先判定这是「该支持但坏了」还是「本来就没这个语法」：
  - 若 `对于 每个 … 在 …` 是文档里承诺过的语法 → **修好**
  - 若从来没承诺过 → **把错误信息改成指路文案**
    （「光明的遍历写法是 `遍历 X 于 表：`」），并在语法文档里明确写不支持
- 顺带核一件既有的口径混乱（前几轮登记过，一直没处理）：
  **推导式介词只认 `之`/`在`，`遍历` 语句认 `于`**——同一个概念两套介词。
  这一轮**不要改语法**（会打红一大片），但要在语法文档里把两套介词并列写明白，
  免得每个新来的人都踩一次

### C3-7　异步文件原语：定性并落地【P2】

`src/lexer.py:260` 的 `异步读取文件` / `异步写入文件` / `异步追加文件`
是**只有词法名、写了就 NameError**。

留名的理由是有道理的（`src/lexer.py:245-254`）：`异步` 是关键字，
删名会让 `异步读取文件("a")` 被切成 `await 异步` + `读取文件('a')`，结果被丢弃——
**用静默错编换掉响亮 NameError，方向相反**。

所以别删名。二选一：

- **A**（推荐）：在 `stdlib/` 建纯光明实现（用线程池把同步文件 IO 包成可等待），
  ⚠️ 但 `stdlib/` 是 A3/B3 的地盘 → **这一轮不做，写进移交清单**
- **B**：在 `src/code_generator.py` 加一条**编译期报错**，
  文案指向「暂无实现，请用同步 `读取文件` 或等待 stdlib 支持」。
  比运行时 `NameError` 早一步、信息量大一截

**选 B**。顺便普查：`src/lexer.py` 的复合标识符白名单（`:259-260` 一带）里
**还有没有别的「有名无实」**？第二轮已删 9 个死名字（依据见 `:239-243`：
全仓 37261 个 `.light` 里 0 处使用），但要重新扫一遍，
逐个确认「有映射 / 有 stdlib 实现 / 故意留名防错编」三者之一，
**都不是的一律处理掉**。清单写进交付报告。
