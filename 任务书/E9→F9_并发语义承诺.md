## 1. 任务池（`任务池(任务函数列表, 并发上限, 失败模式="逐条收集")`）

这是 F9 worker 主循环 / HTTP 服务端 handler 并发、调度器多 RPC fan-out 的**主入口**。

| 维度 | 承诺 | 违背时会怎样 |
|---|---|---|
| **签名与兼容** | `失败模式` 第三参可选，默认 `"逐条收集"`；调用方 `任务池(列表, N)`（两参）与 E9-S1 之前行为向后兼容。 | 若把默认值改成 `"全或无"`，现有两参调用方的兄弟错误会炸全场、取消所有请求 → F9 单条 worker 任务异常 → 整批同组被取消。 |
| **失败模式 = `"全或无"`** | ① 任一子任务抛 **Exception**（含用户业务异常，不含 CancelledError/KeyboardInterrupt 等 BaseException），**第一个发生的异常**记为「首异常」；② 首异常被捕获的瞬间，对所有 `not t.done()` 的兄弟任务调 `t.cancel()`；③ 所有兄弟任务必须在函数返回前**真正终结**（无孤儿 Task，即 `asyncio.all_tasks()` 排除当前后 ∀ PENDING）；④ 清理过程中若因 Python 3.11+ `CancelledError = BaseException` 漏网，会被外层 `尝试/最终` 兜底并**重新抛出首异常**；⑤ 最终调用方永远拿到**首异常**，不会拿到 CancelledError。 | 若跳过「取消兄弟」一步（反跑 2 验证）：asyncio.run 退出时未完成子任务仍在睡 → 孤儿数 ≥1，调用方断言红；若取消后不清理（CancelledError 漏出）：调用方拿到 CancelledError 不是业务异常，F9 重试链会误判。 |
| **失败模式 = `"逐条收集"`** | ① 每个子任务各自跑，成功槽 = 返回值，失败槽 = **异常对象本身**（不是 None、不是字符串，是真正的 `isinstance(x, Exception)`）；② 结果顺序 **严格等于提交顺序**（`结果[i]` 对应 `任务函数列表[i]`）；③ 不会因为第 i 条失败就影响第 j 条调度（不取消兄弟）；④ 所有任务（含失败的）全部跑完后才返回。等价 `asyncio.gather(*tasks, return_exceptions=True)`。 | 若改成「失败直接抛」（反跑 6.2 验证）：gather 炸锅、返回列表长度 < len(输入)、顺序断言红；若把失败槽填 `None`（A9 catch 折叠 bug 的旧行为）：`isinstance(None, Exception)=False`、`错误串 is in str(None)=False` → 红。 |
| **并发上限（背压-钳制）** | ① `并发上限 = N` 时，同一时刻真正在 `await 用户函()` 的任务数 **≤ N**（滑窗：完成一个立即补一个，**不是分批 barrier**）；② 信号量获取在 `尝试` 之前、释放在 `最终`，即使子任务抛异常/被取消也必归还（**绝不永久泄漏令牌**）。 | 若把释放从 `最终` 拿出来：异常路径漏释放 → 信号量慢慢死锁、后续任务永远拿不到令牌 → 并发上限 2 在 2 次失败后变 0；若改成「分批 barrier 实现」（反跑 1 验证）：长尾耗时 0.30+0.01s 的节奏变成 0.30+max(0.01,0.01)=0.31 但起跑时序变了，滑窗时序断言红。 |
| **模式非法值** | 失败模式不为 `"全或无"` 也不为 `"逐条收集"`（含 `None / "" / 任意其他串`），立即抛 **ValueError**，且 `err.args[0]` 一定包含**中文字面量「失败模式」**四个字；不会把非法值静默当默认。 | 会把 F9 传的错参数（如 "failfast"、"`batch"`）悄悄放行，造成上面两项的语义不可控；且任何 debug 时都会看不见根因。 |
| **提交流程** | 返回列表长度 == `len(任务函数列表)`；第 i 个槽 = 第 i 个子任务结果（成功值 or 失败异常对象 or 全或无模式下不存在，因为直接抛）。 | 顺序错/长度错 → F9 调度器 worker id 与结果对不上、幂等键重派 → 重复计分、丢条、不幂等（直接踩 M24 分布式终验红线）。 |

### 滑窗 ≠ 分批 的承诺（长尾判据）

这一条是分布式调度器「**总耗时 ≈ 长尾单条耗时 + 首条串行初始化**」结论的地基，不是单纯性能调优：F9 若把 E9 的任务池当成分批器，会把「worker 队列的等待时长」算错 2×–N×。

```
耗时数组 = [慢任务0.30s, 快任务0.01s, 快任务0.01s, 快任务0.01s], 并发上限=2
滑窗 E9 承诺  ：总耗时 ≈ 0.30s，第 3 个任务的起跑时刻  < 慢任务的完成时刻（0.30s档）
分批 barrier  ：总耗时 ≈ 0.30 + 0.01*2 = 0.32s，第 3 个任务的起跑时刻 >= 慢任务的完成时刻（等整批）
```

**违反后果**：F9 调度器按「N 任务分 ceil(N/上限) 批」算时间余量，会把 worker kill kill 阈值设早了 / 晚了 → M24 中途 kill 一条时 worker 可能任务还在跑（不该丢的丢了）或 kill 后等太久（该杀的没杀）。

## 2. 信号量背压（`异步信号量(N)` / `信号量获取` / `信号量释放`）

| 维度 | 承诺 | 违背时会怎样 |
|---|---|---|
| **等待语义** | `信号量获取(信号量)` 在令牌数 = 0 时**阻塞等待**，不会抛异常、不会返回假值；令牌一有释放即按 asyncio 默认 FIFO 公平性竞争（F9 不得假设严格公平，但也不得假设饥饿）。 | 若改成「满了抛错」：F9 要在外层加 while/retry，且可能和调度器自旋抢令牌造成活锁；E9 不保证自旋时的公平性。F9 不要赌。 |
| **释放后必归还** | `信号量释放` 写在 `最终` 块内（见 `带限流`），用户任务抛 Exception / CancelledError / 任何路径（甚至 Python GIL 级异常）只要出了协程栈，令牌必归还。 | 泄漏令牌 = 死锁，E9 S1 代理循环并行段「槽位回填在 最终」同样口径兜底。 |
| **N=0 或负** | `异步信号量(N)` 行为与 `asyncio.BoundedSemaphore(N)` 一致（Python 3.8+ 语义：BoundedSemaphore(0) 即永远拿不到，不抛 ValueError）。E9 不改变这口径。 | 若上层传 0，属于调用方 bug；E9 不拦，直接透传 asyncio 行为。 |

## 3. 并发等待 / 全或无等待（结构化并发的两块基石）

| 原语 | 承诺 |
|---|---|
| `并发等待(任务列表)` → `List[结果]` | 等价 `asyncio.gather(*tasks)`：**失败快进**——任一条抛 Exception，其他任务**不取消**、继续跑到终结，函数把第一个异常向上抛出（这是与「全或无等待」的关键区别）。调用方需要兄弟取消时，必须显式改用「全或无等待」或「任务池+"全或无"」。 |
| `全或无等待(任务列表)` → `List[结果] or 抛首异常` | ① 成功 = 并发等待语义；② 首异常发生：`遍历任务.cancel() 非完成 → create_task(吞异常等待) 并等待清理完毕 → 用 最终 兜底重新抛出首异常（绕 CancelledError=BaseException）`。**调用方永远拿不到 CancelledError 作为首异常**。 |

**承诺对 F9 的意义**：HTTP 服务端 handler 并发查询多个节点（fan-out）时，如果希望「一个节点超时 = 整个请求失败且取消所有其他节点请求」，就把 fetch 列表包进「任务池(..., 失败模式="全或无")」，F9 自己不用写取消传播逻辑；如果希望「能拿几个算几个、坏的填 None」就用 "逐条收集"。

## 4. 取消传播（这是结构化并发 vs 老 asyncio 最大分野）

| 维度 | 承诺 |
|---|---|
| **谁有权取消** | 只有 `全或无等待` 捕获到首异常后，**自动**调用兄弟 `.cancel()`；调用方（F9）也可以对 `任务池` 外面的 `create_task` 包一层再 `.cancel()`——E9 不会在内部把 CancelledError 换成 Exception 吞掉（`带限流` 的 `捕获 异常 e: 抛出 e` 只抓 Exception，CancelledError 是 BaseException 原样透传）。 |
| **取消是协作式** | 取消靠 `await` 点（`asyncio.sleep`、`socket.recv` 协程化后的 await 等）传播；纯 CPU 死循环 `while True: pass` 不会被取消（这是 asyncio 本质，E9 不承诺强杀）。 |
| **取消不丢信号量** | `带限流` 的 `最终` 一定跑，取消路径下令牌不泄漏（§1 并发上限承诺不变）。 |
| **CancelledError vs 业务异常的优先级** | 「业务异常（Exception）+ 兄弟取消引发 CancelledError」同时发生时，E9 承诺**业务异常优先**——调用方拿到的是业务 Exception，不会被 CancelledError（BaseException）盖住首异常。 |

**F9 注意点**：写 F9 的 HTTP handler / worker 主循环时，**不要**在最外层写 `except Exception: 吞掉一切`，CancelledError、KeyboardInterrupt、SystemExit 是 BaseException，必须原样上抛，否则 asyncio.run 无法干净退出，harness 测到孤儿。

## 5. 超时中断（`超时运行(协程, 秒)`，S1 已存在 + E9 验证）

| 维度 | 承诺 |
|---|---|
| 等价 `asyncio.wait_for(协程, 秒)`，**超时抛 TimeoutError**，协程本体的取消会沿 await 点协作传播；如果子协程里用了 `任务池` 里面的 `带限流`：信号量归还仍然靠 `最终` 不漏。 |
| **注意（已知限制，S2 解决）**：今天 `examples/harness/评测驱动.light` 的「限时」包了 `asyncio.to_thread(...)` —— wait_for 掐掉的只是「等待线程完成」的那个 Future，**线程里真正跑的阻塞调用不会被强杀**。这个限制 E9 S2「超时能真掐」会处理，S1 F9 使用时若把真实阻塞 RPC 包进 to_thread，请接受此限制或自行用进程隔离 kill。 |

## 6. 速率限制（min-interval pacing，`速率限制(每秒次数)` / `等待令牌(限制器)`）

| 维度 | 承诺 |
|---|---|
| 相邻两次 `等待令牌` 返回之间，**真实 wall-clock 间隔 ≥ 1/每秒次数 秒**；首个令牌**不**等（立即放行）；模块级共享同一 `限制器` dict（`编排限流器`）会保留「上次放行时间」状态（跨调用不丢）——这是 F9 HTTP 服务端做「QPS 防护」时可直接复用的 pacing 原语。 |
| 若 `每秒次数 = 0` 或负，行为未定义（F9 不要传）。 |

## 7. 代理循环 · 工具并行段（`并行槽体 接收 槽号, 项`）

| 维度 | 承诺 |
|---|---|
| 每一个工作线程 body（`并行槽体`）无论正常结束、`执行工具` 内部转成错误文本、还是线程级 Exception 逃逸，**都会在 最终 里写自己槽号的结果文本**（预置哨兵文本 + 最终兜底 = 双重保险）——不会出现「某一槽永远空着、join 完了还 None，主线 读槽位 卡死」这种故障模式。 |
| 槽位读写有 `并行槽锁` 保护（threading.Lock），并发写不同槽号不要求锁，但写同一结果表对象有 GIL + 锁双重保障。 |
| 这是 代理循环工具链 内部协议，F9 除非复用同一个代理循环，否则不直接消费；列在这里是因为 E9 S1 动过它，行为已从「哨兵文本单独兜底」升级到「哨兵文本 + 最终 双兜底」，语义更硬、无回退。 |

## 8. 变更通知流程

本文件任何一条承诺的**语义必须**变（例如：修了 A9 codegen bug 后把「双层捕获/抛出 e」绕法删了），按以下流程走：

1. E9 在 worktree 改 `stdlib/并发.light` + 本文件对应行的**承诺说明**，并加「变更日期 + 对应 A9 单号」注释；
2. 跑 `_taskE9_antirun{1,2}.py` 两条反跑 + TestTaskPool 6 条，确认绕法清理后仍 **正常绿 / 反跑红** 双边成立；
3. 给主线发一条消息并 @ F9 负责人（或等主线轮询）：「E9→F9 语义承诺的第 X 条 Y 维度，绕法 Z 因 A9 的 W 交付可清理了，请 F9 在自己的下一阶段里复查并删对应依赖」；
4. 只有 **F9 确认自己没有反向依赖**（或已改掉）后，E9 才合入下一阶段。本承诺**不做静默升级**。
