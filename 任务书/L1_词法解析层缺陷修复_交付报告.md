## 3. 根因分析

缺陷族根因（L-004/L-010/L-011/L-012/L-015）同源：**`lexer.py` 的 `_tokenize_chinese_sequence` 在遇到连续汉字串时按「关键字前缀」做边界拆分**。当调用方模块不认识被调方成员名/模块名（不在预扫描白名单 `user_definitions` 内）时：

- `对象.导出事件表` → `导出`(KEYWORD) + `事件表`(IDENTIFIER)
- `结果.返回码` → `返回`(KEYWORD) + `码`(IDENTIFIER)
- `外部命令.等待进程` → `等待`(KEYWORD) + `进程`(IDENTIFIER)
- `终端.终端会话` →（DOT 前 `终端` 靠 `导入 终端` 白名单保整段；DOT 后 `终端会话` 无白名单）→ `终`(KEYWORD) + `端会话`
- `从 异步样例 导入` → 预扫描只收集 `导入` 之后的名字，模块名 `异步样例` 不在白名单 → `异步`(KEYWORD) + `样例`

L-002 独立根因：`parser_expr.py` 的 `_parse_list_literal` 内「普通字典字面量」分支（`键: 值, 键: 值`）在逗号后与收尾 `]` 前没有跳过 NEWLINE/INDENT/DEDENT（同文件 `_parse_dict_literal` 花括号分支已有该逻辑，此处漏写）。

## 4. 修复方案（全部落在允许修改的 2 个文件内）

### 4.1 成员访问整段标识符（L-004 / L-010 / L-011 / L-012 成员部分）

`light-merge-task-L1/src/lexer.py` · `_tokenize_identifier_or_keyword` 入口

在进入三层分词前新增分支：

```
if _is_han(source[i]) and i > 0 and source[i - 1] == '.':
    收集其后连续汉字序列 → 单一 IDENTIFIER 返回
```

- 依据：语言规范中 `.` 之后只可能是属性/方法名，绝不可能是语句关键字；此上下文整段匹配无歧义、不破坏「甲加乙→甲 加 乙」的无空格分词机制（该机制只作用于非 DOT 上下文）。
- 作用：`导出事件表`/`返回码`/`等待进程`/`终端会话` 等在 DOT 后一律整段成词。

### 4.2 模块限定类名（L-012）

`light-merge-task-L1/src/parser_expr.py` · `新建` handler

类名读取循环新增 DOT 分支，把 `模块.类名` 视为完整类名：

```
elif ct.type == TokenType.DOT:
    class_name_parts.append('.'); self._consume()
```

- 需与 4.1 配合：`终端会话` 整段成词后，`新建` 才能把 `终端.终端会话` 完整读入。
- 修复后生成代码：`终端.终端会话("python", [], None, None, None)`（不再是 `终端().终(...)`）。

### 4.3 模块名整段收集（L-015）

`light-merge-task-L1/src/lexer.py` · `_scan_user_definitions` 预扫描

- `search_targets` 增加 `'从'`；
- 新增 `从` 分支：跳过空白与相对导入前缀 `.`/`..`，收集模块名（汉字/ASCII/下划线/点号，支持 `a.b.c` 路径）进白名单（`ALL_KEYWORDS` 除外）。
- 与既有「`导出`/`导入` 列表收集」机制同构，属同机制补全。

### 4.4 多行字面量续行（L-002）

`light-merge-task-L1/src/parser_expr.py` · `_parse_list_literal` 内普通字典字面量分支

- 逗号后：跳过 NEWLINE/INDENT/DEDENT 再解析下一键；
- 收尾 `]` 前：跳过 NEWLINE/INDENT/DEDENT。
- 与同文件 `_parse_dict_literal`（花括号分支）行为对齐。

## 6. L-011 专项说明

**编译器侧修复已完成且正确**：`等待进程` 在 DOT 后整段成词，生成代码为 `外部命令.等待进程(None, 5)`；用 `校验编译.py` 与生成代码核验均确认成员不再被拆。

**原始判据用例无法转绿的唯一原因在用例自身**：`test_L011.light` 的「主」段落第 7 行 `设 结果 为 外部命令.等待进程(空, 5)` 把 `空`(None) 作为进程参数传入。stdlib `等待进程` 要求 `subprocess.Popen`，`None.communicate(...)` 运行期抛 `AttributeError`。这不是编译产物错误，而是调用约定不成立——`空` 不是合法进程，与编译器无关。

- 判据文件 `docs/功能对标/反跑判据.md` 亦明确：断言段（`断言修复后()`）才是语义判据，而它内部正是用 `后台执行("echo hi")` 取真实进程再调用 `等待进程(进程, 5)`。
- 为完整验证「外部命令.等待进程(进程, 超时) 正常调用」这一期望能力，构造了 `_taskL1_断言/test_L011_真实进程.light`（仅把主段落的 `空` 换成与断言段一致的真实进程，其余不动），启用断言后运行退出码 0，输出 `hi`，断言 `长度(结果.标准输出) > 0` 通过。
- 由于 lightharness 与 stdlib 均只读、且不在本次允许修改文件列表内，`等待进程(None)` 的容错属用例/载体层面问题，超出编译器修复作用域；若验收要求原始用例全绿，需用例方将主段落入参改为真实进程（或 stdlib 对 `空` 容错），此点已在报告中如实标注。
