## 0. 一句话目标

修复光明编译器**跨目录点号模块导入**缺陷（L-001）：`从 子目录.模块 导入 符号` 当前编译期不内联、运行期 `No module named '子目录.模块'`（即使子目录有 `__init__.py` 也不解析），使 `lightharness/examples/test_L001.light` 从「红」转「绿」。

## 1. 为什么必须做

真实工程项目都是分层目录组织（原版 deepseek harness 是 50 个分层 package）。光明目前只支持平铺/单层目录模块，无法承载真实工程结构。lightharness 已为此付出绕法成本（模块改名、复制 stdlib 等），L-001 是工程落地的基本门槛。

## 2. 现有基础（只读）

- 缺陷账 L-001 原文：`_resolve_local_imports` 只认同目录模块，点号导入不内联；运行期导入钩子也不解析 `子目录.模块`。
- 已定位：`_resolve_local_imports` 位于 `cli/light.py`（导入内联逻辑）。
- 运行期 `No module named '子目录.模块'`：涉及 lightharness 运行器安装的 `_light_import_hook` 与 light-merge 的模块解析链（`src/module_resolver.py` 等）。
- 已有最小复现包：`lightharness/examples/_import_test/`（含 `__init__.py` + `数据.light`），证明即使包目录正确也不解析。

## 3. 修复范围与文件边界（本任务独占，其他文件只读）

| 文件 | 说明 |
|---|---|
| `cli/light.py` | 导入内联（`_resolve_local_imports`）主战场 |
| `src/module_resolver.py` | 模块解析链 |
| 运行器导入钩子 `_light_import_hook`（lightharness 侧的 .py 钩子若需同步，**先读后改并注明**；原则上以编译器侧修复为主） | 运行期 .light 模块发现 |

**只读**：`src/lexer.py`/`tokens.py`/`parser_*`（L1 任务）、`src/code_generator*.py`（L2 任务）、lightharness 的 `examples/`（验收只读）。

> 注：本任务边界最小（单个缺陷），但**允许跨 `cli/light.py` 与 `module_resolver.py` 联调**——只要都在第 3 节范围内。若确需动 lightharness 侧 `_light_import_hook`，把改动理由写清楚并单独提交，不要混入编译器改动。

## 5. 验收标准

1. 在**你的独立编译器副本**上：
   `cd lightharness && set LIGHT_MERGE=G:\dswork\duan-light-merge\light-merge-task-L3 && python 运行.py examples/test_L001.light`
   **红→绿**（`造值()==42` 断言通过）。
2. 修复后**启用「修复后断言段」**（`断言修复后()`，断言 `造值()==42`）。
3. 反跑判据：删掉 `_import_test/__init__.py` 或改用平铺名，用例应红（证明不是假绿）；改回点号导入后恢复绿。
4. 不回归：`examples/test_工具.light`、`test_客户端.light` 等依赖 `从 src 模块 导入` 的用例仍全绿（排除 test_L0* 后 lightharness 全量不得新增红）。
5. 至少覆盖三种形态：① `从 子目录.模块 导入 符号`；② 多层 `从 a.b.c 导入`；③ `导入 子目录.模块` 后成员访问。
