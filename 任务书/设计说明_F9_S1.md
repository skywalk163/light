## 1. 为什么是 JSON-RPC over HTTP/1.1

| 候选 | 结论 | 理由 |
|---|---|---|
| gRPC / protobuf / HTTP2 | 不做 | 总纲红线 4 不许 pip 装第三方；自己实现 protobuf+HTTP2 吃掉整轮工时，M24 不需要 |
| 第三方 MQ（Redis/Kafka/RabbitMQ） | 不做 | 同红线 4 |
| 裸 TCP + 自定义帧 | 不选 | 客户端 `stdlib/流式.light` 已是 HTTP/1.1（socket+ssl 底座），服务端与之对称最省力；HTTP 的 Content-Length/chunked/keep-alive 语义现成 |
| **JSON-RPC 2.0 风格 over HTTP/1.1** | **冻结** | 客户端已有（`流式.light`），服务端 S1 自建；JSON 直接用 `stdlib/模式校验.light` 校验；错误码结构天然表达「可重试/不可重试」 |

## 2. 消息类型与状态机

六类消息：`注册 / 注销 / 领任务 / 交结果 / 心跳 / 取消`。

```
worker 启动 ──注册──▶ master（登记节点、建心跳表）
worker 空闲 ──领任务──▶ master（队列出队；空则 201）
worker 执行 ──交结果──▶ master（按任务ID 去重结算）
worker 周期 ──心跳──▶ master（刷新心跳表；带回取消指令）
worker 退出 ──注销──▶ master（在跑任务标记可重派）
master ──取消──▶ worker（S3 取消传播，中断在跑任务）
```

统一包装（每 RPC 一请求一响应，同步语义）：

```json
// 请求
{"jsonrpc": "2.0", "方法": "领任务", "参数": {"节点ID": "N3F2A1B0"}, "id": 7}
// 响应（成功）
{"jsonrpc": "2.0", "结果": {"任务": {...}}, "错误": null, "id": 7}
// 响应（失败）
{"jsonrpc": "2.0", "结果": null, "错误": {"码": 201, "消息": "无可用任务"}, "id": 7}
```

`id` 由客户端自增，服务端原样带回（HTTP/1.1 流水线/重排时对得上）。

## 3. 幂等键：M24「无重复计分」的唯一保障

三个概念必须分清：

- **任务ID**（`T<时间戳>-<随机>`）：任务的唯一身份，master 生成，**重派不变**。
- **幂等键**（`I<随机16hex>`）：一次**派发**的身份，master 每次派发新生成，随任务下发，交结果时原样带回。
- **去重表**：master 内存表 `task_id → 首次结算结果`，窗口 1800s（可配）。

为什么这么拆：M24 的杀 worker 场景里，同一任务会被派给 worker A（被杀）再派给 worker B（重派）。若去重按「幂等键」，两次派发的键不同，无法互认；按**任务ID** 结算，A 的结果丢了没交上、B 的结果正常结算，而「A 其实跑完了、结果也交上了、但 master 因超时已重派」这种情形下，A/B 两份结果同任务ID → 后到者被去重记账。重派换新幂等键则保证了「结果与哪次派发对应」可审计。

窗口 = 2 × 任务最大执行时间（默认 1800s）。窗口内重复 → `已接受=false`、去重数+1；窗口外同任务ID → 视为过期新任务。**去重必须记账**（报告里「重派 N 次、去重 M 条」），不能静默丢。

## 4. 错误码与可重试性

协议层错误码 0/100-104/200-202/300/500，与 harness 六类（超时/HTTP状态/连接/解析/工具/未分类）的映射见 `分布式线协议.json §错误码 §可重试口径`。要点：

- 六类口径直接复用 `examples/harness/错误分类.light:36-64`，不另造一套（任务书 F9 §3.1 硬要求）。
- 可重试 = 服务端暂态（201 队列空 / 202 撞上已结算 / 500 内部错 / 200 任务过期）或网络侧（超时/连接）；**协议/客户端错误（100-104）与任务执行失败（300）重试无意义**。
- worker 对可重试错误走退避（指数+抖动，S2 接 `stdlib/重试.light` 的 `退避秒`）。

## 5. 版本字段与演进

- `版本.major.minor`，请求里带 `协议版本` 字符串。
- major 不同 → 服务端回 100；minor 只升不降，服务端要求 `客户端.minor <= 服务端.minor`。
- 字段演进纪律：major 相同只允许「新增可缺省字段」，不许改语义、不许删字段。

## 6. 安全（S1 已定、S2 实施）

- **传输**：默认 `127.0.0.1` 回环。跨机监听需要显式开关 + 显式声明风险（S2 再说）。
- **认证**：预共享 token 放 `X-Auth-Token` 头，**常量时间比较**（`hmac.compare_digest` 等价物）。S1 服务端未实施认证——**当前无认证，仅限本机回环**（交付报告已显式声明）。
- **入站校验**：所有 RPC 消息先过 `stdlib/模式校验.light`（`$defs` 里的 schema 就是为它准备的），不信任任何字段。
- **路径参数**：落盘路径一律过 D9 `路径护栏`，远端不指定落盘路径（协议里没有路径字段——刻意）。

## 7. S1 服务端与协议的关系

S1 只交付「协议冻结 + HTTP/1.1 服务端」：

- 服务端是**通用 HTTP/1.1** 层（方法/路径/头/体 → 响应），RPC 语义（注册/领任务…）是 S2 在它之上的路由层。
- 服务端判据（`tests/test_http_server_light.py` 六例）验证传输层正确性：Content-Length / chunked / keep-alive / 并发 / 断连不崩。它们不验证任何 RPC 语义——那是 S2 的事。
- 协议 JSON 的 schema 在 S2 直接喂 `模式校验.light`，S1 先用 Python 侧 `json.loads` + 模式校验做一轮语法自检（见交付报告）。

## 8. 明确不做（记账）

gRPC / protobuf / 第三方 MQ / 选主 / 分布式事务 / 一致性存储 / 跨机加密（TLS 留给 B9 的 POSIX TLS 落地后评估）。
