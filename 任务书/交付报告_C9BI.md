### 3.2 处置：一律选 (a) 改指真实现

```python
'包含':       '_light_builtin.字符串包含',   # 原 _light_builtin.包含
```

**理由**：

1. `包含` 有真调用者，按任务书口径必须选 (a)，没有选择权；
2. 另两条选 (a) 而不是删，是因为真实现就在 `stdlib/builtins.py` 里现成躺着（`字符串包含 :512` / `替换字符串 :492` / `分割字符串 :482`），而本项目已定口径是「别名从缺算缺陷」。这一族的命名本来就松散且不自洽——`字符串包含` 是「字符串+动词」，`替换字符串`/`分割字符串` 是「动词+字符串」，同族两种词序并存。补上 `字符串替换`/`字符串分割` 让整族对称，零新机制零新语义；
3. 三条统一走 (a) 还有一个工程好处：护栏（§4.1）只需要「表里每个目标都必须真存在」一条规则，不需要为「哪些名字允许缺席」维护白名单。

### 3.3 顺手清掉的一处真隐患：降级兜底里的实参错序

`src/code_generator.py` 的产物前言有两条降级路径（stdlib 物理缺失时补 lambda）。里面写着：

```python

_light_builtin.字符串包含 = lambda s, sub: sub in s   # 容器在前

```

`包含` 那条的实参顺序**与全仓其余一切相反**：

- 真调用者 `包含(输入, 元素)` 是容器在前；
- 成员形式 `容器.包含(元素)` 发射 `(元素 in 容器)`，函数式等价物也是容器在前；
- 同族 `字符串包含` / `列表包含` 全是容器在前。

remap 之后这三条兜底 lambda（`包含` / `字符串替换` / `字符串分割`，两个分支各一份共 6 行）已经**无人发射**，成了死代码。我把它们删了：留着一条实参顺序写反的死代码，是等着下一个人照它去补内置、把语义写反。同时在两处留了注释说明为什么删。

`src/code_generator_unified.py` **不需要改** —— 实测它的 `builtin_map`（`:88` 起）里根本没有这三个 key，只有 `分割字符串`(:148) / `替换字符串`(:150)，本来就是干净的。

**取证（已逐字核对，不是猜）**：
