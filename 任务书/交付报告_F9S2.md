- 分支：`task-F9S2`（基于 main `38d5e270`），工作目录 `wt-F9S2`
- 交付范围：修好 gitea run 99 的挂死；把 `任务书/分布式判据清单.json` 的 **故障隔离** 从 `none` 抬回 `partial`
- 实测平台：**Windows 10 / CPython（本机）**。FreeBSD 一次都没跑过 —— 全文凡属推断处均已显式标注

## 1. 根因

### 1.1 取证链（三条事实，不得删）

1. gitea CI 只有一个 runner，是 FreeBSD（`fb5-freebsd`），一个 run 一个 job。**「本机 Windows 全绿」对 CI 零保证力。**
2. run 99（`286ac1f7`）pytest 跑到 97% 卡约 12 分钟被杀，日志里**没有一行 FAILED**。
3. 相邻 run 98（`7e4524b2`）同一 runner 通过，两个 run 的差异只有 F9 这一路。

事实 2 的形态（零进展 + 无 FAILED + 要外部杀）本身就是判据：**测试框架的超时、asyncio 的 cancel、代码里的读超时，三层兜底同时失效**，只有「事件循环被一个内核态阻塞调用冻住」能同时解释这三件事。

### 1.2 H1（头号根因）：accept 出来的连接套接字从未显式置非阻塞

S1 版只在监听套接字上做了 `setblocking(假)`（`stdlib/分布式/HTTP服务端.light:77`），accept 回来的连接套接字直接进 `新建连接`，靠「继承」。

- POSIX 明确规定 `accept()` 返回的套接字**不继承** `O_NONBLOCK`；
- Winsock 事实上继承 —— 所以 Windows 的绿是**踩在未定义行为上的巧合**，不是正确性；
- 一旦不继承：`收字节` 里的 `recv` 在内核里真阻塞 → 整个 asyncio 事件循环冻结 → 同一个 loop 里的客户端协程再也拿不到 CPU（双向死锁）→ 卡在系统调用里的协程 `cancel` 打不进去、`asyncio.run` 的收尾也打不进去 → 进程只能被外部杀。
- 读路径的 monotonic 截止（本用例 5.0s）在这里**救不了场**：截止是在 `捕获` 分支里检查的，而阻塞的 `recv` 根本不抛异常、永不返回。

**本机已实测证实（见 §3.1 探针 F）**：把 `置非阻塞` 反跑成 `setblocking(真)`（等价于模拟 POSIX 不继承），Windows 上立刻复现同一形态 —— `HUNG= True`，阻塞栈是 `处理连接 → 读请求头 → 收字节`，且 `RESP_LEN` 一次都没打印出来（客户端排队的写都刷不出去）。这不是「类似现象」，是同一条死锁。

### 1.3 H2：accept 腿「非 EAGAIN 即永久退出」

S1 版 `异步接受` 只有两臂：愿等 → 回选择器；**其他一切 → 返回 空**。而 `处理循环` 把 `空` 当停机信号 `跳出`。于是 FreeBSD 上一次 `ECONNABORTED`（客户端握手完成后立刻 RST）或一次 `EMFILE` 就让监听腿永久退出；此时 backlog 里的三次握手**已由内核完成**，客户端 `open_connection` 照样成功，然后对着一个再也不 accept 的服务端永远等响应 —— run 99 挂死的第二只脚。

### 1.4 S1 写错的归因，现予纠正

S1 合并点把根因写成「就绪探测在 kqueue 与 Windows select 上行为不一致」。**这条站不住，已在代码注释与判据清单里改写：**三处轮询（`收字节`/`发送字节`/`异步接受`）都是**先做 I/O、失败了才问 selector**，selector 假阴只多睡 0.5ms、假阳只多转一圈，都造不出 12 分钟零进展。纠正落点：

- `tests/test_http_server_light.py:52-82`（原 44-47 的错归因整段重写）
- `任务书/分布式判据清单.json:93`（原 91 行的 备注 整条重写）

### 1.5 顺手查出的另两处真缺陷

- **H3 选择器泄漏**：每条连接惰性建的 selector 只随套接字一起被丢掉，从不 `close`。Windows 的 `SelectSelector` 是纯 dict、不占内核 fd，所以本机永远看不出来；FreeBSD 的 `KqueueSelector` 每个都是一个真 kqueue fd。每条连接漏一个，叠上 CI 的并发与 jail 的 fd 上限，把 accept 推进 `EMFILE/ENFILE` —— 在 S1 版里那等于**直接触发 H2**，两个缺陷是串联的。
- **H4 发送侧无上界**：`是否愿等写` 原来只认 `SSLWantWriteError`，裸 socket 的 `EAGAIN` 落不进「愿等写」，于是发送侧一遇缓冲满就当致命错误抛。补了 EAGAIN 之后，`发送字节` 的 `当 偏移 < 总长` 循环就从「恒假、永不进入」变成**无上界自旋** —— 所以补 EAGAIN 与加截止**必须同时做**，单做任何一边都是把一个 bug 换成另一个。

### 2.2 `stdlib/选择器.light`（跨平台判定表，`流式.light` 与 `HTTP服务端.light` 共用）

- 抽出 `是否EAGAIN`，`是否愿等读` / `是否愿等写` 都走它 —— **`是否愿等写` 补上 EAGAIN/EWOULDBLOCK（H4 的一半）**。
- 新增 `是否可恢复接受错误(e)`：`ECONNABORTED / EMFILE / ENFILE / EINTR / ENOBUFS / ENOMEM`，全部用 `errno.*` 常量，**没有一个数字字面量**。
- 三类分法（愿等 / 可恢复 / 致命）写进注释；**认不出来的一律算致命**，白名单是刻意的：把未知错误当可恢复，等于给「监听腿已经废了却还在转」发通行证。
- `是否愿等写` 里删掉了一条冗余的 `ssl.SSLWantReadError` 臂（行为不变：`SSLWantReadError` 的 errno 是 `SSL_ERROR_WANT_READ=2`，不是 EAGAIN，由 `tests/test_stream_light.py:88` 看守），换成注释 —— 目的是不让 Python 直调门禁的计数无谓地涨。
- 头部能力清单同步加了 `是否可恢复接受错误(e)`；文件尾 `导出 是否可恢复接受错误`。

### 2.3 `tests/test_http_server_light.py`（330 → 603 行）：挂死必须表现为失败

> 这一项任务书写明「比修 bug 本身更重要」，理由 run 99 已经演示过了：挂死的红**不可诊断**。

- **删掉 S1 的 `pytestmark = pytest.mark.skipif(freebsd)`**。跳过不是修好，修好了就不许继续跳。
- 头部注释重写（`:52-82`）：保留三条取证事实，明确写「kqueue vs select 归因已被证伪」，把 H1/H2 写成真相。
- `限时(可等对象, 说明, 秒=5.0)`（`:88-94`）：`asyncio.wait_for` 超时 → `AssertionError("等「…」超过 N 秒仍未完成 —— 挂死必须表现为失败，不是卡死")`。**每一个会等网络的 await 都过它**：`asyncio.open_connection` / `read(4096)` / `readexactly` / `drain` / `wait_closed`。
- `跑服务端`（`:207`）三层兜底：用例主体套 `用例超时=60.0`；cancel 之后的收尾 await 也套；最外面挂 `faulthandler.dump_traceback_later(用例超时 + 30, exit=True)` —— **这一层是给「事件循环被冻住、wait_for 的定时器也不跑」准备的**，H1 那种挂死只有带外看门狗能打破，退出时会把所有线程栈打出来。
- 六判据扩到十判据，新增四条（每条都配已实跑的反跑，见 §3）：

| # | 用例 | 断言 |
| --- | --- | --- |
| 7 | `test_accept可恢复错误不终止监听` `:421` | 注入两次 `ECONNABORTED` 后：`状态 == 200`、`体字节 == b"ok"`、`已注入 == 2`、`接受重试数 == 2`、`完成数 == 1` |
| 8 | `test_停机原因区分正常停机与致命错误` `:450` | 优雅 `停止()` 后 `终止原因 == "正常停机"`，且 `错误数` 前后快照相等（不多记一笔） |
| 9 | `test_每条连接的选择器都被关掉` `:516` | `建 != 0` 且 `关 == 建`（给 `新建选择器`/`关闭选择器` 记账 —— fd 泄漏在 HTTP 语义上不可观察） |
| 10 | `test_发送超时不无界自旋` `:570` | `pytest.raises(连接中断)`、`尝试次数 > 1`（真自旋过，不是一次就放弃）、`0.4 <= 耗时 < 5.0`（截止真生效且没跑满上限） |

两处刻意的写法，避免假测试：

- 判据 8 的 `终止原因` 在**主体内部**优雅停机后轮询读取（≤2s），不是等 `跑服务端` 返回后读 —— 后者拿到的是 `''`，因为 `循环任务.cancel()` 早于 accept 协程恢复。并且**不在 `停止()` 里写这个标记**，让反跑点仍然指向 `异步接受`。
- 判据 10 用一个「恒抛 EWOULDBLOCK」的桩套接字，而不是真 socket 灌大包：Windows 会把 1MB 全缓冲下去（首版就是这么 `DID NOT RAISE` 的），而 `数据[偏移:]` 的 O(n²) 切片让更大的包不现实。**被桩掉的是操作系统的回答，不是被测代码**：`发送字节` 的截止判断、自旋、抛错全在真代码里跑。

## 4. 哪些是实测，哪些是推断

| 结论 | 性质 |
| --- | --- |
| 阻塞的连接套接字会冻住整个事件循环、cancel 打不进去、进程要外部杀 | **实测**（探针 F，Windows，`HUNG= True` + 阻塞栈） |
| H1/H2/H3/H4 的修复在本机行为正确、十条判据全绿、四条反跑都能立红 | **实测**（Windows） |
| `是否愿等写` 缺 EAGAIN、发送侧无截止是真缺陷 | **实测**（探针 D、E） |
| POSIX 的 `accept()` 不继承 `O_NONBLOCK` | 规范条文 + Windows 侧反向实测（本机 `accepted.getblocking()` 返回 `True` 却仍抛 `WinError 10035`，说明 Windows 这条路本身就不可信）。**FreeBSD 上未实测** |
| run 99 的挂死就是 H1（+H2 助攻） | **推断**。证据很强（形态唯一吻合、本机能复现同一死锁、相邻 run 只差这一路），但**没有 run 99 的进程栈**（它是被杀的，没留 dump），也没有一次 FreeBSD 上的运行 |
| H3 的 fd 泄漏在 FreeBSD 上会真把 accept 推进 EMFILE | **推断**。泄漏本身是实测的（判据 9 记账），「泄漏 × 连接数 > jail 的 fd 上限」这一步没有 FreeBSD 数据 |
| 修完之后 CI 会绿 | **未经验证**。本机是 Windows，`fb5-freebsd` 摸不到。要等这一路进 CI 才有第一份真数据 |

**一句话诚实版**：我在 Windows 上证明了「这几处确实是缺陷、修法确实有效、挂死确实能被本机复现」，我没有在 FreeBSD 上跑过任何一次。

### 4.1 FreeBSD 上一分钟内证实/证伪 H1 的探针（可直接粘到 runner）

```
python3 -c "import socket,os,fcntl;s=socket.socket();s.bind(('127.0.0.1',0));s.listen(1);s.setblocking(False);c=socket.create_connection(s.getsockname());a,_=s.accept();f=fcntl.fcntl(a.fileno(),fcntl.F_GETFL);print('listen_nonblock=',not s.getblocking(),'accepted_blocking=',a.getblocking(),'accepted_O_NONBLOCK=',bool(f&os.O_NONBLOCK));[x.close() for x in (a,c,s)]"
```

判读：

- 打印 `accepted_blocking= True accepted_O_NONBLOCK= False` → **H1 证实**：FreeBSD 不继承，S1 版必然在 `recv` 上冻住事件循环。
- 打印 `accepted_blocking= False accepted_O_NONBLOCK= True` → **H1 在该平台被证伪**，挂死另有归因，请优先怀疑 H2/H3，并把 `faulthandler` 的 dump 捞出来（`跑服务端` 已内建带外看门狗，下次挂死会自己吐栈而不是静静地卡死）。

配套两条（各 1 秒，选做）：

```
python3 -c "import selectors;s=selectors.DefaultSelector();print(type(s).__name__,'has_fd=',hasattr(s,'fileno') and s.fileno())"
```
→ 打出 `KqueueSelector has_fd= 3` 就说明 H3 的每条连接确实各漏一个真 fd（Windows 上这里是 `SelectSelector has_fd= False`，这就是本机看不出泄漏的原因）。

```
timeout 300 python3 -m pytest tests/test_http_server_light.py -v
```
→ 修完之后应当 10 passed；万一还挂，`timeout` 会给出 124 而 `faulthandler` 会先吐栈，不会再出现「12 分钟无 FAILED」的不可诊断态。

## 5. 残留欠账

1. **FreeBSD 实测为零** —— 头号欠账。这一路进 CI 的第一个 run 就是它的第一份真数据；若仍挂，先看 `faulthandler` 的栈（现在一定有栈）。
2. **故障隔离只到连接级** —— 节点级（一个 worker 炸不影响其余）尚不存在，S3 验收。
3. **没有「慢客户端不拖垮整机」的配额判据** —— 现在只保「不永等」（读写各有 monotonic 截止），没有并发连接数配额、没有单连接带宽/时长配额。
4. **`发送字节` 的 `数据[偏移:]` 是 O(n²)** —— 大响应体上是真开销（判据 10 的首版就是因此写不下去），本轮不改：改它要动切片写法，属于性能议题，不该混进挂死修复。
5. **认证仍未实施** —— S1 的欠账原样保留：`X-Auth-Token` 只在协议里冻结了，服务端不校验，仅限本机回环。
6. **`python_direct_calls` 基线待在合并点重建**（`248 → 251`）。
7. **`是否可恢复接受错误` 的白名单是刻意保守的** —— FreeBSD 若吐出白名单外的 errno，会被当致命错误终止监听（但**这次会记 `错误数` 并留下 `终止原因`**，不再是静悄悄地永久停止 accept）。这是有意的取舍：宁可显式炸出来，也不给「监听腿已废却还在转」发通行证。
