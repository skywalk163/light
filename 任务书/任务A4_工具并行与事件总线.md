## 0. 为什么并行不必等异步

复核确认：线程在这个仓库里**已经是真能用的**——
`进程树.light:313-314` 真用 `threading.Thread` 读 stdout/stderr，
`伪终端.light:112,234,301` 真用 threading/Lock。

而工具执行的本质是「一次阻塞的本地 I/O」（读文件、listdir、grep），
线程池就够；等 C4 的非阻塞 socket 是**网络**那条腿的事，两件事不必绑在一起。

所以本任务不依赖 C4。**但你要留出接口**：将来 `run_command` 若改异步，
`分发工具` 的调度层不该重写。

## 1. A4-1：注册表加 `副作用` 判据字段

现状 `代理循环.light:280-283`，注册表只有 4 个字段：

```
设 己.工具表[名称] 为 ["名称": 名称, "描述": 描述, "参数模式": 参数模式, "实现": 实现]
```

全仓 `.light` grep `只读|read_only|readOnly` 只命中无关的 `积木库/…/系统只读.light`——
**没有任何现成判据可用**。

按总纲 §4.1 扩成：

```
己.注册工具(名称, 描述, 副作用, 参数模式, 实现)   ← 不要这样，位置参数插中间会打断 B4
己.注册工具(名称, 描述, 参数模式, 实现, 副作用)   ← 按这个，第五参可省
```

- `副作用` 取值**只许** `"只读"` / `"写"` / `"执行"`，其它值必须**报错**而不是当默认
- **省略时默认 `"写"`**——默认必须最保守，漏标不许变成默认并行
- 下发给模型的 `工具声明`（`:295-301`）**不许带这个字段**（OpenAI 协议里没有它，
  多发字段有服务端 400 的风险；第三轮的教训就是协议层的东西不能想当然）

**判据 A4-1**：
1. 四参注册（省略第五参）的工具，`工具表` 里 `副作用` 是 `"写"`——**断字典内容，不是断没报错**
2. 传非法值（如 `"readonly"`、`"只讀"`、空串）必须抛错，用例断异常类型与消息
3. `工具声明` 的输出**逐字段断言**只有 `name`/`description`/`parameters`，不含 `副作用`
4. **反跑**：把默认值改成 `"只读"`，判据 1 必须变红

## 2. A4-2：`分发工具` 并行调度（只并行只读三件）

现状 `代理循环.light:460-478`：单层 `遍历 tc 之 调用`，逐个 `执行工具`（`:473`）后
`己.会话.追加工具(调用id, 名称, 执行文本)`（`:474`）。纯串行。

要做的：

1. 拿到一批 `tool_calls` 后，按 `副作用` 分组
2. **全部为 `"只读"`** 的一批 → 走线程池并行
3. 混有 `"写"` / `"执行"` 的 → **整批串行**（不许「先并行只读的再串行写的」重排——
   模型可能依赖调用顺序，比如先 write 再 read 同一个文件）
4. **结果回填顺序必须与模型给的 `tool_calls` 顺序一致**，不许按完成先后追加
5. 单个工具失败仍转成可读文本作为 tool 消息回喂，**不许让一个失败拖垮整批**。
   ⚠️ 这里原先写的是「仍按现状转成 `"工具调用失败: <原因>"`」——**那句话记错了现状**，
   而且不许照它去统一措辞。代码里两个前缀是**刻意区分**的，且是第三轮定的口径：
   - `"工具调用失败: "` —— 参数不是合法 JSON / 不合 schema / 工具未注册（`解析并校验`、`编排一项`）
   - `"工具执行出错: "` —— 工具实现自己抛了异常（`执行工具`）
   区分的意义在于这两个前缀是喂给**模型**看的分类信号：前者是「你的参数不对，改参数重试」，
   后者是「环境有问题，换路径或换工具」。合并成一个不会让模型看不懂（原因文本还在），
   但白扔一个零成本的分类。
   而且 `tests/test_harness_e2e.py:19` 的模块 docstring 与 `:151` 的
   `assert "工具执行出错" not in 工具消息["content"]` 已经把这个口径钉住了——
   统一措辞会让那条断言失去指向（`"工具调用失败"` 会同时覆盖校验失败）。
   **裁决（2026-08-23）：保留区分，改本文档措辞，不改代码。**

6. 并发度可配，默认给个小值（4 之类），并说明为什么

**这一条最容易写出「看起来并行了其实没并行」**，所以判据要死：

**判据 A4-2**：
1. **时序判据**：三个只读工具各故意 `sleep(0.3)`，并行跑总耗时 **< 0.5s**；
   把同样三个标成 `"写"`，串行跑 **> 0.9s**。**同一份用例里两种都跑，断比值。**
2. **顺序判据**：三个只读工具的完成顺序故意打乱（sleep 时间递减），
   断言回填进会话的 tool 消息顺序**仍与 `tool_calls` 顺序一致**
3. **隔离判据**：混合批（两只读 + 一写）必须串行——用同一组 sleep 断言总耗时 > 串行下界
4. **失败判据**：并行批里一个工具抛异常，断言其余两个的结果**都正常回填**，
   且失败那个是 `"工具执行出错: ..."`（**不是** `"工具调用失败: "`——见上面第 5 点的
   裁决，抛异常走 `执行工具`，参数/schema/未注册才是「工具调用失败」）。
   再加一条：失败**不许让整批退化成串行**，所以这条用例的总耗时也要断在并行区间内。

5. **反跑**：把线程池换回串行循环，判据 1 必须变红；
   把回填改成「按完成顺序」，判据 2 必须变红
