    11.1 pytest 捕获流被收紧成 strict，全量跑连锁报错¶

    tests/test_summary.py、test_class_definition.py、test_comprehensive.py 在模块顶层 调 sys.stdout.reconfigure(encoding='utf-8')——只给 encoding 会把 errors 一并重置回 strict，而 pytest 的 fd 捕获流本来是 errors='replace'。收紧后只要后面有用例往捕获流写进 非法字节，每次 setup/teardown 的 snap() 都抛 UnicodeDecodeError：实测 pytest tests --ignore=tests/e2e 出约 3565 个 ERROR、约 1780 条用例根本没真跑，而单独跑 那几个文件全绿——典型的顺序相关、单跑看不见的门禁污染。PYTHONUTF8=1 挡不住， 因为 reconfigure 的 strict errors 覆盖它。

    修法：补回 errors='replace'，并加 AST 级护栏 tests/unit/test_capture_encoding_guard.py（谁再写出不带 errors= 的 reconfigure 立刻红； 用 AST 而非正则，因为正则会把注释与文档字符串里的示例也算成调用）。

    11.2 Windows 上「引 C」整条链是死的¶

    L4「引 C」发射器只发一条 GNU 风格命令 -shared -fPIC -O2 ... -lm。Windows 上 clang 的默认 target 是 msvc，-fPIC 是硬错误（unsupported option '-fPIC' for target 'x86_64-pc-windows-msvc'），去掉后 -lm 又让 lld-link 去找不存在的 m.lib。

    修法：签名提取上移到编译之前并派生导出符号表，编译改成两条命令按返回码逐条回退， 第二条是 -shared -O2 -o LIB -Wl,/EXPORT:<每个符号> SRC（不写 .def）。两条都失败才报错， 报错带两次完整命令行与 stderr。判据 test_c_真编译真调用_取值正确：真编译真经 ctypes 调用， fact(5)==120、tri(2.5)≈7.5。

    11.3 文本级 IR 优化删 br 留标签，产出非法 IR¶

    optimizer_pipeline.py 的 _peephole_pass 有一条 re.sub(r'br label %(\w+)\s*\n\s*\1:', r'\1:')，把无条件跳转删掉只留目标标签，前驱块因此 没有终结指令；_merge_blocks_pass 也不看目标标签有几个前驱。clang 的报错形态是在标签行上 expected instruction opcode，落点全是 endif_2: / while_cond_1: / param_end_3: 这类行。 代价是 tests/test_p3_comprehensive.py 15 条红。

    修法：删掉那条不安全规则；_merge_blocks_pass 改为先算本函数内的标签引用计数 （覆盖 br label、条件 br 两个分支、switch 的 default 与每个 case 的单行/多行两种发射形态、 phi 的来源块），只有单前驱才合并，且此时 br 与标签行一起删。判据 8 条含两条反跑。

    11.4 每帧约 96KB 的临时槽位池¶

    codegen_typed.py 的 _temp_slot_pool_size = 2048 在 emit 时就写死进 alloca， LIGHTVALUE_STRUCT 对齐后 48 字节 × 2048 ≈ 96KB/帧，递归深一点直接爆栈。

    修法：延迟填数（_begin_temp_slot_pool() 发占位行 → _emit_temp_slot_pool() 按真实 _temp_slot_index 回填），4 处 alloca 走同一条路径；2048 保留为上限，溢出仍硬报错。 反跑取证：同一份 IR 把元素数改回 2048 → rc=0xC00000FD STATUS_STACK_OVERFLOW、stdout 空； 按真实用量 → stdout 20100。

    11.5 纯光明 .light 完全遮蔽同名 .py，能力倒退¶

    stdlib/_light_import_hook.py:141,155 的规则是：同名 .py 存在时，只要 .light 首行带 「纯光明实现」魔数就用 .light 完全取代 .py——不是兜底。断言工具 / 数据结构 / 字符串工具 / 日期时间 四份 .light 都带了魔数，把 77 / 29 / 81 / 100+ 个导出的 .py 换成 9 / 14 / 28 / 11 个导出的 .light，且命名不兼容。代价：test_stdlib_phase2.py 三条红、test_stdlib_phase9.py 一整批取不到符号、test_datetime.py 曾变成 collection error。

    修法：加「轻量」后缀独立成名（同 JSON → JSON编解码 的既有处置），原模块名仍由 .py 提供。 stdlib/列表工具.light 保留原名——它与 .py 导出名完全一致（各 10 个），遮蔽不丢能力。

    11.6 测试里的跨机绝对路径与子进程编码¶

    tests/test_stdlib_phase9~13.py 各自 sys.path.insert 了 'c:/traework/light/stdlib' / 'c:/dumatework/light/{stdlib,contrib}'——两种前缀混杂，都是别的机器上的路径，本机不存在， 整文件 ImportError。路径统一收到 tests/conftest.py 按 __file__ 推导。 积木库/评估/冒烟.py 的 subprocess 只在父侧写了 encoding='utf-8'（解码端），子进程无 env， Windows 下按 GBK 输出会被当成乱码误判成冒烟不通过；现钉 PYTHONIOENCODING=utf-8。

    15.2 stdout 的字节编码（Windows 上非 ASCII 输出不同字节）——已修复¶

    同一句 打印 "光明"。，输出重定向进管道/文件时：

    • 原生腿的 exe：吐 UTF-8 字节 e5 85 89 e6 98 8e
    • 转译后端（light run，本质是个 Python 进程）：修复前吐平台 ANSI 代码页 字节（中文 Windows 上是 cp936 的 b9 e2 c3 f7），修复后吐 UTF-8 字节 e5 85 89 e6 98 8e，与原生腿一致。

    根因：转译后端没有钉死自己的 sys.stdout 编码，跟随 locale.getpreferredencoding()； 原生腿写的是裸字节，源码是 UTF-8 就是 UTF-8。

    修复方案：在 src/code_generator.py 生成头区块（import sys 之后、stdlib 路径探测之前）注入：

    try:
    sys.stdout.reconfigure(encoding='utf-8', errors='replace')
    sys.stderr.reconfigure(encoding='utf-8', errors='replace')
except (AttributeError, ValueError):
    pass

    errors='replace' 是硬性要求——第四轮已踩过「reconfigure 默认收紧成 strict、 整场级联炸」的坑（见 §14.1），不加 errors='replace' 会把原本能输出的字符 变成 UnicodeEncodeError，比 cp936 丢字节更严重。

    反跑判据验证：Windows 下 打印 "光明" 重定向进文件，修复前字节为 cp936 （b9 e2 c3 f7），修复后字节为 UTF-8（e5 85 89 e6 98 8e），实测通过。

    测试覆盖： - tests/test_llvm_c3_expr.py::test_stdout_utf8_bytes——新增字节断言用例， 显式移除 PYTHONIOENCODING 和 PYTHONUTF8，重定向 stdout 进文件，断言 UTF-8 字节存在且 cp936 字节不存在。该用例不依赖 _run_transpiled 的环境变量 守卫，独立捕获 reconfigure 失效。 - tests/test_llvm_c3_expr.py::_run_transpiled 中原有的 PYTHONIOENCODING=utf-8 保留为回归守卫——若生成头 reconfigure 被移除或 破坏，此环境变量仍能拉平编码，使双后端字符级比对不因编码差异假红；但字节断言 用例会独立捕获 reconfigure 失效。

    R10-12c T5C：集合/随机/对象池缓存 .light 化 — O0 codegen 缺陷与能力边界¶

    概述¶

    T5C 将 stdlib/集合.light、stdlib/集合工具.light、stdlib/集合操作.light、 stdlib/随机.light、stdlib/对象池缓存.light 五个「decl 0 空壳」补为纯光明 真实现，并在 runtime_typed.c 新增确定性随机数运行时（dv_random / dv_random_seed / dv_random_bits），O0 下与 CPython random.seed(同种子) 逐位对拍（固定种子 42）。过程中发现的 O0 codegen 缺陷均以纯光明 workaround 绕过，不触碰 codegen 核心（归 T7）。

    算法偏离（任务书 LCG → MT19937，已定案）¶

    任务书要求 LCG，但对拍判据是「与 Python random.seed(同种子) 逐位一致」， LCG 不可能对齐 CPython —— 实现改为 MT19937（genrand_res53），并对齐 CPython 3.14 的播种口径：整数种子一律走 init_by_array（小端 32 位字切分； |seed| 取绝对值；seed=0 补单字 [0]）。dv_random_bits(k) 对齐 getrandbits「右移保留高 k 位」，k ≤ 63（k>63 截断、k≤0 返回 0，i64 上限）。

    缺陷清单¶

    T5C-01：builtin 浮点返回值参与算术时被误取 i64 槽（恒 0）¶

    • 现象：随机数() 乘 9007199254740992.0、时间戳() 乘 1.0 均为 0； 与浮点字面量的比较路径同样错。
    • 根因：_infer_expr_type(BinaryOp) 把「未知类型操作数 + 浮点字面量」 误判 FLOAT，_gen_typed_binary_op 快路径对未知侧执行 extractvalue ..., 1 取 i64 槽（浮点 DV 的 i64 槽恒 0）。
    • 修复：codegen_typed.py 三处 —— ① 算术分支要求两侧均在 ('FLOAT','INT') 才推断类型；② 算术 FLOAT 快路径加同条件；③ 比较 FLOAT 快路径加同条件。任一侧未知时回退通用 dv_* 路径，由运行时标签决定。
    • 归属：本批已修（codegen 3 处），非 workaround。

    T5C-02：追加 对函数参数（REF）无效，对字典读出句柄有效¶

    • 现象：函数内对参数列表调 追加 不生效（唯一元素(列表(1,2,1,3,2)) 得 0 元素）；对本函数内新建列表或字典读出的列表调 追加 生效。
    • 根因：O0 下参数经浅拷贝 REF 传递，列表扩容（realloc）后栈上壳指针 未写回。
    • Workaround：集合族所有变长构建改走「字典读出句柄」—— 设 元素 为 集合_列表(集合) 后再 集合_加(元素, ...)；或函数内自建 局部列表直接构建。
    • 归属：codegen 参数/写回语义，归 T7。
    • 状态：已修复（T7B / 2026-09-06）。codegen 新增「参数写回」链： 被调侧在返回出口把未被重新绑定的形参槽写回 %args[i]，调用侧再把 %args[i] 搬回实参变量（_emit_param_writeback + _emit_args_writeback）， O0 下列表/字典 REF 传递语义与 Python 一致。反跑 test_codegen_ref_dict_O0.py ::test_T5C02_REF参数追加写回_O0 绿。

    T5C-03：设 列表[i] 为 值 索引赋值损坏 REF 列表¶

    T5C-04：字典新增键经函数参数（REF）写回丢失¶

    • 现象：函数内 字典设置(缓存, "新键", 42) 对新增键无效（主内读回 空）；对已有键更新与重建值列表 + 字典设置生效。

    • 契约：缓存值不可为 空（与缺失语义冲突）。
    • 归属：codegen 字典写回，归 T7。
    • 状态：已修复（T7B / 2026-09-06）。字典新增键经函数参数的写回由 参数写回链覆盖（同 T5C-02）。workaround 已回退：对象池缓存.light 缓存 家族改回 {键: 值} / {键: [值, 截止]} 纯字典存储；新注册 字典删除 builtin（dv_dict_remove，codegen 声明+映射）支撑删除/清空。 反跑 test_T5C04_字典新增键REF写回_O0 与 test_对象池缓存_冒烟_O0 绿。

    T5C-07 [高] 字典设置 使写回前的列表句柄失效 → 读脏值 / 写丢失（本批已修，workaround）¶

    • 现象（同一根因的两种表现）：
    • 读脏值（仅 POSIX 暴露）：集合.移除元素 对存在的元素也抛 值错误。
    • 写丢失（双平台均存在）：集合操作.分组 每个分组恒少收 1 个元素 —— 分组(列表(1, 1, 2)) 得 {1:[1], 2:[]}，而应为 {1:[1,1], 2:[2]}。
    • 根因：字典设置(字典, 键, 值) 会重绑/释放底层缓冲，使「写回前取到的 列表句柄」失效。事后对该句柄的读是未定义行为，写则落进已释放缓冲。
    • 移除元素 原实现在 字典设置 之后才比较 长(列表) 与新长度： Windows 上该块内存读作 0（0 != 2，不抛错 —— 侥幸通过）； POSIX/glibc 上被复用后读作 2（与新列表同长）→ 误判「没删掉」而抛错。
    • 分组 原实现在 字典设置 之后才 追加(组, …)，该次写入丢失。
    • 取证：探针打印「写回后旧句柄长度」——Windows 0 / Linux 2。同一份 UB 读出两种脏值，是「Windows 绿、POSIX 红」的直接证据（探针见交付记录）。
    • 修复（.light 层 workaround，不碰 codegen，归 T7）：
    • 移除元素：写回前先 设 原长 为 长(列表) 快照，比较前置。顺带使 「元素不存在」时不再产生半截写入，与 Python set.remove 抛 KeyError 且 不改集合的语义一致。
    • 分组：新建组改为先追加、后写回；已存在的组走「字典读出的句柄 + 追加」（T5C-02 认定该路径生效）。
    • 回归测试：test_集合_移除元素_句柄失效回归_O0（含「缺失元素仍须抛错」的 尝试/捕获 断言，防止修复把语义改成静默成功）、 test_集合操作_分组_组内元素不丢失_O0。
    • 注意（测试盲区）：原 test_集合操作_排序_打乱_去重_对拍_O0 只校验 分组 的键数（恒为 2），掩盖了组内元素丢失；新用例补齐值维度。
    • 归属：根因仍在 codegen 的字典写回 / 句柄失效语义，归 T7；本批以 .light 层 workaround 修，与 T5C-02~04 同一处置口径。
    • 状态：部分已修复（T7B / 2026-09-06），拆两个维度：
    • REF 函数参数维度（跨函数把 dict/list 传入、函数内 字典设置 改到 实参上）：由参数写回链根因修复，与 T5C-02/03/04 同批生效。

    能力边界（诚实声明）¶

    • 安全随机类（安全随机整数/令牌/URL令牌）：无 OS 级安全熵 —— 用 dv_random（MT19937）加种子实现，不具密码学安全性，仅格式对齐。
    • 随机字节 返回十六进制字符串（原生腿无 bytes 类型），与 .py 的 bytes 对象不等价；单字节内 nibble 序按小端字节取（低 在前），对拍 oracle 同步。
    • 随机UUID 为 v4 格式（第 13 位固定 4、第 17 位 8+随机下限(4)）， 31 次 4 位随机 + 1 次 2 位随机消耗。
    • set 无原生类型：集合族用列表模拟（插入序），弹出元素 取列表首个 —— 与 CPython set 哈希序不同（对拍 oracle 按插入序镜像）。
    • 随机位 上限 63 位（i64）；随机0到1/正态分布 等浮点语义与 CPython 逐位一致（Box-Muller 同构 + 缓存第二个随机值）。
    • 函数值/回调不可用（编译期「未定义的段落」）→ 对象池缓存的装饰器类返回 空/池本身，仅标注能力边界。
    • POSIX 实测账（T5C-POSIX 专项，2026-09-06 收口）：
    • 首轮（随 T6B）：dv_random 系列（MT19937 纯整数运算 + dv_timestamp 播种）经 test_随机_固定种子42逐位对拍_O0 passed；同轮全量原生腿回归 中 test_集合_运算对拍_O0（移除元素）暴露原生腿 值错误。已确认 非 T6B 引入（T6B 的 codegen/runtime 改动仅涉 time/sys builtin 与 sys.stderr 链改写，git diff 已核零集合/移除相关代码），根因是 T5C 集合族 缺陷，登记为 T5C-07。
    • 修复后（本轮）：移除元素 修好，并顺带修掉同根因的 分组 组内元素 丢失（该缺陷双平台均存在，此前未被测试覆盖）。POSIX 全量原生腿回归 36 passed / 0 failed（T5A + T5B + T5C + T6B）；Windows 同组合亦 36 passed。T5C「未在 POSIX 实测」的缺口由此关闭。
    • 环境：Ubuntu 24.04.4 / clang 18.1.3 / 3.9GB 空闲 / 4 核； 本机 Windows 对照为 clang 22.1.8 + MSVC 14.29 + Win10 SDK 10.0.19041 （T5A/T5B/T5C/T6B 两套工具链版本不同，是本次能暴露平台相关 UB 的前提）。

    T6C-01：关键字参数（KeywordArg）对用户段调用不可靠（已规避）¶

    • 现象：添加参数(p, "--输出", 短名称="-o", 值类型="整数", 默认值=1) 中 默认值/值类型/ 标志/计数 绑定错位：IR 实证 添加参数(q,"--a", 默认值=3) 只推 3 个实参（q, 名, 3）， 默认值 绑到槽 2（短名称），名称 占了 默认值 槽；标志=真 推出 4 个实参（q,名,空,真） 绑到槽 3（值类型）。
    • 根因：_merge_kwargs 尾递归兜底按「追加顺序」绑定参数槽，未按形参名匹配；隔离段落内 偶发正确（探针 试参数(1,2,d=9) 输出 A/1/B/2/C/9/D/0），跨模块 / 长参表场景不可依赖。
    • 规避：模块内部与全部测试一律全位置参数调用；声明式形参默认值（X = Y）不受影响。

    T6C-02：运行时 查找 返回字节偏移，与 截取/长 的字符语义不一致（已规避）¶

    • 现象：查找("--输出=7", "=") 返回 8（字节偏移），而 截取/长 按字符； 多字节选项名（如 --输出=7）按 查找+截取 组合解析会错位/截到整串。
    • 规避：参数解析模块内逐字符扫描找 =（如果 词[j] == "="），不依赖 查找 的字节偏移。

    T6C-03：REF 字符串（列表元素）上 截取/开头 失效（已规避）¶

    • 现象：截取(列表[i], 0, 6) / 开头(列表[i], "-") 对 REF（列表元素引用）返回整串/不可靠。
    • 规避：解析循环先 设 词 为 转字符串(列表[i]) 解引用后再做 开头/截取/字符扫描。

    T6C-04：跨模块同名段落 → LLVM IR 重定义（同 T5C-06，未修，规避）¶

    • 本批 5 模块间无同名导出（五模块联合导入测试通过）；该限制对 stdlib 双模块同名导出普遍成立 （T5A-05 / T5C-06 同根因），合并期导入组合需注意。

    T6C-05：GBK/GB2312/GB18030/BIG5 双向转换能力边界（8 导出返回空串）¶

    • 原生腿无这些编码的码表（纯光明无 codecs）；GBK转UTF8/UTF8转GBK/GB2312转UTF8/ UTF8转GB2312/GB18030转UTF8/UTF8转GB18030/BIG5转UTF8/UTF8转BIG5 8 个导出 返回空串 ""（诚实边界）；ISO8859-1 双向按字节/码位实现（ASCII 域正确，超 255 返空）。
    • 检测编码 恒返回 "utf-8"（无启发式）；字符集转换/字符集转字符串 仅同编码直通 （utf-8 直通时对 hex 串做 UTF-8 解码）。

    T6C-06：类不可实例化、类方法整条不可用（12.1 既有）¶

    • 向量.py/复数.py 的 类 向量/复数/矩阵 以构造函数形态导出（向量/矩阵/复数/创建向量/ 创建复数/创建矩阵/极坐标转复数），类方法整条不可用；对拍按函数形态验证。

    能力边界（诚实声明）¶

    • 参数解析：支持子集 = 位置参数 / 选项参数 / --x=y 形式 / 默认值 / 整数·浮点数·字符串 类型转换 / 标志（布尔）/ 计数 / 子命令 / 帮助文本与用法文本；不支持 argparse 的 nargs 列表、choices 校验、互斥组、前缀缩写匹配等高级特性。
    • 颜色：RGB↔HSV / RGB↔HSL 按 colorsys 算法纯光明重写；颜色混合/颜色亮度/颜色反转/ 颜色变亮/颜色变暗/颜色透明/获取颜色名称 按 .py 常量表实现（名称映射仅内置常用色， 未命中返回 未知）；hex 解析支持 #RRGGBB/#RGB/rgb(r,g,b)/r,g,b 四种形式。
    • 向量/矩阵：矩阵行列式/矩阵逆矩阵 为 2×2、3×3 通用实现；矩阵乘法要求左列数 == 右行数 （不合规返回空列表）；向量夹角 对零向量返回 0。
    • 编码解码：Base64 / Base32 / Base16 / URL / Hex / Unicode 实体 / UTF-8·ISO8859-1 字符集 全对拍；GBK 族见 T6C-05。
    • 浮点输出：原生腿 输出 用 %g（6 位有效数字）→ 数值对拍统一用 abs diff < 1e-4， 不做字符串级比对。
    • O0 codegen 既有限制（T5A 已记录）：负数字面量失效 → 一律 0 - x；输出(列表)/输出(字典) 显示为 []/{} → 逐项输出；含 为 关键字的函数名被词法切分（如 字符集转换为字符串）→ 编码解码导出以「字符集转字符串」命名提供。
