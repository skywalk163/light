    语言自举率报告（D3-4 / D3-6）¶

    第三轮 D3 交付。把「语言自举率」与「引 Python 逃逸计数」两个核心度量落进 tools/ci/bootstrap_rate.py，按 第三轮总纲.md §2.3 的唯一口径输出， 杜绝第二轮文档里 0/134、8/63、16/68 三个口径互相打架。 本文件为度量报告 + 战略性边界收口（D3-6）；门禁脚本见 tools/ci/bootstrap_rate.py。

    〇、先说清楚「自举」的定义（省掉后来者每一轮的重新纠结）¶

    「自举」在本项目里的定义是「不经 stdlib 的 Python 封装、不写 引 Python 块」， 不是「脱离 CPython 运行时」。

    纯光明模块照样 导入 socket / 导入 ssl / 导入 json / 导入 re / 导入 subprocess / 导入 codecs —— 这是既定口径，不是妥协。 真正的边界是「不在光明层包一层 Python 函数再转调 CPython」，而是用光明语法 直接表达算法/协议/数据结构。因此 C 扩展（ssl/hashlib/psutil/msvcrt/fcntl） 与三方包（lunardate/cryptography）是天花板，不是偷懒。

    一、唯一口径（§2.3）¶

    项 定义
    code 非空且不以 # 开头的行
    decl 行首为「段落 / 类 / 函数」定义的行（^\s*(段落|类|函数)\b，不含「调用 函数甲()」这类纯调用行）
    有真实现 decl ≥ 1
    主报维度 文件维度：有真实现的 .light 文件数 / 顶层 .light 总数
    行维度 decl / code，虚高，明确标注不许引用（见下）

    为什么行维度不许引用：一个 .light 文件哪怕只有一行真定义、其余全是注释， 行维度也会很高；文件维度才反映「有多少模块真正自举了」。第二轮曾因混用口径 闹出 0/134、8/63、16/68 三个数字，本轮统一到文件维度。

    二、首次实测快照（第三轮 D3-4，合入 main 之前）¶

    这一节不是当前真值。 当前真值见下面「六、第四轮合并后更新」（18/70 = 25.71%）。 本节保留的是第一次把口径落成脚本时的原始数字，用来对照后面每一轮的增量。

    项 数值
    stdlib 文件维度自举率 16 / 68 = 23.53%
    （仅供参观、不许引用）行维度 decl/code 314 / 3311 = 9.48%
    stdlib 「引 Python」逃逸 0 处（破零成果守住）
    全仓 .light 「引 Python」 19 处 / 15 文件（全在 examples/ 的 L3/L4 分层教学示例，属教学用途，不算违规）
    stdlib/lightpub/ .light = 0，.py = 56（仅记录，不设门禁）

    门禁判据（bootstrap_rate.py 实现）： 1. stdlib/ 下「引 Python」计数 > 0 即红（守住破零成果）。 2. 文件维度自举率只许升不许降（基线写进 bootstrap_rate_baseline.json）。 3. stdlib/lightpub/ 计入报告但不设门禁（这一层本轮不动）。

    三、自举率天花板：永久 Python 边界清单（D3-6）¶

    只读复核给出的重写难度排序，写成正式清单，免得每一轮都有人重新纠结一次。

    3.1 值得继续自举（下一批目标）¶

    # 模块（行数） 已有反证（说明可做）
    1 stdlib/JSON.py（1147） JSON编解码.light 211 行代码做完了核心编解码，纯字符串算法零 C 依赖
    2 stdlib/Base64.py（238）/ stdlib/编码解码.py（292） 纯查表 + 位运算
    3 stdlib/HTTP.py（269） 流式.light 260 行在 raw socket 上实现了 HTTP/1.1 + chunked；但 TLS 必须留 导入 ssl → 只能算「协议层自举、传输层借 C」
    4 stdlib/临时文件.py（293）/ stdlib/高级文件.py（120） 薄封装，os 系统调用是硬边界
    5 stdlib/外部命令.py（293）/ stdlib/进程.py（448） 进程树.light 375 行覆盖启动/等待/超时/进程组终止；但 multiprocessing（进程.py 里 7 处）涉及 fork/pickle，光明层无对应能力
    6 stdlib/时间管理.py（513） 纯逻辑但依赖 threading
    7 stdlib/正则表达式.py（383） 真自举得自己写 NFA/回溯引擎，纯算法无需 C；但工作量大且性能会掉一个数量级，当前所有纯光明模块都在 导入 re，这条腿实际没自举

    3.2 明确放弃、写进永久 Python 边界¶

    # 模块（行数） 不可自举的根因
    8 stdlib/日期时间.py（1616） 时区 + ISO 解析 + 农历（三方 lunardate，缺包时直接 RuntimeError，即门禁里那 8 条红）；对齐成本极高
    9 stdlib/文件系统.py（1522） 体量最大，文件锁走 msvcrt/fcntl 两套 C 扩展
    10 stdlib/哈希.py（153）/ stdlib/加密.py（634） 依赖 OpenSSL / cryptography / PyCryptodome；自己实现密码学原语不该做也做不动
    11 stdlib/系统接口.py（437）/ stdlib/环境.py（215） 全靠 psutil（三方 C 扩展）读平台内核接口，无替代路径

    结论回到本节开头那句：「自举」= 不经 stdlib 的 Python 封装、不写 引 Python 块， 不是脱离 CPython 运行时。第 8–11 类是 C 扩展 / 三方包硬边界，属永久 Python 边界， 不再投入自举；第 1–7 类是可继续推进的目标，但第 3、5、6、7 类会受 ssl/threading/ multiprocessing/re 的 C 依赖制约，只能做到「协议/算法层自举、系统层借 C」。

    四、与门禁脚本的关系¶

    • tools/ci/bootstrap_rate.py --root . 输出本节第二节全部数字 + 门禁判据，< 5s 跑完。
    • 基线：tools/ci/bootstrap_rate_baseline.json（文件维度 25.71%，另含 shadow_count=53 与 built_from_commit）。自举率提升后 用 --write-baseline 重新生成并提交（commit message 写明提升原因）。
    • CI 接入见 D3-3（*.workflows/ci.yml 新增一步调用本脚本，红则阻断）。
